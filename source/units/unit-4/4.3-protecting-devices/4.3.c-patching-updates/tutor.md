# 4.3.c tutor notes

Notes for the pre- and post-lecture tutor posts.

## The intuition to hold onto
The sentence worth sitting with before the lecture: publishing a patch also publishes a roadmap of exactly what was broken, because attackers can reverse-engineer the diff between the old code and the new code to see precisely what the vendor just fixed. That single fact is why "patch promptly" isn't just good hygiene, it's a race that starts the moment the fix ships, and it reframes the whole atom around a genuinely surprising idea: the vulnerability becomes *more* dangerous, not less, in the hours right after it gets patched, because that's exactly when weaponized exploit code starts circulating against everyone who hasn't updated yet.

## The big picture
The zero-day versus n-day distinction is the one piece of vocabulary here worth never confusing, because it flips the popular narrative about breaches on its head: the dramatic, expensive zero-day, exploited before any fix exists, is actually rare, while the overwhelming majority of real breaches exploit n-day vulnerabilities, flaws with a perfectly good patch sitting unapplied for months. That should change how you read the "why organizations delay patching" section, compatibility risk, downtime, scale, legacy systems, not as excuses but as the genuine engineering costs that make the patch gap a real tradeoff rather than pure negligence, which is exactly why mature patch management runs as a formal process (inventory, prioritize, test, deploy, verify) rather than an instinct to patch everything instantly. Notice, too, that the CVSS severity score reappears almost unchanged as the "weight" concept in 4.4.c's compromise scoring, this course keeps reaching for the same idea, turning fuzzy risk into a number you can set a threshold against, because "patch everything with equal urgency" is exactly as unworkable here as "defend against every threat equally" was back in Unit 2's risk-management atom.
