Lab, IDS Detection: Signatures, Anomalies, and False Positives

Catch attacks two ways, and feel the trade-off every analyst lives with.

An intrusion detection system watches traffic a firewall has already allowed and asks: does this look like an attack? You will run a real detector over a captured stream of ~160 events. First you write a signature that matches a known-bad payload, and watch a disguised variant of the same attack slip straight past it. Then you switch to an anomaly rule and tune a threshold, reading a live confusion matrix (TP, FP, TN, FN) that shows how a looser rule catches more attacks but buries the analyst in false alarms.

Two detectors, two blind spots

A signature is fast and precise, but it only matches patterns someone has already written down. The attacker changed UNION SELECT to UNION/**/SELECT and the exact-match rule went blind, a false negative, which is why signature databases must be updated constantly and still miss zero-days. An anomaly rule needs no prior knowledge of the payload: a host touching dozens of ports stands out as a port scan whatever it carries. But its threshold is a dial between recall and false positives, set it too low and an ordinary busy server (the monitoring host) becomes a false alarm, and a flood of false positives is how real alerts get missed (alert fatigue). Neither method caught everything here: the anomaly rule never saw the SQL-injection payloads, and the signature never saw the scan. That is why defenders run both, the IDS/IPS, signature-vs-anomaly, and TP/FP/TN/FN trade-off at the center of LO 3.5.A.
