I. Detecting an Adversary Already Inside

Where Unit 1 examined the human perimeter and Unit 3's earlier topics examined the architecture of segmented, firewalled networks, this topic addresses a harder problem: what happens after an adversary is already inside, or is actively probing the boundary. Prevention, access control lists, firewall rules, authentication gates, is necessarily incomplete. Every mature security program therefore assumes a degree of assumed breachAssumed BreachA planning posture in which defenders design their monitoring and response capability as if an attacker has already gained a foothold, rather than betting everything on keeping them out. It shifts investment from pure prevention toward detection and response. Formalized in zero-trust architecture guidance; see NIST SP 800-207, which explicitly rejects the idea of a trusted internal network. and invests in network threat detectionNetwork Threat DetectionThe organized practice of observing traffic traversing a network, packets, flows, and logs, to identify malicious or anomalous activity as early as possible in the attack lifecycle. It combines purpose-built sensors, log aggregation, and human analysis. Detection is one function within the NIST Cybersecurity Framework 2.0's "Detect" category (DE.CM, DE.AE). See NIST SP 800-94 for foundational IDS/IPS guidance.: the disciplined practice of watching the wire and the logs for the signatures and shapes of an intrusion.

The theoretical backbone of this discipline is the Cyber Kill ChainCyber Kill ChainA model developed by Lockheed Martin describing the sequential stages an attacker typically moves through: reconnaissance, weaponization, delivery, exploitation, installation, command and control, and actions on objectives. Detection tooling is often mapped to specific stages so defenders know where in the chain a given alert falls. Hutchins, Cloppert & Amin (2011), Lockheed Martin. A related, more granular model is MITRE ATT&CK, which enumerates specific techniques rather than sequential phases., which frames intrusions as a sequence of discrete stages rather than a single event. Because a network-based intrusion nearly always requires the attacker's traffic to traverse a wire, a switch, or a DNS resolver at some point, during reconnaissance, lateral movement, or exfiltration, the network itself becomes a rich source of forensic and real-time evidence, independent of whether the compromised host's own logs have been tampered with by the intruder.

Two complementary detection philosophies dominate the field. Signature-based detectionSignature-Based DetectionMatching observed traffic or files against a database of known-bad patterns, specific byte sequences, regular expressions, or hashes tied to previously identified attacks. Fast and low false-positive, but blind to anything novel. Analogous to antivirus definition files. Snort and Suricata rules are the canonical signature format for network traffic; see Roesch (1999), "Snort: Lightweight Intrusion Detection for Networks." compares traffic against a curated library of known-malicious patterns, much as antivirus software matches file hashes. It is precise and computationally cheap, but structurally incapable of catching a threat nobody has documented yet, the classic zero-dayZero-DayA vulnerability or exploit technique that is unknown to defenders (and often the vendor) at the time it is first used, meaning there are "zero days" of prior warning to prepare a signature or patch. Zero-day exploitation is tracked by organizations like Google's Project Zero and Mandiant's annual zero-day reports. problem. Anomaly-based detectionAnomaly-Based DetectionBuilding a statistical or behavioral baseline of "normal" network activity and flagging deviations from it, rather than matching known-bad patterns. Can catch novel attacks but tends to generate more false positives, since "unusual" is not the same as "malicious." Formal treatments include Denning (1987), "An Intrusion-Detection Model," IEEE Transactions on Software Engineering, one of the foundational papers of the field., by contrast, builds a statistical model of what "normal" looks like for a given host, user, or network segment, and raises alerts on meaningful deviation. It can, in principle, catch attacks nobody has ever seen before, at the structural cost of a higher false-positive rate, since novelty and maliciousness are not the same thing.

Two detectors, two different ways of being wrong Think of signature detection as a bouncer with a stack of mugshots: extremely accurate for known troublemakers, completely useless against someone he has never seen before. Anomaly detection is a bouncer who has worked the same door every night for a year and has learned the regulars' rhythms, he'll notice something is "off" about a stranger even without a mugshot, but he'll also occasionally flag a regular who is just having an unusual night. Mature SOCs run both bouncers side by side, because their failure modes are different and complementary.

Detection also differs by deployment topology and by scope. A Network Intrusion Detection System (NIDS)NIDS, Network Intrusion Detection SystemA sensor that monitors traffic across an entire network segment, typically fed by a switch's mirrored port (SPAN) or a physical network tap, and analyzes copies of packets without sitting in the direct forwarding path. Example implementations: Snort, Suricata, Zeek. Contrast with HIDS, which watches a single endpoint's internal state (file integrity, process activity, system calls). observes traffic for an entire segment, while a Host-based Intrusion Detection System (HIDS)HIDS, Host-Based Intrusion Detection SystemAn agent installed on an individual endpoint that monitors local activity, file integrity, running processes, registry changes, system calls, rather than network traffic. Complements NIDS by catching threats that never traverse the monitored network segment, such as USB-delivered malware. Examples: OSSEC, Wazuh, Tripwire (file integrity monitoring specifically). instruments a single machine's internal state. Separately, deployment mode determines whether the system can only observe (passive/tap-mode IDSPassive / Tap-Mode IDSA detection sensor that receives a copy of traffic, via a network tap or a switch SPAN port, and can alert on malicious activity but cannot itself drop or modify packets in real time, since it is not in the direct path of the traffic. Latency and fail-open behavior are non-issues for passive sensors, which is why they remain popular for high-throughput backbone monitoring despite lacking blocking capability.) or can actively intervene (inline IPSInline IPS DeploymentPlacing a detection engine directly in the physical or logical path of traffic, so that it can drop, reset, or otherwise block a malicious packet or flow in real time rather than merely alerting after the fact. The tradeoff is that a hung or overloaded inline device can itself become a single point of failure or added latency. Most modern NGFWs embed IPS engines inline; "fail open" versus "fail closed" behaviour during device failure is one of the defining design decisions of an inline deployment: fail-open preserves availability at the cost of an unfiltered window, fail-closed preserves the security boundary at the cost of an outage.). This distinction, IDS as a smoke detector versus IPS as a sprinkler system, recurs throughout the rest of this chapter, and it carries a consequence that Section II develops in detail: the two deployment modes do not merely differ in what they can do, they fail in categorically different ways.

Scope and authority are independent axes, not a single ladder Two questions decide what a sensor is, and they are answered separately. The first is scope: does it watch a network segment (NIDS) or the internal state of one machine (HIDS)? The second is authority: does it only observe and alert (IDS) or does it sit in the forwarding path and drop packets (IPS)? All four combinations exist and are deployed. A network-wide inline blocker is a NIPS; a host agent that kills a process or blocks a local port is a host-based prevention system. "Inline" is a statement about where the device sits in the traffic path, not about how much of the network it covers, and conflating the two produces designs that block traffic nobody meant to block or watch segments nobody can act on.

Finally, no detection system is judged on accuracy alone, it is judged on the tradeoff between two error types. A false positiveFalse PositiveAn alert generated for benign activity that was incorrectly classified as malicious. High false-positive rates cause "alert fatigue," in which analysts begin to distrust or ignore the detection system entirely, arguably the single most consequential failure mode in the entire discipline. Base-rate neglect (a statistical/cognitive bias) explains why even a highly accurate detector produces mostly false positives when the true attack rate is very low relative to total traffic volume. wastes analyst time and, cumulatively, erodes trust in the system; a false negativeFalse NegativeA failure to detect genuinely malicious activity, allowing the attacker to proceed undetected. Unlike a false positive, a false negative usually produces no signal at all, it is often only discovered retroactively, during incident response or forensic review after a breach has already caused damage. The Target and SolarWinds case studies in Section III are, at their core, failures at the response stage following weak or ignored detection signal, illustrating that a detection system's value is contingent on the human process around it. is far more dangerous, since it represents an intrusion that proceeds entirely unnoticed. Tuning a detection program is fundamentally an exercise in managing this tradeoff under a fixed budget of analyst attention.

II. Sensors, Packet Inspection, and Judging a Detector

1. The Tooling Taxonomy: What Each Sensor Can and Cannot See

Practitioners speak of "detection tools" as though they formed a single category, but the tools differ along three independent dimensions, and confusing them produces architectures with expensive blind spots. The first dimension is vantage: a network sensor sees traffic on a segment and nothing about what a process did on disk; a host agent sees process creation, file writes, and system calls, and nothing about the segment its host does not talk on. The second is authority: a sensor either sits beside the traffic path and can only report, or sits in it and can drop. The third is fidelity: how much of each conversation the tool retains, every byte, or a summary line.

Vantage and authority together fix the failure mode, and this is the point most often skipped. A passive sensor fed by a network tapNetwork TapA purpose-built hardware device inserted into a physical link that copies every frame passing through it to a monitor port, while passing the original traffic through unaltered. Because most taps are passive or fail-open by design, a failure of the monitoring device does not interrupt the production link. Contrast with a SPAN/mirror port, which is a software function of a switch: SPAN is free and reconfigurable, but the switch drops mirrored frames first when its backplane or the mirror port is oversubscribed, so SPAN data is silently lossy under exactly the traffic conditions that matter most. or a SPAN portSPAN (Switched Port Analyzer) / Mirror PortA switch feature that copies traffic from one or more source ports or VLANs to a designated destination port for monitoring. Convenient and free, but the copy is best-effort: if the aggregate source traffic exceeds the mirror port's capacity, or the switch is under load, mirrored frames are dropped without any notification to the monitoring tool. A 1 Gbps mirror port fed by several 1 Gbps sources will silently discard traffic. This is the standard argument for hardware taps at any link the organization genuinely depends on monitoring. fails silently and toward blindness: if it crashes, is oversubscribed, or drops mirrored frames, production traffic continues undisturbed and the only casualty is the record of it. Nobody phones the help desk about traffic that was never inspected. An inline IPS fails loudly and toward one of two extremes: configured fail-open, a device failure leaves the link forwarding unfiltered traffic, so the security control is gone but the business runs; configured fail-closed, the same failure severs the link entirely. Add to this that an inline device introduces latency and becomes a target itself, and the reason large organizations run passive sensors on backbone links and reserve inline blocking for a small number of well-understood chokepoints becomes an engineering conclusion rather than a preference.

Fidelity is the third axis, and it is chiefly a budget question. Full packet captureFull Packet Capture (FPC)Recording every byte of every frame crossing a monitored link, payloads included, so that an investigation weeks later can reconstruct exactly what was transferred. The evidentiary value is unmatched and the storage cost is brutal: a link averaging 1 Gbps sustains roughly 10 terabytes per day, so most organizations either capture only at high-value chokepoints or keep a short rolling window. Implementations include Arkime (formerly Moloch), Stenographer, and commercial network forensics appliances. Retention is typically measured in days for FPC and months or years for the flow records described alongside it. answers any question an investigator will ever ask, and costs on the order of ten terabytes per day for a link averaging a single gigabit per second, which is why it is deployed at a handful of chokepoints and kept for days. Flow records answer a narrower set of questions for roughly a thousandth of the storage, which is why they are kept for a year. A SIEMSIEM, Security Information and Event ManagementA platform that ingests, normalizes, indexes, and correlates log and event records from across an infrastructure, providing search, alerting, and long-term retention over the combined data set. Its distinguishing capability is correlation across sources that individually reveal nothing. Its distinguishing costs are ingestion licensing, which is usually priced per gigabyte per day and therefore shapes what an organization can afford to collect, and the rule-engineering labour without which the platform is an expensive log archive. ingests all of it as text and charges by the gigabyte, which is why the question "what do we send to the SIEM?" is a security decision and not merely a procurement one. Network Detection and Response (NDR)NDR, Network Detection and ResponseA product category that applies behavioral analytics and machine learning to network telemetry (flows, protocol metadata, and often decoded transactions from a Zeek-style engine) rather than relying primarily on signature matching, and pairs the detections with response workflow. The category descends directly from what Gartner previously called network traffic analysis; the "response" half denotes integration with firewalls, EDR agents, and SOAR playbooks so that a detection can trigger containment. Its detections are behavioral, so its output requires triage in exactly the way Topic 1.5's base-rate arithmetic predicts. platforms sit on top of this telemetry and apply behavioral analytics rather than signatures, and are discussed in that light later in this section.

2. Packet-Level Inspection and Its Encrypted-Traffic Limit

At the packet level, detection begins with deep packet inspection (DPI)Deep Packet Inspection (DPI)Examining the actual payload contents of a packet, not merely its header fields (source/destination IP, port), to identify protocols, applications, or malicious content embedded inside otherwise permitted traffic. DPI is computationally expensive relative to header-only filtering and is a defining capability of Next-Generation Firewalls (NGFW) and IPS engines. Raises privacy and legal considerations when applied to encrypted or personal traffic., which reaches past the header fields a stateful firewall would examine and inspects the payload itself for known-malicious byte patterns, protocol violations, or embedded command strings. Analysts performing this work by hand typically rely on a protocol analyzerProtocol AnalyzerSoftware that captures and decodes network traffic frame-by-frame, reconstructing the layered protocol structure (Ethernet, IP, TCP/UDP, application layer) so a human can read it. Wireshark is the dominant open-source example; tcpdump is its command-line counterpart used for capture. Wireshark decodes hundreds of protocols and supports display filters (e.g., tcp.flags.syn==1 && tcp.flags.ack==0) for isolating traffic of interest within a large capture. such as Wireshark, which reconstructs a raw pcappcap (Packet Capture)A file format (and the underlying libpcap/WinPcap library) for storing captured network packets exactly as they traversed the wire, including all header bytes. The standard interchange format for network forensics, nearly every packet-capture and IDS tool can read and write it. File extension .pcap or the newer .pcapng. tcpdump's -w flag writes a pcap file; Wireshark and tshark both read and write it natively. file into a human-readable, layered view.

Reading a TCP conversation requires fluency in the TCP flagsTCP FlagsSingle-bit control fields in the TCP header that signal the state of a connection: SYN (synchronize, start a connection), ACK (acknowledge receipt), FIN (finish, graceful close), RST (reset, abrupt abort), PSH (push data immediately), URG (urgent). Their combinations reveal whether traffic follows a normal handshake or is being used for reconnaissance. RFC 9293 is the current consolidated TCP specification (obsoleting RFC 793). Unusual flag combinations, such as SYN+FIN together, are a strong signature of crafted scanning tools. that govern the three-way handshake (SYN, SYN-ACK, ACK) and connection teardown (FIN or RST). Deviations from this expected sequence are themselves detection signal. A SYN scanSYN Scan (Half-Open Scan)A port-scanning technique that sends a SYN packet and, upon receiving a SYN-ACK, immediately sends an RST instead of completing the handshake with an ACK. Because the full TCP connection is never established, it evades some legacy connection-logging systems while still revealing which ports are open. The default scan mode of Nmap (-sS), sometimes called a "stealth scan," though modern IDS signatures readily detect its characteristic pattern., for example, produces a distinctive burst of SYN packets to sequential ports from a single source with no completed handshakes, a textbook port scan signaturePort Scan SignatureThe traffic pattern characteristic of an attacker enumerating which services are listening on a target: many connection attempts to different ports (or many hosts) in a short time window, typically with abnormally low completion rates. Detection thresholds (e.g., "more than 20 distinct destination ports from one source IP within 60 seconds") are a common Suricata/Snort rule pattern; see the "detection_filter" and "threshold" keywords. that both Snort and Suricata detect out of the box.

Below is a representative Suricata rule written to flag exactly this pattern, a source IP attempting connections to an unusual number of distinct destination ports in a short window, a strong indicator of active reconnaissance:

Suricata Rule 
# Local rule; sid drawn from the 1000000+ range reserved for locally authored rules.
alert tcp $EXTERNAL_NET any -> $HOME_NET any ( \
  msg:"LOCAL SCAN half-open SYN sweep from single source"; \
  flow:stateless; flags:S,12; \
  threshold:type both, track by_src, count 20, seconds 60; \
  classtype:attempted-recon; \
  metadata:attack_target Server, created_at 2026_09_02; \
  reference:url,attack.mitre.org/techniques/T1046/; \
  sid:1000501; rev:1;)

The rule repays a field-by-field reading, because every clause is doing distinct work.

  • alert tcp $EXTERNAL_NET any -> $HOME_NET any is the header: action, protocol, and a direction specification of source address, source port, arrow, destination address, destination port. $EXTERNAL_NET and $HOME_NET are variables defined in the sensor's configuration, not literals; a rule that hard-codes addresses is a rule that breaks the first time the network is renumbered. The action alert is what makes this a detection rule, on an inline sensor the same rule with drop becomes a prevention rule, which is the entire IDS-versus-IPS distinction expressed as one word of configuration.
  • flow:stateless instructs the engine to evaluate the packet without requiring an established session. This matters precisely because a SYN scan never establishes one; a rule left at the more common flow:established would never fire on the traffic it is written to catch.
  • flags:S,12 is the flag test. S requires the SYN bit set. The comma introduces a mask of bits to ignore, and 1 and 2 name the two high-order bits, CWR and ECE, used by explicit congestion notification. Without that mask, an ECN-capable client whose SYN legitimately carries ECE would not match, and the rule would quietly miss a fraction of real scans. The clause therefore reads: SYN set, every other flag clear, congestion bits disregarded.
  • threshold:type both, track by_src, count 20, seconds 60 converts a per-packet match into a rate condition. A single SYN is ordinary traffic and must never alert. type both combines a floor and a ceiling: fire only after twenty matches from one source within sixty seconds, and then fire once for that window rather than once per packet. This one clause is the difference between a usable rule and a hundred thousand alerts a day, and it is the concrete form of the tuning argument that Section IV develops.
  • classtype, metadata, reference, sid, and rev are the bookkeeping that makes a rule maintainable: a severity class the SIEM can route on, a link to the technique it detects (MITRE ATT&CK T1046, Network Service Discovery), a unique signature identifier, and a revision number. Local rules take signature identifiers from 1000000 upward so they cannot collide with vendor or community rule sets.

Note what the rule does not establish. It fires on a traffic shape, not on intent: a vulnerability scanner running on schedule, a network inventory tool, and a load balancer's health checks all produce the same shape. The rule identifies candidates for a human to adjudicate, which is the correct standing for nearly every detection an analyst will ever tune.

Payload matching is the other half of signature detection, and it depends on the sensor being able to read the payload at all. The following Snort-syntax rule illustrates deep packet inspection applied to an HTTP request body:

Snort Rule 
alert tcp $EXTERNAL_NET any -> $HOME_NET $HTTP_PORTS \
  (msg:"WEB-SHELL Possible cmd.jsp webshell upload"; \
  flow:established,to_server; content:"POST"; http_method; \
  content:"cmd.jsp"; http_uri; content:"Runtime.getRuntime"; http_client_body; \
  classtype:web-application-attack; sid:1000451; rev:2;)

Here the qualifier is decisive: http_client_body can only match if the sensor can read the request body, and on a modern network it usually cannot. The overwhelming majority of interesting traffic is wrapped in TLS, and a passive sensor holds no key. This is not a gap that better signatures close. Payload signatures are structurally unavailable on encrypted traffic, and an organization that does not understand this will buy DPI capability it cannot use.

What survives encryption is metadata, and there is more of it than defenders once assumed. The TLS handshake itself is sent in the clear before the session key exists, and its contents are characteristic of the client software that produced it: the offered cipher suites, the extension list and their order, the supported groups and signature algorithms. Hashing those fields yields a TLS client fingerprintJA3 and JA4 TLS FingerprintingA method of identifying the software originating a TLS connection by hashing selected fields of its unencrypted ClientHello, TLS version, cipher suites, extensions, elliptic curves, and curve formats. Because a given library and version negotiate in a distinctive way, the resulting fingerprint often identifies the client stack even when everything after the handshake is encrypted. JA3 was published by Salesforce in 2017. Its reliability eroded once browsers began randomizing extension order to prevent exactly this profiling, so John Althouse (JA3's originator) published JA4 through FoxIO in 2023, designed to be stable under that randomization; the wider JA4+ family extends the idea to server responses (JA4S), HTTP requests (JA4H), X.509 certificates (JA4X), SSH, and TCP.. A workstation whose handshakes suddenly carry a fingerprint matching a Go or Python HTTP library rather than the browser it has used for months is a strong signal about what is running on it, obtained without decrypting a byte. Alongside the fingerprint, a sensor still reads the Server Name Indication (SNI)SNI, Server Name IndicationA TLS extension in which the client states, in plaintext during the handshake, the hostname it intends to reach, so that a server hosting many sites can present the correct certificate. Historically this made the destination hostname visible to any on-path observer, which defenders used heavily for policy and detection. Defined in RFC 6066. Encrypted Client Hello (ECH), specified by the IETF TLS working group, conceals SNI and is progressively removing this visibility, pushing defenders further toward flow timing, volume, and certificate-independent behavioral signals., the certificate the server presents (its issuer, validity window, and subject), the sizes and timing of records, and the flow's overall byte counts and duration. Detection on encrypted networks is largely the discipline of reasoning from these residues.

Signature rules operate on packets. A different class of tool, exemplified by ZeekZeekA network analysis framework, originally released as Bro by Vern Paxson in 1998 and renamed Zeek in 2018, that does not primarily match signatures. It decodes protocols and writes structured transaction logs, one line per connection, DNS query, HTTP request, TLS handshake, file transfer, which are then queried and analyzed. Its output (conn.log, dns.log, ssl.log, http.log, files.log) has become a de facto interchange format for network security analytics, and its embedded scripting language allows detection logic to be expressed over reconstructed protocol semantics rather than raw bytes., converts traffic into structured records of what happened, one line per connection, per DNS query, per TLS handshake, and leaves detection to analysis over those records. This inverts the workflow productively: instead of asking "does any packet match this byte pattern," an analyst asks "which internal hosts negotiated TLS with a self-signed certificate to an address in a country we do no business in." A short Zeek script, loaded into a running sensor, expresses the fingerprint-drift idea directly:

Zeek script, flag rare TLS client fingerprints 
# rare-ja3.zeek, report TLS client fingerprints seen from very few hosts.
# Requires Zeek's JA3 package: zkg install ja3
@load base/protocols/ssl

module RareTLSClient;

export {
    redef enum Notice::Type += { Rare_Fingerprint };
    # A fingerprint used by at most this many distinct internal hosts is unusual.
    const host_threshold = 2 &redef;
}

global fp_hosts: table[string] of set[addr];

event ssl_established(c: connection)
    {
    if ( ! c$ssl?$ja3 )
        return;

    local fp = c$ssl$ja3;
    local src = c$id$orig_h;

    if ( fp !in fp_hosts )
        fp_hosts[fp] = set();
    add fp_hosts[fp][src];

    if ( |fp_hosts[fp]| <= host_threshold )
        NOTICE([$note=Rare_Fingerprint,
                $conn=c,
                $msg=fmt("Rare TLS client fingerprint %s from %s to %s",
                         fp, src, c$id$resp_h),
                $identifier=cat(fp, src)]);
    }

The falsepositives block is not boilerplate. Several large content delivery networks and endpoint-protection products encode lookup data into hostnames as a matter of design, and a rule of this shape deployed without a baselining period will alert on them continuously until an analyst stops reading its output. Writing the known benign producers into the rule at authoring time is what keeps it alive in production.

Not every environment can afford full packet capture at scale, payload storage and DPI processing are expensive at multi-gigabit line rates. This is where flow-based metadata analysis complements packet-level inspection. NetFlowNetFlowA Cisco-originated protocol (and now a general term for similar technologies) that records summary metadata about network conversations, source/destination IP and port, protocol, byte and packet counts, and duration, without capturing the full packet payload. Vastly cheaper to store and analyze than full pcap at scale. Cisco NetFlow v9 and the vendor-neutral IPFIX (RFC 7011) are the dominant standards; sFlow (sampled flow) is a competing, sampling-based alternative popularized by switch vendors like Juniper and Arista. and its open-standard descendant IPFIXIPFIX, IP Flow Information ExportThe IETF-standardized successor to Cisco's proprietary NetFlow v9, defining a common format for exporting flow metadata from routers and switches to a collector for analysis. RFC 7011 is the core IPFIX protocol specification, part of a broader RFC series (7012–7015) covering information elements, file format, and applicability. record who talked to whom, for how long, and how much data moved, sufficient to detect a beaconing patternBeaconingA recurring, low-volume outbound connection from an infected host to an external command-and-control server at a regular or near-regular interval, resembling a compromised implant "checking in" for instructions. Detectable in flow data even without inspecting payload, purely from the regularity of connection timing. Malware families frequently randomize (jitter) their beacon interval specifically to evade naive periodicity-based detection; SOC analysts often use statistical techniques like Fourier analysis or standard-deviation-of-interval scoring to catch jittered beacons. or a slow exfiltration event purely from timing and volume statistics, without ever inspecting the encrypted payload itself.

DNS tunnelling is invisible to the firewall and obvious in the resolver log DNS is almost universally permitted outbound through firewalls because blocking it breaks the internet for everyone. Attackers exploit this trust by encoding stolen data into a stream of DNS queries, DNS tunnelingDNS TunnelingEncoding arbitrary data (commands, stolen files) inside DNS queries and responses, typically within subdomain labels or TXT records, to smuggle traffic through a channel that is almost never blocked by firewalls, since DNS resolution is essential to normal network function. Tools such as iodine and dnscat2 implement this technique; detection relies on identifying abnormally long or high-entropy subdomain labels and unusually high query volume to a single authoritative domain.. A query like 4a6f68e9f1c8b2a9.exfil-drop.malicious-domain.com looks superficially like a normal DNS lookup but is actually a base32-encoded data chunk. The telltale indicators, high query volume to one authoritative domain, abnormally long or high-entropy subdomain labels, and TXT record queries at a rate no legitimate application would generate, appear clearly in DNS logs even though the firewall sees nothing but "allowed" UDP/53 traffic.

Individually, packet captures, flow records, firewall logs, and endpoint logs are each incomplete. 3. Evaluating a Detection Method: Precision, Recall, and the Cost of Being Right Rarely

A detection method is chosen, but it must also be evaluated, and the evaluation is not a matter of taste. Four quantities govern it. RecallRecall (True Positive Rate, Sensitivity)Of all the genuinely malicious events that occurred, the fraction the detector flagged. Recall answers "what did we miss?" and its complement is the false-negative rate. Recall is measured against ground truth, which in security is rarely available: an organization knows how many attacks it detected, not how many occurred. Purple-team exercises and adversary emulation exist largely to manufacture the ground truth that makes recall measurable. is the fraction of real attacks the method catches. PrecisionPrecision (Positive Predictive Value)Of all the alerts the detector raised, the fraction that were genuinely malicious. Precision answers "when this thing alerts, should I believe it?" and it is the quantity that determines an analyst's working day, because it fixes how much of their time is spent on nothing. Precision depends on prevalence as well as on the detector: the same detector applied to a rarer threat has lower precision, with no change in the model. Topic 1.5 derives this dependence from Bayes' rule. is the fraction of alerts that were real. Between them sits alert volume, the absolute number of alerts per day, and behind that sits analyst capacity, the number of alerts a staffed team can genuinely investigate.

Topic 1.5 derives the relationship between these quantities from Bayes' rule, and the derivation is not repeated here; the conclusion, however, applies with particular force to network detection, because network event volumes are larger than almost any other telemetry an organization collects. A mid-sized enterprise readily produces tens of millions of flow records a day. Suppose ten million connections cross a monitored boundary in twenty-four hours and roughly a hundred of them belong to an intrusion, a prevalence of one in a hundred thousand. A detector with 99 percent recall and a false-positive rate of one percent catches 99 of those hundred connections and also flags 99,999 benign ones. Its accuracy is 99 percent, a number that would pass any procurement review, and its precision is one alert in a thousand. Deployed, it produces a hundred thousand alerts a day for a team that can work perhaps a few hundred, which means in practice that it produces zero investigated alerts, and the 99 true positives inside the pile are not found.

Three consequences follow, and they are what "evaluate the impact of a detection method" means concretely. First, the quantity to interrogate is the false-positive rate, not accuracy: driving the false-positive rate from one percent to one in ten thousand leaves recall untouched and moves precision from 0.1 percent to roughly 9 percent, and driving it to one in a million yields about 91 percent. Second, alert volume must be measured against staffing before deployment, not discovered after: a rule that adds four hundred alerts a day to a three-analyst team has consumed the team, whatever it detects. Third, precision is raised most cheaply by corroboration rather than by better models, requiring a beaconing score to coincide with a rare TLS fingerprint and a first-seen destination multiplies roughly independent false-positive rates together, which buys orders of magnitude where model tuning buys percentage points.

Impact also includes what the method costs when it is right, and what it costs when it acts. An inline block on a false positive severs a legitimate business flow, so the threshold for automated blocking is properly far higher than the threshold for alerting; the same detector can reasonably feed a ticket at a score of 0.7 and a block at 0.99. And impact includes visibility: a method's most important property is often the traffic it never sees. A perimeter sensor evaluating only north-south traffic scores perfectly on the traffic it inspects and detects no lateral movement whatsoever, because that traffic never crosses its vantage point. This is an evaluation failure that no confusion matrix will reveal.

4. Reading the Logs: From Records to Indicators

Detection ultimately reduces to a claim about a pattern in recorded data, and the analyst's core skill is recovering that pattern from records that individually look unremarkable. Four indicators recur often enough to be worth working through in the data that carries them.

Beaconing with jitter

An implant that checks in for instructions produces a sequence of short, similar connections to the same destination. The firewall transcript earlier in this section shows the naive case: near-identical byte counts at almost exactly thirty seconds. Real malware jitters the interval precisely to break that regularity, so the test cannot be "are the gaps equal." The workable test is that the gaps are consistent relative to their own size, measured by the coefficient of variation, the standard deviation of the intervals divided by their mean. It is unitless, so a thirty-second beacon and a thirty-minute beacon are judged on one scale, and human-driven traffic, which arrives in bursts separated by idle periods, scores far above machine-scheduled traffic.

DNS tunnelling and the entropy of a subdomain

Encoding data into DNS requires putting bytes somewhere, and the leftmost label of the queried name is the usual place. RFC 1035 caps a single label at 63 octets and a full name at 255, so an encoder that wants throughput pushes against those limits, producing long labels of base32 or base64 output. Because that output is close to uniformly distributed over its alphabet, its Shannon entropyShannon EntropyA measure, in bits per symbol, of how unpredictable a sequence is: H = −Σ p(x) log₂ p(x) over the symbols present. English words score low because a few letters dominate; base32 or base64 output of encrypted data scores near the maximum for its alphabet because every symbol is roughly equally likely. Shannon, C. E. (1948), "A Mathematical Theory of Communication," Bell System Technical Journal. Entropy is used the same way in Topic 1.5 to identify ransomware-encrypted file writes; the mathematics is identical and only the input changes. is high, but only in absolute terms, and this is where a naive implementation fails.

Entropy is bounded above by the logarithm of the string's length, so a short label cannot score high no matter what it contains. Normalizing entropy by that ceiling, which seems like the obvious correction, destroys the signal instead of sharpening it: the ordinary hostname api reaches its ceiling exactly, scoring a normalized 1.00, while the encoded label MFYGCNRTGIYDIMBWG44DIMZUG4 scores 0.79. The discriminating combination is absolute entropy together with length, a label of thirty-odd characters carrying better than four bits per character is doing something no naming convention does, reinforced by query volume to a single authoritative domain. The program below computes both quantities and the beacon statistic above; it uses only the standard library and runs as written.

Python 3, subdomain entropy and beacon-interval variation 
"""Recover two network indicators from log data using only the standard library.

  1. Shannon entropy of a DNS label, to expose data encoded into subdomains.
  2. Coefficient of variation of connection start times, to expose beaconing.

Tested on CPython 3.11.  Run:  python3 netdetect.py
"""
from __future__ import annotations

import math
import statistics
from collections import Counter


def shannon_entropy(s: str) -> float:
    """Entropy of s in bits per character.  Shannon (1948)."""
    if not s:
        return 0.0
    n = len(s)
    h = -sum((c / n) * math.log2(c / n) for c in Counter(s).values())
    return h if h else 0.0          # normalise the -0.0 that arises when h == 0


def label_score(label: str) -> tuple[float, float, float]:
    """Return (entropy, ceiling, ratio) for one DNS label.

    Entropy cannot exceed log2(len(label)), so short labels are capped by
    arithmetic rather than by content.  The ratio is reported to show that
    normalising by the ceiling is the WRONG correction: 'api' hits 1.00 and
    an encoded 26-character label sits at 0.79.  Absolute entropy paired
    with length is what separates them.  RFC 1035 caps a label at 63 octets.
    """
    h = shannon_entropy(label)
    ceiling = math.log2(len(label)) if label else 0.0
    return h, ceiling, (h / ceiling if ceiling else 0.0)


def interval_cv(timestamps: list[float]) -> tuple[float, float, float]:
    """Return (mean gap, population stdev, coefficient of variation).

    CV is unitless, so a 30-second beacon and a 30-minute beacon are scored
    on the same scale.  Needs at least three timestamps to give two gaps.
    """
    if len(timestamps) < 3:
        raise ValueError("need at least three timestamps")
    gaps = [b - a for a, b in zip(timestamps, timestamps[1:])]
    mean = statistics.mean(gaps)
    sd = statistics.pstdev(gaps)
    return mean, sd, (sd / mean if mean else float("inf"))

Case Study 3.5.1: The 2013 Target Corporation Breach, A Detection-Response Gap

Between November and December 2013, attackers who had gained network access through a compromised HVAC vendor's credentials deployed memory-scraping malwareMemory-Scraping Malware (RAM Scraper)Malware that reads unencrypted payment card data directly out of a point-of-sale terminal's volatile memory during the brief window before the data is encrypted for transmission, bypassing encryption-at-rest and in-transit protections entirely. This case is taught less as a detection failure and more as a canonical detection-response gapDetection-Response GapA structural failure mode in which a detection system correctly identifies malicious activity, but organizational, procedural, or staffing shortcomings prevent that signal from being translated into timely containment action, meaning the technology "worked" while the security program as a whole still failed. A working sensor is not a working security programme Students often assume that buying better detection tools solves the intrusion problem. Target had genuinely good detection technology in 2013, arguably ahead of many peers at the time. The lesson is that a detection system is only the sensory organ of a security program; the SOC's triage process, staffing levels, and escalation authority are the nervous system and muscles. A perfectly functioning eye is useless if the signal it sends never reaches a hand that can act on it.

IV. Building a Detection Program: Sensors, SIEM, Baselines, Escalation

An effective network threat detection program is built in layers, following the guidance of NIST SP 800-94NIST SP 800-94The "Guide to Intrusion Detection and Prevention Systems (IDPS)," NIST's foundational special publication covering the design, deployment, and tuning of IDS/IPS technologies across network-based, wireless, and network behavior analysis approaches. Scarfone, K. & Mell, P., February 2007; it superseded SP 800-31. A revision was drafted in 2012 and later retired without being finalized, NIST noting that its inputs no longer matched current technologies and threat models, so the vocabulary remains canonical while the document itself predates encrypted-by-default traffic, cloud workloads, and machine-learning detection, and must be read accordingly., which frames detection not as a single product purchase but as an ongoing operational discipline requiring sensor placement strategy, tuning, staffing, and a defined incident response process to translate alerts into action.

1. Layered Sensor Placement

No single sensor location provides complete visibility. Best practice places NIDS sensors at key network chokepoints, the perimeter, between security zones, and near high-value asset segments, using taps or SPAN ports to avoid introducing a single point of failure, while inline IPS devices are reserved for chokepoints where active blocking is operationally acceptable. HIDS agents on individual endpoints then close the visibility gap for host-internal activity (such as living-off-the-land process abuse) that never generates network traffic distinguishable from legitimate use.

2. SIEM Centralization and Correlation Rule Engineering

Raw sensor output has limited value without correlation. Organizations should route firewall, IDS/IPS, DNS, endpoint, and identity logs into a centralized SIEM and invest deliberately in correlation rule engineering, chaining low-confidence individual signals (a single failed login, an unusual DNS query, a new device registration) into higher-confidence composite alerts, directly addressing the alert-fatigue failure mode discussed in Section II and illustrated by the Target case study.

3. Baseline Establishment for UEBA and Anomaly Systems

Anomaly-based and UEBA systems are only as good as the baseline period used to train them; deploying such a system during an already-compromised state risks baselining attacker behavior as "normal." NIST guidance recommends a defined baseline observation window, periodic baseline revalidation, and retention of human review authority over any automated containment action, directly operationalizing the human-in-the-loop principle from Section II.

4. A Deliberate Position on Encrypted Traffic

Because payload signatures are unavailable on encrypted traffic, every organization takes a position on this question whether or not it makes one consciously. There are three coherent answers, and each has a cost. Terminate TLS at an inspection point, and payload detection returns at the price of holding decrypted copies of employee and customer traffic, a privacy and compliance exposure that must be scoped so that categories such as banking and health traffic are excluded. Decline to decrypt and invest in metadata detection instead, flow statistics, TLS fingerprints, certificate attributes, resolver logs, accepting that some payload-borne threats will pass. Or push detection onto the endpoints, where an EDR agent sees the plaintext before it is encrypted and after it is decrypted, accepting that unmanaged devices then fall outside coverage entirely. Most mature programs combine the second and third, decrypting narrowly at a small number of chokepoints if at all. What is not coherent is buying deep packet inspection, encrypting all traffic, and assuming the two arrangements compose.

5. Defined Escalation and Response Procedures

Detection technology must be paired with an unambiguous escalation chain specifying who is notified, within what time window, and with what authority to contain a confirmed threat, the single control whose absence most directly explains the Target breach's outcome despite functioning detection technology.

A detection is worthless until it becomes a rule change Notice how this topic connects directly back to Topic 3.4's firewall and access-control material: detection findings (a confirmed beaconing host, a scanning source IP) are only actionable if the organization can rapidly translate them into a firewall rule change, an access revocation, or a network segmentation adjustment. Detection and prevention are not separate disciplines, they form a continuous feedback loop, and the SolarWinds case shows that even the vendor supplying your firewall or monitoring software can itself become the initial attack vector.
Every indicator has a natural sensor, and choosing the wrong one wastes the signal Detection design is largely the work of matching an indicator to the data source that carries it. A burst of SYN packets across sequential ports lives in packet headers, so a signature rule on a NIDS with a rate threshold is the right instrument. A login at an hour that is unusual for that particular account lives in identity logs and needs a per-entity baseline, which is what UEBA provides and what a global threshold cannot. High-entropy subdomain labels queried in volume against one authoritative domain live in resolver logs and are recovered by an entropy computation, not by payload inspection. A repeating outbound connection of near-constant size at a jittered interval lives in flow records, where timing and byte counts survive even though the payload is encrypted. Point a sensor at the wrong layer and the indicator is not merely missed, it was never in the data the sensor collected.

Self-Check Review Questions

Question 1: Distinguish between signature-based and anomaly-based detection, and explain why a mature security operations center deploys both rather than choosing one exclusively.

Signature-based detection matches observed network traffic or file content against a curated database of known-malicious patterns, such as Snort or Suricata rules encoding specific byte sequences or protocol violations associated with previously documented attacks. It is computationally efficient and produces low false-positive rates, but is structurally blind to novel or zero-day techniques that have not yet been catalogued into a signature. Anomaly-based detection instead establishes a statistical or behavioral baseline of expected activity, for a host, user, or network segment, and flags meaningful deviations from that baseline, whether via simple statistical thresholds or machine-learning-driven UEBA platforms. This approach can, in principle, detect previously unseen attack techniques, at the cost of a structurally higher false-positive rate, since statistical novelty does not necessarily indicate malicious intent. Because these two approaches fail in complementary ways, signature detection fails against the unknown, anomaly detection fails toward excess noise, mature SOCs deploy both in parallel, using signature detection to efficiently and reliably catch known threats while reserving anomaly and behavioral analysis, backed by human-in-the-loop review, to catch novel intrusions that would otherwise evade the signature layer entirely.

Question 2: Using the 2013 Target breach as a case study, explain the difference between a detection failure and a detection-response gap, and describe why this distinction matters for allocating security investment.

A detection failure occurs when a monitoring system fails to correctly identify malicious activity at all, the sensor itself produces no accurate alert. A detection-response gap, by contrast, occurs when a detection system functions correctly and generates a timely, accurate alert, but organizational, procedural, or staffing deficiencies prevent that alert from being translated into effective containment action. In the Target breach, the deployed FireEye-based malware detection platform generated legitimate alerts identifying the point-of-sale malware as early as late November 2013, weeks before the breach's full scope became public. These alerts were escalated through Target's security monitoring team but were not acted upon in time to prevent the exfiltration of approximately 40 million payment card records. Post-incident analysis identified alert fatigue, insufficient SOC staffing, and unclear escalation authority, not a technical shortcoming of the detection tooling, as the primary root causes. This distinction matters directly for security investment decisions: an organization experiencing detection failures should prioritize improving sensor coverage, signature libraries, or anomaly-detection capability, while an organization experiencing a detection-response gap should instead prioritize SOC staffing, defined escalation procedures, and clear containment authority, since additional detection technology alone would not have altered the Target outcome.

Question 3: Describe how the 2020 SolarWinds/SUNBURST compromise was ultimately identified, and explain why this detection could not have relied on traditional signature-based methods alone.

The SUNBURST backdoor was distributed to approximately 18,000 organizations through a legitimately signed SolarWinds Orion software update, having been inserted into the vendor's build process itself. Because the malicious update carried a valid vendor code-signing certificate and was delivered through an expected, trusted software update channel, it could not be identified through file-hash or certificate-based signature matching, which relies on flagging content already known or provably untrustworthy. The compromise was instead surfaced through behavioral anomaly detection at FireEye, one of the affected organizations: security staff noticed that a new device had been registered to an employee's multi-factor authentication profile in a manner inconsistent with that employee's normal registration behavior. This anomaly prompted deeper investigation, which traced back to SUNBURST's presence on the network. Network traffic analysis subsequently corroborated the finding by identifying jittered, low-and-slow DNS beaconing to command-and-control infrastructure disguised to resemble legitimate SolarWinds telemetry domains. This case demonstrates the structural necessity of anomaly-based and behavioral detection (UEBA) as a complement to signature-based systems: a sufficiently sophisticated, trust-exploiting supply-chain attack can be engineered specifically to produce no signature match, and only deviation from an established behavioral baseline, reviewed by a human analyst, was capable of surfacing the intrusion.

1. 3.5.A A sensor receives its traffic from a hardware tap on the internet uplink. The sensor's analysis process crashes at 02:00 and is not restarted until 09:00. What is the consequence?
  • A. The uplink goes down for seven hours, because the sensor was in the forwarding path.
  • B. Traffic continues to flow normally and the organization simply has no record of what crossed the link during those seven hours.
  • C. All traffic is permitted without inspection and users receive certificate errors.
  • D. The tap buffers the traffic and replays it to the sensor when it restarts.
2. 3.5.A 3.5.C An organization must retain a full year of evidence about which internal hosts communicated with which external addresses, and the security budget cannot absorb petabytes of storage. Which data source fits?
  • A. Full packet capture on every link, retained for twelve months.
  • B. Flow records such as NetFlow or IPFIX, which summarize each conversation's endpoints, byte and packet counts, and duration without storing payload.
  • C. Host-based file integrity monitoring logs.
  • D. Snort payload signatures with the alert text retained.
3. 3.5.C Nearly all traffic leaving a company is TLS-encrypted and the company has decided not to decrypt it. Which detection approach remains available?
  • A. Deep packet inspection of HTTP request bodies for known web-shell strings.
  • B. Analysis of metadata that survives encryption, TLS client fingerprints, the server name and certificate offered during the handshake, and flow timing and byte volumes.
  • C. Matching the SHA-256 hash of the plaintext payload against a malware database.
  • D. No network detection is possible; only endpoint agents can contribute anything.
4. 3.5.D Ten million connections cross a monitored boundary each day and about a hundred belong to an intrusion. A detector flags 99 of those hundred and also flags one percent of the benign connections. What is the operational problem?
  • A. Recall is too low, so most intrusions are missed.
  • B. Roughly 100,000 alerts are produced per day and only about one in a thousand is real, so no realistic analyst team can work the queue and the true positives go uninvestigated.
  • C. The detector's accuracy is below 90 percent and it should be replaced.
  • D. There is no problem; 99 percent accuracy is an acceptable operating point.
5. 3.5.E A flow log shows one internal address sending single-packet, SYN-only, zero-duration records to 227 ports across 14 hosts within one second, with no reply flags on any record. Which indicator is this, and what is the analyst's first corroborating check?
  • A. Beaconing; check whether the interval between connections is constant.
  • B. Scan fan-out; check whether the source address belongs to the organization's own authorized vulnerability scanner before escalating.
  • C. Data exfiltration; check the ratio of bytes sent to bytes received.
  • D. DNS tunnelling; compute the entropy of the queried hostnames.
6. 3.5.E An analyst wants to detect data encoded into DNS subdomain labels. Which test actually separates encoded labels from ordinary hostnames?
  • A. Shannon entropy normalized by its length-dependent maximum, flagging any label above 0.9.
  • B. Absolute Shannon entropy combined with label length, supported by query volume to a single authoritative domain.
  • C. Any hostname containing a digit.
  • D. Any DNS query using UDP rather than TCP.
7. 3.5.B 3.5.D Free response. A security manager proposes replacing the organization's signature rule set with a machine-learning anomaly platform, arguing that it catches novel attacks and reports 99 percent accuracy in the vendor's evaluation. Explain what artificial intelligence genuinely contributes to detection and response, evaluate the manager's proposal using the relationship between prevalence, recall, precision, and alert volume, and state what you would deploy instead and why.
8. 3.5.C 3.5.E Free response. A workstation at 10.20.4.17 shows three things over one week: outbound TLS connections to a single external address every 30 minutes give or take two minutes, each carrying roughly 500 bytes; DNS queries whose leftmost labels run 40 to 60 characters of mixed-case alphanumerics, several hundred per hour, all under one parent domain; and, on one night, a single 31-minute connection that sent 611 MB and received 1.1 MB. Explain what each observation indicates, identify which log source and analytic technique recovers each one, and explain why none of the three requires decrypting the traffic.

Answer Key

1. B3.5.A

A tap-fed sensor sits beside the forwarding path, not in it, so its failure removes visibility and nothing else, and it does so silently, since no user experiences a symptom to report. That is the characteristic failure mode of passive monitoring and the reason such outages are found by monitoring the monitor rather than by the help desk. A describes the fail-closed behaviour of an inline device, which a tapped sensor is not. C describes an inline device failing open, again a property of in-path deployment, and the certificate errors belong to a TLS-terminating proxy, which is a different thing entirely. D is fabricated: a tap is a passive copier with no buffer and no replay capability.

2. B3.5.A, 3.5.C

Flow records answer exactly the question posed, who talked to whom, when, for how long, and how much moved, at roughly a thousandth of the storage of full capture, which is what makes year-long retention affordable. A is the option the constraint explicitly rules out: a single sustained gigabit link produces on the order of ten terabytes a day, so a year across many links is far beyond the stated budget. C answers a host question, not a network-communication one, and would not record external peers at all. D retains only the alerts a signature happened to fire on, so it holds no record of the connections that matched nothing, which is most of them.

3. B3.5.C

Encryption conceals the payload and leaves a substantial amount of observable metadata: the ClientHello is sent in the clear and yields a JA3 or JA4 fingerprint of the client software, the handshake exposes the server name and the presented certificate, and flow timing, record sizes, and byte totals are visible to any on-path observer. Detection then reasons from those residues. A and C both require plaintext the sensor does not have, that is the premise of the question, not an oversight to be corrected by better signatures. D overstates the limit: the metadata channel is precisely why beaconing, fingerprint drift, and volumetric exfiltration remain detectable on the network without decryption.

4. B3.5.D

One percent of roughly ten million benign connections is about 99,999 false alerts, against 99 true ones, so precision is about one in a thousand and daily volume is six orders of magnitude above what a small team can investigate. The detector's true positives exist but are unreachable, which is the operational failure. A misreads the figures: recall is 99 percent, which is excellent, and recall is not what is wrong. C is arithmetically false and also names the wrong metric, accuracy here is 99 percent and is uninformative precisely because the negative class dominates. D takes accuracy at face value, which is the specific error the base-rate arithmetic in Topic 1.5 exists to correct.

5. B3.5.E

One source touching many destination-host and port pairs with a single SYN each, zero duration and no reply, is the signature shape of service discovery: a real client completes a handshake and transfers something, and this source never does. Because an authorized vulnerability scanner produces an identical shape, confirming whether the source is the scanner is the cheapest check that separates a finding from an incident. A describes a different indicator entirely, and interval regularity is meaningless across records that all share one timestamp. C names the exfiltration indicator, which depends on sustained byte asymmetry that these 60-byte records do not show. D names the DNS indicator, and these are TCP connection records with no queried names to score.

6. B3.5.E

Entropy is bounded by the logarithm of the string's length, so absolute entropy is meaningful only when read together with length, a thirty-character label carrying better than four bits per character is doing something no naming convention does, and query volume against one authoritative domain corroborates it. A is the plausible-looking trap and is wrong for a concrete reason shown in the worked output: normalizing by the ceiling scores the ordinary hostname "api" at 1.00 and an encoded 26-character label at 0.79, inverting the ranking the analyst wants. C would flag a large fraction of ordinary infrastructure hostnames while missing any purely alphabetic encoding. D is not an indicator at all: DNS uses UDP by default under RFC 1035, so this describes essentially all DNS traffic.

7. Free response3.5.B, 3.5.D

Model answer. Machine learning contributes three things that signatures cannot. It builds per-entity baselines, so a deviation is judged against what that specific account or host normally does rather than against an organization-wide threshold, which is how compromised-credential misuse and insider activity surface. It requires no labels, so an unsupervised model such as an Isolation Forest can flag a technique nobody has catalogued, which is the structural blind spot of every signature. And it performs triage at volumes no analyst team can read, narrowing millions of events to a reviewable candidate set. What it does not do is establish that a flagged event is malicious: "unusual" and "malicious" are different predicates, and in an enterprise most unusual things are a quarterly batch job, a new build agent, or a laptop back from leave.

The proposal fails on the arithmetic. Accuracy is uninformative when the negative class dominates: at a prevalence near one in a hundred thousand, a detector can be 99 percent accurate and still produce a hundred thousand false alerts a day for ninety-nine real ones, a precision of about 0.1 percent. The figures to demand from the vendor are the false-positive rate, the resulting alert volume at this organization's own event rate, and precision at the intended operating point, not accuracy and not ROC area, which flatters low-prevalence detectors because a one-percent false-positive rate looks negligible on a ROC axis and means a hundred thousand alerts in practice. Replacing signatures compounds the error, since signature rules are the cheapest and most precise way to stop what is already known.

The right deployment keeps both layers and adds a third. Signature rules, rate-thresholded, handle the known and carry high precision. The anomaly platform runs as a triage layer feeding candidates, not alerts, into review. Precision is then raised by corroboration rather than by model tuning: requiring an anomaly score to coincide with a rare TLS fingerprint and a first-seen external destination multiplies roughly independent false-positive rates and buys orders of magnitude where retuning buys percentage points. Automated action is gated at a far higher threshold than alerting, and a human retains authority over containment.

A grader should look for: (i) at least two genuine contributions of machine learning, per-entity baselining, label-free detection of novel techniques, or triage at volume; (ii) an explicit statement that accuracy is the wrong metric at low prevalence, with the alert-volume and precision consequence worked through in numbers; (iii) the recommendation to retain rather than replace signatures, with a reason; (iv) at least one concrete mechanism for raising precision, such as corroboration across independent signals or a higher threshold for automated action than for alerting. An answer that only asserts "AI has false positives" without connecting prevalence to precision and alert volume has not evaluated the impact.

8. Free response3.5.C, 3.5.E

Model answer. The first observation is beaconing: a compromised host checking in with a command-and-control server on a schedule, the small and near-constant payload being a request for instructions rather than a data transfer. The two-minute spread is deliberate jitter intended to defeat a test for equal intervals, so the analytic technique is a variation measure rather than an equality test, the coefficient of variation of the gaps, which for a 30-minute beacon jittered by a few percent lands near 0.06, roughly two orders of magnitude below the value human browsing produces. The log source is flow data, NetFlow or IPFIX, or equivalently firewall connection records.

The second is DNS tunnelling, used for command and control or exfiltration and mapped to ATT&CK T1071.004 and T1048. Data is being encoded into the leftmost label, whose length is pushing toward the 63-octet ceiling RFC 1035 imposes, and whose mixed-case alphanumeric content is base32 or base64 output with entropy far above any naming convention. The technique is to compute Shannon entropy on the leftmost label and read it together with the label's length, then corroborate with the query rate to a single authoritative domain; the log source is the resolver's query log or a Zeek dns.log. The third is exfiltration: 611 MB sent against 1.1 MB received is a 555-to-one ratio, and a workstation is normally a net receiver of bytes, so the direction of the asymmetry is itself the indicator. The technique is a ratio test on flow byte counts over a sustained window.

None of the three needs decryption because none of them lives in the payload. Beacon detection uses connection start times and byte counts, which are properties of the flow record. Tunnelling detection uses the queried name, which DNS carries in the clear whether or not the later session is encrypted. Exfiltration detection uses byte totals and direction. Encryption conceals content and leaves timing, volume, direction, and names exposed, which is exactly the metadata these three techniques consume. Corroboration also matters: the same host produces all three indicators, and their coincidence raises confidence far above any one of them alone.

A grader should look for: (i) all three indicators named correctly, jittered beaconing, DNS tunnelling, and outbound data exfiltration; (ii) a specific analytic technique for each, with the recognition that jitter requires a variation measure rather than an equality test and that entropy must be read alongside label length; (iii) the correct log source for each, flow records for the first and third and resolver logs for the second; (iv) the explanation that these indicators are metadata rather than payload and therefore survive TLS. Credit the observation that the three coincide on one host and corroborate one another. An answer that proposes decrypting traffic to find any of these has missed why metadata analysis is the right instrument.
