Denial of service guide

Exam day outage

Beginner · about 45 min

Five minutes into an online exam, the school's portal stops answering, and an extortion email arrives. Tell real students from attack traffic, name the three kinds of flood, and choose how to get the exam back.

Worked exampleGuidedOn your own

09:15, Monday 9 Nov. Northfield Academy's online exam portal has been down since 09:07. 312 students were five minutes into their CS paper. An email arrived at 09:12 demanding money. You lead the response.

The evidence is in ~/case (Linux) and case/ (Python). The network tools (nmap, curl, wget, tshark, dig, nslookup, host, whois, ping, traceroute, nc, ssh, openssl, nikto, gobuster) work on a recorded copy of the case network; nothing leaves your browser.

The steps follow the incident response lifecycle: verify, scope, find the way in, preserve evidence, contain, eradicate, recover, learn. The order is based on the open LetsDefend incident response playbooks (MIT licence).

What you'll learn

  • Tell a flash crowd from a denial of service attack
  • Name volumetric, protocol and application floods from evidence
  • Count attack sources with sort and uniq
  • Choose a response that brings real users back

How to use this runbook

  • Run a cell with Shift+Enter (or its Run button). Run the cells in order: the first Linux cell copies the evidence into ~/case.
  • Tick each - [ ] box when you have done it.
  • Stuck? Open a Hint under the step.
  • Type your answer into each check box and it tells you if you are right. Answers are short: an address, a name, a number or a time such as 09:05.
  • Write your notes under each step. Download .ipynb keeps your notes and every output.

2. Verify: is this real?

Alerts are often wrong. Before you wake anyone up, decide whether this is a true positive.

  • ☐ What exactly raised the alarm, and when?
  • ☐ Name two pieces of evidence that prove something bad really happened
  • ☐ What harmless explanation would make this a false positive? Can you rule it out?
  • ☐ Decision: true positive / false positive (write it here)

Hint: A true positive needs evidence, not a feeling. Look for something only an attacker would do, such as a file that should not exist or a connection to an address nobody uses. Question: How many SYN-RECV connections did exam01 have at 09:06?

3. Busy, or under attack?

Exams start at 09:00, so some extra traffic is expected (a flash crowd). Prove it is more than that.

  • ☐ How many requests come from students, and how many from everything else?
  • ☐ What do real students ask for that the attack traffic never does?

Hint: Real students load the exam pages. Compare the paths the flood requests with the paths everyone else requests. Question: How many requests are in access.log? Question: Which path under /exam/ do students use to save their answers?

from collections import Counter
import re

rows = []
for line in open("case/access.log"):
    m = re.match(r'(\S+) .*?\[(.+?)\] "(\S+) (\S+)[^"]*" (\d+) \d+ "[^"]*" "([^"]*)"', line)
    if m:
        rows.append(m.groups())
print(len(rows), "requests")
paths = Counter(r[3].split("?")[0] for r in rows)
print("by path:", paths.most_common())
agents = Counter(r[5] for r in rows)
for ua, n in agents.most_common():
    print(str(n).rjust(4), ua)

4. Three kinds of flood

DDoS attacks hit different layers. Use the firewall counters and the capture to name each one.

  • ☐ Volumetric: what fills the 10 Gbit/s link? Why do DNS answers arrive that nobody asked for?
  • ☐ Protocol: what fills the server's connection table? What is SYN-RECV?
  • ☐ Application: which page is hammered, and which user agent does it? (A CTF flag is hiding in it.)

Hint: Source port 53 means DNS answers. Your network never asked for them: someone forged your address. That is reflection. Hint: The flag is inside the user agent of the GET /login?ts= requests. Submit it on the CTF board. Question: Which source port does the volumetric flood come from? Question: Which TCP state fills the connection table? (the state name)

7. Initial access: how did they get in?

The way in is the door you must close, or it happens again. Tick the one the evidence supports, and write the evidence next to it.

  • ☐ Phishing (a message that tricked someone)
  • ☐ Exploit of a public-facing application (a website or service bug)
  • ☐ Valid accounts (a real username and password or key, stolen or misused)
  • ☐ External remote services (VPN, remote desktop, SSH)
  • ☐ Drive-by compromise (a booby-trapped website)
  • ☐ Supply chain or trusted partner
  • ☐ Hardware added (a USB device or rogue machine)
  • ☐ Insider using access they were given
  • ☐ No intrusion (for example, traffic from outside that never got in)

8. Preserve the evidence

Cleaning up destroys evidence. Copy everything to a safe place, record the hashes and pack it before you change anything.

  • ☐ Copy the evidence and write SHA256SUMS
  • ☐ Note who collected it, when, and where it is stored (chain of custody)
mkdir -p ~/evidence && cp -r ~/case/* ~/evidence/
cd ~/evidence && find . -type f ! -name SHA256SUMS -exec sha256sum {} + > SHA256SUMS
pack=~/evidence-$(date -u +%Y%m%dT%H%M).tar
tar cf "$pack" -C ~/evidence .
(gzip -f "$pack" 2>/dev/null && echo "packed $pack.gz") || echo "packed $pack"
ls -l ~/evidence-*
wc -l SHA256SUMS
cd ~/case

9. Contain

Each layer needs its own fix. The cell prints the commands; nothing touches a real system.

  • ☐ Volumetric: ask the ISP for scrubbing (option 2). Why not blackhole (option 1)?
  • ☐ Protocol: turn on SYN cookies
  • ☐ Application: rate-limit /login per address and drop the bot's user agent
  • ☐ Tell students and the exams board before 10:07 so the paper can restart

Hint: A blackhole drops all traffic to the portal, the good with the bad. That finishes the attacker's job for them. Question: Which ISP option should you choose? (1 or 2)

echo "reply NOC-55102: option 2, scrubbing approved by the IT lead"
echo "sysctl -w net.ipv4.tcp_syncookies=1"
echo "sysctl -w net.ipv4.tcp_max_syn_backlog=65536"
echo 'nginx: limit_req_zone $binary_remote_addr zone=login:10m rate=5r/m;'
echo 'nginx: if ($http_user_agent ~* "Gecko/20100101") { return 444; }'
cat isp_ticket.txt | head -3
curl -s https://status.fiberlink.example/
