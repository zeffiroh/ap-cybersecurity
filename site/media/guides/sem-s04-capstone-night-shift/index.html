1. How the night desk works

A capstone uses every program from seminars 2 and 3 at once, so start by seeing how they fit. Each program answers one kind of question, and a night shift moves through them in order:

Program The question it answers Reads
Alert queue What do I have to decide tonight? alerts-night.json
SIEM search How big is it: which hosts, how often, how much data? fw_sessions.csv, dns.log, process.csv, the event logs
Event viewer What exactly ran on the laptop, started by what? eventlogs/*.jsonl
Packet viewer What really crossed the wire, and to where? capture.pcap
Indicators and ATT&CK Has anyone seen this before, and what do we call it? intel.json
Sigma rules How do we catch it sooner next time? the event logs
Report builder What does the client need to decide, and what does the morning shift need to know? your notes

2. Start of shift

You are the overnight analyst at a managed SOC. The queue has twelve alerts and no severities: the client's old SIEM doesn't send them. One real intrusion is in there. The rest is ordinary noise.

This is a capstone: the steps say what to deliver, not how. Hints cost one point each on the rubric, so open one only when you are stuck, and write down how many you opened.

Start by hashing the evidence and reading the queue end to end before you touch anything.

  • ☐ Hash every evidence file and keep the list
  • ☐ Read all twelve alerts once, quickly
  • ☐ Write down your first guess of which ones belong together: you will test it

Hint: Group alerts by host first. One laptop appears far more often than any other.

Question: How many alerts are in the night queue?

cd ~/case
sha256sum *.* eventlogs/*
echo ---
grep -c '"id"' alerts-night.json
grep -E '"(id|host|rule)"' alerts-night.json

3. Work the queue

Give every alert a disposition and a reason. A reason is a log line or a fact you checked, not a feeling. Severity is yours to judge: the queue doesn't tell you.

  • ☐ Every alert has a disposition
  • ☐ Every reason points at evidence
  • ☐ Alerts that belong to one intrusion say so
  • ☐ Use "needs more information" only with a question someone can answer

Hint: Five alerts are on acc-lt03. A program from a three-day-old domain at 00:03, a remote access tool at 00:04 and a new program in ProgramData at 00:13 on the same laptop are not a coincidence.

Use the Alert queue on alerts-night.json.

Question: Which host do the related alerts share?

4. Scope it with search

Before you escalate, know how big it is. Which laptop sent the most data out, where did it go, did anyone else talk to the same places, and what did the firewall stop?

  • ☐ Which host sent the most bytes out? Is that normal for it?
  • ☐ Who sends data to storage.cloudbox.example, and how much? (check intel.json: is that site allowed?)
  • ☐ Who else asked DNS for ledgerpro-support.example?
  • ☐ What did the firewall deny?
  • ☐ Write the cloud-storage search in KQL

Hint: stats sum(bytes_out) as sent by src_host adds up the bytes per laptop. Reception sends files to clients through cloud storage every day; compare its numbers with acc-lt03's.

Use SIEM search. Search: source=*fw_sessions.csv | stats sum(bytes_out) as sent by src_host | sort - sent

Use SIEM search. Search: source=*fw_sessions.csv dst_host=storage.cloudbox.example | stats count sum(bytes_out) as sent by src_host

Use SIEM search. Search: source=*dns.log ledgerpro-support.example | stats count by src_ip

Use SIEM search. Search: source=*fw_sessions.csv action=deny | table _time src_host dst_host dport app

Use SIEM search (KQL). Search: fw_sessions | where dst_host == "storage.cloudbox.example" | summarize sum(bytes_out) by src_host

Question: Which host sent the most data out? Question: How many hosts sent data to storage.cloudbox.example? Question: Which site did the firewall block for acc-lt03?

5. Confirm on the host and the wire

Search results are a summary. Confirm on the laptop's own logs and on the packet capture: which programs ran, which one sent the data, what it really is, and where the data went.

  • ☐ Sysmon event 1: follow the chain from the download to the copy tool
  • ☐ Sysmon event 1 shows OriginalFileName, the name the program was built with. Which program is hiding under a new name?
  • ☐ Sysmon event 3: which program connected to 203.0.113.150, and how many times?
  • ☐ Capture: find the TLS Client Hellos to the storage site

Hint: In the packet viewer, the filter tls.handshake.extensions_server_name contains cloudbox shows the start of each upload stream. rclone is a real, free copy tool for cloud storage: useful to IT, and to anyone stealing files.

Use the Event viewer on eventlogs/Sysmon.jsonl.

6. Check the indicators

Pull every indicator out of the evidence and check it against the intel feed and the client's allow list. Map what you saw to ATT&CK so the morning team and the client speak the same language.

  • ☐ Extract indicators from the logs
  • ☐ Which are on the feed, which are new, and which are on the allow list?
  • ☐ An allowed destination received the stolen files. What does that mean for blocking?
  • ☐ Map the behaviour to ATT&CK techniques
  • ☐ Defang indicators before you paste them anywhere

Hint: A phone call that talked the user into it, a remote access tool, three discovery commands, a download, a renamed program, and an upload to cloud storage.

Use the Indicators and ATT&CK.

Question: From which domain was the remote access program downloaded?

7. Escalate

Write one escalation for the whole intrusion, not one per alert. The client's practice principal reads it on a phone, between clients.

  • ☐ The ask first, with a time in UTC and in Brisbane time
  • ☐ Severity and the fact that decided it
  • ☐ Know / don't know
  • ☐ What you have and haven't changed

Hint: Say clearly that you have not touched the laptop. The client decides on isolation; you give them what they need to decide. Client tax files are personal information, so the client may have to tell people: say what was copied, not just that something was.

Use the Report builder.

8. Leave a new detection behind

The client's upload rule (AL-8406) fired at 00:46, thirty minutes after the copy started, because it waits for 1 GB. Write a better one: something the copy tool did before any data moved, that normal programs don't do. Test it, and write what would make it noisy.

  • ☐ A Sigma rule on Sysmon process events
  • ☐ Test it: it should match the renamed copy tool and nothing else
  • ☐ When would it have fired, compared with AL-8406?
  • ☐ One tuning note

Hint: Sysmon records OriginalFileName from inside the program, so renaming the file doesn't change it. A program whose OriginalFileName is rclone.exe but whose file name is something else is hiding.

Use the Sigma rules.

Question: How many events does your renamed-rclone rule match? Question: How many minutes before AL-8406 would it have fired?

9. Shift report

Close your shift. Everything open, by ID, with an owner. Everything closed in one line. What the morning should watch. Who you called and when. How many hints you opened.

  • ☐ Open items by ID with owners
  • ☐ Closed items
  • ☐ Watch list including your new rule
  • ☐ Calls with times
  • ☐ Hints opened

Use the Report builder.
