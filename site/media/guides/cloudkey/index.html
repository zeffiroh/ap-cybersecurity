Cloud breach guide

The key in the commit

Intermediate · about 60 min

A deploy key with admin rights sat in an old Git commit. The repo went public for one evening. By 02:00 someone had copied customer data, made a backdoor admin and started 20 crypto-miners. Trace it, shut it down and fix the root cause.

Worked exampleGuidedOn your own

07:31, Tuesday 3 Nov. A budget alert at Paperplane Apps: today's cloud bill is forecast at $3,812. A normal day is about $42. You are on call.

The evidence is in ~/case (Linux) and case/ (Python). The network tools (nmap, curl, wget, tshark, dig, nslookup, host, whois, ping, traceroute, nc, ssh, openssl, nikto, gobuster) work on a recorded copy of the case network; nothing leaves your browser.

The steps follow the incident response lifecycle: verify, scope, find the way in, preserve evidence, contain, eradicate, recover, learn. The order is based on the open LetsDefend incident response playbooks (MIT licence).

What you'll learn

  • Read a cloud audit log and group events by identity and address
  • Find a secret in Git history, even after it was deleted
  • Spot attacker persistence: a backdoor user and key
  • Contain a cloud breach in the right order

How to use this runbook

  • Run a cell with Shift+Enter (or its Run button). Run the cells in order: the first Linux cell copies the evidence into ~/case.
  • Tick each - [ ] box when you have done it.
  • Stuck? Open a Hint under the step.
  • Type your answer into each check box and it tells you if you are right. Answers are short: an address, a name, a number or a time such as 09:05.
  • Write your notes under each step. Download .ipynb keeps your notes and every output.

2. Verify: is this real?

Alerts are often wrong. Before you wake anyone up, decide whether this is a true positive.

  • ☐ What exactly raised the alarm, and when?
  • ☐ Name two pieces of evidence that prove something bad really happened
  • ☐ What harmless explanation would make this a false positive? Can you rule it out?
  • ☐ Decision: true positive / false positive (write it here)

Hint: A true positive needs evidence, not a feeling. Look for something only an attacker would do, such as a file that should not exist or a connection to an address nobody uses.

import csv

rows = list(csv.DictReader(open("case/billing.csv")))
normal = sum(float(r["compute_usd"]) for r in rows[:-1]) / (len(rows) - 1)
last = rows[-1]
print("normal compute per day: $%.2f" % normal)
print("%s compute: $%s, %.0f times normal" % (last["date"], last["compute_usd"], float(last["compute_usd"]) / normal))

4. What did the attacker do?

  • ☐ Group the audit log by source address
  • ☐ List every action in order, with the identity used
  • ☐ Which actions failed?

Hint: The Python cell counts events per address and identity. Anything from 203.0.113.x is the attacker. Question: How many events came from 203.0.113.151? Question: Which action was denied? (action name)

import json
from collections import Counter

ev = json.load(open("case/audit.json"))
by_ip = Counter((e["source_ip"], e["identity"]) for e in ev)
for (ip, who), n in by_ip.most_common():
    print(ip.ljust(15), who.ljust(15), n, "events")
print()
for e in ev:
    if e["source_ip"].startswith("203.0.113"):
        extra = e.get("policy") or e.get("new_key_id") or e.get("bytes") or ""
        print(e["time"][11:19], e["identity"].ljust(15), e["action"].ljust(18), e["resource"][:45].ljust(45), e["result"][:20], extra)

8. Initial access: how did they get in?

The way in is the door you must close, or it happens again. Tick the one the evidence supports, and write the evidence next to it.

  • ☐ Phishing (a message that tricked someone)
  • ☐ Exploit of a public-facing application (a website or service bug)
  • ☐ Valid accounts (a real username and password or key, stolen or misused)
  • ☐ External remote services (VPN, remote desktop, SSH)
  • ☐ Drive-by compromise (a booby-trapped website)
  • ☐ Supply chain or trusted partner
  • ☐ Hardware added (a USB device or rogue machine)
  • ☐ Insider using access they were given
  • ☐ No intrusion (for example, traffic from outside that never got in)

9. Preserve the evidence

Cleaning up destroys evidence. Copy everything to a safe place, record the hashes and pack it before you change anything.

  • ☐ Copy the evidence and write SHA256SUMS
  • ☐ Note who collected it, when, and where it is stored (chain of custody)
mkdir -p ~/evidence && cp -r ~/case/* ~/evidence/
cd ~/evidence && find . -type f ! -name SHA256SUMS -exec sha256sum {} + > SHA256SUMS
pack=~/evidence-$(date -u +%Y%m%dT%H%M).tar
tar cf "$pack" -C ~/evidence .
(gzip -f "$pack" 2>/dev/null && echo "packed $pack.gz") || echo "packed $pack"
ls -l ~/evidence-*
wc -l SHA256SUMS
cd ~/case

11. Fix the root cause

  • ☐ Rotate, don't just delete: a secret in Git history is public forever once cloned
  • ☐ Give the CI key only what CI needs (least privilege), or better, short-lived credentials with no stored secret
  • ☐ Turn on secret scanning so commits with keys are blocked
  • ☐ Only admins can make repos public
  • ☐ Budget alerts every hour, not every morning
