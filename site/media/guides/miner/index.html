The miner in the build server

Intermediate · about 60 min

Brightloom Games' build server has run at full CPU all night. Trace a brute-forced CI login to a script console, a dropper, three kinds of persistence and a cryptominer talking to a mining pool, then clean up and rebuild.

WalkthroughPracticeSolo

08:30, Thursday 5 Nov. Monitoring says build01 at Brightloom Games has been above 95% CPU for six hours, and developers say game builds take 38 minutes instead of 6. build01 runs Forgeway CI, a Jenkins-style build server. You are on call.

The evidence is in ~/case (Linux) and case/ (Python). The network tools (nmap, curl, wget, tshark, dig, nslookup, host, whois, ping, traceroute, nc, ssh, openssl, nikto, gobuster) work on a recorded copy of the case network; nothing leaves your browser.

The steps follow the incident response lifecycle: verify, scope, find the way in, preserve evidence, contain, eradicate, recover, learn. The order is based on the open LetsDefend incident response playbooks (MIT licence).

What you'll learn

  • Spot a cryptominer hiding behind a kernel thread's name
  • Prove a brute force on a CI login, and why a script console is a remote shell
  • Find three kinds of Linux persistence: cron, systemd and SSH keys
  • Follow mining traffic to a pool and contain, eradicate and rebuild

How to use this runbook

  • Run a cell with Shift+Enter (or its Run button). Run the cells in order: the first Linux cell copies the evidence into ~/case.
  • Tick each - [ ] box when you have done it.
  • Stuck? Open a Hint under the step.
  • Type your answer into each check box and it tells you if you are right. Answers are short: an address, a name, a number or a time such as 09:05.
  • Write your notes under each step. Download .ipynb keeps your notes and every output.

2. Verify: is this real?

Alerts are often wrong. Before you wake anyone up, decide whether this is a true positive.

  • ☐ What exactly raised the alarm, and when?
  • ☐ Name two pieces of evidence that prove something bad really happened
  • ☐ What harmless explanation would make this a false positive? Can you rule it out?
  • ☐ Decision: true positive / false positive (write it here)

On Linux, real kernel threads such as kswapd0 show in ps with square brackets and use almost no CPU. A program in /var/tmp with the same name is a disguise.

5. From login to shell: the script console

A CI server's script console runs any code on the server, as the CI user. Admin on a CI server means a shell on the box, and access to every secret the builds use.

  • ☐ What did the attacker run through the console? List both scripts
  • ☐ Which secrets file did they read? What lives in it (Git tokens, cloud keys, signing keys)?
  • ☐ Where did the dropper script come from?

Hint: grep script-console ci_audit.log shows each script. The second one downloads and runs a shell script with curl | sh. Question: Which file of secrets did the attacker print through the console? (file name) Question: Which IP address served x.sh?

echo ---

echo ---

6. Read the dropper and the miner

Read x.sh line by line. Never run malware to see what it does; read it.

  • ☐ Which competing miners does it kill first?
  • ☐ Which files does it download, and where does it hide them?
  • ☐ How does it become root? What is in persist/sudoers.d_forgeway, and why was it added?
  • ☐ What do the strings say the "kswapd0" program really is?

7. Persistence: every way back in

Attackers rarely leave one way back. If you remove one and miss another, the miner is back in 15 minutes.

  • ☐ The cron file: how often does it re-download x.sh?
  • ☐ The systemd service: what does it start, and what happens if you kill the process?
  • ☐ The SSH keys: which key doesn't belong? Was it used? (A CTF flag is in the key's comment.)
  • ☐ The forgeway user's own crontab: is it clean?

Hint: In cron, */15 in the minute field means every 15 minutes. In systemd, Restart=always brings a killed process back. Hint: Compare the two keys in root_authorized_keys. Then grep auth.log for root logins. Question: How many different persistence mechanisms did the attacker add? Question: What is the file name of the attacker's systemd unit? Question: At what time (HH:MM) did the attacker log back in as root over SSH?

11. Preserve the evidence

Cleaning up destroys evidence. Copy everything to a safe place, record the hashes and pack it before you change anything.

  • ☐ Copy the evidence and write SHA256SUMS
  • ☐ Note who collected it, when, and where it is stored (chain of custody)

Hint: Collect before you clean. Once you delete the cron file and kill the miner, that evidence is gone forever.

mkdir -p ~/evidence && cp -r ~/case/* ~/evidence/
cd ~/evidence && find . -type f ! -name SHA256SUMS -exec sha256sum {} + > SHA256SUMS
pack=~/evidence-$(date -u +%Y%m%dT%H%M).tar
tar cf "$pack" -C ~/evidence .
(gzip -f "$pack" 2>/dev/null && echo "packed $pack.gz") || echo "packed $pack"
ls -l ~/evidence-*
wc -l SHA256SUMS
cd ~/case

13. Eradicate

Remove all three ways back in, then the miner. Order matters: stop the service and the cron entry before you kill the process, or they start it again.

  • ☐ Remove the cron file and the systemd unit
  • ☐ Remove the attacker's SSH key, keep the real one
  • ☐ Delete the miner and its config
  • ☐ Remove the NOPASSWD sudo rule

Hint: grep -v prints every line that does NOT match, so it keeps the good key.

echo "systemctl disable --now sysupdate.service"
rm -f persist/etc_cron.d_sysupdate persist/sysupdate.service
grep -v Hq7mXbV0 persist/root_authorized_keys > /tmp/keys && mv /tmp/keys persist/root_authorized_keys
echo 'forgeway ALL=(root) NOPASSWD: /usr/bin/docker' > persist/sudoers.d_forgeway
rm -f suspect/config.json
echo "kill 4242; rm -rf /var/tmp/.cache"

14. Recover

A server where someone was root can't be fully trusted again. The safe path is to rebuild it.

  • ☐ Rebuild build01 from a clean image and restore only the job configs
  • ☐ Put Forgeway behind the VPN, with single sign-on and MFA; lock accounts after failed sign-ins
  • ☐ Give the CI user only the sudo it needs (or none: run builds in containers)
  • ☐ Watch: CPU on build servers, outbound connections to port 3333, new cron files and systemd units

Hint: Builds were 6x slower. Check that build times are back to normal after the rebuild: that is your recovery test.
