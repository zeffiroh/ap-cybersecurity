Authorised testing: web, APIs and findings that get fixed

Practitioner · about 360 min

1. Authorisation and scope, before anything else

A test without written permission is an attack. Read the letter of authorisation all the way through, then turn it into rules of engagement: who authorised it, exactly what is in and out of scope, the window, what you may and may not do, when you stop and who you call, and how you treat data.

Use the Report builder.

  • ☐ Every in-scope address and URL, and every out-of-scope one
  • ☐ The stop contact and number, written where you'll see it
  • ☐ What data you may touch, and how much

Hint: A host can be on the same network and look like part of the shop and still be out of scope. Only the owner of a system can authorise testing it.

Question: Which IP address is out of scope? Question: Who is the stop contact? (full name)

2. Recon, inside the lines

Scan only what's in scope. Name each address on the command line, so you can't accidentally sweep the whole range and hit the payment host. Then look at what you found.

  • ☐ Which services run on each in-scope host, with which versions?
  • ☐ Which one looks like it shouldn't be on the internet?
  • ☐ What did you find in the staging JavaScript file?

Hint: A "debug" API on port 8080 is a classic staging leftover. Read the saved app.bundle.js: developers leave things in bundles that everyone can download.

3. Finding 1: a login that trusts what you type

In the shop, the login puts the email straight into a SQL query inside quotes. End the quote and comment out the password check, and you're whoever you name. Prove it with one request in the web proxy, as admin, and stop there.

Use the Web proxy.

Then do the same in Hack the shop (mission "Log in as the admin"), and see the fix in the SQL injection lab: a parameterised query.

  • ☐ The request, the response status and the role you got
  • ☐ Why it works: the query the server built
  • ☐ The fix, in one line a developer can follow
  • ☐ The retest: the same request should now get 401

Hint: '-- closes the email's quote, and -- starts a SQL comment, so AND password = ... is never checked.

Question: Which HTTP status does the injected login get?

4. Finding 2: someone else's order

Log in as the demo customer and open one of your orders. The API call is /api/orders/ and a number. Change the number. If the shop gives you an order that isn't yours, that's an insecure direct object reference (IDOR): the API checks that you're logged in, not that the thing is yours.

Use the Web proxy.

  • ☐ Log in as demo@nimbu.shop first (Login tab), so {{token}} holds your token
  • ☐ Your own orders are 3 and 4; ask for 2
  • ☐ Note what you saw, then stop: one record proves it
  • ☐ The fix: the query must include the caller's user ID

Hint: Writing down someone's address in a report is itself a data leak. Say "order 2 belongs to another customer; it showed a delivery address", not the address.

Question: Which order number belongs to someone else and proves the finding?

5. Finding 3: a token anyone can forge

The staging bundle holds a login token. A JWT is three parts: header, payload, signature. The signature only protects the token if its secret is hard to guess. Load the token in the JWT inspector, read what it says, and check its secret against the wordlist. That's an offline check: nothing is sent to the server.

Use the JWT inspector.

  • ☐ What's in the header and payload? Which algorithm?
  • ☐ Is the secret in the wordlist? Which word?
  • ☐ With the secret, what could an attacker change? (role: admin)
  • ☐ Two fixes: a long random secret from a vault, and the token out of the bundle

Hint: The shop's own mission "Forge a token" shows the other classic JWT mistake: a server that accepts alg: none.

Question: Which signing algorithm does the token use? Question: What is the token's secret?

6. Score and rank

Score each finding's CVSS vector, then rank the register. CVSS describes the flaw; the ranking adds whether it's reachable from the internet and whether anyone is exploiting it.

Use the CVSS and patch priority.

  • ☐ Score all three vectors
  • ☐ Rank the register: which is first, and why?
  • ☐ For NM-02, why is Privileges Required "Low"?

Hint: The IDOR needs a customer account, which anyone can create for free. So PR:L is honest, but don't let it make the finding sound minor.

Question: What is the CVSS base score of the login bypass?

7. Write findings a developer can fix

A finding nobody can reproduce doesn't get fixed. For each one: the exact request, what came back, why it works, the fix in code terms, and the retest. Keep the data out: say what you saw, not the customer's address.

Use the Report builder.

  • ☐ A developer could reproduce each finding from your text alone
  • ☐ Each fix is specific (a query, a setting), not "improve security"
  • ☐ Each has a retest
  • ☐ "What went well" is honest: tests that only list failures get ignored

8. Retest, then tell the board

Retest each fix the same way you proved it: the same request should now fail. Then write the board note: no SQL, no CVSS, just what could have happened to the business, what it costs to fix, and what you need them to decide.

Use the Report builder.

  • ☐ The ask is the first line
  • ☐ Impact in business words: money, customers, regulators
  • ☐ What you don't know (has anyone else found these?)

Hint: Boards decide on money, time and risk. "Two days of developer time to close three ways in" is a decision they can make.
