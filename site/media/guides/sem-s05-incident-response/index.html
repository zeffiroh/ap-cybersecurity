Incident response: ransomware, lateral movement and memory

Practitioner · about 360 min

Take a ransomware incident at an engineering firm from the first call to the executive summary: keep a chain of custody, rebuild the night from VPN, Windows, Sysmon and process logs, read memory-forensics and triage output, map every step to ATT&CK, decide under pressure in a tabletop, and write the report.

1. Take custody of the evidence

Before you read anything, hash it, and start a chain of custody: who handled which file, when, and what its hash was. If this ends up with the police, an insurer or a court, the custody log is what makes your evidence count.

Use the Hex, strings and hashes on suspect/RESTORE-FILES.txt.

  • ☐ Hash every file (the Linux cell)
  • ☐ In the Hex tool, open the ransom note, hash it and add a custody entry
  • ☐ Add a custody entry for locker.strings.txt too
  • ☐ Download the chain of custody

Hint: A custody entry says what you did ("received from IT", "hashed", "copied for analysis"), when, and who you are.

4. The process tree: from a shell to the keys

Every program has a parent. The process tree shows who started what, so you can follow the attacker's hands on each machine. The tool flags the usual tells: programs in folders anyone can write to, hidden PowerShell, downloads, deleting backups.

Use the Process tree.

  • ☐ On eng-ws14: what did the attacker run from the RDP session's cmd.exe, in order?
  • ☐ Which process read lsass's memory, and with which DLL?
  • ☐ On fs02: what started the encryption, and what ran just before it?
  • ☐ Mark every attacker process

Hint: comsvcs.dll is a real Windows DLL; its MiniDump function writes a process's memory to a file. Attackers use it because it's already on every machine.

Question: Which DLL was used to dump lsass's memory? Question: Which service started the programs on fs02?

5. Memory: what the RAM remembered

The incident team took a memory image of eng-ws14 at 01:14 and ran Volatility on it. We can't re-run Volatility in the browser, but we can read its saved output. Memory shows things logs can miss: exited processes, the command lines, network connections and who was in which session.

  • ☐ Which PID is lsass, and which process dumped it?
  • ☐ What did nt.exe do with the dump?
  • ☐ Which account and password hash did px.exe use, against which server?
  • ☐ Which session were they in, and whose was the other one?

Hint: In px.exe's command line, -H is an NTLM hash. Using a hash instead of a password is "pass the hash". The netscan line shows the connection it made.

Question: What is lsass's PID on eng-ws14? Question: Which account did px.exe use on fs02? Question: In which RDP session number was the attacker?

8. Decide under pressure

Responders make calls before they have all the facts. Play the tabletop as the incident lead. Each choice costs time; the debrief at the end says what good looks like.

Use the Tabletop exercise on tabletop-garnet-ransomware.json.

  • ☐ Play it once as the incident lead
  • ☐ Play it again as the managing director: which call is hardest from that seat?
  • ☐ For each decision, one line on why

Hint: Isolate, don't power off: memory is evidence. And the six-hour CERT-In clock starts when you noticed, not when you finish investigating.

Question: What is the best score you can get in the tabletop?

9. Write the executive summary and the technical annex

Two readers, one report. The Summary section is the executive summary: half a page a managing director can act on, with the decisions needed today. The rest is the technical annex for IT, the insurer and CERT-In.

Use the Report builder.

  • ☐ The summary has no jargon and ends with the decisions needed
  • ☐ The timeline is in UTC and matches your merged timeline
  • ☐ Scope says what was affected and what was checked and not affected
  • ☐ Each lesson leads to an action

Hint: Read your summary as if you were the managing director at 08:00 on a Saturday. Can you decide from it? Is "pass the hash" in it? It shouldn't be.
