Insider threat guide

The night shift download

Beginner · about 50 min

An engineer who has just resigned to join a competitor badges into an empty office at 01:47. Build a timeline from badge, VPN, Git, USB and DLP records, and handle it the right way: evidence first, then HR and Legal.

Worked exampleGuidedOn your own

Tuesday 3 Nov, 08:40. Security at Halcyon Aero sees three data loss (DLP) alerts from overnight, all for one engineer. Your job: find out what happened, prove it with evidence, and handle it lawfully and fairly.

The evidence is in ~/case (Linux) and case/ (Python). The network tools (nmap, curl, wget, tshark, dig, nslookup, host, whois, ping, traceroute, nc, ssh, openssl, nikto, gobuster) work on a recorded copy of the case network; nothing leaves your browser.

The steps follow the incident response lifecycle: verify, scope, find the way in, preserve evidence, contain, eradicate, recover, learn. The order is based on the open LetsDefend incident response playbooks (MIT licence).

What you'll learn

  • Build one timeline from badge, VPN, Git, USB and proxy records
  • Compare normal behaviour with a suspicious night
  • Tell a policy gap from a technical gap
  • Handle an insider case lawfully: evidence first, then HR and Legal

How to use this runbook

  • Run a cell with Shift+Enter (or its Run button). Run the cells in order: the first Linux cell copies the evidence into ~/case.
  • Tick each - [ ] box when you have done it.
  • Stuck? Open a Hint under the step.
  • Type your answer into each check box and it tells you if you are right. Answers are short: an address, a name, a number or a time such as 09:05.
  • Write your notes under each step. Download .ipynb keeps your notes and every output.

2. Verify: is this real?

Alerts are often wrong. Before you wake anyone up, decide whether this is a true positive.

  • ☐ What exactly raised the alarm, and when?
  • ☐ Name two pieces of evidence that prove something bad really happened
  • ☐ What harmless explanation would make this a false positive? Can you rule it out?
  • ☐ Decision: true positive / false positive (write it here)

Hint: A true positive needs evidence, not a feeling. Look for something only an attacker would do, such as a file that should not exist or a connection to an address nobody uses. Question: How many DLP alerts are in dlp_alerts.json?

7. Build the timeline

Put every event from every source in one list, sorted by time. This is the heart of the case.

Hint: Read the timeline top to bottom and say each line out loud as a sentence. Gaps between events tell a story too. Question: Which happened first: the USB copy or the FileCrate upload? (usb or upload)

import csv, json, re

ev = []
for r in csv.DictReader(open("case/badge.csv")):
    ev.append((r["time"], "badge", r["user"] + " " + r["door"] + " " + r["result"]))
for line in open("case/vpn.log"):
    ev.append((line[:19].replace("T", " "), "vpn", line[20:].strip()))
for line in open("case/git_audit.log"):
    if "clone" in line:
        ev.append((line[:19].replace("T", " "), "git", line.split("repo=")[1].split()[0]))
for r in csv.DictReader(open("case/ws_events.csv")):
    ev.append((r["time"], "workstation", r["event"] + " " + r["detail"]))
for line in open("case/usb.log"):
    ev.append((line[:19], "usb", line[29:].strip()))
for line in open("case/proxy.log"):
    ev.append((line[:19], "proxy", " ".join(line.split()[4:6])))
for t, src, what in sorted(ev):
    if t >= "2026-11-02 20":
        print(t, src.ljust(11), what[:90])

8. Before anyone talks to him

This is a people case as much as a technical one.

  • ☐ Preserve the evidence: hashes, logs, the workstation image, the USB serial
  • ☐ Don't confront him or warn him. Involve HR and Legal first (policy 9.1)
  • ☐ Ask FileCrate to preserve the account through Legal, not by logging in yourself
  • ☐ Write facts, not guesses: "copied 2.3 GB to USB", not "stole the designs"
  • ☐ Respect his privacy: only collect what the investigation needs

9. Initial access: how did they get in?

The way in is the door you must close, or it happens again. Tick the one the evidence supports, and write the evidence next to it.

  • ☐ Phishing (a message that tricked someone)
  • ☐ Exploit of a public-facing application (a website or service bug)
  • ☐ Valid accounts (a real username and password or key, stolen or misused)
  • ☐ External remote services (VPN, remote desktop, SSH)
  • ☐ Drive-by compromise (a booby-trapped website)
  • ☐ Supply chain or trusted partner
  • ☐ Hardware added (a USB device or rogue machine)
  • ☐ Insider using access they were given
  • ☐ No intrusion (for example, traffic from outside that never got in)

10. Preserve the evidence

Cleaning up destroys evidence. Copy everything to a safe place, record the hashes and pack it before you change anything.

  • ☐ Copy the evidence and write SHA256SUMS
  • ☐ Note who collected it, when, and where it is stored (chain of custody)
mkdir -p ~/evidence && cp -r ~/case/* ~/evidence/
cd ~/evidence && find . -type f ! -name SHA256SUMS -exec sha256sum {} + > SHA256SUMS
pack=~/evidence-$(date -u +%Y%m%dT%H%M).tar
tar cf "$pack" -C ~/evidence .
(gzip -f "$pack" 2>/dev/null && echo "packed $pack.gz") || echo "packed $pack"
ls -l ~/evidence-*
wc -l SHA256SUMS
cd ~/case

12. Fix the gaps

  • ☐ Access review on the day notice is given (ticket 77104 was still open)
  • ☐ Give people only the repos their job needs (least privilege)
  • ☐ Block USB storage by default; allow approved, encrypted drives
  • ☐ Alert in real time on bulk clones and after-hours badge use, not the next morning
