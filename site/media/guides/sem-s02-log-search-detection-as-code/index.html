1. How the search program works

Before you hunt, learn the program. A SIEM (security information and event management system) does four things with every log file it is given:

  1. Reads each file and splits it into events, usually one line or one JSON record each.
  2. Stamps every event with a time, _time, so events from different files line up on one clock.
  3. Recognises the format and records it as the sourcetype: syslog for Linux logs, access_combined for web server logs, json for Windows events.
  4. Extracts fields such as src_ip, user, status or EventID, so you can search on them instead of on raw text.

On screen you have a search box with a language switch (SPL or KQL), Run, a chart of events over time, the field list on the left (click a field to see its values and add one to your search), and the results as events or as a statistics table. Help lists the commands this teaching version knows.

The SIEM here is the company's: Chandni Textiles in Surat, a fabric shop that also sells online. Four logs from Monday 9 November have been loaded. Read README.txt first.

  • ☐ Run the first search: what did the program make of each file?
  • ☐ Run the second search: which programs wrote to auth.log?
  • ☐ Click the field src_ip in the field list and read its values

Hint: * means every event. stats count by source sourcetype makes one row per file and format, with the number of events in each.

2. Start with the raw log

A hunt starts with a question, not a tool. Ours: did anyone get into shop01, how did they do it, and what did they take? You'll answer it three times: in SPL, in KQL and in SQL. Real teams use different SIEMs, and moving a hunt between them is a daily job.

The SIEM search here is a teaching subset of each language, so not every command works. When you want the real thing, the free KC7 game and the free Azure Data Explorer help cluster run full KQL.

First read the raw log with grep, so you know exactly what the search program is reading.

  • ☐ How many lines does auth.log have?
  • ☐ Which line types do you see: Failed, Accepted, sudo, CRON?
  • ☐ Which address keeps failing, and which accounts did it try?

Hint: grep -c counts matching lines. awk '{print $(NF-3)}' prints the fourth word from the end, which is the source address on every Failed line.

Question: How many lines in auth.log contain "Failed password"?

cd ~/case
wc -l auth.log access.log lookbook_access.log
grep -c 'Failed password' auth.log
grep 'Failed password' auth.log | awk '{print $(NF-3)}' | sort | uniq -c | sort -rn
grep 'Failed password' auth.log | awk '{print $(NF-5)}' | sort | uniq -c

3. SPL: count, then pivot

SPL reads left to right: a search, then a pipe |, then a command that works on the results. stats count by src_ip groups the failures by address, and sort - count puts the biggest first.

Then pivot: take what you found and search again from a new angle. First the address, then the account it reached, then what that account did.

  • ☐ Run the failure count and read the table
  • ☐ Find the Accepted login from the same address
  • ☐ Find where that account normally logs in from
  • ☐ Find what it did with sudo, and compare with its normal sudo use

Hint: Field names come from the parsed log: action, src_ip, user, auth_method, process, command. Click any field name in the results to add it to the search.

Use SIEM search. Search: sourcetype=syslog action=failure | stats count by src_ip | sort - count

Use SIEM search. Search: Accepted src_ip=203.0.113.45 | table _time user auth_method

Use SIEM search. Search: process=sshd user=catalog | table _time src_ip action

Use SIEM search. Search: process=sudo | table _time user run_as command

Question: Which address failed most often? Question: Which account did that address log in as? Question: From which address does that account normally log in? Question: Which program did the attacker run with sudo to copy every database? (program name)

4. The same hunt in KQL

KQL starts with a table, then pipes into operators: where filters, summarize count() by groups, project picks columns, sort by orders. The table is named after the file: auth for auth.log. The answer must be the same as in SPL. If it isn't, one of the two searches is wrong.

  • ☐ Run the failure count in KQL and compare with SPL
  • ☐ Write the success pivot in KQL
  • ☐ Note one thing that is easier in each language

Hint: In KQL the count column is called count_. Strings use == and double quotes.

Use SIEM search (KQL). Search: auth | where action == "failure" | summarize count() by src_ip | sort by count_ desc

Use SIEM search (KQL). Search: auth | where src_ip == "203.0.113.45" and action == "success" | project _time, user, auth_method

Question: How many failed logins came from that address? (KQL count_)

5. SQL over the same logs

Every log is also a table. The SQL tool names each table after its file (auth, access, security) and makes a column for each field. SQL is the language behind most data lakes, so it is worth having in your pocket.

Searches only work on fields someone parsed. When a log arrives that your SIEM doesn't know, you write the parser. The log parser uses %{TYPE:name} pieces, the same idea as Grok in log pipelines.

7. Hunt the web attack in SPL and KQL

The SSH password guessing failed. So how did the attacker have catalog's password 40 minutes later? Look at the web log. uri_path is the page without the query string, which makes grouping easy.

  • ☐ Which tool did the attacker use? (look at the user agent)
  • ☐ Which database table did the injection read?
  • ☐ What did they do in the admin pages, and how big was it?
  • ☐ Write both searches into your hunt pack

Hint: %20 is a space, %27 is a quote and %3D is = in a URL. CyberChef's URL Decode makes the requests readable.

Use SIEM search. Search: sourcetype=access_combined useragent=sqlmap* | table _time clientip uri status

Use SIEM search. Search: sourcetype=access_combined clientip=203.0.113.45 uri_path=/admin* | table _time method uri status bytes

Use SIEM search (KQL). Search: access | where clientip == "203.0.113.45" and uri_path startswith "/admin" | project _time, method, uri, status, bytes

Question: Which scanner's name is in the user agent? Question: Which table held the staff passwords? Question: Which admin page did the attacker download? (the path, without ?from=...)

8. From hunt to rule: your first Sigma rule

A hunt you run once finds one attack. A rule finds the next one. Sigma is the open format for detection rules: one YAML file that converts to SPL, KQL and others.

9. Test for false positives, then tune

A rule that fires on everything is worse than no rule: people stop reading it. Test every rule twice: does it catch the attack (true positives) and does it stay quiet on normal work (false positives)?

The first rule below is deliberately noisy. Tick the events that are really malicious; the tool scores precision. Then use the tuned rules, which each describe one thing an attacker did.

  • ☐ Run the noisy rule and tick the malicious events
  • ☐ Run each tuned rule: each should match only attack events
  • ☐ Write one tuning note per rule: what it misses, and what would make it noisy

Hint: Good rules describe behaviour that normal users don't have: a program in C:\Users\Public, shadow copies deleted, a new member of Administrators.
