Digital signatures

Coding problem, 5.4.c: Implement RSA digital signatures (hash-then-sign)

Skill: Mitigate Risk · Maps to: 5.4.B · Language: Python 3 (pytest)

Problem

A software vendor wants to let users verify that a downloaded update really came from them and was not modified in transit. Rather than signing the whole update file directly with RSA (slow, and structurally risky per atom.md), implement the standard "hash, then sign" digital signature scheme: hash the message with SHA-256, reduce the digest mod n, and apply the RSA private-key operation to that digest, not the raw message.

Function contract

Implement, in the code editor: - sign(message: bytes, d: int, n: int) -> int, return the signature (SHA-256(message) mod n)^d mod n, using the signer's private exponent d and modulus n. - verify(message: bytes, signature: int, e: int, n: int) -> bool, recompute SHA-256(message) mod n and compare it to signature^e mod n, using the signer's public exponent e and modulus n. Return True iff they match. - solve(data: dict) -> dict, the blackbox entry point that dispatches to the two functions above (see the Reference section below).

You may use hashlib.sha256 for the hash step only. Implement the digest-reduction and the modular exponentiation (pow(base, exp, mod) is fine, it's Python's built-in, not an external crypto library) yourself, per the construction below.

The construction

digest        = int.from_bytes(SHA256(message).digest(), "big") % n
sign:         signature = digest^d mod n
verify:       recovered = signature^e mod n     ; valid iff recovered == digest (recomputed)
  • Hashing first keeps the signature a fixed size regardless of message length, and means a single changed byte in message produces a completely different digest (avalanche effect, 5.3.b), which is what makes tampering detectable.
  • d and n form the private key; e and n form the matching public key (5.4.b).

Input / Output

  • sign(message, d, n): message: bytes, d: int, n: int -> int signature.
  • verify(message, signature, e, n): signature: int, e: int, n: int -> bool.
  • solve(data): data = {"op": "sign", "message": "<str>", "d": <int>, "n": <int>} -> {"signature": <int>}, or data = {"op": "verify", "message": "<str>", "signature": <int>, "e": <int>, "n": <int>} -> {"valid": <bool>}.

Examples

Using the textbook-scale key pair p=61, q=53 -> n=3233, e=17, d=2753:

sign(b"pay Bob $50", 2753, 3233)        -> some int in [0, 3233)
verify(b"pay Bob $50", <that signature>, 17, 3233)   -> True
verify(b"pay Bob $950", <that signature>, 17, 3233)  -> False   # message tampered after signing

Constraints

  • Deterministic, offline, standard library only (hashlib only, no external crypto packages).
  • Correctness is checked in the tests against an independent oracle that recomputes the same hash-then-sign math directly (not by importing your functions).
  • Must pass all cases in the tests (visible + hidden), including: a tampered message failing verification, a wrong public key failing verification, an empty message, and determinism (signing the same message twice yields the same signature).

Reference

Any implementation that satisfies this interface can be swapped in (reference, student, or composite) and must pass the tests unchanged.

Entry points

def sign(message: bytes, d: int, n: int) -> int
def verify(message: bytes, signature: int, e: int, n: int) -> bool
def solve(data: dict) -> dict

solve() is the blackbox entry point; sign() and verify() are the underlying primitives it's built on and are tested directly as well.

Input

  • sign(message, d, n): message is raw bytes of any length (including empty); d is the signer's private exponent; n is the RSA modulus (both small, textbook-scale ints).
  • verify(message, signature, e, n): message as above; signature is the claimed signature (int); e is the public exponent; n is the modulus that must match the key pair used to sign (verifying with a different n/e pair must fail).
  • solve(data): data is a dict with "op" equal to "sign" or "verify".
  • "sign": {"op": "sign", "message": <str>, "d": <int>, "n": <int>}
  • "verify": {"op": "verify", "message": <str>, "signature": <int>, "e": <int>, "n": <int>}
  • message arrives as a plain UTF-8 string (encode with .encode("utf-8")).

Output (result)

  • sign(...) returns an int signature in the range [0, n).
  • verify(...) returns bool.
  • solve(...) returns {"signature": <int>} for op "sign", or {"valid": <bool>} for op "verify".

Guarantees / rules

  • Pure functions, deterministic, no I/O, no network. Standard library only (hashlib.sha256 may be used as the hash primitive; the RSA sign/verify math itself, reducing the digest mod n and using modular exponentiation, e.g. Python's built-in pow(base, exp, mod), must be implemented directly, not via any external crypto library).
  • Must implement "hash, then sign": signature = (SHA-256(message) mod n)^d mod n; verification recomputes SHA-256(message) mod n and compares it to signature^e mod n.
  • Any single-bit change to message must (with overwhelming probability) produce a different signature, and verification against the original signature must then fail.
  • Verifying a genuine (message, signature) pair with an unrelated key pair's public key (e, n) must return False.
