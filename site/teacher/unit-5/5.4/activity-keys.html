Asymmetric Cryptography · instructor-only · 4 entries

Skill 5.4.a

Public/private key pairs

Instructor notes

  • Expected reasoning: n and phi(n) come directly from p, q; d is the modular inverse of e mod phi(n); "encrypt with public / decrypt with private" for confidentiality, "sign with private / verify with public" for authenticity.
  • Common stumble: students swap which key does what for signing vs. encryption, or think the message-sender uses their OWN key rather than the recipient's public key, walk through the Alice-to-Bob example from atom.md explicitly.
  • Feeds the simulation's scenario-classification rounds and the coding problem (problem/), which implements the same n / phi(n) / valid-keypair math programmatically.
Skill 5.4.b

RSA algorithm

Instructor notes

  • Expected reasoning: n and phi(n) come directly from p, q; d is the modular inverse of e mod phi(n) (verify with (e*d) mod phi(n) == 1); encryption and decryption are the same operation (modular exponentiation) with different exponents; the round trip always recovers m exactly.
  • Common stumble: students forget m must be less than n, or make an arithmetic slip in the repeated-multiplication exponentiation, have them reduce mod n after each multiplication step rather than computing the full power first, to keep numbers small.
  • Feeds the simulation's encrypt/decrypt rounds and the coding problem (problem/), which implements the same key derivation, encrypt, and decrypt operations programmatically via modular exponentiation.
Skill 5.4.c

Digital signatures

Instructor notes

  • Expected reasoning: signing uses the private exponent d; verification uses the public exponent e; a tampered message changes the recomputed digest so it no longer matches the recovered value; verifying with the wrong public key recovers a different (wrong) digest even though the signature bytes are untouched, so it must be classified FORGED.
  • Common stumble: students think "the signature itself wasn't changed" means a wrong-public-key case should verify as VALID, walk through the fact that pow(signature, e, n) depends on which (e, n) you use, so an unrelated key pair recovers an unrelated digest.
  • Feeds the simulation's VALID/FORGED classification rounds and the coding problem (problem/), which implements the same hash-then-sign math programmatically and tests exactly these tampered-message and wrong-key scenarios.
Skill 5.4.d

PKI and digital certificates

Instructor notes

  • Expected reasoning: checks run in a fixed order (validity window, then revocation, then issuer/subject linkage or trust-store membership, then signature) and the FIRST failure is the reported reason, this mirrors validate_chain() in problem/solution.py.
  • Common stumble: students conflate "signature verifies" with "should be trusted." A self-signed cert's signature can verify (it signed itself) while still being untrusted because its subject is absent from the trust store, walk through scenario 4 from the simulation explicitly if this comes up.
  • Another common stumble: checking the leaf's signature against its OWN public key instead of the issuer's (next certificate's) public key. Reinforce: "you never trust a certificate to vouch for itself except at the root, and only if the root is already in the trust store."
  • Feeds the simulation's six-scenario TRUST/REJECT drill and the coding problem (problem/), which implements the identical leaf-to-root walk programmatically over real (small-number RSA) signatures instead of pre-computed true/false flags.
