Encryption vs. hashing

Unit 5 · Securing Applications and Data · 5.3 Symmetric Encryption, Hashing and Key Storage

Before class today. When a system needs to protect stored data, engineers reach for two very different tools: encryption and hashing. On the surface both produce an unreadable-looking blob of bytes from readable input. Below the surface they have opposite goals, and choosing the wrong one is a common and costly mistake.

The intuition to hold onto: The single question worth carrying into this lecture: do you ever need the original value back? If yes, encrypt. If no, hash. That one question does almost all the work in this skill, and it's worth testing against every scenario you meet from here forward, a payroll system needs to read salaries back out, so it encrypts; a login system never legitimately needs to see your actual password again, only whether what you typed matches, so it hashes. Confusing the two isn't a minor mistake, it's storing the wrong kind of secret for the job, and the cost of getting it backwards (plaintext-recoverable passwords sitting in a breached database) is exactly the kind of high-severity data breach 5.1.d taught you to score.

A myth worth busting before we start: "I can hash a file and recover it later." → Hashing is one-way; the digest cannot be reversed.

Today's goal: Distinguish encryption from hashing, explain the one-way property that makes them suited for different jobs, and choose the correct control when a scenario requires either confidentiality or integrity verification. Handout: pre-lecture-handout.docx.
