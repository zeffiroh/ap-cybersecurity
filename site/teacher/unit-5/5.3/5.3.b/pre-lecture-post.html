5.3.b, Symmetric encryption and key management

Before class today. When organizations need to protect the confidentiality of stored data (data-at-rest), they use symmetric cryptography. Symmetric encryption uses a single secret key for both encryption and decryption. Because the same key does both jobs, it must be kept secret; if an unauthorized party obtains the key, the protection is completely lost.

The intuition to hold onto: The image worth holding onto before this lecture: ECB mode is what happens when you encrypt each block of a message completely independently, and independence is exactly the problem, identical plaintext blocks produce identical ciphertext blocks, so the shape of your data leaks straight through the encryption, like tracing a photograph through frosted glass. That single image (the ECB-encrypted bitmap where you can still see the outline of the picture) is worth more than the definition, because it makes viscerally clear that "encrypted" is not a binary property, a cipher can be mathematically unbreakable and still leak everything that matters if it's chained together wrong.

A myth worth busting before we start: "Hardcoding a key in a private Git repository is safe." → Private repositories can be compromised, and any developer with clone access can copy the key. Keys should be stored in environment variables or secrets managers.

Today's goal: Explain the mechanics of symmetric encryption, differentiate between ECB and secure modes of operation (like CBC and GCM), and describe the key lifecycle management principles necessary to protect keys from compromise. Handout: pre-lecture-handout.docx.
