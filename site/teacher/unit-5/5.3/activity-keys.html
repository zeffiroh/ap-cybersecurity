Topic 5.3 Activity Answer Keys

Symmetric Encryption, Hashing and Key Storage · instructor-only · 3 entries

Skill 5.3.a

Encryption vs. hashing

Instructor notes

  • Scenario A Answer: Encryption. Medical records must be read in their original form (reversible) to provide patient care, but must remain confidential.
  • Scenario B Answer: Hashing (with salt). Passwords should never be recovered. Verification only requires checking if the computed hash matches the stored hash.
  • Scenario C Answer: Encoding (Base64). This is a formatting change to allow binary data in text environments. It provides no security.
  • Common stumbling block: Students often confuse encoding with encryption. Emphasize that encoding is a public, keyless standard that anyone can reverse.
Skill 5.3.b

Symmetric encryption and key management

Instructor notes

  • Expected reasoning: ECB is disqualified whenever the data has repeating structure (images, repeated field values); GCM is preferred whenever both confidentiality AND tamper-detection matter (e.g., sensitive database columns, network traffic); CBC is an acceptable middle ground when only confidentiality is needed and a fresh IV is guaranteed each time.
  • Common stumble: students think "AES is AES" and forget that the mode of operation, not just the cipher, determines whether patterns leak, reinforce with the ECB bitmap example from atom.md.
  • Common stumble on key management: students propose storing the DEK in plaintext "since it's already encrypted data next to it", steer them to envelope encryption (wrap the DEK with a KEK) and remind them a hardcoded/plaintext key defeats the whole system if the storage leaks.
  • Feeds the unit project (data-at-rest protection plan) and the coding problem's key-wrapping / weak-RNG / ECB-leakage toolkit.
Skill 5.3.c

Integrity and authenticity (HMAC)

Instructor notes

  • Expected reasoning: plain hash is always VULNERABLE against an attacker who can rewrite both the message and its accompanying digest, since hashing is public and keyless. Naive H(key+message) is VULNERABLE to length-extension attacks even though a secret is involved, because Merkle-Damgard hashes (SHA-256 included) expose their internal state as the digest. Real HMAC is SECURE because its double-nested construction never exposes a state an attacker can extend.
  • Common stumble: students think "any design with a secret key is safe." Reinforce that naive concatenation still has a real, historically-exploited weakness (length extension), the fix is specifically HMAC's nested structure, not just "add a key somewhere."
  • Common stumble: conflating integrity with authenticity. A plain hash can offer integrity over a channel the attacker cannot tamper with, but never authenticity, since anyone can compute it.
  • Feeds the coding problem (problem/), which has students implement HMAC-SHA256 by hand (ipad/opad nesting) and confirm a single tampered bit changes the tag.
