The big picture: The connective thread worth keeping is that every practice in this skill is least privilege (5.2.a) applied to code instead of people: a database connection scoped to only the tables it needs, a web server process that never runs as root, an error handler that fails closed by default rather than accidentally granting access when something goes wrong. That's the same blast-radius logic from 5.2.b, just moved from human roles to running processes, if an attacker exploits a bug in code running with excessive privilege, the bug becomes a full system compromise instead of a contained one. Also worth remembering: a verbose error message leaking a stack trace or internal file path is not a cosmetic issue, it's free reconnaissance handed straight to an attacker, which connects forward to 5.6.a's point that what an application logs (and what it exposes) shapes how much an attacker can learn before you ever notice them.

Key terms to lock in: - Least privilege (in code), running application processes and database connections with only the minimum access they need to function. - Parameterized query, a database query where user-supplied values are passed as separate, typed parameters rather than concatenated into the query string, preventing SQL injection. - Secrets management, storing credentials, API keys, and encryption keys outside source code (environment variables, a secrets manager) so they can be rotated without a code change. - Fail securely, designing error/exception paths to deny access by default rather than accidentally granting it when something unexpected happens. - Dependency management, pinning, tracking, and patching third-party library versions so a known vulnerability in a dependency does not become an unpatched vulnerability in the app.

Common misconceptions -- don't fall for these: - "Secure coding is just input validation done well." → Input validation is one practice among several; parameterized queries, secrets management, least privilege, and dependency management each close a different, independent class of vulnerability. - "A verbose error message is only a usability issue." → Detailed stack traces and internal paths shown to an attacker are reconnaissance information that materially helps them plan an attack. - "As long as the code works and passes QA, it's secure enough." → Functional correctness and security are different properties; code can pass every functional test while still building queries insecurely or running with excessive privilege.

Learning objective(s): 5.5.A, 5.5.B
