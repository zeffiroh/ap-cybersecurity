5.5.a, Input validation and sanitization

Before class today. Every application is, at its core, a machine that takes input from a user and does something with it: stores it, displays it, uses it to build a database query, or passes it to another program.

The intuition to hold onto: The rule worth memorizing cold before this lecture: client-side validation is a user-experience feature, not a security control, full stop, an attacker who disables JavaScript or sends a request with curl never touches your browser-side checks at all. That single fact rhymes directly with 5.1.c's BOLA lesson about hidden UI buttons: anything enforced only in the client was never actually enforced. Everything security-relevant in this skill has to happen again, independently, on the server, on every request, because the server is the one place the attacker can't reach in and edit.

A myth worth busting before we start: "Client-side (JavaScript) validation is good enough security." → It improves user experience but provides zero security guarantee, since an attacker fully controls the client and can bypass it entirely; all security-relevant validation must be re-checked on the server.

Today's goal: Explain why every application must treat user input as untrusted, distinguish allowlist from denylist validation, describe where validation must occur to be trustworthy, and identify how input validation prevents injection classes like SQL injection, cross-site scripting, and command injection. Handout: pre-lecture-handout.docx.
