Application security testing (SAST/DAST)

Unit 5 · Securing Applications and Data · 5.5 Secure Web Application Design

Before class today. Writing secure code is not the same as knowing your code is secure. Every application security program eventually asks the same question: how do we find the vulnerabilities before an attacker does? Two complementary families of automated testing answer that question from opposite directions, SAST (static application security testing) and DAST (dynamic application security testing).

The intuition to hold onto: The distinction worth carrying into this lecture: SAST reads code without running it, DAST attacks a running system without reading its code, and they are blind to exactly each other's territory, which is why the AP framework wants you to be able to sort a given finding into one bucket or the other, not just recognize that "testing happened." SAST can see every code path, including ones nobody has exercised yet, but it can't tell whether a flagged pattern actually reaches attacker-controlled input, so it over-flags. DAST only knows what it actually attacked, but when it finds something, that something is almost always real.

A myth worth busting before we start: "SAST and DAST find the same bugs, so you only need one." → They find different, mostly non-overlapping classes of issues, SAST sees the code but not runtime behavior; DAST sees runtime behavior but not the code. Mature pipelines run both.

Today's goal: Explain how static application security testing (SAST) and dynamic application security testing (DAST) find different classes of vulnerabilities, describe the tradeoffs of each, and classify a given finding as something SAST would catch, something DAST would catch, or neither.
