5.1.a

SQL Injection

Unit 5 · Securing Applications and Data · 5.1 Application Code Vulnerabilities

Before class today. Web applications that store data almost always use a relational database behind the scenes. When a user logs in, searches for a product, or retrieves a record, the application typically builds a SQL query using whatever the user typed. SQL injection (SQLi) happens when an attacker types SQL syntax instead of ordinary data, and the application blindly pastes it into the query without checking.

The intuition to hold onto: Carry this framing into the lecture: SQL injection is not really a database problem, it's a language problem, the application asked a user for a piece of data and got back a piece of code instead, and never noticed the swap. Every payload family in this skill, from admin'-- to UNION SELECT, is the same trick wearing different clothes: sneak syntax into a slot the program assumed would only ever hold values. Once you see it that way, the fix stops being a filter you bolt on afterward and becomes obvious from the start, never let user data and query syntax share the same string in the first place.

A myth worth busting before we start: "Encoding the output prevents injection", output encoding prevents cross-site scripting; SQL injection is an input parsing problem and requires parameterized queries or strict input validation, not output encoding.

Today's goal: Identify SQL injection attack patterns in web application input, explain how unsanitized queries expose database contents, and apply detection logic to flag malicious parameter strings. Handout: pre-lecture-handout.docx.
