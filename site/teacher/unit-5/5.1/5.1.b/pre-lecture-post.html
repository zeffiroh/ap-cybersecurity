5.1.b

Cross-site scripting (XSS)

Unit 5 · Securing Applications and Data · 5.1 Application Code Vulnerabilities

Before class today. A web application usually takes input from one user (a comment, a search term, a profile field) and displays it back, to that user, to an admin, or to every visitor. Cross-site scripting (XSS) happens when an application includes untrusted input in a page it sends to a browser without properly neutralizing it first.

The intuition to hold onto: The mental model to bring into this lecture: XSS is SQL injection's twin, just aimed at the browser instead of the database. In both cases the root failure is identical, data and code sharing one channel, so a program that expected to receive text ends up executing instructions instead. Once you already understand that a database can't tell apart "the string admin'--" from "a SQL comment," it should feel natural that a browser can't tell apart "the string <script>" from "an instruction to run JavaScript." The specific fix differs, escaping output for HTML instead of parameterizing a query, but the diagnosis is the same question asked in a new context: where did code and data get mixed?

A myth worth busting before we start: "Filtering <script> tags is enough." → Attackers use countless other vectors (onerror=, javascript: URLs, SVG, <img> tags), deny-listing tags is easily bypassed; escaping output is the reliable fix.

Today's goal: Explain how cross-site scripting (XSS) lets an attacker inject and run malicious script in another user's browser, identify the three main XSS variants, and recognize the input-handling mistakes that make an application vulnerable. Handout: pre-lecture-handout.docx.

## 5.1.b, Cross-site scripting (XSS)
**Before class today.** A web application usually takes input from one user (a comment, a search term, a profile field)
and displays it back, to that user, to an admin, or to every visitor. **Cross-site scripting
(XSS)** happens when an application includes untrusted input in a page it sends to a browser
*without properly neutralizing it first*.

**The intuition to hold onto:** The mental model to bring into this lecture: XSS is SQL injection's twin, just aimed at the browser instead of the database. In both cases the root failure is identical, data and code sharing one channel, so a program that expected to receive text ends up executing instructions instead. Once you already understand that a database can't tell apart "the string admin'--" from "a SQL comment," it should feel natural that a browser can't tell apart "the string `<script>`" from "an instruction to run JavaScript." The specific fix differs, escaping output for HTML instead of parameterizing a query, but the diagnosis is the same question asked in a new context: where did code and data get mixed?

**A myth worth busting before we start:** "Filtering `<script>` tags is enough." → Attackers use countless other vectors (`onerror=`, `javascript:` URLs, SVG, `<img>` tags), deny-listing tags is easily bypassed; escaping output is the reliable fix.
