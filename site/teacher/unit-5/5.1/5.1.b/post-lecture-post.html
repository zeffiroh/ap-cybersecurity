The big picture: The detail worth remembering longest here is that the three XSS variants are really differentiated by one question: does the malicious payload have to survive a trip to the server, or not? Reflected XSS needs the victim to click something, because the payload lives only in that one request. Stored XSS is scarier precisely because it removes that requirement, once it's saved in a comment or profile field, every visitor including an administrator is compromised just by loading the page, no phishing step needed. DOM-based XSS removes the server from the picture entirely, which is exactly why a server-side filter can look completely clean while the page is still vulnerable. That's the exam trap: students who memorize "XSS = unescaped input" without sorting by where the unescaped step happens will misclassify DOM-based cases as safe because the server-side log shows nothing wrong.

Key terms to lock in: - Cross-site scripting (XSS), injecting attacker-controlled script into a page viewed by other users, by exploiting unescaped output of untrusted input. - Reflected XSS, payload delivered via the request (e.g., URL parameter) and echoed immediately in the response; requires tricking the victim into a crafted link. - Stored XSS, payload saved server-side and served to every subsequent viewer. - DOM-based XSS, payload never reaches the server; client-side script writes untrusted data into an unsafe DOM sink. - Output encoding / escaping, converting special characters (<, >, ", ', &) to their literal-text equivalents before placing data into HTML.

Common misconceptions -- don't fall for these: - "Filtering <script> tags is enough." → Attackers use countless other vectors (onerror=, javascript: URLs, SVG, <img> tags), deny-listing tags is easily bypassed; escaping output is the reliable fix. - "XSS only matters if the attacker can guess a password." → XSS runs in the victim's already authenticated browser session, no password is needed, it hijacks trust that already exists.

## 5.1.b recap, Cross-site scripting (XSS)
Nice work today. Here's what to lock in:

- Recap handout: `post-lecture-handout.docx`
- Simulation: SimLab
- Self-check quiz: due before next class

**The big picture:** The detail worth remembering longest here is that the three XSS variants are really differentiated by one question: does the malicious payload have to survive a trip to the server, or not? Reflected XSS needs the victim to click something, because the payload lives only in that one request. Stored XSS is scarier precisely because it removes that requirement, once it's saved in a comment or profile field, every visitor including an administrator is compromised just by loading the page, no phishing step needed. DOM-based XSS removes the server from the picture entirely, which is exactly why a server-side filter can look completely clean while the page is still vulnerable. That's the exam trap: students who memorize "XSS = unescaped input" without sorting by *where* the unescaped step happens will misclassify DOM-based cases as safe because the server-side log shows nothing wrong.

**Key terms to lock in:**
- **Cross-site scripting (XSS)**, injecting attacker-controlled script into a page viewed by other users, by exploiting unescaped output of untrusted input.
- **Reflected XSS**, payload delivered via the request (e.g., URL parameter) and echoed immediately in the response; requires tricking the victim into a crafted link.
- **Stored XSS**, payload saved server-side and served to every subsequent viewer.
- **DOM-based XSS**, payload never reaches the server; client-side script writes untrusted data into an unsafe DOM sink.
- **Output encoding / escaping**, converting special characters (`<`, `>`, `"`, `'`, `&`) to their literal-text equivalents before placing data into HTML.

**Common misconceptions -- don't fall for these:**
- "Filtering `<script>` tags is enough." → Attackers use countless other vectors (`onerror=`, `javascript:` URLs, SVG, `<img>` tags), deny-listing tags is easily bypassed; escaping output is the reliable fix.
- "XSS only matters if the attacker can guess a password." → XSS runs in the *victim's already authenticated* browser session, no password is needed, it hijacks trust that already exists.

**Learning objective(s):** 5.1.A, 5.1.B
