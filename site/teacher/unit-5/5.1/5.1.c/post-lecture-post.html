## 5.1.c recap, API vulnerabilities
Nice work today. Here's what to lock in:

**The big picture:** The idea worth keeping past this lecture is that BOLA is what happens when a UI's convenience gets mistaken for a security boundary. Hiding the "view account 483" button for a user who's logged in as account 482 feels like it should be protective, but an attacker who calls the API directly with curl never sees that button in the first place, the missing check was never really enforced, only politely suggested by the interface. That's the same lesson 5.5.a will drive home about client-side validation being worthless for security, just applied one layer earlier: whatever the client shows or hides is a UX decision, and every security-relevant decision has to be re-verified on the server, on every request, with no exceptions.

**Key terms to lock in:**
- **API (application programming interface)**, the defined set of endpoints/requests a client uses to interact with a server's data and functionality.
- **Broken Object Level Authorization (BOLA) / IDOR**, an API accepts a client-supplied object ID and returns/modifies that object without verifying the caller is authorized for that specific object.
- **Authentication vs. authorization**, authentication proves *who you are*; authorization checks *what that identity is allowed to do/see*. BOLA is an authorization failure, not an authentication failure.
- **Excessive data exposure**, an endpoint returns more fields/data than the client needs, relying on the front-end (not the server) to hide sensitive fields.
- **Broken function-level authorization**, an endpoint intended for a privileged role is reachable by any authenticated user because the server never checks role/permission.

**Common misconceptions -- don't fall for these:**
- "If the request needs a valid login token, it's secure." → Authentication only proves identity; BOLA happens precisely when authorization (per-object permission) is never checked afterward.
- "Hiding a button in the UI prevents unauthorized access." → Attackers call the API directly with tools like curl/Postman; hiding a button does not stop a raw HTTP request.
