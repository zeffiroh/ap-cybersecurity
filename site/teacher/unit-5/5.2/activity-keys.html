Linux Permission Controls · instructor-only · 3 entries

Skill 5.2.a

Access control models (RBAC, DAC, MAC)

Instructor notes

  • Expected reasoning: DAC decisions hinge on an owner's grant list, MAC decisions hinge on a label comparison (subject clearance >= object classification), RBAC decisions hinge on whether the subject's assigned role includes the requested permission.
  • Common stumble: students conflate RBAC with "just having an admin decide", clarify that RBAC decisions come from a role's fixed permission set, not case-by-case admin judgment.
  • Feeds the unit project (access-control policy review) and the coding problem's decision function.
Skill 5.2.b

Roles, permissions, and least privilege

Instructor notes

  • Expected outcome: students should be able to state which specific permission is unnecessary for a given job function, not just "this looks like too much access."
  • Common stumble: students conflate "this permission might be useful someday" with "this permission is needed now", reinforce that least privilege is about current job function, not hypothetical future need.
  • Feeds the unit project (access-control policy review) and the coding problem's violation detector.
Skill 5.2.c

Credential theft prevention and lateral movement

Instructor notes

  • Expected reasoning: host count and timing anomalies are the primary tells; the fix should map directly to the specific weakness shown (shared credentials -> credential hygiene; broad access -> least privilege/segmentation; stolen password alone worked -> MFA).
  • Common stumble: students propose "better passwords" as a universal fix, steer them toward MFA and segmentation, since pass-the-hash attacks bypass password strength entirely.
  • Feeds the unit project (incident-response tabletop) and the coding problem's lateral-movement detector.
