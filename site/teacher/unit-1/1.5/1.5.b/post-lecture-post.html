**Key terms to lock in:**
- **Static analysis**, examining source code without executing it to detect bugs and security vulnerabilities by pattern matching or data-flow modeling.
- **Code injection**, a class of attacks where an attacker supplies input that is interpreted as code by the application (e.g., via `eval`).
- **OS command injection**, an attack where user input is passed to a shell, allowing the attacker to append arbitrary shell commands (`os.system`, `subprocess shell=True`).
- **Deserialization vulnerability**, a bug where loading serialized data from an untrusted source executes attacker-controlled code (e.g., `pickle.loads`).
- **Broken cryptography**, use of algorithms (MD5, SHA-1) that are no longer considered secure for the intended purpose (passwords, signatures).
- **Hardcoded credential**, a password or key embedded directly in source code, making it accessible to anyone who can read the file.

**Common misconceptions -- don't fall for these:**
- "Static analysis finds all vulnerabilities." → Static analysis finds known patterns; novel logic bugs, authentication flaws, and business-logic errors usually require human review or dynamic testing.
- "MD5 is only a problem for passwords." → MD5 is broken for any security use: file integrity, signatures, or tokens. It is fine for non-security checksums (e.g., cache keys).
- "subprocess is safe if I use it instead of os.system." → subprocess with `shell=True` has the same injection risk as os.system. The safe usage is passing a list of arguments with `shell=False`.
