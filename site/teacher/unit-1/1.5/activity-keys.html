AI-Powered Threat Detection · instructor-only · 4 entries

Skill 1.5.a

AI reviewing security configurations

Instructor notes

  • Expected flags for Config A: PermitRootLogin yes, PasswordAuthentication yes, X11Forwarding yes.
  • Expected flag for Config B: ssl = false (maps to insecure:SSLDisabled rule).
  • Config C should produce zero findings, students should notice ALL changes from A.
  • Common stumble: students flag AllowTcpForwarding yes, it is a legitimate security concern (can tunnel traffic through SSH), but it is not in the rule set for this skill. Discuss how rule sets are curated and never exhaustive.
  • Feeds the unit project (hardened server config) and scenario stage where an AI audit catches a misconfiguration that enabled the attacker's initial foothold.
Skill 1.5.b

AI analyzing code for vulnerabilities

Instructor notes

  • Snippet A: expected tags are vuln:pickle_loads, vuln:md5, vuln:hardcoded_password.
  • Snippet B: expected tags are vuln:os_system, vuln:subprocess_shell.
  • Snippet C: zero findings, use this to drive the "static analysis has limits" discussion. Business-logic bugs, insecure deserialization with json (usually safe), authorization gaps, none are caught by pattern matching.
  • Common stumble: students may flag hashlib import as suspicious. It is not a finding; only the use of md5() within it triggers the rule.
  • Feeds the unit project (secure code review for the scenario's web application) and the scenario stage where attackers exploit a pickle endpoint.
Skill 1.5.c

AI suggesting detection rules

Instructor notes

  • Expected flagged IP from printed log: 10.0.0.5 (6 failures within 41s, well inside 60s window).
  • 172.16.1.9 has only 2 failures spread 200s apart -- below threshold, correct answer is no rule.
  • 10.0.0.3 has only 2 failures total -- no rule.
  • Common stumble: students count all failures ever rather than within a rolling window. Use the sim to show what the window-based count looks like.
  • Feeds the unit project (threat detection pipeline) and scenario stage 3 (SOC triage).
Skill 1.5.d

Faster, more accurate threat detection and response

Instructor notes

  • Expected MTTR: (600 + 60 + 30 + 300 + 30) / 5 = 204.0 seconds.
  • Auto-resolved: INC-003 (auto=Yes) -> auto_resolved = 1.
  • Key insight: MTTR is a mean of fixed times; severity ordering does not change MTTR but does change when the most critical incidents are first seen by an analyst. This is the distinction between MTTR (mean) and time-to-touch (per severity tier).
  • Common stumble: students assume sorting changes the response times -- it does not. Correction: the resolution clock starts at detected_at, not at when the analyst picks it up.
  • Feeds the unit project (incident dashboard) and scenario stage 4 (response coordination).
