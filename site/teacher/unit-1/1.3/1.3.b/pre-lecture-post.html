1.3.b

Evil twin attack

Unit 1 · Introduction to Security · 1.3 Public Network Sniffing

Before class today. When you connect to Wi-Fi in a cafe, airport, or hotel, your device searches for a network name (SSID) it recognizes or that you select from a list. It does not, by default, verify that the access point broadcasting that name is the legitimate one.

The intuition to hold onto: The evil twin attack is a great case study in a pattern you'll see across this entire course: an attacker exploiting a gap between what a system displays and what it actually verifies. Your device shows you an SSID, a plain-text label anyone can broadcast, and calls that "the network." It never asks the deeper question: which piece of hardware, identified by which BSSID, is actually on the other end? The name is theater; the BSSID is the closest thing to ground truth available, and even that only works if someone maintained an approved list to check it against.

A myth worth busting before we start: "If I see HTTPS in my browser, the connection is safe even on public Wi-Fi." → SSL stripping can remove HTTPS before your browser receives the page. Always check for HTTPS and be suspicious if it is absent where you expected it.

Today's goal: Explain how an evil twin attack works at the network level, identify the indicators that reveal a rogue access point in a wireless scan, and apply those indicators to detect one programmatically. Handout: pre-lecture-handout.docx.
