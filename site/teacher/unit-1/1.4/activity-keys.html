Skill 1.4.b

Generative-AI phishing; prompt injection against LLM apps

Instructor notes

  • Expected answers for exit ticket item 3: Input sanitization via substring filter (fast and easy), privilege separation (the structural answer, limits blast radius), human-in-the-loop for flagged inputs (high-confidence but adds latency). Accept any of these with a coherent explanation.
  • Common stumble: Students often write "add a rule to the system prompt that says don't obey injection attempts." Push back: the atom explains why natural-language prohibitions in the system prompt are bypassable. The structural controls are the better answer.
  • If the simulation is unavailable: Use the five pattern examples from atom.md as cards. Students write hypothetical SecureBot responses and then compare to the scripted responses described in the atom's lesson section.
  • Timing: Most pairs finish the five probes in 6-8 minutes if they read the objective first. If pairs finish early, have them attempt paraphrase variants of each pattern (e.g., "disregard" vs. "set aside" vs. "forget") and discuss whether a substring filter would catch all variants or only the canonical form.
  • Feeds: Unit project (building a prompt-injection detector) and unit scenario stage 2 (the attacker at Meridian Health pivots from vishing to indirect injection via email summarizer). Students who understand why the substring detector is incomplete are better prepared for that stage.
Skill 1.4.c

Prompt extraction of sensitive info

Instructor notes

Expected answers by leak class:

  • API key: harm = attacker can call the downstream service using the operator's credentials, incurring costs or accessing private data; defense = do not embed live keys in the system prompt; use a secrets manager and retrieve credentials at inference time in a sandboxed backend, never passing them to the LLM context.
  • System prompt: harm = competitor or attacker learns business logic, persona rules, and gap in the bot's instructions; defense = treat the system prompt as containing no exploitable logic by itself; do not put rules like "never mention our pricing above $X" that reveal pricing strategy.
  • Email address: harm = phishing list of internal staff not otherwise publicly reachable; defense = do not include internal contact addresses in the system prompt; use a support ticket URL instead.
  • Password: harm = direct account takeover if the password is for any live service; defense = never pass credentials through the LLM context; authenticate users on the application layer before the LLM sees any message.

Common stumbles: - Students conflate "the model is told to keep it secret" with "it cannot be extracted." Remind them the model has no technical mechanism to enforce secrecy, it is all text in one window. - Some students will say "use a bigger/better model" as a defense. This is not a reliable control; even large models can be prompted to leak context. Redirect to architectural controls. - Snippet 6 (account number in a transfer confirmation) is intentionally borderline. The account number 4872 is not in the four defined data classes. If students mark it as a leak, use it to discuss why policy definitions matter: a real filter defines exactly which classes it monitors, and anything outside the defined classes passes through.

Connection to unit project / scenario: This activity directly feeds the unit's scenario in which students audit a deployed chatbot for data handling risks. The leak-class vocabulary and the concept of output filters will appear in the scenario's threat model worksheet.

Skill 1.4.d

False information in LLM training sets (data poisoning)

Instructor notes

Expected answers for step 3: all three poisoned rows in the sim serve integrity attack goals rather than availability attacks because each row is targeted at a specific class boundary rather than randomly distributed across classes. Students may initially call Row 6 an availability attack because it looks chaotic -- redirect them by asking what would happen to any input that contains the trigger token after training.

Common stumbles: students flag Row 4 ("Average product. Neither great nor terrible.") as poisoned because the label is positive and the content sounds neutral. This is a good teaching moment -- a neutral-content/positive-label sample is not a mismatch because positive is a reasonable label for neutral reviews in some annotation schemes. The detection rule requires the content to have more negative words than positive, not simply to lack strong positive words.

Timing: steps 1-2 often run long if pairs debate Row 4 or Row 7. Cap step 2 at 5 minutes and let the sim feedback resolve disputes so you have time for step 4.

Unit project connection: the exit-ticket rows can feed into the unit scenario where students must audit a dataset before a simulated model retraining event. Collect them and use them as additional test cases in a follow-up lesson.

Skill 1.4.e

AI reconnaissance and enhanced malware coding; defenses (shared secrets, MFA, verify output)

Instructor notes

Expected table answers: - Line 2: technique = active port scanning / automated host discovery; defense = rate-limit-port-scans - Line 4: technique = subdomain enumeration (DNS brute-force); defense = dns-query-rate-limiting - Line 6: technique = credential stuffing / username enumeration; defense = login-velocity-controls - All three entries also trigger ip-reputation-blocking because they share the same source IP (203.0.113.42).

Common stumbles: Students often flag Line 3 (single DNS query for www.meridianbank.com) as suspicious because it follows the port scan temporally. Emphasize that timing proximity is not the indicator, volume and speed are. One DNS query for the primary domain is normal browser behavior.

Timing: Steps 1-3 run to 21 minutes; the exit ticket is the final 4 minutes. If pairs finish early, have them re-read the atom's "Phase 2, AI-Enhanced Malware Coding" section and discuss why the same source IP that ran recon might next attempt to deliver a polymorphic payload.

Connection to unit project / scenario: The 203.0.113.42 IP appears in the unit scenario as the attacker's reconnaissance probe. Students who correctly identify all three recon indicators in this activity will recognize the same patterns when they appear in the unit-level incident response scenario.
