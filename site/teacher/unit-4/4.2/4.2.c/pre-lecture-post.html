4.2.c, Session security

Before class today. Authentication (checking a username and password) happens once, but a user typically stays "logged in" across many page loads and API calls. Re-entering a password on every click would be unusable.

The intuition to hold onto: Here's the mental model to hold before the lecture starts: a session token is a temporary password that gets reissued every time you log in, and whoever holds a copy of it is you, as far as the server is concerned. That single fact reframes everything else in this skill, hijacking isn't about breaking your real password at all, it's about stealing the token that already proves you logged in, which means every defense here is really about protecting a piece of data, not a secret you memorized.

A myth worth busting before we start: "Deleting the cookie on logout fully logs the user out." → False. If the server does not invalidate the session record, a copy of the token captured earlier (e.g., via network sniffing) remains valid and can still be replayed after the user thinks they logged out.

Today's goal: Explain how session tokens keep a user authenticated across requests, identify session hijacking and session fixation from a described scenario, and recommend the specific control (secure cookie flag, timeout, or session regeneration) that mitigates each.
