Session security

Unit 4 · Securing Devices · 4.2 Device Authentication Hardening

Nice work today. Here's what to lock in:

  • Recap handout: post-lecture-handout.docx
  • Simulation: SimLab
  • Self-check quiz: due before next class

The big picture: The distinction the exam will test hardest is fixation versus hijacking, and the cleanest way to keep them straight is by timing: fixation plants a known ID before you ever log in and just waits for you to authenticate into it, while hijacking steals a live ID after you're already authenticated, which is exactly why they need different fixes. Session regeneration (a fresh ID issued at the moment of login) defeats fixation because the attacker's pre-planted ID never becomes valid; secure cookie flags and encrypted transport defeat hijacking because they close the specific paths, XSS reading JavaScript-accessible cookies, plaintext sniffing on public Wi-Fi, that let an attacker steal a token that already works. The detail most students miss, and that connects directly back to 4.2.b's MFA fatigue lesson, is that logout has to be a server-side action: deleting a cookie from your browser is cosmetic if the server-side session record is still alive, because a token an attacker copied five minutes ago is just as valid after you click "logout" as it was before, the button gave you the feeling of safety without the substance of it.

Key terms to lock in:

  • Session: a server-side record that a specific browser has successfully authenticated.
  • Session token / session cookie: the random string identifying a session, sent by the browser on every request.
  • Session hijacking: stealing and reusing a victim's already-authenticated session token.
  • Session fixation: forcing a victim to authenticate under a session ID the attacker already controls.
  • Idle timeout: session expiration triggered by a period of no activity.
  • Absolute timeout: session expiration triggered after a fixed total duration.
  • Secure flag: cookie attribute restricting transmission to HTTPS only.
  • HttpOnly flag: cookie attribute hiding the cookie from JavaScript, blunting XSS theft.
  • SameSite: cookie attribute limiting cross-site sending, mitigating CSRF.
  • Session regeneration: issuing a fresh session ID at login / privilege change, defeating fixation.

Common misconceptions to watch for:

  • "Deleting the cookie on logout fully logs the user out." → False. If the server does not invalidate the session record, a copy of the token captured earlier (e.g., via network sniffing) remains valid and can still be replayed after the user thinks they logged out.
  • "HTTPS alone makes sessions un-hijackable." → False. HTTPS protects the token in transit, but if the cookie is missing the HttpOnly flag, a successful XSS injection can still read it directly from the page's JavaScript context and send it to the attacker, no network sniffing required.
  • "Session fixation and session hijacking are the same attack." → False. Fixation plants a known ID before login; hijacking steals a live ID after login. The defenses differ: regeneration stops fixation, while secure flags and encrypted transport stop hijacking.

Learning objective(s): 4.2.B
