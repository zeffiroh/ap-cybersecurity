Skill 4.2.a

Passwords and password policies

Instructor notes

  • Expected answers: A=reject (too short, no upper, no symbol), B=reject (on banned_list despite looking complex), C=accept (meets all five rules), D=reject (reused_password, matches history), E=reject (no_upper and no_symbol, length alone does not satisfy complexity rules when they are turned on).
  • Common stumble: students accept Candidate E because it is long and "looks like NIST would approve it." Clarify that this specific policy still has require_upper/require_symbol turned on, the sim/problem enforces whatever policy dict is given, not the NIST-recommended policy. Distinguish "what NIST recommends" (lesson content) from "what this policy enforces" (the exercise).
  • Attack-mapping table expected highlights: minimum length -> brute-force (exponentially larger search space); complexity ban on predictable patterns -> dictionary attack (blocks common words/substitutions); history/reuse check -> password cycling (Password1 -> Password2 -> Password1); account lockout -> online guessing (attacker cannot make unlimited interactive attempts); breach/banned-list check -> credential stuffing (blocks passwords already known from other breaches).
  • Feeds the unit project (device hardening plan) and reinforces the coding problem (problem/validate_password), which formalizes the same classification logic.
Skill 4.2.b

Multi-factor authentication

Instructor notes

  • Expected answers: A = knowledge + possession, true MFA but phishable (SMS/SIM-swap risk). B = knowledge + possession, technically true MFA but the weakest link is the unverified push approval, vulnerable to MFA fatigue/push bombing. C = knowledge + knowledge (a security question is still "something you know"), NOT true MFA. D = knowledge + possession, true MFA and phishing-resistant (FIDO2). E = inherence unlocking a stored knowledge credential on the same device, commonly marketed as MFA but functions closer to single-device convenience; discuss whether the biometric and password are truly independent factors here (both live on/protect the same device) versus being combined with a genuinely separate possession factor.
  • Common stumble: students assume any two-step login is MFA. Reinforce the category rule: same category twice (Scenario C) is not MFA regardless of step count.
  • Table expected highlights: password-only (knowledge, not phishing/SIM-swap resistant, avoid alone); SMS (knowledge+possession, not resistant to either, acceptable only as fallback); TOTP app (knowledge+possession, resists SIM-swap but not real-time phishing relay); push (same as TOTP but adds MFA-fatigue risk if unverified); hardware key (knowledge+possession, resists both, recommended for admin/high-value accounts); biometric (inherence, device-bound, good UX layer but not a network-facing factor on its own).
  • Feeds the unit project (authentication hardening plan) and scenario stage covering credential theft and account takeover.
Skill 4.2.c

Session security

Instructor notes

  • Expected answers: A=hijacking (token sniffed over unencrypted HTTP; fix: enforce HTTPS + Secure flag), B=fixation (attacker-supplied ID used before login; fix: regenerate session ID on authentication), C=improper timeout (no idle timeout; fix: configure idle + absolute timeouts), D=insecure cookie flag (missing HttpOnly; fix: set HttpOnly on the session cookie), E=improper logout / hijacking risk (server-side session not invalidated; fix: invalidate the session record server-side on logout, not just delete the client cookie).
  • Common stumble: students conflate B (fixation) with A/E (hijacking) because both end with the attacker using a valid session. Clarify the timing test: did the attacker supply the ID before login (fixation) or steal an ID that was already authenticated (hijacking)?
  • Defense table expected highlights: hijacking (HTTPS/Secure flag, HttpOnly flag, network encryption); fixation (session regeneration at login/privilege change); improper timeout (idle timeout, absolute timeout); insecure cookie flag (set Secure, HttpOnly, SameSite explicitly).
  • Feeds the unit project (authentication hardening plan) and reinforces 4.2.a/4.2.b (MFA, password policy) as complementary, not substitute, controls for session integrity.
Skill 4.2.d

Least privilege and access control models

Instructor notes

  • Expected answers: A = RBAC context but violates least privilege (no task justifies the access, deny); B = privilege creep, violates least privilege (should have been caught by a periodic access review); C = just-in-time access, does NOT violate least privilege (time-bound, justified); D = MAC (centrally enforced classification labels, no owner override); E = ABAC (dynamic evaluation of department, device, and time attributes).
  • Common stumble: students confuse RBAC and ABAC because both scenarios "seem to check conditions." Clarify that RBAC decisions come from a static role assignment made in advance; ABAC decisions are computed fresh from attributes at the moment of the request.
  • Comparison table expected highlights: DAC (owner sets, high flexibility, personal file shares); MAC (central authority sets, low flexibility, military/government); RBAC (admin sets via role, moderate flexibility, enterprise IT); ABAC (policy engine sets via rules, high flexibility, cloud/dynamic environments).
  • Feeds the unit project (access control policy design) and reinforces the coding problem's priority-order reasoning (justification first, then review recency, then time-bound status).
