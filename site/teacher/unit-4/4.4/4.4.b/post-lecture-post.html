The big picture: The Meridian scenario is worth remembering in exact structure, because it contains a trap the exam loves: six failed logins followed immediately by a success, from the same IP, in under a minute. Read the final line alone and it looks like someone finally got their password right, completely unremarkable. Read the whole sequence as a correlated unit and it's a textbook brute-force success. That gap between what one line suggests and what the sequence proves is the entire argument for correlation, and it's the same argument you'll meet again in 4.4.c when individual IOCs get combined into a compromise score, a single artifact is ambiguous, several artifacts pointing the same direction are not. The threshold-tuning discussion (5 failures in 60 seconds, not 2, not 50) deserves equal weight: it's the same false-positive-versus-false-negative tradeoff you saw in 4.3.b's behavioral detection, and "alert fatigue" is worth naming explicitly as a security failure in its own right, a detection rule tuned so sensitively that analysts start ignoring it is functionally the same as having no detection rule at all, just with extra noise and false confidence layered on top.

Key terms to lock in: - Log entry, a single timestamped record of an event (e.g., a login attempt, a blocked connection). - Authentication log, a log recording every login attempt, its result, source, and account. - Correlation, linking multiple log entries together (by user, IP, or time) to reveal a pattern that no single entry shows alone. - Brute-force attack, repeated, rapid login attempts (often automated) trying to guess a valid password. - Detection rule, a formal, repeatable condition (e.g., "5+ failures in 60 seconds") used to flag a pattern automatically. - SIEM (Security Information and Event Management), a platform that ingests logs from many systems and applies correlation rules at scale to raise alerts. - Alert fatigue, the desensitization that occurs when detection thresholds are too sensitive and generate too many false alarms, causing analysts to start ignoring real alerts.

Common misconceptions -- don't fall for these: - "A single failed login is proof of an attack." → One failed login is ordinary human error. Attacks are recognized through correlated patterns, multiple entries linked by user, IP, and tight time windows, not a single log line in isolation. - "More sensitive detection rules are always better." → Overly sensitive thresholds generate false positives that cause alert fatigue, where analysts start ignoring alerts altogether, potentially missing a real attack buried in the noise. - "Logs are only useful in real time." → Logs are equally critical after an incident, for forensic reconstruction of what an attacker did, especially once the attacker is no longer active on the system.
