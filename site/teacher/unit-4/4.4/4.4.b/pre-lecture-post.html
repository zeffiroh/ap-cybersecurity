Log analysis

Unit 4 · Securing Devices · 4.4 Endpoint Threat Auditing

Before class today. Every meaningful action a device or application takes can be recorded as a log entry, a timestamped record of an event. A failed login, a file being opened, a firewall blocking a connection, a new process starting: each of these can generate a line in a log file. Individually, a single log line rarely proves an attack happened.

The intuition to hold onto: The habit worth building before this lecture: never judge a single log line. One failed login is background noise, everyone mistypes a password sometimes, and the entire skill this skill teaches is refusing to draw a conclusion until you've looked at several entries linked by the same user, the same IP, or a tight time window. A log analyst's job isn't reading logs, it's reading patterns that only exist once you stop looking at any one line in isolation.

A myth worth busting before we start: "A single failed login is proof of an attack." → One failed login is ordinary human error. Attacks are recognized through correlated patterns, multiple entries linked by user, IP, and tight time windows, not a single log line in isolation.

Today's goal: Explain what a security log records and why it matters, identify the common log sources security analysts review, and detect a brute-force login pattern by correlating multiple log entries over time. Handout: pre-lecture-handout.docx.
