Skill 4.4.a

Endpoint detection and response (EDR)

Instructor notes

  • Expected suspicious rows: 1, 3, 5 (all three use legitimate OS tools as parents from unusual parents and write suspicious files or call out to external IPs).
  • Benign rows: 2 (Chrome opened normally by explorer, no file write), 4 (Notepad writing a text file, normal parent).
  • Common stumble: students mark row 3 benign because cmd.exe is a legitimate tool. Clarify that svchost.exe spawning cmd.exe is highly unusual; the file write to Windows directory escalates it.
  • Feeds unit project (device-attack detection report) and scenario stage 4 (incident triage).
  • Row IP addresses use RFC 5737 / RFC 3849 documentation ranges, they are not real targets.
Skill 4.4.b

Log analysis

Instructor notes

  • Expected answer: jsmith shows a brute-force pattern, 5 failed attempts within 46 seconds (09:12:01 to 09:12:47), followed immediately by a success from the SAME IP, consistent with an automated tool that guessed the password on the sixth attempt.
  • agarcia's two failures are 26 minutes apart, far outside any reasonable correlation window, consistent with an ordinary person mistyping a password twice, not an attack.
  • Threshold table expected highlights: 2/60s would catch the attack but generates heavy false positives (many users fail twice); 5/60s catches the attack with much lower false-positive risk (this is the rule used in the coding problem); 20/60s would miss slower or smaller brute-force attempts entirely.
  • Feeds the coding problem's exact detection rule (5+ failures within any 60-second window per user) and reinforces the unit's alert-fatigue theme from EDR (4.4.a).
Skill 4.4.c

Identifying compromised devices (indicators of compromise)

Instructor notes

  • Expected scores/verdicts: A = 9 (compromised), B = 1 (clean), C = 11 (compromised), D = 3 (clean), E = 5 (suspicious).
  • Common stumble: students assume any device with 2+ IOCs must be "compromised." Emphasize that the threshold is score-based, not count-based, Device E has two IOCs but is only "suspicious" because neither weight is very high.
  • Device B and D are deliberate "clean" traps: a single low-weight IOC alone should not trigger an escalation, reinforcing the misconception correction in atom.md.
  • Feeds the coding problem's exact weighted-scoring logic and reinforces the unit's EDR (4.4.a) response-action vocabulary.
