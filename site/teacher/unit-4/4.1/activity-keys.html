Topic 4.1 Activity Answer Keys

Device and Endpoint Vulnerabilities · instructor-only · 3 entries

Skill 4.1.a

Malware types (viruses, worms, trojans, ransomware)

Instructor notes

  • Expected answers: A=worm (autonomous network scanning), B=trojan (disguised installer), C=virus (host file, user opened attachment, copies made), D=ransomware (encryption + demand), E=virus (USB as host, manual file access spreads it).
  • Common stumble: students classify the USB incident (E) as a worm because it "spreads across machines." Clarify that it required a user to plug in the USB and then open shared folders, user action at each step = virus, not worm.
  • Defense table expected highlights: virus (email filtering, attachment scanning); worm (network segmentation, patching); trojan (app whitelisting, source verification); ransomware (offline backups, least-privilege access).
  • Feeds the unit project (device hardening plan) and scenario stage 4 (malware response drill).
Skill 4.1.b

Device tampering and physical compromise

Instructor notes

  • Expected Vulnerabilities & Solutions:
    • Receptionist USB ports exposed: Patients could plug in a USB Rubber Ducky. Mitigation: USB port blockers, chassis lock box, or turning the computer case around.
    • Hallway network printer: Attacker could plug an unauthorized laptop into the printer's Ethernet port. Mitigation: Mac-address filtering (logical) and physical Ethernet port locks.
    • Server closet keys unlocked: Server could be stolen or offline-booted. Mitigation: Keypad access, BIOS passwords, and FDE.
    • Exam room laptops open: Unauthorized reading or command execution. Mitigation: Strict screensaver auto-lock (e.g., 60 seconds) or physical cable locks.
  • Common Stumbles: Students may suggest software-based firewalls to prevent USB Rubber Ducky attacks. Remind them that Rubber Duckies emulate keyboards, which firewalls trust implicitly.
  • Unit Link: Feeds into the unit-wide device hardening guidelines.
Skill 4.1.c

IoT device vulnerabilities

Instructor notes

  • Expected answers: A=default_credentials (factory login never changed, overrides other checks), B=exposed_port (Telnet open on port 23), C=outdated_firmware (EOL device, unpatched known vulnerability), D=unauthenticated_api (no auth token required to read another user's data), E=unencrypted_traffic (plaintext commands on local network).
  • Common stumble: students classify Device C as "secure" because it has no open ports or default password. Clarify that EOL/outdated firmware is itself the vulnerability even with everything else locked down, the flaw lives inside the code that never gets patched.
  • Defense table expected highlights: default credentials (forced password change at setup, unique per-device passwords); outdated firmware (vendor support lifecycle checks, network segmentation for EOL devices); exposed port (disable Telnet/UPnP, close unused ports); unauthenticated API (require auth tokens, rate-limit and validate every request); unencrypted traffic (enforce TLS, VPN for remote management).
  • Feeds the unit project (device hardening plan) and connects to 4.1.a (malware) via the Mirai botnet example, an insecure IoT device is a stepping stone to a much larger attack.
