Incident response sequence

Unit 3 · Securing Networks · 3.5 Network Threat Detection

Before class today. Detecting an attack, via a firewall log, an IDS alert, or a traffic anomaly, is only the beginning. What an organization does in the minutes, hours, and days after detection determines whether the incident is a contained inconvenience or a catastrophic breach.

The intuition to hold onto: The single sentence worth memorizing before this lecture, because it's the atom's entire argument in miniature: detecting an attack is the beginning of the story, not the end of it, and what an organization does in the next few hours is what actually determines whether this becomes a contained inconvenience or a catastrophe. Every detection tool this unit has built up, firewalls, IDS/IPS, traffic monitoring, exists to trigger this skill's process, not to replace it.

A myth worth busting before we start: "You should remove the malware as soon as you find it." → Removing malware before containment can tip off the attacker or allow reinfection; contain first, then eradicate.

Today's goal: Name the six phases of the NIST incident-response lifecycle in order, classify a given response action into its correct phase, and explain why performing actions out of order (for example, eradicating before containing) can make an incident worse. Handout: pre-lecture-handout.docx.
