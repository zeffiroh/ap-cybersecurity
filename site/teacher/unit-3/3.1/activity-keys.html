Topic 3.1 Activity Answer Keys

Network-Level Exploits · instructor-only · 4 entries

Skill 3.1.a

TCP/IP fundamentals and network topology flaws

Instructor notes

  • Common stumble: students confuse IP addresses (internet layer) with MAC addresses (network access layer). Reinforce: IP = routing across networks, MAC = delivery on one local segment.
  • Common stumble: students think switches make all interception impossible. Clarify MAC flooding and ARP spoofing as switch-defeating techniques (bridged to 3.1.c).
  • The topology diagram step surfaces the concept of lateral movement, connect it to the breach-containment role of segmentation.
  • This activity feeds the unit project (network threat model) and connects to 3.1.b-d for the full attack chain.
Skill 3.1.b

DNS attacks (spoofing, cache poisoning)

Answer key (instructor only)

# Verdict Reasoning
1 POISON All three fields match on both replies; attacker's forged reply arrived first and is cached.
2 WIN Attacker's reply has the wrong tx_id (1111 vs 8821) so it's rejected as a candidate; the authoritative reply matches and is cached.
3 REJECT Only reply has the wrong port (40000 vs 33221), no valid candidate, nothing cached.
4 WIN Both replies match all three fields, but the legitimate reply arrived first (arrival 1) and is cached before the attacker's later reply arrives.

Instructor notes

  • Timing: rows 1-2 are the core matching-rule cases; row 3 tests the "no valid candidate" case; row 4 is the deliberate teaching moment that arrival order, not merely matching, decides the winner when both replies are valid.
  • Common stumble: students assume any attacker reply that "shows up" in the log wins, without checking that all three fields (tx_id, port, qname) match the outstanding query.
  • A second common stumble: students think REJECT is a form of poisoning being "close", reinforce that REJECT means nothing was cached at all.
  • Feeds forward to 3.1.c (MITM/ARP spoofing) and 3.1.d (packet capture), which use the same discipline of checking exact field matches in captured traffic.
Skill 3.1.c

Man-in-the-middle and ARP spoofing

Answer key (instructor only)

# Verdict Reasoning
1 LEGIT Same MAC (aa:01) across all three refreshes.
2 SPOOFED A different MAC (ff:99) claims the gateway's IP shortly after the trusted binding was established.
3 LEGIT Only one reply exists; there is no prior binding to contradict, so it cannot yet be called spoofing.
4 SPOOFED (discuss) The binding did change; instructors should let groups argue both ways but land on: any unexplained binding change should be flagged and investigated, even if the timing alone is not conclusive proof.

Instructor notes

  • Timing: rows 1-2 are the core matching-rule cases; row 3 tests "not enough evidence yet"; row 4 is the deliberate ambiguous case meant to provoke discussion about false positives (legitimate MAC changes) versus real attacks.
  • Common stumble: students treat every MAC change as automatically SPOOFED without considering legitimate causes (hardware replacement, DHCP reassignment), push them to explain what additional evidence (e.g., frequency, target being the gateway, timing) increases confidence.
  • A second common stumble: students think a single observed reply (row 3) can be judged SPOOFED or LEGIT with confidence, reinforce that a baseline is required first.
  • Feeds forward to 3.1.d (packet capture), where students learn to gather the actual evidence (captured ARP frames) that feeds this kind of analysis.
Skill 3.1.d

Packet capture and traffic sniffing

Answer key (instructor only)

# Verdict Reasoning
1 LEAK Port 80 (HTTP, cleartext); payload contains password=Pass123!.
2 SAFE Port 443 (HTTPS, encrypted); payload is unreadable ciphertext regardless of what's inside.
3 LEAK Port 23 (Telnet, cleartext); full username/password visible.
4 SAFE Port 80 is cleartext-capable, but this GET request has no credential in the payload.
5 LEAK Port 21 (FTP control, cleartext); USER/PASS authentication visible in plaintext.

Instructor notes

  • Timing: rows 1-2 are the core rule cases; row 3 reinforces that "administrative" traffic is not automatically safe; rows 4-5 are the deliberate teaching moment that protocol/port AND payload content both matter, cleartext capability alone does not mean every packet leaks something.
  • Common stumble: students assume any HTTP (port 80) traffic is automatically a LEAK regardless of payload content, push them to check whether an actual credential is present.
  • A second common stumble: students assume HTTPS traffic must be SAFE only because "it looks scrambled," rather than understanding WHY (TLS encryption) it is unreadable.
  • Feeds forward to 3.1.b (DNS attacks) and 3.1.c (ARP spoofing/MITM), both of which are enabling techniques that put an attacker in a position to capture traffic like this in the first place.
