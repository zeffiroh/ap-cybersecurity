1.2 Activities

Suspicious Website Logins · 3

Skill 1.2.a · pairs · 20 min · Offline: yes

Password-attack signs (failed attempts, unusual times, unknown devices)

Goal

Students practice reading an authentication log excerpt, identifying the three signals of a password attack (failure spikes, unusual times, unknown devices), and writing a plain-English detection rule, tying to LO 1.2.A (detect attacks).

Materials

Log excerpt (fallback if sim unavailable)

2024-03-15 02:13:44  FAIL  admin       192.168.1.201
2024-03-15 02:13:45  FAIL  admin       192.168.1.201
2024-03-15 02:13:46  FAIL  admin       192.168.1.201
2024-03-15 02:13:47  FAIL  admin       192.168.1.201
2024-03-15 02:13:48  FAIL  admin       192.168.1.201
2024-03-15 02:13:49  OK    admin       192.168.1.201   <-- DEVICE UNKNOWN
2024-03-15 08:45:02  OK    jsmith      192.168.1.10    (normal)

Ask: (a) How many signals do you see for admin? (b) When was this? (c) Is 192.168.1.201 in your known-device list?

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation. They watch the real-time log scroll and must flag which account is under attack before the attacker succeeds. They may click the suspect username at any time; the sim scores their timing (early = fewer false positives = better).
  2. After the sim, pairs answer: Which of the three signals (failure spike, unusual time, unknown device) did they use to make their decision? Write one sentence per signal observed.
  3. Pairs write a plain-English detection rule: "Flag an account when ..." filling in the exact threshold they would choose and why. They compare rules with another pair.

Collaborate

Assign roles: one partner is the "blue-team analyst" (flags the attack and explains the signals), the other is the "attacker" (argues why the legitimate user might have done this). After two minutes, the attacker must concede if all three signals are present simultaneously. Swap roles for a second scenario.

Exit Ticket

AP

Certificate of Completion

Each student submits a one-paragraph incident report: "At [time], account [X] showed [signals]. I conclude [determination]. Recommended response: [action]." Model answer: lockout + side-channel notification + log review for prior success.

Skill 1.2.b · pairs · 20 min · Offline: yes

Weak authentication patterns; adversary dictionary construction

Goal

Students apply the four password weakness rules to a set of candidate passwords, predict which will be flagged and why, and then reason about how an adversary would construct a wordlist to crack each weak password. Ties to LO 1.2.B (evaluate authentication strength; explain dictionary construction).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation. For each password in the simulator, they discuss and agree on every weakness flag before clicking Check. They record their prediction in writing before submitting.
  2. For each password that is flagged, they write one sentence describing exactly which wordlist entry and mangling rule an attacker would use to crack it (e.g., "'sunshine' appears verbatim in rockyou.txt; no mangling required").
  3. Pairs design one password that passes all four rules and one that fails exactly two rules. They trade with another pair, who must name the exact failing rules without using the sim.

Collaborate

Assign roles: one partner is the "password auditor" (applies the rules, names the flags), the other is the "attacker analyst" (explains how the cracking tool would find it). Swap roles for steps 2 and 3.

Exit Ticket

AP

Certificate of Completion

Each student submits: one password they designed that passes all four rules + a one-sentence explanation of why length matters more than complexity substitutions.

Skill 1.2.c · pairs · 25 min · Offline: yes

Strengthening authentication: length/complexity, randomness, MFA

Goal

Students work through the TOTP algorithm by hand (with a calculator) for one time step, verify their result matches the simulator, and then reason about the security properties that emerge from the algorithm's design. Ties to LO 1.2.C (evaluate stronger authentication: length, randomness, MFA).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Pairs open the simulation and read Scenario 1 (fixed key and timestamp). Before entering anything, they write out the algorithm steps on paper: a. Compute the time step: step = floor(t / 30). b. Note the key bytes from the hex string. c. The sim uses a deterministic synthetic HMAC (documented in the legend). Predict the code by working through the JavaScript in the sim (open browser DevTools console and call computeTOTP("0a1b2c3d", 1700000010) to verify). d. Enter the code in the sim and submit.
  2. For Scenario 2 (expired code), both partners predict whether the code will be valid 35 seconds later BEFORE reading the sim feedback. They write their prediction and the reasoning.
  3. For Scenario 4 (replay attack), partners write one paragraph explaining why the 30-second window defeats replay even if the attacker acts within 10 seconds of interception.

Collaborate

Assign roles: one partner is the "authenticator" (computes what code the app would show), the other is the "server" (checks whether the submitted code matches the current step). Swap for Scenario 3. For the replay scenario, one partner plays the attacker; the other argues why the defense works.

Exit Ticket

AP

Certificate of Completion

Each student submits: (1) the correct TOTP code for Scenario 1 with the algorithm trace showing step, digest concept, and final 6-digit code; (2) one sentence explaining what a time-step window prevents and one sentence describing what it does NOT prevent (real-time phishing relay).
