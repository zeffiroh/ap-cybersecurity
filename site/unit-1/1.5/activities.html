1.5 Activities

AI-Powered Threat Detection · 4

Skill 1.5.a · pairs · 25 min · Offline: yes

AI reviewing security configurations

Goal

Students practice reading configuration files with an auditor's eye: identifying insecure directives, naming the specific risk, and proposing the corrected setting. Ties to LO 1.5.A (explain how AI tools support configuration review and risk mitigation).

Materials

Config snippets for review

Config A, SSH server (sshd_config)

Port 22
PermitRootLogin yes
PasswordAuthentication yes
X11Forwarding yes
AllowTcpForwarding yes

Config B, database proxy

bind_address = 0.0.0.0
port = 5432
ssl = false
max_connections = 100
log_connections = off

Config C, hardened SSH (compare)

Port 22
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
X11Forwarding no
AllowTcpForwarding no

Steps

Check off all materials above to unlock the steps.
  1. Each pair reads Config A. For each line, decide: insecure (flag it) or acceptable (pass). Write the finding tag (e.g., insecure:PermitRootLogin) and one sentence explaining the risk.
  2. Repeat for Config B. Note that ssl = false uses different syntax than SSH, discuss why a rule engine must handle multiple config formats.
  3. Compare Config A and Config C. List every change and explain why each change reduces attack surface. Identify which changes are "must fix" vs. "nice to have."
  4. Open the simulation and work through the auditor simulation, reaching the target score.

Collaborate

Assign roles: one partner is the "AI auditor" (reads each line, applies the rule set, emits findings), the other is the "security engineer" (reviews each finding and decides: fix, document as exception, or dismiss with justification). Swap roles between configs.

Exit Ticket

AP

Certificate of Completion

Each student submits: one insecure directive from today's configs + the corrected setting + a one-sentence explanation of why the original was dangerous.

Skill 1.5.b · pairs · 25 min · Offline: yes

AI analyzing code for vulnerabilities

Goal

Students practice reading Python code with a security analyst's eye: identifying dangerous patterns, naming the vulnerability class each pattern creates, and explaining why AI scanning cannot replace human code review. Ties to LO 1.5.A (explain how AI tools support vulnerability detection in code).

Materials

Code snippets for review

Snippet A, authentication module

import hashlib, pickle

def verify_user(username, token_bytes):
    user = pickle.loads(token_bytes)          # deserialize session
    pw_hash = hashlib.md5(user['pw'].encode()).hexdigest()
    password = "fallback_admin"               # emergency access
    return pw_hash == user['hash']

Snippet B, command runner

import os, subprocess

def run_scan(target):
    os.system("nmap -sV " + target)
    result = subprocess.run("ping " + target, shell=True, capture_output=True)
    return result.stdout

Snippet C, data processor

import json

def process_request(payload_str):
    data = json.loads(payload_str)
    name = data.get("name", "")
    value = data.get("value", 0)
    return {"name": name, "doubled": value * 2}

Steps

Check off all materials above to unlock the steps.
  1. Each pair reads Snippet A. List every dangerous pattern and the vulnerability tag it would get from a scanner (e.g., vuln:pickle_loads). Write one sentence per finding: what could an attacker do to exploit it?
  2. Repeat for Snippet B. Note that BOTH os.system and subprocess shell=True appear, explain why both are flagged even though they do similar things.
  3. Read Snippet C. The scanner finds zero findings. Discuss: does "no findings" mean "secure"? What other vulnerabilities might exist that static analysis cannot detect?
  4. Open the simulation and reach the target score in the code review simulation.

Collaborate

Assign roles: one partner is the "AI scanner" (applies the rule set mechanically), the other is the "security engineer" (reviews each finding and drafts the fix). The engineer must justify every fix: what is the safer replacement for each dangerous pattern?

Exit Ticket

AP

Certificate of Completion

Each student submits: one vulnerable code snippet they found + the tag + one sentence describing the safer replacement (e.g., "replace md5 with sha256 for password hashing").

Skill 1.5.c · pairs · 25 min · Offline: yes

AI suggesting detection rules

Goal

Students practice the detection-engineering loop: read a log stream, identify suspicious patterns manually, propose rule strings, then verify their rules against the sim and the coding problem. Ties to LO 1.5.A (explain how AI-assisted tools generate and apply detection rules).

Materials

Printed log excerpt (if devices unavailable)

ts=0   src=10.0.0.5  event=login_fail
ts=8   src=10.0.0.5  event=login_fail
ts=17  src=10.0.0.5  event=login_fail
ts=25  src=10.0.0.5  event=login_fail
ts=33  src=10.0.0.5  event=login_fail
ts=41  src=10.0.0.5  event=login_fail
ts=0   src=172.16.1.9 event=login_fail
ts=200 src=172.16.1.9 event=login_fail
ts=5   src=10.0.0.7  event=login_ok
ts=90  src=10.0.0.3  event=login_fail
ts=100 src=10.0.0.3  event=login_fail

Steps

Check off all materials above to unlock the steps.

  1. Manual scan (8 min). Each pair reads the printed log or the sim's log stream and marks every IP they think is suspicious. They write down a plain-English rule: "Flag IP X because it had N failures in Y seconds."

  2. Rule formalization (5 min). Convert each plain-English rule into the structured format defined in interface.md: ALERT brute_force src=<IP> count=<N> window=60s Decide which IPs to include and which to exclude, and justify each decision.

  3. Sim verification (7 min). Open the simulation. Step through the log stream and observe which IPs the engine flags. Compare to your manual findings. Note any discrepancies.

  4. Discussion (5 min). Answer: If you lowered the threshold from 5 to 2, what would change? If you raised it to 10? Which threshold produces the best outcome for a real SOC?

Collaborate

Assign roles: one partner is the AI engine (applies the rule mechanically, counts events), the other is the analyst (decides whether each flagged IP is actually suspicious or a known safe host). Swap roles between the printed and sim exercises.

Exit Ticket

AP

Certificate of Completion

Each student submits: - The rule string(s) they generated for the printed log. - One sentence explaining why the threshold value matters and what goes wrong when it is set too low or too high.

Skill 1.5.d · pairs · 25 min · Offline: yes

Faster, more accurate threat detection and response

Goal

Students experience the difference between arrival-order and severity-order triage by manually processing an incident queue both ways, then compute MTTR for each approach and compare. Ties to LO 1.5.B (explain how AI reduces MTTR and improves response accuracy).

Materials

Printed incident queue (if devices unavailable)

ID       Arrival  Detected_at  Resolved_at  Severity  Auto
INC-001  T=0      0            600          low       No
INC-002  T=5      5            65           critical  No
INC-003  T=10     10           40           high      Yes
INC-004  T=15     15           315          medium    No
INC-005  T=20     20           50           critical  No

Steps

Check off all materials above to unlock the steps.

  1. Arrival-order pass (7 min). Process incidents INC-001 through INC-005 in the order listed (T=0 first). Record the order you would hand each to an analyst and estimate when each is resolved (use the resolved_at values). Compute MTTR manually: MTTR = (600 + 60 + 30 + 300 + 30) / 5 = 204 seconds.

  2. Severity-order pass (7 min). Re-sort the queue: critical first, then high, medium, low. Assume the same resolved_at values (resolution time does not change; only analyst attention changes). Identify which incidents are auto-resolved (they require no analyst time). Compute what the effective analyst queue looks like after removing auto cases.

  3. Discussion (6 min). Answer: Does MTTR change between the two orderings? Why or why not? (MTTR is a mean of fixed response times, so ordering does not change it -- but the time until the CRITICAL incidents are first touched changes dramatically.) What metric captures that difference? (Time-to-touch for critical incidents, sometimes called "time to triage".)

  4. Sim verification (5 min). Open the simulation. Triage the queue in severity order and observe how the sim tracks which critical incidents were handled first.

Collaborate

Assign roles: one partner is the AI triage engine (assigns severity scores and sorts the queue), the other is the SOC analyst (decides which incidents to auto-close and which to escalate). After the first pass, swap roles and discuss whether you would auto-resolve INC-003 given only the information shown.

Exit Ticket

AP

Certificate of Completion

Each student submits: - The MTTR value for the printed queue (should be 204.0 seconds). - One sentence explaining why sorting by severity matters even though it does not change MTTR.
