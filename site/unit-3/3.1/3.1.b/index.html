3.1.bDNS attacks (spoofing, cache poisoning)

Objective

Explain how the Domain Name System (DNS) is vulnerable to interception and spoofing, trace the mechanics of a DNS cache poisoning attack, and identify modern cryptographic and architectural controls used to protect name resolution.

Lesson

The Domain Name System (DNS) is the directory service of the internet, translating human-friendly names (like example.com) into computer-routable IP addresses (like 192.0.2.1). Because almost every internet connection starts with a DNS lookup, compromising this process allows an attacker to redirect traffic silently and globally.

The plumbing of name resolution

DNS is hierarchical and distributed. When you request a domain, your device asks a local recursive resolver (often provided by your ISP or a public service like Google). If the resolver does not have the answer cached, it queries the hierarchical DNS system in order: 1. The Root name servers (which point to TLD servers). 2. The Top-Level Domain (TLD) name servers (like the .com or .org registry). 3. The Authoritative name servers (which hold the actual zone files for the domain).

To maximize performance, recursive resolvers save (cache) the results of these queries for a period called the Time to Live (TTL).

Why DNS is vulnerable: the UDP design flaw

DNS queries and responses primarily use UDP port 53. Unlike TCP, UDP is connectionless and stateful handshakes are absent. A device sends a single packet query and waits for a single packet reply. This creates a critical attack surface: * No session verification: Anyone who knows or guesses that a query was sent can forge a UDP response. The resolver has no built-in way to verify that the incoming packet actually came from the authoritative server. * The race condition: When a resolver asks an authoritative server for an IP address, it accepts the first valid response that arrives. An attacker who can send a forged response that reaches the resolver before the real server's response will trick the resolver into accepting the false data.

DNS cache poisoning mechanics

For a forged DNS reply to be accepted by a resolver, the attacker's packet must match three specific values from the original query: 1. The Destination Port: The port from which the resolver sent the query (often randomized). 2. The Query Domain: The exact name requested (e.g., bank.com). 3. The Transaction ID (TX ID): A 16-bit number (0 to 65,535) generated by the resolver.

If the attacker guesses the TX ID and the source port, the resolver accepts the packet, caches the fake IP mapping, and serves it to all users on that network until the TTL expires. This is DNS cache poisoning.

Resolver                      Authoritative Server
   | --- Query: bank.com? --------> |
   |     TX_ID: 48291               |
   |                                |
   | <--- FORGED REPLY: 9.9.9.9 --- |  <-- Attacker sends this first!
   |      TX_ID: 48291 (GUESSED)    |      Matches TX_ID. Cached.
   |                                |
   | <--- REAL REPLY: 1.1.1.1 ------|  <-- Arrives late, discarded.

In the classic Kaminsky attack, the attacker triggers a resolver to request a non-existent subdomain (e.g., 1.bank.com, 2.bank.com) which forces the resolver to send queries to the authoritative server. The attacker floods the resolver with fake replies containing guessed Transaction IDs. Because the domain is unique, the resolver has no cached entry and must query the root/authoritative name servers, giving the attacker multiple attempts to win the race. Once they guess the ID, they redirect the entire domain (bank.com) by rewriting the authoritative name server (NS) records in the payload's authority section.

Defense and mitigation

Modern networks protect DNS using multiple layers of control: 1. Source Port Randomization: Instead of sending queries from a static port (like 53), resolvers randomize the outbound UDP port across all available ephemeral ports (~64,000 possibilities). Together with the 16-bit Transaction ID, this increases the guessing space from 65,536 to over 4 billion, making blind guessing mathematically impractical. 2. DNSSEC (Domain Name System Security Extensions): DNSSEC adds cryptographic signatures to DNS records. The authoritative server signs records with a private key, and resolvers verify them using a public key hierarchy starting at the root zone. Even if an attacker wins the UDP race, the resolver discards the spoofed packet because it lacks a valid digital signature. 3. DoH and DoT (DNS over HTTPS / DNS over TLS): These protocols encrypt the connection between the user's workstation and the recursive resolver, preventing local eavesdropping and spoofing, though they do not protect the resolver-to-authoritative path (which relies on DNSSEC).

Key terms

  • DNS, Domain Name System; translates human-readable domain names into IP addresses.
  • Recursive resolver, A server that queries the DNS hierarchy on behalf of a client and caches results.
  • Authoritative name server, The definitive source of DNS records for a specific domain zone.
  • DNS cache poisoning, Tricking a DNS resolver into caching a fake IP address mapping, redirecting all subsequent lookups.
  • Transaction ID (TX ID), A 16-bit identifier in a DNS header used to match queries with responses.
  • UDP Port 53, The standard port and protocol for DNS traffic.
  • DNSSEC, Cryptographic extensions to DNS that authenticate DNS responses through digital signatures.

Common misconceptions

  • "DNS cache poisoning only affects one user." → False. It affects the recursive resolver. Any user or device using that resolver (e.g., an entire corporate network or ISP customer base) is redirected to the attacker's server.
  • "HTTPS protects against DNS spoofing." → HTTPS prevents the attacker from reading your encrypted web traffic, but it does not prevent DNS spoofing. If spoofed, your browser connects to the attacker's server, which will fail the SSL/TLS certificate check (assuming the attacker cannot forge a certificate). However, the user still experiences a denial of service or may click through certificate warnings.

  • Coding problem: Parse a DNS resolver log and identify matching responses that represent a cache poisoning race (duplicate responses for the same query ID and domain with different answer IPs).
