3.4 Activities

Firewall Access Controls · 2

Skill 3.4.a · pairs · 25 min · Offline: yes

Firewall types (stateful vs. stateless)

Goal

Students distinguish stateless and stateful firewall behavior by manually processing a packet stream, first as a stateless rule-matcher and then as a stateful connection tracker. Ties to LO 3.4.A (explain the difference between firewall types and their inspection methods).

Materials

Printed packet table (deterministic seed)

# Rule set (apply top to bottom, first match wins)
Rule 1: ALLOW TCP any -> 443
Rule 2: ALLOW TCP any -> 80
Rule 3: DROP  any any -> any  (implicit deny)

Pkt  Src IP          Dst IP          SrcPt  DstPt  Proto  Flags   Notes
A    203.0.113.10    10.0.0.5        55001  443    TCP    SYN     New HTTPS request
B    10.0.0.5        203.0.113.10    443    55001  TCP    SYN-ACK Server reply
C    203.0.113.10    10.0.0.5        55001  443    TCP    ACK     Handshake complete
D    198.51.100.7    10.0.0.5        44000  443    TCP    ACK     ACK with no prior SYN
E    192.0.2.99      10.0.0.5        62000  22     TCP    SYN     SSH attempt (not in rules)
F    203.0.113.10    10.0.0.5        55001  443    TCP    RST     Spoofed reset
G    10.10.10.1      10.0.0.5        51000  80     TCP    SYN     Internal HTTP request
H    10.0.0.5        10.10.10.1      80     51000  TCP    SYN-ACK HTTP server reply

Expected stateless verdicts: A=ALLOW, B=ALLOW, C=ALLOW, D=ALLOW, E=DROP, F=ALLOW, G=ALLOW, H=ALLOW

Expected stateful verdicts: A=ALLOW (add SYN_SENT), B=ALLOW (state->ESTABLISHED), C=ALLOW, D=DROP (no session for this ACK), E=DROP (no rule + no session), F=DROP (RST for established session from wrong direction, optional discussion), G=ALLOW (add SYN_SENT), H=ALLOW.

Steps

Check off all materials above to unlock the steps.

  1. Round 1, Stateless (10 min). Each pair receives the packet table below. Working only with source IP, destination port, and protocol, they apply the three rules in order and mark each packet ALLOW or DROP. One partner reads the packet fields aloud; the other finds the matching rule and records the verdict.

  2. Round 2, Stateful (10 min). The same packet stream is re-processed, but now the pair also tracks a connection table on paper (a blank grid: src_ip, dst_ip, src_port, dst_port, state). They update the table for SYN packets (add entry, state=SYN_SENT), SYN-ACK (update to ESTABLISHED), and RST/FIN (remove entry). Packets that do not match any table entry and also do not match an inbound-permit rule are dropped.

  3. Compare (5 min). Pairs compare their stateless and stateful verdict lists. They identify every packet that received a different verdict in the two rounds and write one sentence explaining why the stateful result is more secure.

Collaborate

Assign roles: one partner is the "firewall" (enforces rules strictly), the other is the "network engineer" (maintains the connection table and challenges any rule the firewall misapplies). After both rounds, partners swap roles and process two additional instructor-supplied packets.

Exit Ticket

AP

Certificate of Completion

Each student writes: one packet scenario that a stateless firewall would allow but a stateful firewall would drop, plus one sentence explaining which firewall characteristic makes the difference.

Skill 3.4.b · pairs · 25 min · Offline: yes

Firewall rules and access control lists (ACLs)

Goal

Students trace first-match-wins ACL evaluation by hand, identify a rule-shadowing bug in a Meridian High School perimeter ACL, and fix it by reordering (not rewriting) rules. Ties to LO 3.4.B / 3.4.C (write and evaluate firewall ACLs; identify rule-ordering vulnerabilities).

Materials

Printed ACL and packet table (deterministic)

# Rule set (apply top to bottom, first match wins) — as originally written (BUGGY)
Rule 1: ALLOW  TCP  any          -> any            port 22   (temporary SSH access, meant to be removed)
Rule 2: ALLOW  TCP  any          -> 10.0.1.5        port 443  (HTTPS to web server)
Rule 3: DENY   TCP  203.0.113.0  -> 10.0.1.10        port 22   (block known-hostile range from file server SSH)
Rule 4: ALLOW  TCP  10.0.4.0     -> 10.0.1.5        port 3306 (accounting subnet to DB)
Rule 5: DENY   any  any          -> any             any       (implicit deny-all)

Pkt  Src           Dst          Port  Proto  Security intent
A    203.0.113.0   10.0.1.10    22    TCP    Should be DENIED (hostile range, SSH to file server)
B    10.0.4.0      10.0.1.5     3306  TCP    Should be ALLOWED (accounting to DB)
C    198.51.100.9  10.0.1.5     443   TCP    Should be ALLOWED (HTTPS)
D    10.0.9.9      10.0.1.5     3306  TCP    Should be DENIED (not accounting subnet)

Traced (buggy) verdicts: A=ALLOW (rule 1 fires first, WRONG, intent was DENY), B=ALLOW (rule 4), C=ALLOW (rule 2), D=DENY (rule 5, implicit deny). Packet A is the shadowing bug: rule 1 is too broad and matches before rule 3 is ever reached.

Steps

Check off all materials above to unlock the steps.

  1. Trace it (10 min). Each pair receives the broken ACL and packet table below. Working top to bottom, they apply first-match-wins to each packet and record the verdict and which rule number fired.

  2. Find the bug (7 min). Pairs identify which packet(s) got the "wrong" verdict relative to the security intent stated in the rule comments, and name the shadowing rule pair (which rule is too broad, and which rule below it never fires).

  3. Fix it (8 min). Pairs reorder the ACL (moving rules, not rewriting their conditions) so every packet gets its intended verdict. They re-trace all packets against the new order to confirm.

Collaborate

Assign roles: one partner is the "auditor" (traces verdicts and flags mismatches with intent), the other is the "firewall admin" (proposes the reordering fix and defends why it does not break any other packet's verdict). Swap roles and check the fixed ACL against two instructor-supplied packets.

Exit Ticket

AP

Certificate of Completion

Each student writes: the corrected rule order (rule numbers only) and one sentence explaining why moving rule 3 above rule 1 fixes packet A without changing the verdict for packets B or C.
