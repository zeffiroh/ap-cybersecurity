Find the over-exposed files, then lock them down with real chmod and chown.

This is a working shell over a small virtual filesystem. Every cat and echo > file is checked against the file's real owner, group, and rwx bits for whoever you are logged in as, so a wrong permission actually lets the wrong person in. A server deployment left two files too open. You will prove the exposure as an untrusted user, then apply least privilege so the discretionary access control (DAC) model on the filesystem enforces who may read and write each file.

Commands: ls -l, whoami, su <user> (root, appuser, mallory), chmod <octal> <file>, chown <user[:group]> <file>, cat <file>, echo text > <file>, help, reset. Files live in /srv/app/; a bare name is resolved there.

Why least privilege works here

Under discretionary access control, every file carries an owner, a group, and three permission triads, owner, group, and other. The kernel checks exactly one triad: your owner bits if you own the file, otherwise the group bits if you are in its group, otherwise the "other" bits that apply to everyone. A mode of 666 hands write access to every account, including an untrusted one like mallory, which is how a leaked config or tampered secret begins. Tightening the modes to 644 and 600 grants each file only the access its legitimate owner needs, the principle of least privilege. Choosing and enforcing who may touch what is the job of an access control model (DAC here, alongside MAC and RBAC), the focus of LO 5.2.A.
