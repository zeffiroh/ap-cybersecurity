I. Subjects, Objects, and Permissions

Every multi-user operating system must answer a deceptively simple question: which subjects are allowed to perform which operations on which objects? On LinuxLinuxA free, open-source operating system kernel originally written by Linus Torvalds in 1991. Nearly all web servers, cloud instances, and Android phones run on a Linux kernel. Because Linux is multi-user by design, meant to be shared by many accounts on one machine, permission enforcement is baked into the filesystem itself, not bolted on afterward. Linux kernel source is maintained at kernel.org. The permission model traces directly back to Dennis Ritchie and Ken Thompson's Unix (1969), specifically the Sixth Edition Unix filesystem of 1975. systems, that question is answered primarily at the filesystem layer through a permission model that has remained structurally unchanged since the earliest versions of Unix. Every file and directory on a Linux system is represented internally by a structure called an inodeInode, Index NodeA data structure that stores all the metadata about a file except its name and its actual content: the owner, the group, the permission bits, the file size, timestamps, and pointers to the disk blocks that hold the data. Think of an inode as a library card catalog entry, it tells you who owns the book and where to find it on the shelf, but the card itself is not the book. Defined by the POSIX filesystem model and implemented by filesystems such as ext4, XFS, and Btrfs. View an inode number with `ls -i`; view raw inode metadata with `stat filename`., and among the fields stored in that inode is a compact 16-bit permission field that governs read, write, and execute access. Understanding this model is foundational to application security because nearly every privilege escalation, data exfiltration, or persistence technique on a Linux host ultimately depends on a permission misconfiguration somewhere in the filesystem.

The Linux permission model divides every file's potential accessors into exactly three classes: the ownerOwner (User)The user account associated with a file, stored in the inode as a numeric User ID (UID). The owner is usually, but not always, the account that created the file. Ownership can be reassigned with the `chown` command by a privileged user. UID 0 is always reserved for the root superuser account, regardless of what that account is named. `/etc/passwd` maps UIDs to human-readable usernames., the groupGroupA named collection of user accounts, stored in the inode as a numeric Group ID (GID). Groups let administrators grant a set of related permissions to many users at once, for example, everyone in the "developers" group might get write access to a shared project directory without each user needing individual permission entries. Group membership is defined in `/etc/group`. A user's primary group is recorded in `/etc/passwd`; supplementary groups are viewed with the `groups` or `id` command., and otherOther (World)Every account on the system that is neither the file's owner nor a member of the owning group. Permissions granted to "other" apply to literally anyone with any kind of access to the machine, including, on an internet-facing server, potentially anonymous processes such as an unauthenticated web server worker. Sometimes called "world" permissions in older Unix documentation. The "other" class is the most dangerous to overprovision because it cannot be scoped down further., colloquially "everybody else." For each of these three classes, the system tracks three independent permission bits: read (r)Read PermissionFor a regular file, read permission allows a process to open the file and view its contents. For a directory, read permission allows listing the names of files contained within it, but not necessarily accessing those files, which is separately gated by execute permission on the directory. Represented internally as octal value 4. Attempting to `cat` a file without read permission returns EACCES (Permission denied) from the kernel., write (w)Write PermissionFor a regular file, write permission allows a process to modify or truncate the file's contents. For a directory, write permission allows creating, deleting, or renaming entries within that directory, critically, deleting a file only requires write permission on its parent directory, not on the file itself. Represented internally as octal value 2. This directory-level write rule is a frequent source of confusion and a real exploitation vector, covered later in this chapter as the sticky bit., and execute (x)Execute PermissionFor a regular file, execute permission allows the kernel to run the file as a program or script. For a directory, execute permission (sometimes called "search" or "traverse" permission) allows a process to `cd` into it or access files inside it by name, even without read permission on the directory itself. Represented internally as octal value 1. A directory with execute-but-not-read permission is "searchable but not listable", useful for hiding directory contents from casual enumeration while still allowing access to known filenames.. Because there are three classes and three permission bits per class, the entire permission state of a file can be represented in nine bits, traditionally displayed as a string such as rwxr-xr-- when a user runs ls -l.

How to Read a Permission String Without Guessing When you run ls -l and see something like -rwxr-xr--, break it into four chunks: the leading character is the file type (- for regular file, d for directory, l for symbolic link), then three groups of three characters each, owner, group, other. So rwxr-xr-- means the owner can read/write/execute, the group can read/execute, and everyone else can only read. Students almost always miscount the leading type character as part of the owner's permissions, it is not. Always subtract one character before you start counting triads.

This tripartite model is intentionally coarse. It cannot express "grant write access to exactly these two users but not the rest of the group," nor can it express default permissions that automatically apply to new files created inside a directory by different users. These limitations motivated the later development of POSIX ACLsPOSIX ACL, Access Control ListAn extension to the traditional rwx model that allows arbitrary numbers of additional users and groups to be granted specific permissions on a single file, beyond the base owner/group/other triad. Where rwx gives you exactly three permission "slots," ACLs give you as many as you need. Standardized as POSIX.1e (a draft standard, IEEE 1003.1e, withdrawn in 1997 but implemented broadly anyway by Linux, Solaris, and BSD). Managed on Linux via the `getfacl` and `setfacl` utilities, requiring filesystem mount support (`acl` mount option on ext4)., discussed in depth in Section II, which layer finer-grained rules on top of the base model without replacing it. It is important to internalize that ACLs are additive, the base rwx bits are always present and always evaluated as part of the access decision, even on a file that also carries an ACL.

The academic and operational significance of correct permission configuration cannot be overstated. The principle of least privilegePrinciple of Least PrivilegeA foundational security design rule stating that every subject (user, process, or program) should be granted only the minimum set of permissions necessary to perform its function, and nothing more. Applied to filesystems, this means a web server process should never be able to write to its own configuration files, and a low-privilege user account should never be able to read another user's private data. Formalized by Saltzer & Schroeder (1975), "The Protection of Information in Computer Systems," Proceedings of the IEEE. Also codified in NIST SP 800-53 control AC-6 (Least Privilege)., one of the oldest and most rigorously validated concepts in computer security engineering, is, on a Linux host, implemented almost entirely through filesystem permissions and the identity of the user account under which a process executes. When a system administrator runs a production web server as the root superuser instead of a dedicated unprivileged service account, or leaves a configuration directory world-writable for developer convenience, they are not making a stylistic choice; they are directly enlarging the attack surfaceAttack SurfaceThe complete set of points where an unauthorized actor could attempt to interact with or exploit a system. Every file that is readable or writable by more accounts than strictly necessary is a small addition to this surface. Reducing attack surface is a continuous engineering discipline, not a one-time task. NIST SP 800-53 discusses attack surface reduction under multiple control families, including CM (Configuration Management) and SC (System and Communications Protection). of the entire host, because any process that is compromised, a vulnerable PHP script, a malicious npm package, a misconfigured cron job, inherits exactly the permissions of the account that runs it.

A 1970s Model Still Decides Who Reads Your Container's Secrets Container platforms like Docker and Kubernetes did not replace the Unix permission model, they run on top of it. A container "root" user is frequently the same UID 0 as the host's root unless user namespace remapping is explicitly configured. Cloud file storage services (AWS EFS, Google Filestore) that mount as Linux filesystems still enforce rwx bits underneath their web consoles. Understanding raw Linux permissions is not legacy knowledge; it is the substrate that modern cloud-native security tooling is built on top of.

II. Data States, Classification, and Managerial Controls

Two questions decide how much protection a particular file deserves, and neither of them is technical. The first is what the data is: a marketing brochure and a payroll register both live on the same disk and are both, mechanically, sequences of bytes, but only one of them creates an obligation if it leaves the building. The second is where the data is at the moment you want to protect it, because the mechanisms available differ completely depending on the answer.

The Three States of Data

Security practice divides data into three states, and each admits a different family of controls.

Data at restData at RestData written to persistent storage, disk, tape, object store, or backup medium, and not currently being transmitted or processed. Protected primarily by storage encryption and by filesystem access control. is data sitting in storage: a database file, an object in a bucket, a backup tape in a vault. The controls that fit are filesystem and object permissions, full-disk or file-level encryption, and physical control of the medium. Note what disk encryption does and does not do. Full-disk encryption defends against the theft of a powered-down laptop; on a running server with the volume already unlocked, every process that can read the file reads plaintext, and the encryption contributes nothing. This is precisely why access control and encryption are complementary rather than alternative answers.

Data in transitData in TransitData moving across a network link, whether across the public internet or between two hosts in the same rack. Protected by transport-layer encryption such as TLS, and by authenticated tunnels such as IPsec or SSH. is data crossing a network. The control is transport encryption, TLS for application traffic, IPsec or SSH tunnels for host-to-host links, and the requirement extends to internal links, since an attacker with a foothold inside the network is exactly the adversary an internal link must resist.

Data in useData in UseData loaded into memory and actively being processed by a program, where it must generally exist in plaintext for computation to occur. The hardest state to protect; approaches include memory protection, process isolation, hardware enclaves, and, for narrow cases, homomorphic encryption. is the hard case. To compute on a value a processor generally needs it in the clear, so the data exists as plaintext in memory for the duration. This is the state Heartbleed attacked: the private keys it disclosed were properly encrypted at rest and properly protected in transit, and were read out of process memory in between. Defenses for this state are weaker and costlier, process isolation, memory zeroing after use, hardware enclaves, and, for a narrow set of computations, homomorphic encryption, which is why minimizing the time sensitive data spends decrypted in memory is itself a control.

Classification

A classification schemeData ClassificationA managerial control that assigns each data item to a sensitivity band, so that handling requirements can be written once per band rather than once per file. Government schemes use Unclassified, Confidential, Secret, and Top Secret; commercial schemes commonly use Public, Internal, Confidential, and Restricted. exists so that handling rules can be written once per band instead of once per file. Government practice uses Unclassified, Confidential, Secret, and Top Secret; commercial practice typically uses Public, Internal, Confidential, and Restricted. The label is administrative, not technical, nothing about a Restricted file makes the bytes different, but the label is what a policy can attach requirements to: this band may be stored only on encrypted volumes, may not leave this jurisdiction, must be retained seven years and then destroyed, may be accessed only by staff who have completed a particular training.

Classification interacts with the states in a way worth stating explicitly. A Restricted record at rest requires encrypted storage and a tightly scoped permission set. The same record in transit requires TLS with a modern cipher suite and certificate validation actually enforced. The same record in use requires that the process holding it be isolated and that the plaintext not be written to a log, a crash dump, or a temporary file. One label; three different engineering obligations.

Two further concepts belong here. Aggregation means that a collection can warrant a higher classification than any of its members: a single employee's office phone extension is Internal, while the complete directory of extensions, names, and reporting lines is a social-engineering asset. Data lifecycle means that classification is not permanent, an unreleased quarterly earnings figure is Restricted until the moment it is filed, after which it is Public, and a retention schedule should ensure that data no longer needed is destroyed rather than accumulated, since data that does not exist cannot be breached.

Managerial Controls

Controls are conventionally sorted into three families by how they operate. Technical controls are enforced by machinery: a permission bit, a firewall rule, an encryption routine. Physical controls act on the material world: a locked rack, a badge reader, a shredder. Managerial controlsManagerial (Administrative) ControlsControls implemented through policy, procedure, and human decision rather than through technology, classification schemes, data ownership, access review, separation of duties, training, and vendor assessment. NIST SP 800-53 organizes controls into families that cut across this distinction; the managerial families include Planning (PL), Risk Assessment (RA), and Program Management (PM). operate through policy, procedure, and human decision, and they are what make the technical controls coherent. A permission bit answers "may this account read this file"; only a managerial control can answer "should this account exist at all, and who decided so."

The managerial controls that bear directly on application and data security are these. A data classification policy defines the bands and their handling rules. Data ownership names a specific person accountable for each data set, distinguishing the owner who decides who may have access, the custodian who operates the storage on the owner's behalf, and the user who works with the data under the rules. Least privilege requires that an account receive only the access its function demands, and the related separation of duties requires that no single person hold every step of a sensitive process, the person who creates a vendor record must not also be the person who approves payments to it. Access review is the periodic re-certification that catches privilege accumulation, which otherwise grows monotonically as people change roles and no one ever removes the old access. Onboarding and offboarding procedures govern the moments when access is granted and, more importantly, revoked. Change management ensures a permission change is requested, approved, and recorded rather than typed into a terminal at midnight. Training and acceptable-use policy put the rules in front of the people expected to follow them, and vendor and third-party assessment extends the same expectations to software and services the organization did not write.

The reason to insist on this family is that most of the well-known data losses of the last two decades were not defeated cryptography. They were an account that should have been closed, an access grant nobody re-examined, a contractor whose scope was never bounded, or a copy of a production database that policy did not forbid a developer from taking home.

III. Access Control Models

An access control model is the rule an organization uses to decide who may reach what. Four models cover nearly all practice, and choosing between them is largely a question of who holds the decision and how often the answer changes.

Discretionary Access Control

Under DACDAC, Discretionary Access ControlThe owner of a resource decides who may access it and may pass that access on. The model implemented by standard Unix file permissions and by Windows NTFS ACLs., the owner of a resource decides who else may use it, and may grant that discretion onward. Standard Unix permissions are DAC: the user who owns a file may chmod it however they like, including making it world-readable. The strength is flexibility and low administrative cost; the weakness is that security policy is delegated to whichever user happens to own the object, and there is nothing to stop an authorized reader from copying the contents into a file they own and open to everyone. DAC therefore cannot enforce a rule about where data may go, only about who may open a particular container.

Mandatory Access Control

Under MACMAC, Mandatory Access ControlA system-wide policy, set by an administrator and not alterable by resource owners, compares subject clearances against object labels to decide access. Implemented on Linux by SELinux and AppArmor; the classical formal treatment is the Bell–LaPadula model., a system-wide policy decides, and owners cannot override it. Subjects carry clearances, objects carry labels, and the reference monitor compares the two on every access. The classical formulation is Bell–LaPadula, whose two rules are worth stating carefully because they are frequently reversed: no read up means a subject may not read an object above its clearance, and no write down means a subject may not write to an object below its clearance, the second rule prevents a cleared user, or malware acting as that user, from copying Secret content into an Unclassified file. On Linux, SELinux and AppArmor supply MAC on top of the discretionary permission bits, which is why an SELinux denial can block an operation that ls -l says is permitted: both must allow it. MAC is rigid and expensive to administer, and is chosen where the cost of a wrong disclosure dominates, defense, intelligence, and increasingly the confinement of internet-facing daemons.

Role-Based Access Control

RBACRBAC, Role-Based Access ControlPermissions are granted to named roles rather than to individuals, and users acquire permissions by being assigned a role. Standardized as ANSI INCITS 359. The dominant model in enterprise systems. attaches permissions to roles rather than to people. Nobody is granted access to the payroll database; the role "payroll analyst" is, and people are assigned that role. The administrative gain is large: a new hire is granted one role rather than forty individual permissions, a departing employee's access is removed by removing role assignments, and an auditor can answer "who can approve payments" by reading a role definition instead of reconstructing it from thousands of grants. RBAC also implements separation of duties structurally, by declaring two roles mutually exclusive. Its limitation is that it is static, the role either has the permission or it does not, regardless of time, location, device, or the properties of the specific record.

Attribute-Based Access Control

ABACABAC, Attribute-Based Access ControlAccess decisions are computed at request time from attributes of the subject, the object, the action, and the environment. Described in NIST SP 800-162. Policies are expressed as rules over attributes rather than as lists of grants. evaluates a policy expression at request time over attributes of the subject, the object, the action, and the environment: permit a clinician to read a record if the clinician is assigned to the patient's care team, the record's classification is at or below the clinician's authorization, the request originates from a managed device on the hospital network, and the current time falls within the clinician's shift. This expresses conditions RBAC cannot, and does so without inventing a role for every combination, the "role explosion" that afflicts large RBAC deployments. The cost is that policies become software: they need authoring, testing, and version control, the attribute sources must be authoritative and current, and a wrong attribute silently produces a wrong decision. NIST SP 800-162 is the standard reference.

In practice the models compose rather than compete. A single enterprise commonly runs RBAC for application entitlements, DAC on the filesystems those applications use, MAC through SELinux to confine the daemons, and ABAC at the API gateway for context-dependent conditions. The design question is not which model is best but which decision each layer is being asked to make.

IV. Configuring Access Control on Linux

Reading ls -l, Field by Field

Everything that follows depends on being able to read one line of output exactly. Consider:

Terminal 
$ ls -l /srv/app/config.yml
-rw-r----- 1 appsvc appadm 2048 Sep  2 09:14 /srv/app/config.yml

Each field carries a distinct piece of the access decision.

  • -, the file type. A hyphen is a regular file; d is a directory, l a symbolic link, c and b character and block devices, s a socket, p a named pipe. This character is not a permission and is often miscounted as one, which is why a mode string is ten characters and a mode number has only three digits.
  • rw-, the owner's permissions: read and write, no execute.
  • r--, the group's permissions: read only.
  • ---, everyone else: nothing. The mode is therefore 640.
  • 1, the hard link count, the number of directory entries pointing at this inode. A count above one on a sensitive file is worth noticing, because a second name for the same inode grants the same access through a path your permission audit may not have examined.
  • appsvc, the owning user, which is what the owner triplet applies to.
  • appadm, the owning group, which the group triplet applies to.
  • 2048, the size in bytes; Sep 2 09:14, the last modification time, which is the field a file integrity monitor watches alongside a hash.

Two details of the evaluation rule are easy to get wrong. First, the three triplets are checked in order and the first match wins: if you are the owner, only the owner triplet is consulted, so a file mode of 077 denies its owner everything while granting everyone else full access. Second, on a directory the bits mean something different from what they mean on a file. On a directory, r permits listing the names inside, w permits creating and deleting entries, and x, the search bit, permits traversing into it to reach a named child. A directory with --x for other lets a user open /srv/app/config.yml if they already know the name, while ls on the directory fails. And because w on a directory governs the directory's entry list rather than the files' contents, write permission on a directory is enough to delete a file inside it that you cannot read and do not own, the problem the sticky bit exists to solve.

An additional character sometimes follows the mode string. A trailing + means a POSIX access control list is present and the nine bits are not the whole story; a trailing . means an SELinux security context is attached. Auditing permissions without noticing a + produces a confidently wrong conclusion.

umask: What New Files Inherit

Permissions on a new file are not chosen by the program that creates it alone. A process asks the kernel for a mode, conventionally 666 for a file and 777 for a directory, and the kernel then clears every bit set in the process's umaskumaskA per-process mask of permission bits to withhold from newly created files and directories. The kernel computes the final mode as the requested mode with every bit set in the umask cleared. Inherited from the parent process; set in login shell configuration or, for services, in the unit file.. The arithmetic is a bit clear, not a subtraction, though for the common values the two agree:

Terminal 
$ umask
0022
$ touch newfile   && ls -l newfile | cut -d' ' -f1     # 666 with 022 cleared
-rw-r--r--
$ mkdir newdir    && ls -ld newdir | cut -d' ' -f1     # 777 with 022 cleared
drwxr-xr-x

# Withhold all access from group and other for this shell and its children
$ umask 077
$ touch private   && ls -l private | cut -d' ' -f1
-rw-------

Note that a plain file never receives the execute bit from the default request of 666, which is why a freshly written script must be made executable explicitly. The umask is per-process and inherited, so setting it in an interactive shell has no effect on a daemon started by the service manager; for a service, the mask belongs in the unit definition (UMask= in a systemd service file) rather than in anyone's .bashrc. A umask of 022 is a reasonable default for a general-purpose machine and a poor one for a host processing regulated data, where 027, nothing for other, or 077 is the appropriate starting position. The umask is a default, not an enforcement mechanism: it decides what a file gets at birth, and any process may chmod afterward.

The nine permission bits described in Section I are most commonly manipulated using two complementary notations: octal notationOctal NotationA base-8 numbering system where each digit ranges from 0–7. Linux permissions map naturally to octal because each permission triad (rwx) is exactly three bits, and three bits can represent values 0 through 7 (read=4, write=2, execute=1, summed together). A permission of "7" means read+write+execute; "5" means read+execute; "0" means no access. Octal was chosen historically because early Unix systems used 6-bit and 9-bit words that mapped cleanly onto base-8 arithmetic; the convention persisted long after word sizes changed. and symbolic notationSymbolic NotationA human-readable syntax for `chmod` that specifies changes using letters instead of numbers: `u` (user/owner), `g` (group), `o` (other), `a` (all), combined with operators `+` (add permission), `-` (remove permission), and `=` (set exactly). Symbolic notation is often preferred when you want to change only one permission without recalculating the entire octal value. Defined in the POSIX.1-2017 specification for the `chmod` utility (IEEE Std 1003.1).. Both notations are accepted by the chmodchmod, Change ModeThe command-line utility used to modify a file or directory's permission bits. The name derives from "change mode," where "mode" is Unix terminology for the permission bits. Only the file's owner or a superuser may invoke chmod on a given file. POSIX.1-2017 §chmod. On Linux, implemented in GNU coreutils; the underlying system call is `chmod(2)` / `fchmodat(2)`. command, and every security-conscious systems administrator must be fluent in both.

Octal notation assigns numeric weights to each permission: read is worth 4, write is worth 2, and execute is worth 1. Summing the applicable weights for each of the three classes (owner, group, other) produces a three-digit number that fully describes the file's mode. A permission of rwxr-xr-x, for example, is computed as owner = 4+2+1 = 7, group = 4+0+1 = 5, other = 4+0+1 = 5, yielding chmod 755.

bash 
# Grant the owner full control, group and other read+execute only
# Typical mode for an executable script or binary
chmod 755 /usr/local/bin/deploy.sh

# Grant the owner read+write, group and other read-only
# Typical mode for a plain configuration or data file
chmod 644 /etc/myapp/app.conf

# Grant the owner full control, deny group and other entirely
# Typical mode for a private SSH key or credential file
chmod 600 ~/.ssh/id_ed25519

# Verify the resulting mode
ls -l /usr/local/bin/deploy.sh
# -rwxr-xr-x 1 root root 812 Jul  9 09:14 /usr/local/bin/deploy.sh

Symbolic notation, by contrast, applies targeted deltas rather than restating the full mode. The syntax combines a class specifier (u, g, o, or a for all), an operator (+ to add, - to remove, = to set exactly), and one or more permission letters. Symbolic mode is especially useful in automated deployment scripts where you want to guarantee an idempotent state change without needing to know or preserve the file's prior mode.

bash 
# Add execute permission for the owner only, leaving group/other untouched
chmod u+x install.sh

# Remove write permission from the group, and set other to read-only exactly
chmod g-w,o=r /etc/nginx/nginx.conf

# Recursively grant read+execute to group and other on a directory tree
chmod -R g+rX,o+rX /var/www/html
# Note: capital X applies execute only to directories and files that
# already have execute for someone -- it will not make plain data files
# unexpectedly executable during a recursive operation.

# Remove all permissions from other on a sensitive directory
chmod o= /etc/myapp/secrets
Octal Is Three Independent Bit Fields, Not a Number It helps to stop reading 640 as the number six hundred and forty. Each digit is an independent three-bit field, and the weights are simply the bit positions: read = 4, write = 2, execute = 1. Because each digit is a sum of distinct powers of two, every combination has exactly one representation (0 = none, 1 = x, 2 = w, 3 = wx, 4 = r, 5 = rx, 6 = rw, 7 = rwx), which is what makes octal and the rwx string interchangeable rather than merely related. Translate a requirement one class at a time: "the owner needs full control, the group needs to read but not modify or run the file, and no other account may see it" yields 6 for the owner, 4 for the group, 0 for other, chmod 640. Working in the other direction is the same operation reversed, and reading a mode aloud as three separate answers rather than one number is what keeps the two triplets from bleeding together.

Ownership itself is a separate axis from permission bits, and is modified with chownchown, Change OwnerThe command used to reassign the user (and optionally group) that owns a file. Only the superuser (root) can transfer ownership of a file to a different user on standard Linux configurations, because allowing ordinary users to give away files could be abused to circumvent disk quota accounting. POSIX.1-2017 §chown. Underlying system call: `chown(2)`. Syntax: `chown newuser:newgroup filename`. and chgrpchgrp, Change GroupThe command used to reassign only the group associated with a file, without touching the owning user. Unlike full ownership transfer, an ordinary user may chgrp a file they own to any group they themselves belong to, without needing root privileges. POSIX.1-2017 §chgrp. Underlying system call: the group component of `chown(2)`.. These utilities are frequently paired with chmod during application deployment to ensure that a service account, rather than the deploying administrator's personal account, ends up as the effective owner of runtime files.

bash 
# Transfer ownership of the web root to the unprivileged www-data service account
sudo chown -R www-data:www-data /var/www/html

# Change only the group of a shared log directory to "loggers"
sudo chgrp -R loggers /var/log/myapp

# Combine ownership transfer with a permission reset in one deployment step
sudo chown deploy:deploy /opt/myapp/release && sudo chmod 750 /opt/myapp/release

Beyond the base nine bits, Linux defines three special permission bitsSpecial Permission BitsThree additional bits stored in the inode alongside the standard nine rwx bits, occupying a fourth octal digit conventionally written to the left of the standard three (e.g. `chmod 4755`). These bits alter how the kernel treats execution or deletion of a file rather than granting straightforward read/write/execute access. Collectively referred to in POSIX as the setuid, setgid, and "restricted deletion" (sticky) bits.: setuidsetuid BitWhen set on an executable file, causes the program to run with the effective privileges of the file's owner rather than the privileges of the user who launched it, regardless of who launches it. Historically used to let ordinary users run a small number of privileged operations (like changing their own password, which requires writing to a root-owned file) without granting them full root access. Octal value 4000, displayed as an "s" replacing the owner's execute bit (e.g. `-rwsr-xr-x`). The classic example is `/usr/bin/passwd`. A setuid binary owned by root is one of the highest-value privilege escalation targets on any Linux host., setgidsetgid BitOn an executable, functions like setuid but for the group instead of the owner. On a directory, setgid has an entirely different and extremely useful effect: any new file or subdirectory created inside it automatically inherits the parent directory's group, rather than the creating user's primary group. This is the standard technique for maintaining consistent group ownership on shared collaborative directories. Octal value 2000, displayed as an "s" replacing the group's execute bit. Widely used in `/var/www` and shared project directories with commands like `chmod g+s /shared/project`., and the sticky bitSticky BitWhen set on a directory, restricts deletion and renaming of files within that directory so that only the file's owner (or the directory's owner, or root) may remove or rename it, even if other users have write permission on the directory itself. Without the sticky bit, any account with write access to a directory could delete any file inside it, including files it does not own, because deletion is governed by directory write permission rather than file permission. Octal value 1000, displayed as a "t" replacing other's execute bit. The canonical example is `/tmp`, which is world-writable (mode 1777) specifically so any user can create temporary files, but the sticky bit prevents users from deleting each other's files..

bash 
# Set the setuid bit on a privileged utility (fourth octal digit = 4)
sudo chmod 4755 /usr/bin/some-privileged-tool
ls -l /usr/bin/some-privileged-tool
# -rwsr-xr-x 1 root root 34216 Jul  9 09:20 /usr/bin/some-privileged-tool

# Set setgid on a shared collaborative directory so new files inherit its group
sudo chmod 2775 /srv/shared/project
sudo chgrp devteam /srv/shared/project

# Set the sticky bit on a world-writable scratch directory (like /tmp)
sudo chmod 1777 /srv/scratch
ls -ld /srv/scratch
# drwxrwxrwt 12 root root 4096 Jul  9 09:22 /srv/scratch

# Audit a filesystem for dangerous setuid/setgid binaries -- a routine
# hardening and incident-response task
find / -xdev \( -perm -4000 -o -perm -2000 \) -type f -exec ls -l {} \; 2>/dev/null
Every setuid Root Binary Is a Standing Offer to Local Attackers Any setuid binary owned by root effectively runs with full root privileges no matter which unprivileged user invokes it. If such a binary can be tricked into reading or writing an attacker-chosen file, through a symlink race, an unsanitized argument, or a shell escape from within the program, the attacker has escalated from an ordinary account straight to root. This is precisely the mechanism exploited by tools such as GTFOBins to catalog "living off the land" privilege escalation paths through legitimately installed setuid binaries. Auditing `find / -perm -4000` output on every hardened host is not optional; it is a baseline control.

The base rwx model, even augmented with special bits, still cannot express arbitrarily granular permission grants, for example, "grant read-only access to exactly one additional user, alice, on a file otherwise restricted to the owner." This is the precise gap that POSIX ACLsPOSIX ACLSee earlier definition. ACL entries are stored as extended attributes on the inode, separate from but consulted alongside the base rwx bits during every access check. close. ACLs are inspected using getfaclgetfacl, Get File ACLDisplays the full access control list of a file or directory, including the base owner/group/other entries and any additional named-user or named-group entries, plus the "effective rights mask" that caps the maximum permissions any ACL entry can actually grant. Part of the acl package (`libacl`) on Linux, implementing the withdrawn POSIX.1e draft standard. and modified using setfaclsetfacl, Set File ACLAdds, modifies, or removes ACL entries on a file or directory. A default ACL can also be set on a directory so that new files created within it automatically inherit specific ACL entries, the ACL analogue of the setgid bit's inheritance behavior, but far more flexible. Part of the acl package on Linux. Requires the underlying filesystem to be mounted with the `acl` option (enabled by default on most modern ext4/XFS mounts)..

bash 
# View the current ACL on a file
getfacl /srv/shared/report.csv
# file: srv/shared/report.csv
# owner: bob
# group: finance
# user::rw-
# group::r--
# other::---

# Grant read-only access to a single additional user, alice,
# without changing the base owner/group/other bits
setfacl -m u:alice:r-- /srv/shared/report.csv

# Grant read+write to a specific group, auditors, on a directory,
# and set a default ACL so new files inherit the same entry
setfacl -m g:auditors:rwx /srv/shared/reports
setfacl -d -m g:auditors:rwx /srv/shared/reports

# Remove a specific ACL entry
setfacl -x u:alice /srv/shared/report.csv

# Strip all extended ACL entries and revert to the base rwx bits only
setfacl -b /srv/shared/report.csv

When both a base permission mode and an ACL exist on the same file, the kernel evaluates access in a defined order: the file owner's rwx bits are always checked first, named-user ACL entries are checked next, then the owning group and any named-group ACL entries (subject to the ACL mask), and finally the "other" bits. A file's ls -l listing signals the presence of an ACL with a trailing + character after the permission string (for example, -rw-rw-r--+), which is a detail security auditors must not overlook, since a seemingly restrictive base mode can conceal a permissive ACL grant layered on top.

V. Case Studies: Writable Cron Directories and Root Containers

Case Study 5.2.1: World-Writable Cron Directories and Local Privilege Escalation

A recurring class of real-world Linux privilege escalation findings, documented repeatedly in penetration testing reports and in automated privilege-escalation enumeration tools such as LinPEAS and linux-exploit-suggester, involves scripts referenced by croncronThe standard Linux time-based job scheduler. A cron daemon reads schedule files (crontabs) and executes the specified commands at the specified times, typically running scheduled jobs as root when configured in system-wide locations like `/etc/cron.d/` or `/etc/crontab`. Defined by POSIX.1-2017 crontab format. System cron jobs commonly run with elevated privileges to perform maintenance tasks like log rotation and backups. jobs that are misconfigured with overly permissive filesystem permissions. In a representative incident pattern, a system administrator creates a maintenance script, for example, a nightly backup or log-rotation script, and places it in a directory referenced by a root-owned crontab entry. During initial setup, to avoid troubleshooting permission errors, the administrator runs chmod 777 on the script or its containing directory "temporarily," intending to tighten it later. That tightening step is frequently forgotten.

Because the script executes with root's privileges (inherited from the crontab entry that references it, not from any setuid bit), any local unprivileged user who can write to that script, permitted because the directory or file is world-writable, can simply append or replace the script's contents with arbitrary commands, such as adding their own account to the sudoers file or spawning a root-owned shell with the setuid bit set. The next time cron fires the job, typically within minutes, the attacker's injected payload executes with full root privileges. This attack requires no exploitation of memory corruption, no exotic zero-day, and no network access beyond an initial low-privilege local foothold, it is a pure filesystem permission failure, and it remains one of the single most commonly identified "quick win" privilege escalation paths in professional penetration testing engagements against Linux hosts to this day.

The Debugging Permission That Outlives the Bug Every experienced Linux administrator has, at some point, run `chmod 777` to unblock themselves during a rushed deployment. The failure is not in reaching for the broad permission during debugging, it is in never returning to narrow it back down. Treat any `777` or `666` permission you find on a production host as an open incident-response finding until proven otherwise, not a stylistic preference. Automated configuration auditing (covered in Section IV) exists precisely because humans reliably forget to revert emergency permission changes.

Case Study 5.2.2: Containers Running as Root and Host Filesystem Compromise

The rise of containerizationContainerizationA technology (popularized by Docker, standardized in the OCI Container Runtime Specification) that packages an application with its dependencies into an isolated runtime environment sharing the host's kernel, rather than virtualizing an entire separate operating system. Because containers share the host kernel, the isolation between a container process and the host is enforced through kernel namespaces and cgroups, not through hardware virtualization. Docker was released in 2013; the Open Container Initiative (OCI) standardized the container image and runtime formats in 2015-2017. introduced a new instance of an old permission problem. By default, unless explicitly configured otherwise, processes inside a Docker container run as UID 0, the same numeric root UID used by the host operating system's actual superuser account, because Linux user IDs are a single global namespace shared between the host and any container that does not use dedicated UID remapping. If an operator mounts a host directory into a container as a bind mountBind MountA Docker/Linux mechanism that makes a directory on the host filesystem directly accessible inside a container at a specified path, as opposed to a container-private volume. Files created or modified through a bind mount are immediately visible on the host filesystem and vice versa, because it is literally the same underlying inode, not a copy. Configured with `docker run -v /host/path:/container/path` or the `--mount type=bind` syntax. and that container's main process is compromised, for instance, through a vulnerable web application dependency, the attacker's shell inside the container is running as root with respect to that bind-mounted host directory's permission checks, even though the container is nominally "isolated."

Multiple publicly documented incidents and vulnerability disclosures (including numerous CVEs against container runtimes and orchestration tooling) have demonstrated variations of this pattern: an attacker who achieves code execution inside a root-privileged container with an insufficiently scoped bind mount can write directly to sensitive host paths, SSH authorized_keys files, systemd unit files, or even parts of the host's own root filesystem if the container was misconfigured with an overly broad mount, achieving full host compromise from what was assumed to be a sandboxed application environment. This is not a flaw in Linux permissions themselves; it is a demonstration that the rwx and ownership model is being correctly enforced exactly as designed, and that the actual security failure was the decision to run the containerized process as UID 0 with unnecessary write access to host paths in the first place.

A Container Boundary Is Not a Privilege Boundary A container boundary is not a substitute for correct Linux permission hygiene, it is an additional layer that still depends on correct permission hygiene underneath it. The defense in both case studies above is identical in principle: the process (cron job or container) should run as the least-privileged account capable of doing its job, and the filesystem paths it can write to should be scoped as narrowly as possible. Modern container tooling supports running as an explicit unprivileged UID (`USER` directive in a Dockerfile, or `--user` at runtime) and read-only bind mounts (`:ro` suffix) specifically to reintroduce least privilege at the container layer.

VI. Least Privilege, Auditing, and POSIX ACLs

Effective Linux permission hardening is a continuous discipline built on several layered controls rather than a single configuration step performed once at deployment time.

1. Applying the Principle of Least Privilege to Service Accounts

Every long-running network-facing service, a web server, database daemon, or application runtime, should execute as a dedicated unprivileged service accountService AccountA user account created specifically to run a particular application or daemon, rather than being associated with a human operator. Service accounts are typically configured with no valid login shell (`/usr/sbin/nologin`) and no password, so they cannot be used for interactive logins even if compromised credentials are somehow obtained. Common examples: `www-data` (Debian/Ubuntu web servers), `nginx`, `mysql`, `postgres`. Creating one: `useradd -r -s /usr/sbin/nologin svc_myapp`. that owns only the files it strictly requires and holds no write access to its own configuration or executable files. A compromised web application process running as an unprivileged account can, at worst, tamper with the files that account owns; the same compromise against a process running as root grants the attacker unrestricted control of the entire host. Standard hardening guidance additionally recommends that configuration directories be owned by a separate administrative account (or root) and mounted read-only to the service account, so that even a fully compromised application process cannot rewrite its own startup configuration to achieve persistence.

bash 
# Create a dedicated, non-interactive service account for an application
sudo useradd -r -s /usr/sbin/nologin svc_myapp

# Web root: readable and executable by the service account, not writable
sudo chown -R root:svc_myapp /var/www/myapp
sudo find /var/www/myapp -type d -exec chmod 750 {} \;
sudo find /var/www/myapp -type f -exec chmod 640 {} \;

# Uploads directory: the one path the service account IS allowed to write to,
# scoped narrowly and with the sticky bit to prevent cross-user file tampering
sudo mkdir -p /var/www/myapp/uploads
sudo chown svc_myapp:svc_myapp /var/www/myapp/uploads
sudo chmod 1770 /var/www/myapp/uploads

# Confirm the service process itself runs as the unprivileged account, not root
ps -eo user,pid,cmd | grep myapp-server

2. Routine Filesystem Auditing

Because permission misconfigurations tend to accumulate silently over time, through emergency debugging shortcuts, incomplete deployment scripts, or forgotten temporary grants, organizations should implement recurring automated audits that specifically flag world-writable files, unexpected setuid/setgid binaries, and files with orphaned or unexpected ownership.

bash 
# Find world-writable files outside of expected scratch/temp locations
find / -xdev -type f -perm -0002 -not -path "/tmp/*" -not -path "/var/tmp/*"

# Find world-writable directories missing the sticky bit (deletion is NOT
# restricted to file owners -- a red flag on any shared directory)
find / -xdev -type d -perm -0002 ! -perm -1000

# Find every setuid/setgid binary system-wide for manual review
find / -xdev \( -perm -4000 -o -perm -2000 \) -type f 2>/dev/null

# Find files with no valid owner (orphaned UID, often left behind
# after an account was deleted without reassigning its files)
find / -xdev -nouser -o -nogroup 2>/dev/null

3. Applying POSIX ACLs and CIS Benchmark Guidance for Granular Cases

When the base owner/group/other model cannot cleanly express a required access pattern, such as a shared audit directory readable by a compliance team but writable only by the application itself, POSIX ACLs should be used deliberately and documented, rather than resorting to broadening the base "other" permissions as a workaround. Organizations aligning with the CIS BenchmarksCIS BenchmarksConsensus-developed, vendor-neutral configuration hardening guides published by the Center for Internet Security, covering operating systems, cloud platforms, and applications. The CIS Linux benchmarks include specific, auditable recommendations for filesystem permissions on sensitive system files (such as `/etc/shadow`, `/etc/passwd`, and cron directories). Published and regularly updated by the Center for Internet Security (cisecurity.org); automated compliance scanning tools such as OpenSCAP and Lynis check systems against CIS Benchmark controls directly. apply standardized, auditable permission baselines to critical system files, for example, mandating that /etc/shadow (which stores hashed user passwords) never be readable by any account other than root, and that /etc/passwd remain world-readable but never world-writable, since many legacy utilities depend on being able to read it for username lookups.

Filesystem Defense Is a Stack, Not a Command Securing an application's filesystem footprint is never a single command. The layers, in the order they should be applied: (1) Identity: dedicated unprivileged service accounts, never root, for every daemon; (2) Base permissions: least-privilege rwx bits (typically 750/640 patterns) set correctly at deployment and verified, not left at 777; (3) Special bits: setgid for shared collaborative inheritance, sticky bit for shared writable directories, setuid audited and minimized; (4) Granular control: POSIX ACLs for exceptions the base model cannot express; (5) Continuous audit: automated scans (CIS Benchmark tooling, `find -perm` sweeps) to catch drift over time. Expect scenario questions that require naming which layer failed.

Self-Check Review Questions

Question 1: A file has the mode rwxr-xr-- and belongs to owner "bob" and group "devteam." Convert this to octal notation, and explain what happens if a user who is neither bob nor a member of devteam attempts to execute this file.

Breaking the permission string into its three triads: owner = rwx (4+2+1 = 7), group = r-x (4+0+1 = 5), other = r-- (4+0+0 = 4). The resulting octal mode is 754. Because the "other" class carries only read permission with no execute bit set, a user who is neither the owner nor a member of the devteam group falls into the "other" class during the kernel's access check and is denied execution. The kernel would return EACCES (Permission denied) to any attempt to run the file, even though that same user could still read the file's contents, since the read bit is granted to other. This illustrates that read and execute permissions are independently evaluated per class, possessing one does not imply the other.

Question 2: Explain the difference between the setuid bit and the sticky bit, including one legitimate real-world use case and one security risk for each.

The setuid bit (octal 4000), when applied to an executable file, causes the operating system to run the program with the effective privileges of the file's owner rather than the privileges of the invoking user, regardless of who executes it. A legitimate use case is /usr/bin/passwd, which must run as root to write to the protected /etc/shadow file even when invoked by an ordinary user changing their own password. The security risk is that any exploitable flaw in a root-owned setuid binary, such as an argument injection or symlink race condition, can be leveraged by an unprivileged local user to escalate directly to root privileges, making setuid root binaries high-value privilege escalation targets that must be minimized and audited. The sticky bit (octal 1000), when applied to a directory, restricts file deletion and renaming within that directory to the file's owner, the directory's owner, or root, overriding the default rule that any account with directory write permission may delete any file inside it. The canonical legitimate use case is /tmp, which is world-writable (mode 1777) so any user or process can create temporary files, while the sticky bit prevents one user from maliciously or accidentally deleting another user's temporary files. The security risk arises primarily from its absence: a world-writable directory without the sticky bit allows any local account to delete or replace files it does not own, which can be leveraged for tampering, denial of service, or, if the directory is referenced by a privileged process such as a cron job, privilege escalation via file substitution.

Question 3: A security team discovers that a production web application runs as root and its configuration directory is mode 777. Applying the principle of least privilege, describe the specific remediation steps you would take, referencing chown, chmod, and account design.

The remediation follows a layered least-privilege redesign. First, create a dedicated, non-interactive service account (for example, via `useradd -r -s /usr/sbin/nologin svc_webapp`) so the application no longer executes as root; this account should hold no valid login shell and no direct human-usable credentials, limiting the blast radius of any future application-level compromise to only the permissions explicitly granted to this account. Second, reassign ownership of the application's configuration and executable files to a separate administrative or root-owned account distinct from the service account, using `chown -R root:svc_webapp /etc/myapp`, so that the runtime service account cannot itself modify its own configuration files even if the running process is compromised. Third, correct the permission mode from the dangerous 777 (world read/write/execute) to a least-privilege value such as 750 for directories and 640 for files, granting the owning administrative account full control, read-only access to the svc_webapp group so the running process can load its configuration, and no access whatsoever to "other." Any specific writable path the application genuinely requires (such as a log or upload directory) should be scoped narrowly and separately, ideally with the sticky bit set if shared among multiple writers, rather than granting broad write access across the entire configuration tree. Finally, this configuration should be captured in a recurring automated audit (for example, a `find -perm -0002` sweep or CIS Benchmark compliance scan) to detect any future drift back toward an overly permissive state.

1. A5.2.D

Permission evaluation stops at the first class that matches. Alice is the owner, so only rw- is consulted and her membership in finance is never examined. B and D both assume the triplets combine or that the most restrictive wins; neither is how the check works, and D describes the classic chmod 077 trap in which an owner locks themselves out precisely because the owner triplet is the only one consulted. C adds an execute bit that is not set; ownership permits Alice to chmod the file, but it does not grant her a permission the mode withholds.

2. B5.2.D

The umask is a per-process property inherited from the parent, so the mask that matters is the daemon's, and for a service-manager-launched daemon that is set in the unit file. With UMask=077 the requested 666 becomes 600. A confuses a directory's own mode with the mode of files created inside it; the two are unrelated. C sets the mask for interactive login shells, a process tree the daemon never belongs to. D misstates setgid on a directory, which causes new entries to inherit the directory's group and has no effect on the permission bits.

3. B5.2.A

Full-disk encryption protects data at rest, meaning a volume that is not mounted and unlocked. On a running server the kernel decrypts transparently on every read, so a process with filesystem access sees plaintext regardless. This is why the state a data item occupies determines which control is even relevant, and why access control is not made redundant by encryption. A describes the state the volume is not in. C confuses at-rest with in-transit protection, which is TLS's job. D inverts the lesson: because encryption is inert while the volume is unlocked, permissions are the control actually carrying the load.

4. D5.2.C

The requirement conditions on a subject attribute (care-team assignment), an object attribute (which patient the record belongs to), and two environment attributes (device posture and time of day), and the care-team relation changes constantly. That is the ABAC pattern described in NIST SP 800-162. C fails on the relational condition: a "clinician" role either can read records or cannot, and manufacturing a role per patient is the role-explosion problem ABAC exists to avoid. A puts a regulated disclosure decision in the hands of whoever owns the object, which no health-records regime permits. B could encode sensitivity levels but not a relationship that changes with each shift's assignments, and MAC labels are administered too slowly for it.

5. A5.2.B

The described condition is privilege accumulation, sometimes called permission creep, and it arises because role changes reliably add access while nothing systematically removes it. Access review is the control that periodically forces an owner to re-justify each entitlement. B addresses user behavior, not the entitlement set. C hardens authentication while leaving the excess authorization untouched, the employee's credentials were never the problem. D protects data at rest against device loss and does nothing about an account legitimately authenticating and then reading more than it should.

6. B5.2.D

The leading 1 in 1777 is the sticky bit. On a directory it overrides the usual rule that write permission on a directory allows removing any entry, restricting unlink and rename to the file's owner, the directory's owner, and root. This is why /tmp is mode 1777. A states the rule that would apply if the sticky bit were absent. C confuses the file's contents with the directory's entry list; deletion is an operation on the directory, not on the file, which is why unreadable files are deletable at all. D misassigns the special bits, setuid is 4, setgid 2, sticky 1, and setuid on a directory is meaningless on Linux.

setfacl -d -m g:auditors:r /srv/app/data
setfacl -d -m o::--- /srv/app/data
The first two establish base ownership and remove all access from other. The third grants the audit group read and search on the directory itself; x is required or the group cannot traverse into it. The fourth and fifth set the default ACL, which is inherited by files created later, without it the ACL protects the directory and not its future contents, which is the most common way this configuration is got wrong. getfacl /srv/app/data confirms the result, and ls -l will now show a trailing + on the mode string, signalling that the nine bits are no longer the whole picture. Note also that the ACL mask can silently reduce granted rights, so the getfacl output should be read for an #effective: annotation. Model attribution: ownership, mode bits, and POSIX ACLs are all discretionary access control, the owner may change any of them, so the arrangement is only as strong as the policy and change management that keep it in place. Making the restriction non-discretionary would require a mandatory layer such as an SELinux type enforcement rule; and the decision that "auditors read, application writes" is itself role-based, implemented here by mapping roles onto Unix groups. Grader look-fors: correct diagnosis that three subjects exceed what the base model encodes; correct setfacl syntax; inclusion of a default ACL for inheritance; x on the directory for traversal; identification of the base model as DAC and the group design as RBAC.
