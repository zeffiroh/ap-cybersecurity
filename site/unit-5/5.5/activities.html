5.5 Activities

Secure Web Application Design · 3

Skill 5.5.a · pairs · 20 min · Offline: yes

Input validation and sanitization

Goal

Pairs design an allowlist rule for a given form field and stress-test each other's rule with adversarial inputs, discovering why allowlists beat denylists. Ties to LO 5.5.A.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair is assigned one field type (phone number, product SKU, discount code, display name). They write a plain-English allowlist rule describing exactly what a valid value looks like.
  2. Pairs swap rules with a neighboring pair, who tries to construct three inputs: one clearly valid, one clearly invalid, and one adversarial value that a lazy denylist might miss but a correct allowlist would still reject (e.g. an encoded traversal sequence, a SQL meta-character hidden in a plausible-looking string).
  3. The original pair checks their rule against all three inputs and fixes any gap the adversarial input exposed.

Collaborate

Assign roles: a "rule author" drafts the allowlist, an "attacker" tries to break it with adversarial input, and both negotiate the final rule together, documenting why each edge case was handled the way it was.

Exit Ticket

AP

Certificate of Completion

Each pair submits: their field type, final allowlist rule, and the one adversarial input that most improved the rule.

Skill 5.5.b · small group (3-4) · 25 min · Offline: yes

Secure coding practices

Goal

Groups perform a mini code review on a printed set of snippets, flagging every secure-coding violation and proposing the one-line fix for each. Ties to LO 5.5.A, 5.5.B.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each group works through the the simulation review queue (or a printed handout of the same snippets), marking each PASS or FLAG.
  2. For every FLAG, the group writes the one-line fix (e.g. "switch to a parameterized query", "load the key from an environment variable", "run as a non-root service account").
  3. Groups then pick their own two-line code/config snippet (from a past project, a textbook example, or invented) and challenge another group to find the violation.

Collaborate

Assign roles: a "reviewer" flags violations, a "fixer" proposes the one-line remediation, and a "referee" checks the fix actually addresses the root cause (not just silences the symptom). Rotate roles partway through.

Exit Ticket

AP

Certificate of Completion

Each group submits: the snippet they wrote for the challenge round, its violation (if any), and the fix.

Skill 5.5.c · small group (3-4) · 25 min · Offline: yes

Application security testing (SAST/DAST)

Goal

Groups triage a mixed batch of security findings, sort each into SAST-catchable, DAST-catchable, or human-pentest-only, and justify the sort. Ties to LO 5.5.B, 5.5.C.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each group receives (or works through in the simulation) a shuffled set of findings: some are source-code snippets, some are live-scan results, some are business-logic descriptions.
  2. Groups sort each finding into three piles: SAST, DAST, NEITHER (human pentest needed), and for each finding write one sentence explaining the sorting rule they applied (does it require a running app? does it require reasoning about intent/business rules?).
  3. Groups then design a one-line CI/CD pipeline order (e.g. "SAST on every commit -> DAST against staging before release -> periodic manual pentest") and justify why that order minimizes wasted effort.

Collaborate

Assign roles: a "static reviewer" argues the SAST case for ambiguous findings, a "dynamic tester" argues the DAST case, and a "pentester" argues for findings that need human judgment. Debate any finding the group disagrees on before recording a final answer.

Exit Ticket

AP

Certificate of Completion

Each group submits: the one finding they debated most, their final classification, and the one-sentence rule that settled it.
