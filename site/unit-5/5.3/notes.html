I. Encryption and Hashing Solve Different Problems

Two mathematical operations sit at the foundation of nearly every data-protection control taught in this course: symmetric encryptionSymmetric EncryptionEncryption where the same secret key both locks (encrypts) and unlocks (decrypts) the data, like a single physical key that both locks and unlocks your front door. Both the sender and receiver must possess an identical copy of the key. Contrast with asymmetric (public-key) cryptography, covered in Topic 5.4. Symmetric algorithms are computationally far cheaper, which is why they protect bulk data while asymmetric algorithms protect key exchange. and cryptographic hashingCryptographic HashingA one-way mathematical function that converts data of any size into a fixed-length "fingerprint." Unlike encryption, hashing has no key and cannot be reversed, you cannot recover the original input from the hash output. Hash functions must exhibit preimage resistance, second-preimage resistance, and collision resistance. See FIPS PUB 180-4.. Although students frequently conflate the two, they solve fundamentally different problems, and confusing them is one of the most consequential errors a security practitioner can make. Encryption is a reversible transformationReversible TransformationA mathematical operation that can be undone. Encryption is reversible because anyone holding the correct key can run the inverse operation (decryption) to recover the exact original plaintext. Formally: for encryption function E and decryption function D under key k, D(k, E(k, m)) = m for all messages m.: ciphertext produced by an encryption algorithmEncryption AlgorithmA precisely defined mathematical procedure for transforming readable plaintext into unreadable ciphertext using a key, and for reversing that transformation given the same (symmetric) or a mathematically related (asymmetric) key. NIST validates implementations through the Cryptographic Algorithm Validation Program (CAVP) and the Cryptographic Module Validation Program (CMVP), referenced in FIPS 140-3. can always be converted back into the original plaintext, provided the correct key is supplied. Hashing, by contrast, is deliberately one-wayOne-Way FunctionA function that is computationally easy to calculate in one direction but computationally infeasible to reverse. Given a hash output, there is no efficient algorithm to compute an input that produces it, you would have to guess inputs and hash each one (brute force). The security of one-way functions underpins hash-based password storage, digital signatures, and blockchain proof-of-work systems.: there is no decryption operation for a hash digest, no key that "unlocks" it, and no legitimate way to recover the original input except by guessing inputs and re-hashing them until a match is found. This single distinction, reversible versus irreversible, determines which tool is appropriate for which job. If data must later be read back in its original form (a customer's credit card number, a hard drive's contents, a database column), it must be encrypted. If data only ever needs to be verified rather than recovered (a password, a downloaded file's integrity), it should be hashed, never encrypted.

The academic study of symmetric cryptography traces to Claude Shannon'sClaude ShannonAn American mathematician and electrical engineer widely regarded as the father of information theory. His 1949 paper "Communication Theory of Secrecy Systems" established the mathematical framework that all modern symmetric ciphers are still evaluated against. Shannon, C.E. (1949). Communication Theory of Secrecy Systems. Bell System Technical Journal, 28(4), 656–715. foundational 1949 paper, which formalized two design properties every strong cipher must exhibit: confusionConfusion (Shannon Property)The property that the relationship between the encryption key and the ciphertext should be as complex and non-linear as possible, so that an attacker cannot deduce the key by studying the ciphertext's statistical patterns. Implemented in AES via substitution boxes (S-boxes). Shannon (1949). Confusion obscures the key-ciphertext relationship; diffusion (below) spreads plaintext influence across the ciphertext. and diffusionDiffusion (Shannon Property)The property that changing a single bit of plaintext should statistically change roughly half the bits of the resulting ciphertext, so that patterns in the plaintext are not visible in the output. Implemented in AES via the ShiftRows and MixColumns steps. Also called the "avalanche effect." A well-diffused cipher makes differential cryptanalysis computationally infeasible.. Confusion ensures that the mathematical relationship between key and ciphertext is so complex that it cannot be reduced to simple algebra; diffusion ensures that flipping a single bit of the input plaintext cascades into changes across roughly half of the output ciphertext bits, the so-called avalanche effectAvalanche EffectA desirable property of both ciphers and hash functions: a tiny change to the input (even one bit) should produce a drastically different, unpredictable output. Named because a small trigger (one bit) causes an "avalanche" of change throughout the output. A well-designed avalanche effect means roughly 50% of output bits flip on average for any single input bit flip, this is empirically tested during algorithm validation.. These two properties remain the benchmark against which the Advanced Encryption Standard (AES)AES, Advanced Encryption StandardThe U.S. government's official symmetric block cipher standard, selected in 2001 through an open, multi-year public competition. AES replaced the aging DES (Data Encryption Standard). It is the cipher used to protect classified information, banking transactions, VPN tunnels, and disk encryption worldwide. Originally submitted as "Rijndael" by Belgian cryptographers Joan Daemen and Vincent Rijmen. Standardized in FIPS PUB 197 (2001). Supports 128-, 192-, and 256-bit keys. and its predecessor, the Data Encryption Standard (DES)DES, Data Encryption StandardA symmetric block cipher standardized by NIST in 1977, using a 56-bit effective key length. Once the U.S. government standard, DES is now considered cryptographically broken due to its short key, a dedicated brute-force machine (the EFF's "Deep Crack," 1998) could exhaust the entire keyspace in under 24 hours. Superseded by AES in 2001 (FIPS 197). Triple DES (3DES) extended its life by applying DES three times, but NIST deprecated 3DES entirely by the end of 2023 per SP 800-131A., are evaluated.

One Key That Both Locks and Unlocks Think of encryption as a reversible safe: you put a document inside, lock it with a key, and anyone with a copy of the key can open it back up and read the document again. Hashing is closer to running a document through a paper shredder in a mathematically consistent way, you can prove two documents were identical by comparing shredded output ("fingerprints"), but you can never reconstruct a document from its shredded remains. Every time you see "hash," ask "am I trying to verify something, or read it back?" If the answer is "read it back," hashing is the wrong tool entirely.

The 56-bit effective keyspace of DES, a design constraint imposed by NSA export-control negotiations during its 1970s standardization, illustrates why key length is not a cosmetic parameter but the primary lever of cryptographic strength. A brute-force attackBrute-Force AttackAn attack that tries every possible key (or password) until the correct one is found. The feasibility of a brute-force attack is a direct function of keyspace size: doubling the key length by just one bit doubles the number of possible keys, and therefore doubles the average time required to exhaust them. A 56-bit keyspace contains 2^56 (about 72 quadrillion) possible keys, trivial for modern ASIC/FPGA clusters. A 128-bit keyspace contains 2^128 keys, considered computationally infeasible to exhaust even with all of Earth's computing power running for longer than the age of the universe. against DES's 256 keyspace was demonstrated practically in 1998 by the Electronic Frontier Foundation's purpose-built "Deep Crack" hardware, which recovered a DES key in under 56 hours. AES, in direct response, was designed with a minimum key length of 128 bits, and offers 192-bit and 256-bit variants, placing its keyspace so far beyond brute-force reach that the primary risk to AES today is implementation error (weak key management, poor mode-of-operation choice, side-channel leakage) rather than mathematical cryptanalysis of the algorithm itself. This is precisely the vulnerability class referenced in the Hooli incident scenario later in this chapter: an audit that discovers legacy 56-bit DES keys still protecting live transaction columns is not merely a compliance footnote, it represents a cipher whose entire keyspace is trivially exhaustible by commodity hardware.

Hash functions evolved along a parallel but distinct academic track, rooted in the need for data integrityData IntegrityThe assurance that data has not been altered, corrupted, or tampered with, whether in transit, at rest, or during processing. Hash functions provide integrity verification: if even one bit of a file changes, its hash output changes completely, immediately revealing tampering. One of the three pillars of the CIA triad (Confidentiality, Integrity, Availability) central to the AP Cybersecurity curriculum. verification rather than confidentiality. The Secure Hash Algorithm (SHA) familySHA, Secure Hash Algorithm FamilyA series of cryptographic hash function standards published by NIST. SHA-1 (1995, 160-bit output) is now considered broken due to practical collision attacks. SHA-2 (2001), which includes SHA-256 and SHA-512, remains secure and is the current industry baseline. SHA-3 (2015) is a structurally different backup standard based on the Keccak sponge construction. SHA-2 is specified in FIPS PUB 180-4. SHA-3 in FIPS PUB 202., standardized by NIST, produces fixed-length digests regardless of input size, SHA-256 always outputs exactly 256 bits, whether hashing one character or an entire terabyte file. A cryptographically secure hash function must satisfy three formal properties: preimage resistancePreimage ResistanceGiven only a hash output, it should be computationally infeasible to find any input that produces that output. This is the property that makes password hash storage meaningful, an attacker who steals a database of hashes cannot mathematically reverse them back into passwords. Formally: given h, it is infeasible to find any m such that H(m) = h. This is the "first preimage" property., second-preimage resistanceSecond-Preimage ResistanceGiven a specific input and its hash, it should be computationally infeasible to find a different input that produces the identical hash. This prevents an attacker from substituting a malicious file that hashes to the same value as a legitimate one. Formally: given m1, it is infeasible to find m2 ≠ m1 such that H(m1) = H(m2)., and collision resistanceCollision ResistanceIt should be computationally infeasible to find any two distinct inputs that produce the same hash output, without being given either input in advance. Collision resistance is the strongest of the three hash properties and the first to break as an algorithm ages, SHA-1 lost collision resistance in 2017 (the "SHAttered" attack by Google and CWI Amsterdam), which is why it is deprecated for security-critical use. Formally: it is infeasible to find any m1 ≠ m2 such that H(m1) = H(m2). By the birthday paradox, collision resistance for an n-bit hash is bounded at roughly 2^(n/2) operations.. When any of these properties fails, as happened to both MD5 and SHA-1, the algorithm is formally deprecated by standards bodies, even though it may remain "usable" in a purely mechanical sense.

A related but distinct family of primitives, key derivation functions (KDFs)Key Derivation Function (KDF)A specialized function that transforms a low-entropy input (like a human-chosen password) into a cryptographically strong key or hash, deliberately designed to be slow and resource-intensive so that brute-force guessing is expensive for an attacker. Unlike general-purpose hash functions (SHA-256), KDFs are intentionally engineered to be computationally and/or memory expensive. Standardized examples: PBKDF2 (NIST SP 800-132), bcrypt (Provos & Mazières, 1999), scrypt (RFC 7914), and Argon2 (winner of the 2015 Password Hashing Competition)., exists specifically to slow down attackers who are hashing password guesses at scale. A general-purpose cryptographic hash like SHA-256 is deliberately fast, a property that is excellent for verifying file integrity but catastrophic for password storage, because a fast hash lets an attacker with GPU or ASIC hardware test billions of password guesses per second. KDFs deliberately sacrifice speed (and, in the case of scrypt and Argon2, consume large amounts of RAM) to make each guess expensive, fundamentally altering the economics of an offline cracking attack.

II. AES, MACs, Key Management, and Password KDFs

AES is formally classified as a block cipherBlock CipherA symmetric cipher that encrypts data in fixed-size chunks ("blocks") rather than one bit or byte at a time. AES operates on 128-bit (16-byte) blocks regardless of the chosen key size. Data longer than one block must be split into multiple blocks and processed according to a "mode of operation." Contrast with stream ciphers (e.g., ChaCha20), which encrypt data as a continuous stream of bits/bytes. AES's block size is fixed at 128 bits per FIPS 197, even though key length is variable., meaning it transforms data in fixed 128-bit chunks through a sequence of internal rounds. The number of rounds scales with key size: 10 rounds for AES-128, 12 for AES-192, and 14 for AES-256. Each round applies four transformations, SubBytes (a non-linear byte substitution via a fixed S-box, providing Shannon's confusion), ShiftRows, MixColumns (together providing diffusion), and AddRoundKey (XORing in a subkey derived from the master key via the key scheduleKey ScheduleAn algorithm that expands a single master encryption key into a series of distinct "round keys," one for each round of the cipher's internal processing. This prevents the same key material from being reused identically across every round, which would weaken the cipher against certain cryptanalytic attacks. AES's key schedule uses byte rotation, S-box substitution, and round constants (Rcon) to generate round keys, specified in FIPS 197 §5.2.). Because a block cipher only defines how to scramble one fixed-size block, it must be paired with a mode of operationMode of OperationAn algorithm that specifies how a block cipher should be repeatedly applied to encrypt data longer than a single block. Different modes have dramatically different security properties, even when using the identical underlying cipher and key. Choosing the wrong mode can completely undermine an otherwise strong cipher. NIST SP 800-38A defines confidentiality-only modes (ECB, CBC, CFB, OFB, CTR). NIST SP 800-38D defines GCM, an authenticated mode. to handle real-world messages spanning many blocks.

ECB Encrypts Every Block in Isolation, and the Picture Survives Electronic Codebook (ECB) modeECB, Electronic Codebook ModeThe simplest (and weakest) block cipher mode: each block of plaintext is encrypted independently with the same key, with no chaining between blocks. Identical plaintext blocks always produce identical ciphertext blocks. This means visual and structural patterns in the original data (famously demonstrated with the "ECB Penguin", an encrypted bitmap image where the penguin outline remains visible) leak directly into the ciphertext. NIST SP 800-38A explicitly warns against ECB for any data with repeating patterns. It is retained in the standard only for narrow, non-recommended use cases. fails in a way that is easy to state and easy to see: encrypting the same plaintext block twice under ECB produces identical ciphertext both times, leaking structural information about the underlying data even though the cipher itself (AES) is mathematically strong. This is why the encrypted "ECB Penguin" image still shows a recognizable penguin silhouette. The lesson: a strong cipher used in a weak mode is still a weak system. Always prefer CBC (with a random, unpredictable IV) or, better, an authenticated mode like GCM.

Cipher Block Chaining (CBC) modeCBC, Cipher Block Chaining ModeA block cipher mode where each plaintext block is XORed with the previous ciphertext block before encryption, "chaining" all blocks together so that identical plaintext blocks produce different ciphertext. The first block is XORed with a random Initialization Vector (IV) instead of a previous ciphertext block. Defined in NIST SP 800-38A. Requires a unique, unpredictable IV per encryption operation, IV reuse under the same key catastrophically weakens confidentiality. CBC provides confidentiality only, not integrity, it must be paired with a separate MAC (Encrypt-then-MAC) to detect tampering. solves the ECB pattern-leakage problem by chaining blocks together via XOR with the previous ciphertext block, requiring a random Initialization Vector (IV)Initialization Vector (IV)A random or unique value used to "seed" the first block of a chaining or counter-based cipher mode, ensuring that encrypting the same plaintext twice under the same key produces different ciphertext each time. The IV does not need to be secret, but it must be unpredictable (CBC) or unique/never reused (CTR, GCM) for every encryption operation under a given key. NIST SP 800-38A §6.1: IVs for CBC must be unpredictable; reuse of an IV/key pair is a critical cryptographic failure. to seed the first block. Crucially, CBC alone provides confidentiality but not authenticated integrityAuthenticated EncryptionAn encryption mode that simultaneously guarantees confidentiality (the data cannot be read without the key) and integrity/authenticity (any tampering with the ciphertext is detected and decryption fails). Modern best practice mandates authenticated encryption for nearly all use cases. Also called AEAD (Authenticated Encryption with Associated Data). GCM and ChaCha20-Poly1305 are the two dominant AEAD constructions in modern protocols like TLS 1.3., a ciphertext can be bit-flipped by an attacker without a key, and CBC alone will not detect the tampering. Galois/Counter Mode (GCM)GCM, Galois/Counter ModeA modern block cipher mode that combines CTR-mode encryption (turning the block cipher into an efficient stream cipher) with a Galois field authentication tag (GMAC), producing both ciphertext and a cryptographic authentication tag in a single pass. Decryption fails loudly if the ciphertext or associated data has been tampered with. Standardized in NIST SP 800-38D. AES-GCM is the default cipher suite in TLS 1.3 and is required in FIPS 140-3 validated modules for authenticated encryption use cases. resolves this by producing an authentication tag alongside the ciphertext in a single efficient pass, making it the modern default for protocols like TLS 1.3 and disk-encryption systems that need both secrecy and tamper-evidence.

Encrypting a file with OpenSSL's AES-256 implementation in CBC mode from the command line illustrates the practical parameters every implementation must supply: a key (or a passphrase from which a key is derived), an IV, and the target mode.

bash 
# Encrypt a file using AES-256 in CBC mode with a PBKDF2-derived key
openssl enc -aes-256-cbc -pbkdf2 -iter 600000 -salt \
  -in transaction_export.csv \
  -out transaction_export.csv.enc \
  -pass pass:'CorrectHorseBatteryStaple!2026'

# Decrypt the resulting file (must supply the identical passphrase)
openssl enc -d -aes-256-cbc -pbkdf2 -iter 600000 \
  -in transaction_export.csv.enc \
  -out transaction_export_recovered.csv \
  -pass pass:'CorrectHorseBatteryStaple!2026'

# Preferred: authenticated AES-256-GCM (detects any tampering on decrypt)
openssl enc -aes-256-gcm -pbkdf2 -iter 600000 -salt \
  -in transaction_export.csv -out transaction_export.csv.gcm.enc \
  -pass pass:'CorrectHorseBatteryStaple!2026'

Note the -pbkdf2 -iter 600000 flags: OpenSSL does not use the raw passphrase directly as an AES key. Instead it runs the passphrase through PBKDF2 (discussed below) with 600,000 iterations to derive a proper 256-bit key, deliberately slowing down any attacker who steals the ciphertext and attempts to brute-force the passphrase offline.

Three Transformations That Are Constantly Confused

Before any of the mechanics, one distinction has to be firm, because misusing these three words causes real defects. Encoding is a reversible change of representation with no secret involved: Base64, URL percent-encoding, and hexadecimal exist so that arbitrary bytes can survive a channel that only accepts certain characters. Anyone can decode them; they provide no confidentiality whatever, and a system that stores "Base64-encrypted" passwords stores plaintext with an extra step. Hashing is a deterministic one-way compression to a fixed length. There is no key and no inverse; the same input always yields the same digest, and the value of the operation is precisely that it cannot be undone. Encryption is a reversible transformation controlled by a key: with the key you recover the plaintext exactly, and without it you should learn nothing.

The practical consequence is that each answers a different question. Encoding answers "will this byte string survive transport?" Hashing answers "is this the same data I saw before?" Encryption answers "can an adversary who holds these bytes read them?" Choosing the wrong one is a category error, not a tuning mistake: hashing a credit card number makes it unusable for the business, and encrypting a password for storage means a key exists somewhere that turns the whole database back into plaintext.

Initialization Vectors and Nonces

Every mode other than ECB needs a per-message value that makes the encryption of identical plaintexts differ. The rules governing that value are strict and mode-specific, and violating them is the single most common way an otherwise sound implementation fails.

An initialization vectorIV, Initialization VectorA block-sized value combined with the first block of plaintext so that encrypting the same message twice under the same key produces different ciphertext. For CBC it must be unpredictable to an adversary; it is not secret and is normally stored alongside the ciphertext. for CBC mode must be unpredictable, not merely unique. This is not pedantry: the BEAST attack against TLS 1.0 exploited exactly the fact that the IV for each record was the previous record's final ciphertext block, and therefore known to an attacker in advance. Generate it with a cryptographically secure random source, Python's secrets or os.urandom, never random, and store it with the ciphertext. It is not a secret and does not need protecting; it needs only to be fresh and unguessable.

A nonceNonceA number used once. For counter-based modes such as CTR and GCM the requirement is uniqueness per key, not unpredictability; repeating one under the same key is catastrophic. for a counter-based mode such as CTR or GCM has a different and harsher requirement: it must never repeat under the same key. Counter modes work by encrypting a counter block to produce a keystream that is XORed with the plaintext. If a nonce repeats, two messages are XORed with the identical keystream, and an adversary who XORs the two ciphertexts together obtains the XOR of the two plaintexts, the key has dropped out of the equation entirely. For GCM the consequence is worse still, because nonce reuse also permits recovery of the authentication subkey and thus lets an attacker forge tags. With GCM's 96-bit nonce, random generation is safe for an enormous number of messages under one key; with a 64-bit nonce it is not, and a counter maintained in durable storage is the correct approach.

MACs, HMAC, and Why Length Extension Matters

A hash tells you whether data changed; it does not tell you who changed it. An attacker who alters a file can simply recompute its SHA-256 digest. Detecting deliberate modification requires a secret, and that is what a message authentication codeMAC, Message Authentication CodeA short tag computed from a message and a secret key, which anyone holding the key can recompute to verify that the message is unmodified and originated from a key holder. Unlike a digital signature, a MAC is symmetric: the verifier can also forge, so a MAC proves nothing to a third party. provides.

The naive construction, tag = SHA256(key || message), is broken, and the reason is instructive. SHA-256, SHA-1, and MD5 use the Merkle–Damgård construction, in which the digest is the algorithm's entire internal state after the final block. An attacker who knows the digest therefore knows the state, and can resume hashing from it. Without ever learning the key, they can append data and compute a valid tag for key || message || padding || extra. This is a length extension attackLength Extension AttackAgainst a Merkle–Damgård hash, an attacker who knows H(secret || message) and the length of the secret can compute H(secret || message || padding || suffix) for a suffix of their choosing, without knowing the secret. SHA-3 and BLAKE2 are not vulnerable, having different internal structures., and it is not theoretical, the 2009 Flickr API signature forgery is a documented case.

HMACHMACA MAC construction defined in RFC 2104 and FIPS 198-1 that nests two hash invocations with two key-derived pads, so that the attacker never sees the internal state of a hash whose input begins with the key. Provably secure given modest assumptions about the underlying hash, and immune to length extension by construction. fixes this by nesting: HMAC(K, m) = H((K ⊕ opad) || H((K ⊕ ipad) || m)). Because the outer hash consumes the inner digest rather than exposing it as the final output, an attacker never obtains a state they can extend from. Two practical notes follow. First, use the library's HMAC rather than composing hashes yourself. Second, always compare tags with a constant-time comparison, Python's hmac.compare_digest, because an ordinary == returns as soon as it finds a differing byte, and the timing difference is enough to let an attacker recover a valid tag one byte at a time.

Python 3, authenticated symmetric encryption with AES-GCM 
import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# 256-bit key from the operating system CSPRNG. In production this comes from a
# key management service or an HSM, never from a literal in source control.
key = AESGCM.generate_key(bit_length=256)
aead = AESGCM(key)

# 96-bit nonce, fresh for every single message under this key.
nonce = os.urandom(12)

plaintext = b"account 4187 balance 92310"
# Associated data is authenticated but not encrypted: it is bound to the
# ciphertext, so an attacker cannot move this record to another account.
aad = b"record-type=ledger;version=2"

ciphertext = aead.encrypt(nonce, plaintext, aad)   # tag is appended to ciphertext
recovered = aead.decrypt(nonce, ciphertext, aad)   # raises InvalidTag if altered
assert recovered == plaintext

The decisive property of this code is the exception. decrypt raises InvalidTag rather than returning corrupted plaintext, because GCM verifies the authentication tag before releasing any output. A CBC-mode implementation without a separate MAC has no such check: it will decrypt attacker-modified ciphertext into attacker-influenced plaintext and hand it to the application, which is the family of padding-oracle and bit-flipping attacks. This is why modern guidance is to use an authenticated mode by default and to treat unauthenticated encryption as a specialist tool requiring justification.

Key Management and Envelope Encryption

Cryptography converts the problem of protecting a large amount of data into the problem of protecting a small key. It does not make the problem disappear, and in most breaches involving encrypted data the cipher was fine and the key handling was not. A key that sits in the application's source repository, in a container image layer, or in an environment variable dumped into a crash report protects nothing.

Envelope encryptionEnvelope EncryptionData is encrypted with a freshly generated data encryption key (DEK); the DEK is then encrypted with a long-lived key encryption key (KEK) held in an HSM or key management service, and the wrapped DEK is stored beside the ciphertext. The pattern used by every major cloud key management service. is the standard structure for handling this at scale. A fresh data encryption key is generated per file, per record, or per tenant, and used to encrypt the data. That DEK is then encrypted, wrapped, under a long-lived key encryption key that never leaves a hardware security module or managed key service. The wrapped DEK is stored next to the ciphertext it belongs to. Three benefits follow directly from the shape. The high-value KEK exists only inside hardware that will perform operations with it but will not export it. Rotating the KEK requires re-wrapping a small set of DEKs rather than re-encrypting terabytes. And revocation becomes tractable: destroy the KEK and every DEK wrapped under it becomes unrecoverable, which is how "cryptographic erasure" of a tenant's data is implemented without physically overwriting it.

Hash Verification and File Integrity

Whereas encryption protects confidentiality, hash-based checksumsChecksumA value computed from a file's contents (typically via a hash function) used to verify the file has not been altered or corrupted, whether by malicious tampering or accidental transmission errors. Comparing the checksum published by a software vendor against a locally recomputed checksum confirms the downloaded file is bit-for-bit identical to what the vendor released. Modern checksums use cryptographic hash functions (SHA-256) rather than older non-cryptographic checksums (CRC32), because CRC32 is trivially forgeable and was never designed to resist intentional tampering. verify integrity. Software distributors publish SHA-256 digests of official release files precisely so that a downloader can independently confirm the file was not corrupted in transit or maliciously substituted by an attacker positioned between the vendor and the user.

bash 
# Compute the SHA-256 digest of a downloaded installer
sha256sum ubuntu-24.04-desktop-amd64.iso
# Output: a1b2c3...e9f0  ubuntu-24.04-desktop-amd64.iso

# Compare against the vendor-published checksum file
sha256sum -c SHA256SUMS
# Output: ubuntu-24.04-desktop-amd64.iso: OK

# Verify an individual file matches a known-good hash without a .sums file
echo "a1b2c3...e9f0  ubuntu-24.04-desktop-amd64.iso" | sha256sum -c -
A Hash Is Not a Cipher, and the Difference Is Reversibility A system that stores "encrypted passwords" has, by that description alone, a design defect, and the defect does not depend on which cipher was chosen. Encryption is reversible by design, so a key exists that turns the entire credential store back into plaintext, and that key must be present on a live server for the system to function. Passwords should be put through a salted, deliberately slow key derivation function instead, which is irreversible and therefore has nothing for an attacker to steal but the hashes themselves. The clearest tell is an offer to email a forgotten password back to the user: an application that can recover the original string is one whose credential database is a decryption key away from being read in full.

Salting and Rainbow Table Defense

Because a given input always produces the identical hash output under a deterministic hash function, an attacker can precompute hashes for millions of common passwords once and reuse that table against any stolen password database, an attack accelerated dramatically by rainbow tablesRainbow TableA precomputed table mapping hash outputs back to their likely plaintext inputs, built once and reused against any number of victim databases. Rainbow tables use a space-time tradeoff (chains of hash-and-reduce operations) to store far more coverage than a naive full lookup table would require in the same disk space. Introduced by Philippe Oechslin (2003), building on Hellman's 1980 time-memory tradeoff. Rainbow tables for unsalted MD5 and SHA-1 covering billions of common passwords are freely available online., which trade storage space for lookup speed using precomputed hash chains. SaltingSalt (Cryptographic)A unique, random value generated for each individual password and stored alongside its hash (not secret), then combined with the password before hashing. import hashlib
import os

def hash_password(password: str) -> tuple[bytes, bytes]:
    """Generate a unique salt and derive a slow, salted hash via PBKDF2-HMAC-SHA256."""
    salt = os.urandom(16)                      # 128-bit random salt, unique per user
    derived_key = hashlib.pbkdf2_hmac(
        "sha256",
        password.encode("utf-8"),
        salt,
        600_000,                                # iteration count per NIST SP 800-63B guidance
    )
    return salt, derived_key

def verify_password(password: str, salt: bytes, stored_key: bytes) -> bool:
    """Re-derive the hash with the stored salt and compare in constant time."""
    candidate = hashlib.pbkdf2_hmac("sha256", password.encode("utf-8"), salt, 600_000)
    return hashlib.compare_digest(candidate, stored_key)   # timing-safe comparison

III. Case Studies: LinkedIn and Ransomware

Case Study 5.3.1: The 2012 LinkedIn Breach, Unsalted SHA-1 at Scale

In June 2012, LinkedIn disclosed that approximately 6.5 million hashed passwords had been posted to a Russian hacking forum; subsequent investigation in 2016 revealed the true scope was closer to 167 million accounts. The root architectural failure was twofold, and both failures map directly onto the concepts introduced in this chapter. First, LinkedIn hashed passwords using bare SHA-1SHA-1A 160-bit cryptographic hash function standardized by NIST in 1995. SHA-1 was formally deprecated for security-critical use starting in 2011 (NIST SP 800-131A) and its collision resistance was practically broken in 2017 by Google and CWI Amsterdam's "SHAttered" attack, which produced two distinct PDF files with an identical SHA-1 hash. FIPS 180-4 retains SHA-1 definition for legacy compatibility only; NIST formally disallows SHA-1 for digital signatures and TLS certificates as of 2016., a general-purpose, deliberately fast hash function never designed for password storage, rather than a slow, purpose-built KDF. Second, and more critically, the hashes were unsaltedUnsalted HashA password hash computed without a unique, per-user random salt value, meaning identical passwords across different user accounts always produce byte-for-byte identical hash outputs. This allows a single precomputed rainbow table to be reused against an entire stolen database simultaneously, rather than requiring per-user computation. The absence of salting was the single largest architectural failure in the LinkedIn 2012 breach, it converted what should have been 167 million independent cracking problems into effectively one shared problem., meaning every account sharing the same password (a statistically enormous population, given how few unique passwords humans tend to choose) produced an identical hash value. Within days, security researchers and criminal groups alike had cracked the overwhelming majority of the dataset using off-the-shelf GPU rigs running standard dictionary and rainbow-table attacks, because a fast, unsalted SHA-1 hash offers essentially no meaningful resistance once an attacker has offline access to the database. LinkedIn's subsequent remediation, migrating to salted bcrypt hashing, is now the textbook example cited in nearly every password-storage postmortem.

Why a Leaked Hash File Keeps Causing Breaches at Other Companies The LinkedIn breach illustrates a property unique to hash leaks that differs from most other data breaches: because passwords are frequently reused across services, the damage from a cracked hash dataset extends far beyond the breached company itself. Years after the 2012 incident, cracked LinkedIn credentials were still being fed into credential stuffingCredential StuffingAn automated attack that takes username/password pairs leaked from one breach and tries them against many other unrelated websites, exploiting the fact that a large percentage of users reuse the same password across multiple services. OWASP classifies credential stuffing as a top-10 automated threat (OAT-008). Defended against primarily via MFA and unique-password enforcement, not password complexity rules alone. attacks against banking, retail, and email providers that had nothing to do with LinkedIn's original breach. This is precisely why salting and slow KDFs matter even for "low value" accounts: a weak hash anywhere becomes leverage everywhere.

Case Study 5.3.2: Ransomware's Deliberate Misuse of Symmetric Encryption

Modern ransomwareRansomwareMalware that encrypts a victim's files and demands payment (typically cryptocurrency) in exchange for the decryption key. Ransomware is one of the only widespread, real-world offensive uses of strong, correctly implemented symmetric cryptography, the attacker exploits the fact that AES is mathematically unbreakable to make file recovery genuinely impossible without their cooperation. MITRE ATT&CK T1486 (Data Encrypted for Impact). Major families include LockBit, Conti, and REvil/Sodinokibi. families such as LockBit and Conti represent a direct, adversarial application of exactly the cryptography this chapter teaches defensively. Rather than exploiting a weakness in AES, these campaigns exploit AES's very strength: they generate a random AES-256 session key per victim, use it to rapidly encrypt the victim's files (often in CBC or CTR mode for speed across large file volumes), and then encrypt that single AES session key itself with an attacker-held asymmetric public key before deleting the original from memory. This hybrid design, symmetric encryption for bulk speed, asymmetric encryption to protect the one small symmetric key, means that without the attacker's private key, file recovery is not merely difficult but mathematically infeasible; there is no flaw in AES-256 itself for defenders or law enforcement to exploit. The only realistic mitigations are preventative: offline, immutable backups (so encrypted files can simply be restored rather than decrypted) and blocking the initial access vector before encryption ever begins, since the cryptography itself, once correctly executed by the attacker, offers no exploitable weakness.

Ransomware Uses the Same AES You Do, Correctly Students sometimes assume that "strong encryption" is inherently a defensive good. Ransomware is the clearest counterexample in the entire curriculum: the same AES-256 that protects a hospital's patient records can just as easily be weaponized by the attacker who has already gained write access to those records. This reframes the real lesson of this chapter, the cryptographic algorithm is rarely the weak point. Key management, access control, and backup strategy are what actually determine whether encryption protects you or is turned against you.

IV. HSMs, Key Rotation, and Password Storage

Correctly selecting AES-256 and a salted, memory-hard KDF solves only half of the problem taught in this topic, the algorithms in isolation are only as strong as the practices surrounding key managementKey ManagementThe full lifecycle of cryptographic keys: secure generation, distribution, storage, rotation, and eventual destruction. Industry breach postmortems consistently show that key management failures, not algorithm weaknesses, are the dominant root cause of cryptographic incidents. NIST SP 800-57 Part 1 provides the authoritative framework for key management lifecycle recommendations, including key length and rotation guidance by algorithm and use case. the key itself. An organization's transaction columns can be protected with a mathematically flawless AES-256 cipher and still be catastrophically insecure if the encryption key sits in an application configuration file, a source code repository, or an environment variable readable by any process on the host. This is the exact failure mode implied by the Hooli scenario's remediation guidance: deploying "AES-256 symmetric keys and HSM storage" is presented as a single control precisely because the algorithm and its storage location are inseparable in practice.

1. Hardware Security Modules (HSMs)

A Hardware Security Module (HSM)HSM, Hardware Security ModuleA dedicated, tamper-resistant physical device (or cloud-hosted equivalent) purpose-built to generate, store, and use cryptographic keys without ever exposing the raw key material outside the device's protected boundary. Applications send data to the HSM to be encrypted or signed; the HSM performs the operation internally and returns only the result, the key itself never leaves. Validated against FIPS 140-3 (or the older FIPS 140-2) at defined security levels. Physical tampering (drilling, probing, extreme temperature) triggers automatic key zeroization. is a physically hardened appliance, or, increasingly, a cloud-hosted equivalent such as a Key Management Service (KMS)Key Management Service (KMS)A cloud provider's managed service for creating, storing, rotating, and controlling access to encryption keys, typically backed by FIPS 140-2/140-3 validated HSMs under the hood. Applications call the KMS API to encrypt/decrypt data or request a key, rather than handling raw key material directly. Examples: AWS KMS, Azure Key Vault, Google Cloud KMS. All provide audit logging of every key-use event, satisfying compliance requirements for demonstrable key access control., designed so that raw key material is generated inside the device and never exported in plaintext form, even to administrators. Applications request cryptographic operations (encrypt, decrypt, sign) from the HSM rather than retrieving the key itself, so a compromised application server never actually possesses the key that protects its data. This design directly defeats the class of attack implied by "cryptographic audit sweeps" scanning for weak keys sitting exposed in application schemas.

2. Key Rotation and Lifecycle Management

NIST SP 800-57 recommends a defined cryptoperiodCryptoperiodThe defined span of time during which a specific cryptographic key is authorized for use before it must be retired and replaced with a new key. Limiting a key's lifetime bounds the damage of an eventual compromise (only data protected during that window is at risk) and limits the amount of ciphertext an attacker can collect under a single key for cryptanalysis. NIST SP 800-57 Part 1 Rev. 5 provides recommended cryptoperiod tables by key type and use case (e.g., symmetric data-encryption keys typically 1–2 years). for every symmetric key, after which it must be rotated. Automated key rotation, enforced by the HSM or KMS rather than a manual process, ensures that a single compromised key exposes only a bounded window of historical data rather than an organization's entire data history.

3. Layered Password Storage Hardening

  • Hash with a memory-hard KDF (Argon2id preferred; bcrypt or PBKDF2-HMAC-SHA256 with 600,000+ iterations as acceptable alternatives).
  • Generate a unique, cryptographically random salt per credential, never a shared or hardcoded salt.
  • Store salt and hash together (the salt is not secret), but never store or log the plaintext password at any point in the pipeline.
  • Enforce mandatory multi-factor authentication so a cracked hash alone is insufficient for account takeover.
The Order in Which Symmetric Defenses Should Be Applied Hardening a system that stores sensitive transaction data is not a single decision but four, and they fail independently. Algorithm and mode comes first: AES-256 in an authenticated mode such as GCM, never DES or 3DES, never unauthenticated ECB. Key custody is second and is the layer that is most often skipped: keys generated inside and never exported from an HSM or a managed KMS, rather than embedded in application source or a configuration file, because a key sitting beside the ciphertext it protects is decoration. Credential storage is third and is a separate problem entirely, solved by a salted memory-hard derivation function rather than by encryption, since a password never needs to be read back. Lifecycle is fourth: a defined cryptoperiod, an automated rotation path, and a destruction procedure for retired key material. An assessment that names a strong cipher and stops has addressed one layer of four, and the remaining three are where most real breaches occur.

Applied to the Hooli scenario introduced at the start of this unit: the syslog trace Crypt-Scan: Weak DES cipher key discovered in active schema on host 10.0.0.42 indicates a legacy 56-bit DES key still protecting a live transaction column. The correct remediation sequence is to isolate the affected segment, re-encrypt the underlying data under a freshly generated AES-256 key issued and held by an HSM or KMS, securely destroy the retired DES key material, and configure SOC detection rules that alert on any future cryptographic audit sweep discovering deprecated cipher suites (DES, 3DES, RC4, or unsalted MD5/SHA-1 password hashes) anywhere in the environment.

Self-Check Review Questions

Question 1: Explain the mathematical and practical distinction between encryption and hashing, and describe a real-world scenario in which confusing the two led to a security failure.

Encryption is a reversible transformation: ciphertext produced by a symmetric algorithm such as AES can always be converted back into the original plaintext given the correct key. Hashing, by contrast, is a deliberately one-way function, a cryptographic hash such as SHA-256 produces a fixed-length digest with no corresponding decryption operation; recovering the original input requires guessing candidate inputs and re-hashing them (a brute-force or dictionary/rainbow-table attack), not mathematically inverting the function itself. This distinction dictates appropriate use: data that must later be read back in its original form (a file, a database record) should be encrypted; data that only needs to be verified, never recovered (a password), should be hashed with a slow, salted key derivation function. Confusing the two has produced real security failures. Systems that "encrypt" passwords so they can later be decrypted and shown to users create an unnecessary and dangerous capability, anyone who compromises the encryption key (or the application itself) can recover every plaintext password at once. The correct design stores only a salted hash, from which the original password can never be recovered, even by the system's own operators.

Question 2: A security audit discovers that a database of user password hashes was stolen. The passwords were hashed using unsalted SHA-1. Explain why this configuration is critically weak and describe the specific remediation steps required, referencing the LinkedIn 2012 breach.

This configuration fails on two independent axes. First, SHA-1 is a general-purpose cryptographic hash function designed to be computationally fast, which is desirable for integrity-checking large files but catastrophic for password storage: a fast hash allows an attacker with commodity GPU hardware to test billions of password guesses per second against the stolen database. Second, and more severely, the hashes are unsalted, meaning that any two users who chose the identical password produce byte-for-byte identical hash values. This allows an attacker to use a single precomputed rainbow table against the entire stolen dataset simultaneously, rather than needing to attack each hash independently. This exact failure occurred in the 2012 LinkedIn breach, where approximately 167 million unsalted SHA-1 password hashes were exposed; the overwhelming majority were cracked within days using standard dictionary and rainbow-table techniques. Because password reuse across services is common, cracked credentials continued to enable credential-stuffing attacks against unrelated platforms for years afterward. Correct remediation requires: (1) migrating to a purpose-built, memory-hard key derivation function such as Argon2id or bcrypt, which is deliberately slow and resistant to GPU parallelization; (2) generating a unique, cryptographically random salt per user and storing it alongside (not instead of) the hash; (3) forcing a password reset for all affected accounts, since the original hashes cannot be "upgraded" without knowing the plaintext password; and (4) enforcing multi-factor authentication so that a cracked hash alone is insufficient for account takeover.

Question 3: Compare AES's Electronic Codebook (ECB) and Galois/Counter Mode (GCM) modes of operation. Why is a mathematically strong cipher like AES still considered insecure when used in ECB mode, and what additional property does GCM provide?

A block cipher such as AES only defines how to transform a single fixed-size block of data (128 bits); a mode of operation specifies how to apply that transformation across messages spanning many blocks. In Electronic Codebook (ECB) mode, each block is encrypted independently under the same key with no chaining between blocks. This means that identical plaintext blocks always produce identical ciphertext blocks, allowing structural patterns present in the original data to leak directly into the ciphertext, famously demonstrated by the "ECB Penguin," an encrypted bitmap in which the penguin's silhouette remains visible. The underlying cipher (AES) is not mathematically broken in this scenario; the failure lies entirely in the mode of operation chosen to apply it, which is why ECB is explicitly discouraged by NIST SP 800-38A for any data exhibiting repetitive structure. Galois/Counter Mode (GCM) addresses this weakness in two ways. First, it uses a counter-based construction (derived from CTR mode) combined with a per-message nonce, ensuring that identical plaintext blocks never produce identical ciphertext under repeated encryption operations. Second, and more significantly, GCM is an authenticated encryption mode: it produces a cryptographic authentication tag alongside the ciphertext in the same operational pass, so that any tampering with the ciphertext during transmission or storage causes decryption to fail rather than silently returning corrupted or attacker-modified plaintext. This combination of confidentiality and integrity in a single efficient construction is why AES-GCM is the default cipher suite in TLS 1.3 and is required for authenticated encryption use cases under FIPS 140-3 validated cryptographic modules.

ECB applies the block cipher to each block independently under the same key, so it is a deterministic function from plaintext block to ciphertext block. 3. B5.3.B

GCM builds its keystream by encrypting a counter seeded from the nonce. D is the most tempting distractor and the one worth arguing against explicitly: authenticity fails harder than confidentiality here, because tag forgery becomes possible.

4. C5.3.B

Salt and work factor are two controls solving two problems, and the frequent error is to credit one with the other's effect. The salt defeats amortization: a precomputed table or a single guess tested against a whole stolen file only works when equal passwords give equal digests, and a unique salt per credential destroys that. The work factor, bcrypt cost, Argon2 time and memory parameters, is what makes each individual guess expensive. A describes a pepper, a genuinely secret site-wide value, which is a different and optional control; salts are stored in the clear beside the digest. B assigns the work factor's job to the salt. 5. C5.3.A

The question is not whether AES is strong but whether the key is separated from the ciphertext by any boundary the attacker must cross twice. Here it is not: one compromise of the service account yields both. The encryption therefore reduces to media protection, which is genuine value, a decommissioned disk or a stolen backup tape is unreadable, but it must be reported as such rather than as protection of the records generally. A answers a cryptanalytic question nobody asked. B mistakes a permission bit for a trust boundary; the service account is exactly the identity the attacker obtains. Grader look-fors: names the specific adversary encryption addresses; states that an authorized session receives plaintext by design; proposes at least two controls on the actual path, drawn from authorization or detection rather than cryptography; concedes the residual value of the encryption instead of dismissing it.

FR 25.3.B

Model response. Three defects, each independent. First, the key is a single unsalted SHA-256 of the passphrase. SHA-256 is fast by design, so an attacker holding the ciphertext can test billions of candidate passphrases per second on commodity hardware, and because there is no salt the same passphrase yields the same key for every user, so one cracked passphrase unlocks every file that used it and precomputation across the whole population is viable. The correct primitive is a password-based derivation function with a deliberate cost, Argon2id, or PBKDF2-HMAC-SHA256 with a high iteration count where a NIST SP 800-132 conformant construction is required, seeded with a fresh random salt of at least sixteen bytes from a cryptographically secure generator such as Python's secrets.token_bytes. Second, the fixed all-zero IV destroys CBC's randomization. Two documents encrypted under the same passphrase that begin with the same bytes produce identical leading ciphertext blocks, revealing shared prefixes and, for structured formats with a fixed header, revealing that two files are of the same type or the same template. CBC additionally requires the IV to be unpredictable, not merely unique, so it must be drawn at random per encryption and stored alongside the ciphertext, where it is not secret. Third, nothing authenticates the output. CBC is malleable: an attacker who cannot read the file can still flip bits in one ciphertext block to make controlled changes in the next plaintext block, and the routine will decrypt the altered file without complaint. The corrected construction stores salt, IV or nonce, and ciphertext together in a defined format, and replaces raw CBC with AES-256-GCM, a single pass giving confidentiality and a tag whose verification failure aborts decryption, or, if CBC must be retained, adds an encrypt-then-MAC layer with HMAC-SHA256 over the IV and ciphertext under a separately derived key, verified with a constant-time comparison such as hmac.compare_digest. Grader look-fors: identifies all three defects separately; explains the consequence of each rather than merely labelling it bad; names a real derivation function and a real authenticated mode; states that salt and IV are stored in the clear; mentions constant-time comparison or the tag-before-plaintext rule if encrypt-then-MAC is chosen.
