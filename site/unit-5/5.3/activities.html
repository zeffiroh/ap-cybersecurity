5.3 Activities

Symmetric Encryption, Hashing and Key Storage · 3

Skill 5.3.a · pairs · 20 min · Offline: yes

Encryption vs. hashing

Goal

Analyze real-world business scenarios and decide whether each data element should be encrypted, hashed (with salt), or encoded, defending the choice based on the requirements for reversibility and confidentiality.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Analyze Scenarios (8 mins): With your partner, read the following three scenarios and determine which control (Encryption, Hashing, or Encoding) is required for each data field.
  2. Scenario A: A patient portal stores medical records (diagnosis, prescription history). The system must display these records to the patient and their doctor.
  3. Scenario B: An e-commerce database stores customer login passwords so the site can authenticate users when they sign in.
  4. Scenario C: An application needs to transmit a binary image file inside a JSON payload (which only supports text strings).
  5. Draft the Defense (6 mins): Write a 2-sentence justification for each choice. Address:
  6. Does the data need to be recovered in its original form?
  7. What happens if the database is breached?
  8. Present (6 mins): Pair up with another group, compare your choices, and discuss any differences in your justifications.

Collaborate

With your partner, roleplay as a Security Auditor and a Software Developer. The Developer wants to use symmetric encryption for passwords "just in case they need to recover a forgotten password for a VIP user." The Auditor must explain the security risks of this approach and advocate for salted hashing.

Exit Ticket

AP

Certificate of Completion

Write down the main difference between Encryption and Hashing in terms of mathematical reversibility and why this difference makes hashing the only acceptable choice for password storage.

Skill 5.3.b · small group (3-4) · 25 min · Offline: yes

Symmetric encryption and key management

Goal

Students work through a set of fictional data-protection scenarios, choosing the correct mode of operation (ECB / CBC / GCM) or key-management practice (generation, storage, wrapping, rotation) for each one, and justify why the wrong choices fail. Ties to LO 5.3.A, 5.3.B.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each group opens the simulation and works through the scenario queue, picking a mode of operation or key-management action for each fictional situation (e.g., "encrypt a bitmap image for storage," "encrypt a database column of SSNs," "generate an AES key for a new microservice," "store a DEK long-term," "a key is suspected compromised").
  2. For each scenario, before submitting an answer in the sim, the group must first write one sentence on the decision sheet explaining WHY the chosen mode/practice is correct and what would go wrong with the most tempting wrong answer (e.g., "ECB would let an attacker see repeated plaintext blocks as repeated ciphertext blocks").
  3. After finishing the sim's scenario queue, the group sketches the key lifecycle diagram from atom.md from memory (Generate -> Store -> Rotate -> Retire) and annotates each stage with the one control that protects it (CSPRNG, HSM/secrets manager, scheduled rotation, cryptographic erasure).

Collaborate

Assign roles: a "cryptographer" proposes the mode/practice for each scenario, a "red teamer" argues for the tempting wrong answer and explains why it would actually fail, and a "recorder" writes the final justification and draws the lifecycle diagram. Rotate roles halfway through the scenario queue.

Exit Ticket

AP

Certificate of Completion

Each student submits: one scenario they got wrong (or found hardest) + the correct choice + a one-sentence explanation of what an attacker could exploit if the wrong choice had been used.

Skill 5.3.c · pairs · 20 min · Offline: yes

Integrity and authenticity (HMAC)

Goal

Classify a set of integrity-check designs (plain hash, naive H(key+message), real HMAC) applied to a tampered vs. untampered message as SECURE or VULNERABLE, and defend the classification by naming the specific attack (or lack of one) that applies. Ties to LO 5.3.B, 5.3.C.

Materials

Steps

Check off all materials above to unlock the steps.
  1. With your partner, open the simulation and work through the scenario queue. For each scenario you are shown a design (plain hash / naive concatenation / real HMAC) and a message that may or may not have been tampered with in transit. Decide: is this design's integrity check SECURE or VULNERABLE against the described attacker?
  2. Before submitting an answer in the sim, write one sentence on the decision sheet naming the specific weakness (or why there is none): "an attacker can recompute the hash over their own tampered message," "vulnerable to length-extension because the digest exposes internal state," or "secure, the attacker cannot produce a valid tag without the shared key."
  3. After finishing the sim's scenario queue, sketch the HMAC construction from memory: HMAC(key, message) = H((key XOR opad) || H((key XOR ipad) || message)), and annotate why nesting the hash twice (rather than once, as in naive concatenation) is what defeats length extension.

Collaborate

Assign roles: an "attacker" argues how they would tamper with the message and forge a valid hash/tag under each design, and a "verifier" explains why that attack succeeds or fails for that specific design. Swap roles halfway through the scenario queue so each partner argues both sides.

Exit Ticket

AP

Certificate of Completion

Each student submits: one design (plain hash, naive H(key+message), or HMAC) they classified, whether it is SECURE or VULNERABLE, and a one-sentence explanation of what an attacker could (or could not) do to forge a valid check under that design.
