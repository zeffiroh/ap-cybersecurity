Lab, Signing, Verifying, and the Private Key

Sign with a private key, verify with the public key, then fail to forge without it.

This uses real RSA-PSS with SHA-256 from your browser's Web Crypto. A digital signature is produced with a private key that only the sender holds, and checked with the matching public key that anyone may have. A valid signature proves three things at once: the message was not altered (integrity), it came from the private-key holder (authenticity), and the signer cannot later deny it (non-repudiation). You will sign and verify a software release, break verification by tampering, and then step into the attacker's shoes, holding only the public key, to see why a forgery is impossible.

Sign, then verify.

Only the private key can sign

Signing hashes the message and transforms that digest with the private key; verification uses the public key to check that the signature matches the hash of the message in hand. Change one byte of the message and the hash changes, so the old signature no longer verifies, that is integrity. Because only the publisher holds the private key, a valid signature could only have come from them, that is authenticity and non-repudiation. An attacker with the public key can verify signatures but cannot create them; signing with any other key produces a signature the real public key rejects. This is the guarantee in LO 5.4.B, and it is stronger than a shared-secret MAC (5.3.c): with a MAC, every party who can verify can also forge, because they share the one secret key.
