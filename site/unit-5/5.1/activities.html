5.1 Activities

Application Code Vulnerabilities · 4

Skill 5.1.a · pairs · 25 min · Offline: yes

SQL injection

Goal

Students learn to identify how unsanitized input leads to SQL execution, trace the resulting database query strings, and rewrite vulnerable queries into parameterized format. Ties to LO 5.1.A (identify vulnerabilities) and 5.1.B (explain defenses).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation and walks through the database console simulation. They must complete the three challenges: comment truncation, OR bypass, and UNION data extraction.
  2. In their pairs, students copy the vulnerable string-concatenation query from the lesson: query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "';" And write out the exact resulting SQL command when the input username is:
  3. admin'--
  4. ' OR '1'='1
  5. Compare the queries. Why did the comment remove the password check? Why did the OR bypass match all rows?
  6. Write down the parameterized version of the query using placeholder values (e.g. ? or %s), showing how the user input is separated from the command logic.

Collaborate

One student acts as the "Penetration Tester" who attempts to craft inputs to bypass the logic. The other acts as the "Secure Developer" who explains how their proposed parameterized query prevents the tester's inputs from executing. Swap roles and try a different payload.

Exit Ticket

AP

Certificate of Completion

Each student submits: One example of a vulnerable concatenated query line they fixed, showing the "Before" (insecure concatenation) and "After" (secure parameterized prepared statement).

Skill 5.1.b · pairs · 25 min · Offline: yes

Cross-site scripting (XSS)

Goal

Students learn to recognize which parts of a web page are attacker-controlled, classify an XSS payload by variant (reflected / stored / DOM-based), and propose the correct output-encoding fix. Ties to LO 5.1.A (identify indicators) and 5.1.B (explain how the vulnerability is exploited).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation and works through the vulnerable vs. hardened comment-box scenarios, testing each payload and recording whether it "executes" in the sandboxed fake DOM.
  2. For each payload that executed, partners write one sentence naming the XSS variant (reflected, stored, or DOM-based) implied by the delivery mechanism described in the scenario text.
  3. Pairs then write the escaped/encoded version of one payload by hand (e.g., replace < with &lt;, > with &gt;) and confirm in the sim that the encoded version no longer executes.

Collaborate

Assign roles: one partner is the "attacker" (chooses payloads and predicts whether they will fire), the other is the "defender" (proposes the escaping fix and explains why it neutralizes the payload). Swap roles halfway through.

Exit Ticket

AP

Certificate of Completion

Each student submits: one payload they tested + its XSS variant + the escaped form that defeats it.

Skill 5.1.c · pairs · 25 min · Offline: yes

API vulnerabilities

Goal

Students practice thinking like an API attacker: given a set of endpoint calls and an object-ownership table, decide which requests should be allowed and which are BOLA violations. Ties to LO 5.1.B (explain how the vulnerability is exploited).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation and works through the mock API console, varying the object-ID parameter on each request and predicting allow/deny before submitting.
  2. For each BOLA violation found, partners write one sentence identifying which check the server skipped (authentication vs. authorization).
  3. Pairs then design one additional endpoint (e.g., GET /api/invoices/{id}) and write, in plain language, the server-side check that would prevent it from being BOLA-vulnerable.

Collaborate

Assign roles: one partner is the "pentester" (chooses which object IDs to probe and predicts the result), the other is the "API developer" (proposes the missing ownership check and explains where in the request-handling code it belongs). Swap roles halfway through.

Exit Ticket

AP

Certificate of Completion

Each student submits: one request they tested + whether it was a BOLA violation + the one-line server-side check that would fix it.

Skill 5.1.d · small group (3-4) · 25 min · Offline: yes

Data breaches and their impact

Goal

Students practice triaging breach reports by severity, reasoning jointly about data sensitivity, scale, and detection time. Ties to LO 5.1.C (explain the impact of a data breach).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each group opens the simulation and works through the queue of synthetic breach reports, agreeing on a severity score for each before submitting.
  2. For the two highest-severity reports in the queue, the group writes two sentences: what data category drove the severity, and what the organization's first containment action should be.
  3. Groups rank all reports in the queue from most to least severe and justify any close calls (e.g., a small breach of health records vs. a large breach of email addresses).

Collaborate

Assign roles within the group: a "triage lead" reads the report aloud, a "scorer" proposes the severity score against the rubric, and a "recorder" writes the one-line justification. Rotate roles each report.

Exit Ticket

AP

Certificate of Completion

Each student submits: the report they found hardest to score + the severity they assigned + one sentence justifying it.
