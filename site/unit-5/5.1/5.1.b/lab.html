Lab, Cross-Site Scripting and the Encoding + CSP Fix

Land a real script injection, then watch output encoding and a CSP turn it into inert text.

This is a mock comment board. Whatever you post is sent back and rendered in the preview on the right, which runs in a sandboxed, isolated frame so nothing can touch the real page. The frame holds a pretend victim session cookie, SESSION=ab12cd34, exactly the kind of secret a real XSS payload steals. In Vulnerable mode the server pastes your comment straight into the HTML. In Defended mode it HTML-encodes your comment and adds a Content-Security-Policy. First exfiltrate the cookie two different ways, then turn on the defenses and confirm both payloads become harmless text.

MISSIONS 0 / 3

  • Steal the session cookie with a classic <script> payload.
    HintPost <script>parent.postMessage('xss:'+document.cookie,'*')</script>. The server drops it into the page unescaped, so the browser runs it and the cookie is sent back to the attacker (you).
  • Steal it again without a <script> tag, to show filters that only block "script" are not enough.
    HintAn event handler needs no script tag: <img src=x onerror="parent.postMessage('xss:'+document.cookie,'*')">. The broken image fires onerror, which runs your code.
  • Switch to Defended mode, resend both payloads, and confirm the cookie never leaks.
    HintEncoding turns < into &lt; so the browser shows the payload as text instead of running it, and the CSP blocks inline script as a second layer. Watch the "server output" panel: your tags are now visible characters, not live HTML.

Why the fix works

XSS is a failure to separate data from code. In vulnerable mode your comment was pasted into the HTML stream, so <script> and an <img onerror> handler both became live instructions that ran with the victim's session and read the cookie. The root defense, named in LO 5.1.B, is output encoding: converting < > & " ' to their HTML entities so untrusted input can only ever render as text. A Content-Security-Policy that forbids inline script is a second layer, and marking the cookie HttpOnly keeps script from reading it even if one slips through. Notice the second payload needed no <script> tag at all, which is why a denylist that just blocks the word "script" fails and encoding every output is the real fix. This is the data-versus-code weakness of LO 5.1.A and its defense in 5.1.B.
