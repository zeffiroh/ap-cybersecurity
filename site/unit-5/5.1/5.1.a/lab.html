Lab, SQL Injection and the Parameterized Fix

Attack a real database, then rebuild the query so the same attack does nothing.

This login form runs a real SQLite database in your browser. The server code is shown exactly as it executes. First you break in by typing SQL instead of a username. Then you switch the server to a parameterized query and watch every payload stop working. That contrast is the whole lesson: a filter can be evaded, but parameterization removes the attack at its root.

MISSIONS 0 / 4

  • Log in as admin without knowing the password, using comment truncation.
    HintIn the username box type admin'--. The -- turns the rest of the line, including the password check, into a comment.
  • Log in with an always-true condition (OR bypass), without using the real username.
    HintTry username ' OR '1'='1'--. The OR makes the condition always true and the -- drops the password check, so the first user is returned.
  • Steal the password reset tokens from the secrets table with a UNION attack.
    HintThe query selects 3 columns (id, username, role). Match that count: ' UNION SELECT label, value, 'x' FROM secrets--
  • Turn on the parameterized query, then try every payload again and confirm they all fail.
    HintFlip the switch to Parameterized, then retry admin'-- and the UNION payload. The input is now treated as one literal username that does not exist.

The secrets table (what the attacker is after)

It holds password-reset tokens. A logged-in user should never be able to read it through the login form.

Why the fix works

In concatenation mode your input became part of the SQL text, so admin'-- and ' UNION SELECT ... changed the structure of the query. In parameterized mode the SQL template is compiled first, with a ? placeholder, and your input is sent afterward as a single data value. The database never re-parses it, so admin'-- is searched for as a literal username, which does not exist. The attack surface is gone, not merely filtered. This is why LO 5.1.B names parameterized queries the primary defense, with input validation and least-privilege database accounts as additional layers.
