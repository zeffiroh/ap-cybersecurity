I. Authentication and Password Storage

AuthenticationAuthenticationThe process of verifying that a user, device, or process is who or what it claims to be, answering the question "are you really who you say you are?" This is distinct from authorization, which answers a different question: "now that I know who you are, what are you allowed to do?" Authentication always happens first. NIST SP 800-63B, "Digital Identity Guidelines, Authentication and Lifecycle Management," is the primary federal standard governing authentication design. is the gatekeeping function that every other endpoint control depends on. A perfectly patched, perfectly hardened device is still fully compromised the moment an attacker obtains valid credentials to log into it, authentication failures bypass the need for any technical exploit at all. This topic examines how credentials are stored, how they are attacked, and how modern authentication design mitigates both.

The starting point is understanding that a well-designed system never stores a user's actual password. Instead, it stores the output of a cryptographic hash functionCryptographic Hash FunctionA mathematical function that converts input data of any size into a fixed-length string of characters (the "hash" or "digest"). A secure cryptographic hash function is one-way (computationally infeasible to reverse), deterministic (the same input always produces the same output), and exhibits the avalanche effect (a tiny change in input completely changes the output). SHA-256, part of the SHA-2 family, is defined in FIPS PUB 180-4 and produces a 256-bit (64 hexadecimal character) digest. applied to that password. When a user logs in, the system hashes the newly entered password and compares the result to the stored hash, if they match, authentication succeeds, and critically, the plaintext password itself is never retained on disk. This design means that even if an attacker steals the entire credential database, they do not automatically obtain usable passwords; they obtain hashes, which they must then attempt to reverse or guess through separate cracking techniques.

What Storing a Digest Actually Buys

The substitution of a digest for a password is a specific answer to a specific threat, and it is worth stating the threat precisely because the answer is not general. The threat is offline attack after credential-store compromise: an adversary who obtains a copy of the authentication database, through SQL injection, a stolen backup tape, an over-permissive cloud bucket, or an insider, and who can then work on it at leisure, on hardware of their choosing, with no rate limit, no lockout, and no logging, because the computation is happening on their machines rather than yours. Every control that lives at the login prompt is absent from this scenario. The only thing standing between the adversary and every user's password is the mathematics of the stored form.

Against that threat, a one-way function does two useful things. Its preimage resistance means there is no known method of computing an input from an output that is meaningfully faster than trying inputs, so the adversary is reduced to guessing rather than inverting. Its determinism means the verifier can still check a submitted password without ever holding the stored one, which is what makes the scheme usable at all. Note what is not on that list: confidentiality of the password against a determined attacker. A digest does not conceal a password. It converts recovering the password from a decryption problem, which would be instant, into a search problem, whose cost the defender then gets to set.

That framing is the whole of Topic 4.2's technical content, and it explains why the vocabulary in the objective is deliberately loose. Checksum, message digest, hash output, and digest all name the same artefact, a fixed-length output computed from arbitrary input, but they carry different connotations from different traditions. A checksum in its original sense (a CRC, say) is designed only to detect accidental corruption and is trivially forgeable; a cryptographic message digest is additionally designed to resist an adversary who is deliberately searching for a second input. When the objective lists the terms as interchangeable, it is naming the artefact, not endorsing every function that produces one. SHA-256 is an excellent cryptographic digest and an unacceptable password store, and the reason is not a defect in SHA-256. It is that a password store needs a property SHA-256 was engineered not to have: slowness.

Three properties must hold simultaneously for a stored credential to resist offline attack, and each is defeated independently:

  1. One-wayness. Recovering the input requires search. Defeated by storing plaintext, or by storing reversible encryption whose key travels with the database, the RockYou failure in Section III is the first case.
  2. Uniqueness per credential. Work spent on one row must not carry over to another. Defeated by the absence of a salt, which is the LinkedIn failure, and note that the algorithm's cryptographic quality is irrelevant to this property.
  3. Cost per guess. Each candidate must be expensive to test. Defeated by any general-purpose hash, including a perfectly sound one, because general-purpose hashes are optimised in exactly the wrong direction.

A system can hold two of the three and still fail completely, which is why "we hash our passwords" is not a statement that carries information. The rest of this section quantifies the third property, because it is the only one whose value is a number the defender chooses.

Not all hash functions are appropriate for password storage, and this distinction is one of the most frequently misunderstood concepts in introductory security education. General-purpose hash functions such as MD5MD5A cryptographic hash function designed in 1991 that produces a 128-bit digest. MD5 is fast to compute, which sounds like an advantage but is actually a critical weakness for password storage, because it allows an attacker to test billions of password guesses per second on modern GPU hardware. MD5 is also cryptographically broken with respect to collision resistance. Rivest, R. (1992). RFC 1321: The MD5 Message-Digest Algorithm. NIST formally deprecated MD5 for security purposes; it remains usable only for non-security checksums like file-integrity verification. and unsalted SHA-256 were designed for speed, verifying file integrity, indexing data structures, and that same speed becomes a liability when applied to passwords, because it allows attackers to test enormous numbers of guesses per second. Password hashing algorithmsPassword Hashing AlgorithmA specialized category of hash function deliberately engineered to be slow and computationally/memory expensive, specifically to resist brute-force and GPU-accelerated cracking attempts, while still completing in an acceptable time (milliseconds) for a single legitimate login. Examples include bcrypt, PBKDF2, and Argon2. OWASP's Password Storage Cheat Sheet ranks these algorithms and recommends Argon2id as the current best choice when available., such as bcrypt, PBKDF2, and Argon2, are purpose-built to be intentionally slow and resource-intensive, dramatically reducing the number of guesses per second an attacker can attempt even with specialized cracking hardware.

Speed is a feature for checksums and a defect for passwords Speed is the property a checksum is designed around: verifying a multi-gigabyte download should not take an afternoon. Speed is also, precisely, what an offline password attack consumes. The same computation the defender performs once per login the attacker performs once per guess, so the ratio between a legitimate authentication and a cracking campaign is fixed by nothing except the number of guesses, and the attacker chooses that number. Measured on one consumer graphics card, the gap between the two families spans eight decimal orders: roughly 1.6 × 1011 MD5 computations per second, against something near 1.4 × 103 bcrypt computations per second at a work factor of 12. That gap is not a side effect of bcrypt being an older or clumsier design. It is the design.

Password hashing alone is insufficient without saltingSalt (Cryptographic Salt)A random string of data generated uniquely for each password and combined with that password before hashing. The salt is stored alongside the hash (it does not need to be secret) and ensures that even if two users choose the identical password, their stored hashes will be completely different, because each was combined with a different random salt before hashing. NIST SP 800-63B §5.1.1.2 mandates a salt of at least 32 bits, generated using an approved random bit generator, for every stored password credential.. Without a salt, two users who choose the same password produce identical hashes, and, more importantly, an attacker can precompute hash values for common passwords once and reuse that precomputed table against any stolen database (a rainbow table attack, detailed below). Salting defeats this by ensuring that even identical passwords hash to entirely different values, forcing an attacker to attack each hash individually rather than reusing precomputed work across the whole database.

Attacks against stored credentials, and against live login endpoints, fall into several distinct categories, and the distinctions are worth holding precisely, because each category is defeated by a different control:

  • Brute-force attackBrute-Force AttackAn attack that systematically tries every possible combination of characters within a defined character set and length until the correct password is found. Given enough time and computing power, a brute-force attack is guaranteed to succeed, the only defense is making the search space (password length/complexity) and the per-guess computation cost (via slow hashing) large enough that the attack is impractical within a useful timeframe. MITRE ATT&CK T1110.002. A brute-force search of an 8-character password using only lowercase letters has 26⁸ ≈ 208 billion possible combinations.: Exhaustively tries every possible character combination; guaranteed to eventually succeed but computationally expensive against long, complex passwords and slow hash functions.
  • Dictionary attackDictionary AttackAn attack that tries a curated list of likely passwords (real words, common passwords like "password123," names, leaked password lists) rather than exhaustively trying every possible combination. Dictionary attacks are far faster than brute force because they exploit the fact that humans choose predictable, memorable passwords rather than truly random strings. MITRE ATT&CK T1110.001. Tools like Hashcat and John the Ripper support "rule-based" dictionary attacks that also apply common mutations (e.g., appending numbers, capitalizing the first letter) to each dictionary word.: Tries a curated wordlist of likely passwords rather than every combination, exploiting predictable human password choices; far faster than brute force against weak passwords.
  • Rainbow table attackRainbow Table AttackAn attack that uses a precomputed lookup table mapping hash values back to their original plaintext inputs, allowing an attacker to reverse a stolen hash almost instantly by simple lookup rather than computing hashes on the fly. Rainbow tables trade storage space for speed, they are generated once (a slow, offline process) and then reused indefinitely against any database using the same unsalted hash algorithm. Salting completely defeats rainbow tables, because a precomputed table cannot account for a unique per-password random salt. Oechslin, P. (2003). "Making a Faster Cryptanalytic Time-Memory Trade-Off." CRYPTO 2003, the paper that introduced the rainbow table technique as an efficient refinement of earlier hash chain methods.: Uses precomputed hash-to-plaintext lookup tables to reverse stolen hashes almost instantly; completely neutralized by proper per-password salting.
  • Credential stuffingCredential StuffingAn attack that takes username/password pairs leaked from a previous, unrelated data breach and automatically tries them against a different target service, exploiting the extremely common human habit of reusing the same password across multiple sites. Unlike brute force or dictionary attacks, credential stuffing does not need to guess anything, it uses passwords that are already known to be real, valid credentials somewhere. MITRE ATT&CK T1110.004. The 2019 "Collection #1" leak of 773 million email/password combinations fueled widespread credential-stuffing campaigns for years afterward.: Reuses username/password pairs leaked from an unrelated breach against a new target, exploiting password reuse across services rather than guessing anything new.
  • Password sprayingPassword SprayingAn online attack that inverts the usual brute-force pattern: instead of trying many passwords against one account, it tries one or two very likely passwords (Autumn2025!, Welcome1, the organisation's name plus a year) against every account in the directory, then pauses and repeats with the next candidate. Because each individual account sees only one or two failures, per-account lockout thresholds are never reached and the attack is invisible to any detection rule that counts failures per user. MITRE ATT&CK T1110.003. The defence is rate limiting and alerting keyed on the source and on the aggregate failure rate across the directory, not on the individual account.: Tries a very small number of highly likely passwords against a very large number of accounts, staying under per-account lockout thresholds by design; defeated by source-based rate limiting and directory-wide failure monitoring rather than by account lockout.
Each attack is identified by where its guesses come from The families are separated by one question, where does the next guess come from? — and the answer determines which defence works. Exhaustive search enumerates the whole keyspace and is beaten by making the keyspace large or the per-guess cost high. A dictionary attack draws from a wordlist of things people actually choose, and is beaten by refusing to accept those choices. A rainbow table draws nothing at all at attack time; the work was done in advance, which salting invalidates. Credential stuffing draws from real pairs that were valid on some other service, so nothing about the password's strength helps and the defence has to be a second factor or reuse detection. Password spraying draws from a very short list of likely passwords tried across a very large list of accounts, and is beaten by rate limits keyed on the source rather than on the account. Notice that no single control covers all five.

II. Inside a Slow Hash: bcrypt and PBKDF2

To make the abstraction of "slow hashing" concrete, consider how bcryptbcryptA password hashing algorithm designed in 1999, based on the Blowfish cipher, that incorporates a configurable "cost factor" (also called a work factor) controlling exactly how computationally expensive each hash computation is. Doubling the cost factor by 1 doubles the computation time required, allowing administrators to keep pace with increasing hardware speed over time by simply raising the cost factor for newly hashed passwords. Provos, N. & Mazières, D. (1999). "A Future-Adaptable Password Scheme." USENIX Annual Technical Conference. bcrypt has a maximum input length of 72 bytes, a lesser-known limitation. and PBKDF2PBKDF2, Password-Based Key Derivation Function 2A password hashing algorithm that derives a cryptographic key from a password by applying an underlying hash function (commonly SHA-256) repeatedly, a configurable number of iterations, before producing the final output. Like bcrypt, increasing the iteration count linearly increases the computational cost per guess. PBKDF2 is FIPS-approved, making it a common choice in government and regulated environments. Kaliski, B. (2000). RFC 2898: PBKDF2 specification. NIST SP 800-132 recommends a minimum of 10,000 iterations, though modern guidance pushes this significantly higher given hardware improvements. encode their computational cost directly into the stored hash string. The following bcrypt hash was generated for the password "Tr0ub4dor&3" with a cost factor of 12:

bcrypt Hash Structure

 │   │                salt (22 chars, base64)      hash output (31 chars)
 │   └─ cost factor: 12  →  2^12 = 4,096 key-stretching rounds

# Doubling the cost factor from 12 to 13 doubles compute time per guess:
# cost=10  -> ~65ms/hash   (2^10  =  1,024 rounds)
# cost=12  -> ~250ms/hash  (2^12  =  4,096 rounds)
# cost=14  -> ~1000ms/hash (2^14  = 16,384 rounds)

Notice that the salt is embedded directly within the stored string alongside the hash itself, it does not need to be kept secret, only unique per password, per the definition in Section I. This is why a bcrypt hash string alone is sufficient for the verification process: on login, the system extracts the algorithm identifier, cost factor, and salt from the stored string, re-hashes the submitted password using those exact same parameters, and compares the result.

A salt is a uniqueness device, not a secret A salt does not have to be secret, and treating it as though it were leads to worse designs rather than better ones, developers who believe the salt is a secret tend to use one global salt, held in a configuration file, which reintroduces the exact precomputation weakness a salt exists to remove. The salt's job is uniqueness. Because it is unique per credential, an attacker cannot amortise work across the database: cracking a million salted hashes costs a million times cracking one, whereas cracking a million unsalted hashes of the same algorithm costs barely more than cracking one. NIST SP 800-63B-4 §3.1.1.2 requires at least 32 bits of salt, chosen so that stored hashes do not collide, and requires that the salt be stored alongside the hash, an instruction that only makes sense because the salt is not secret. The construction that is secret is the pepper, described later in this section, and it is a separate mechanism with a separate purpose.

Modern authentication design mitigates all of these attack types by requiring more than a password alone. Multi-Factor Authentication (MFA)Multi-Factor Authentication (MFA)An authentication scheme requiring proof from at least two independent categories: something you KNOW (a password or PIN), something you HAVE (a phone, hardware security key, or smart card), or something you ARE (a biometric trait). Requiring multiple independent factors means that compromising one factor alone, such as stealing a password through credential stuffing, is insufficient to gain access. NIST SP 800-63B §4.3 defines Authenticator Assurance Levels (AAL1–AAL3), with AAL2 and above requiring multi-factor authentication. combines factors from these independent categories so that a single compromised element (e.g., a stuffed password) is insufficient on its own:

  • Knowledge factor: Passwords, PINs, vulnerable to all four attack types described above.
  • Possession factor: Hardware tokens, authenticator apps generating TOTPTOTP, Time-based One-Time PasswordA short numeric code, typically six digits, generated by combining a shared secret key with the current time (rounded to a 30-second window) using an HMAC algorithm. Because the code changes every 30 seconds and is derived partly from the current time, a stolen code becomes useless almost immediately, unlike a static password. RFC 6238. NIST SP 800-63B §5.1.4 classifies standard TOTP as a "restricted authenticator" because it remains vulnerable to real-time phishing proxy attacks, unlike FIDO2/WebAuthn. codes, SMS codes, vulnerable to SIM-swapping and real-time phishing proxies but far stronger than passwords alone.
  • Inherence (biometric) factor: Biometric authenticationBiometric AuthenticationVerifying identity using a measurable physical or behavioral characteristic unique to an individual, fingerprint, facial geometry, iris pattern, or voice. Biometric authentication is convenient because it cannot be forgotten like a password, but it introduces a unique risk: unlike a password, a biometric trait cannot be "changed" if compromised, since a person only has one face or one set of fingerprints. ISO/IEC 19795 defines biometric performance testing standards. False Acceptance Rate (FAR) and False Rejection Rate (FRR) are the two core metrics used to evaluate biometric system accuracy. such as fingerprint or facial recognition, cannot be guessed or stuffed, but raises distinct privacy and revocation concerns since biometric traits cannot be reset the way a password can.
Two of the same category is still one factor Multi-factor means multiple categories, not multiple steps. A password followed by a security question is one factor asked twice: both are things the user knows, both can be captured by the same phishing page, and both can be recovered from the same breach or the same social-media profile. The categories have to be independent in the sense that compromising one does not tend to compromise the other. This is also why NIST SP 800-63B-4 §3.1.1.2 clause 8 now forbids knowledge-based authentication questions outright when choosing passwords, the answers are neither secret nor memorable, which is the worst pairing available. Independence is a property of the threat model, not of the user interface: a one-time code delivered to the same laptop that holds the password manager is nominally a possession factor and practically a second copy of the first one.

II-A. The Arithmetic of Guessing

Almost every claim made about password strength is a claim about the size of a search space, and almost every argument about password policy is settled by evaluating that size. The evaluation is short enough to do on paper.

Model a password as a string of length $L$ drawn from an alphabet of $R$ distinct symbols, with every symbol chosen independently and uniformly at random. The number of possible strings is $R^L$, and the information content, conventionally reported in bits, and usually called the entropyPassword EntropyA measure, in bits, of how many equally likely possibilities a password was drawn from. Each additional bit doubles the size of the search space. Entropy of $H$ bits means $2^H$ possibilities, so a 50-bit password is drawn from about a quadrillion candidates. The measure is only valid for passwords generated by a uniform random process; for a human-chosen password it is an upper bound that is usually wildly optimistic, because human choices are concentrated on a tiny fraction of the nominal space. NIST SP 800-63B-4 Appendix A discusses precisely this gap and is the stated reason the guidelines abandoned composition rules in favour of blocklists., is

$$H = \log_2\left(R^L\right) = L\,\log_2 R$$

Each additional bit of $H$ doubles the work. Because search is on average half-complete when it succeeds, the expected number of guesses to a hit is $2^{H-1}$, and the expected time is that count divided by the attacker's guess rate:

$$t = \frac{2^{\,H-1}}{r}$$

Everything contentious about password policy is contained in the three quantities $L$, $R$, and $r$ — and in the fact that the defender controls only two of them directly, while controlling the third, $r$, far more powerfully than the other two combined.

A worked example

Take an eight-character password drawn from the 95 printable ASCII characters. Then

$$H = 8 \times \log_2 95 = 8 \times 6.570 = 52.6\ \text{bits}, \qquad R^L = 95^8 = 6.63 \times 10^{15}$$

and the expected guess count is $3.32 \times 10^{15}$. That number means nothing until it is divided by a rate, so fix one. Published hashcat v6.2.6 benchmarks for a single NVIDIA RTX 4090 give roughly $1.6 \times 10^{11}$ MD5 computations per second, $2.2 \times 10^{10}$ SHA-256 computations per second, and $1.8 \times 10^{5}$ bcrypt computations per second at the benchmark work factor of 5. Bcrypt's cost parameter is an exponent, so each increment halves the rate; at the commonly deployed work factor of 12 the rate falls by a factor of $2^{7} = 128$, to about $1.4 \times 10^{3}$ per second. Dividing:

  • Against unsalted SHA-256: $3.32 \times 10^{15} / 2.2 \times 10^{10} \approx 1.5 \times 10^{5}$ seconds, about 42 hours on one graphics card.
  • Against bcrypt at work factor 12: $3.32 \times 10^{15} / 1.4 \times 10^{3} \approx 2.4 \times 10^{12}$ seconds, about 75,000 years on the same card.

The password did not change. Its length did not change. Its alphabet did not change. The only thing that changed is a single integer in the verifier's configuration, and it moved the outcome by more than seven orders of magnitude. This is the argument for key stretching, stated in full.

Two further columns of the same table are worth computing, because they bound the discussion from both ends. An eight-character lowercase-only password gives $H = 8 \log_2 26 = 37.6$ bits and an expected $1.04 \times 10^{11}$ guesses, which against SHA-256 resolves in under five seconds. A six-word passphrase drawn uniformly from the 7,776-word Diceware list gives $H = 6 \log_2 7776 = 77.5$ bits and an expected $9.0 \times 10^{22}$ guesses, which even against unsalted SHA-256 runs to roughly $1.3 \times 10^{5}$ years. Between those two rows lies a useful and frequently missed observation: a four-word Diceware passphrase carries 51.7 bits, essentially identical to the random eight-character ASCII string, and falls to the same 23-hour attack. Length in characters is not the quantity that matters; $L \log_2 R$ is, and a passphrase buys its bits from $R$ rather than from the number of keystrokes.

The formula measures a generator, not a password $H = L \log_2 R$ is exact for a string produced by a uniform random process and is close to meaningless for a string produced by a person. Human choices are concentrated: a large fraction of real passwords fall within a few million candidates, so the effective entropy of a human-chosen eight-character password with a symbol and a digit is nothing like 52.6 bits, empirically it is often below 25. This is the single most important caveat in the section, and it is the reason NIST SP 800-63B-4 abandoned composition rules. A rule that says "must contain an upper-case letter, a digit, and a symbol" does not raise $H$; it narrows the region of the space people search, because almost everyone satisfies it the same way, capitalise the first letter, append a digit and an exclamation mark. Screening the candidate against a list of known-common and known-breached passwords attacks the actual distribution instead of a proxy for it, which is why the guidelines replaced the one with the other. When a password is machine-generated, quote $H$; when a human chose it, quote the blocklist you checked it against.
Python 3, search-space arithmetic (standard library only) 
"""Expected time to a first hit, as a function of alphabet, length, and rate.

Runs on a stock Python 3.8+ interpreter; no third-party packages.
"""
import math

SECONDS_PER_YEAR = 365.25 * 24 * 3600

# Published hashcat v6.2.6 single-GPU benchmarks (NVIDIA RTX 4090), in
# hashes per second. bcrypt's cost is an exponent, so each increment above
# the benchmark cost of 5 halves the achievable rate.
RATES = {
    "MD5 (unsalted)":        1.6e11,
    "SHA-256 (unsalted)":    2.2e10,
    "bcrypt cost 5":         1.8e5,
    "bcrypt cost 12":        1.8e5 / 2 ** (12 - 5),
}

def entropy_bits(length: int, alphabet_size: int) -> float:
    """H = L * log2(R). Valid only for uniform random generation."""
    return length * math.log2(alphabet_size)

def expected_seconds(bits: float, rate_per_second: float) -> float:
    """Search is on average half done when it succeeds: 2**(H-1) guesses."""
    return 2 ** (bits - 1) / rate_per_second

def humanise(seconds: float) -> str:
    if seconds < 60:
        return f"{seconds:.1f} s"
    if seconds < 3600:
        return f"{seconds / 60:.1f} min"
    if seconds < 86400:
        return f"{seconds / 3600:.1f} h"
    if seconds < SECONDS_PER_YEAR:
        return f"{seconds / 86400:.1f} days"
    return f"{seconds / SECONDS_PER_YEAR:.3g} years"

CANDIDATES = [
    ("8 chars, lowercase only",      8,   26),
    ("8 chars, printable ASCII",     8,   95),
    ("12 chars, printable ASCII",    12,  95),
    ("4 Diceware words",             4,  7776),
    ("6 Diceware words",             6,  7776),
]

for label, length, alphabet in CANDIDATES:
    bits = entropy_bits(length, alphabet)
    print(f"{label:<28} H = {bits:5.1f} bits  space = {alphabet ** length:.3g}")
    for scheme, rate in RATES.items():
        print(f"    vs {scheme:<20} {humanise(expected_seconds(bits, rate))}")
    print()

Running it reproduces the figures above and makes the sensitivity easy to explore. Two experiments are worth doing. Raise the length of the ASCII password from 8 to 12 and the bcrypt column becomes geological while the SHA-256 column becomes merely large, length helps, but it helps a defender who has already fixed their storage. Then divide every rate by the cost of the KDF and notice that the ratio between the best and worst password in the list stays fixed while every absolute number moves together. The storage decision is a multiplier applied to the entire user population at once; the password decision applies to one account. That asymmetry is why an engineer's first hour is better spent on the verifier than on the policy document.

II-B. Salts, Peppers, and Memory-Hard Derivation

Section II-A established that the defender's most powerful lever is the per-guess cost $r$. This section is about how that cost is actually imposed, and about the two auxiliary values, the salt and the pepper, that are frequently confused with each other and with the key.

Salt: removing the attacker's economies of scale

A salt is a random value, unique per credential, that is combined with the password before hashing and stored in the clear alongside the result. It is not secret and does not need to be. Its function is entirely economic: it destroys the attacker's ability to amortise work across rows. Against an unsalted database, computing the digest of summer2025 once tests that candidate against every account simultaneously, so the cost of cracking $N$ hashes is approximately the cost of cracking one. Against a salted database, each row has a different effective function, so the cost is $N$ times the cost of one. For a database of 167 million rows, the LinkedIn figure, that factor is the difference between an afternoon and a geological era, and it is obtained from 16 random bytes per user.

The same property is what defeats a rainbow tableRainbow Table, PreciselyNot simply a lookup table of hashes. Oechslin's construction (CRYPTO 2003) is a time-memory trade-off: chains of alternating hash and reduction steps are computed in advance and only the first and last element of each chain is stored, so a table covering an enormous keyspace fits in tractable storage at the cost of some recomputation at lookup time. The "rainbow" refers to using a different reduction function at each position in the chain, which suppresses the chain collisions that plagued Hellman's earlier method. Oechslin, P. (2003). Making a Faster Cryptanalytic Time-Memory Trade-Off. CRYPTO 2003, LNCS 2729, pp. 617-630. A salt of $k$ bits multiplies the required table size by $2^k$, which is why 32 bits of salt is sufficient to make the technique economically impossible and why no serious modern attack uses rainbow tables against salted stores., and the mechanism is worth stating exactly because the usual summary is imprecise. A rainbow table is not a dictionary of hashes; it is a precomputed time-memory trade-off covering a keyspace, and its value comes entirely from being computed once and reused many times. A per-credential salt of $k$ bits means the adversary would need $2^k$ separate tables. NIST SP 800-63B-4 §3.1.1.2 requires at least 32 bits, which puts that multiplier above four billion and ends the technique as a practical matter.

Pepper: a secret the database copy does not contain

A pepper is a single secret value, shared across all credentials, that is not stored with them, it lives in a hardware security module, a trusted platform module, a key-management service, or at minimum a configuration store on a different machine than the database. The password is combined with it, typically through a keyed operation such as HMAC, before or after the slow derivation. NIST SP 800-63B-4 §3.1.1.2 recommends exactly this: an additional iteration of a keyed hashing or encryption operation using a secret key known only to the verifier, generated by an approved random bit generator and stored separately from the hashed passwords, ideally inside a hardware-protected area.

The threat model is the point of difference. A salt assumes the attacker has the database and accepts it; a pepper assumes the attacker has the database and not the key, which is a common outcome, since SQL injection and stolen backups yield table contents rather than the contents of an HSM. If that assumption holds, offline cracking is not merely expensive but impossible, the adversary cannot compute a single candidate digest. If the assumption fails and the key leaks alongside the database, the pepper contributes nothing and the salted, stretched hash is all that remains. A pepper is therefore a valuable additional layer and a catastrophic sole defence, and the two must be deployed together. The operational cost is real: rotating a pepper requires re-deriving every stored credential, which can only be done as users authenticate, so peppered schemes need explicit versioning from the first day.

Why memory-hardness, and not merely iterations

PBKDF2 imposes cost by repetition, the same small HMAC computation, tens or hundreds of thousands of times. This is effective against an attacker with the same hardware as the defender and much less effective against one with different hardware. A PBKDF2 evaluation needs almost no memory, so an adversary can place thousands of independent instances on a single GPU, or bake a few thousand onto an FPGA or a custom ASIC, and obtain a throughput advantage of several orders of magnitude over the defender's server. The defender's cost per hash and the attacker's cost per hash are not the same quantity, and compute-only functions let that gap grow.

Memory-hard functionsMemory-Hard FunctionA function deliberately designed so that computing it requires a large working memory that cannot be traded away for extra computation without incurring a heavy penalty. Because memory is expensive in area on custom silicon and limited in quantity on a graphics card, requiring 64 MiB per evaluation caps how many evaluations an attacker can run in parallel regardless of how many arithmetic units the hardware has. The design goal is to make the attacker's cost per guess track the defender's cost per guess even when the hardware differs completely. Percival, C. (2009), "Stronger Key Derivation via Sequential Memory-Hard Functions," introduced scrypt with this argument; Biryukov, Dinu and Khovratovich's Argon2 (2016) refined it and won the Password Hashing Competition. attack that gap directly. scrypt, introduced by Percival in 2009, and Argon2, which won the Password Hashing Competition in 2015 and is specified in RFC 9106, both require a large, randomly accessed working buffer for every evaluation. Memory is the resource that does not shrink when you move to custom silicon: an attacker who wants a thousand parallel Argon2id evaluations at 64 MiB each needs 64 GiB of fast memory, and no amount of arithmetic throughput substitutes for it. The parallelism advantage that makes GPUs devastating against SHA-256 is bounded by a quantity the defender sets.

RFC 9106 §4 names Argon2id as the variant to use when there is no reason to prefer another, because it runs data-independently over the first half of the first pass, limiting side-channel leakage, and data-dependently thereafter, which resists time-memory trade-off attacks. Its two recommended parameter sets are worth quoting as targets: the first is $t = 1$ iteration, $p = 4$ lanes, $m = 2^{21}$ KiB (2 GiB), with a 128-bit salt and a 256-bit tag; the second, appropriate for the memory budgets most authentication servers actually have, is $t = 3$ iterations, $p = 4$ lanes, $m = 2^{16}$ KiB (64 MiB), with the same salt and tag sizes. Argon2d is for settings such as proof-of-work where side channels are not a threat; Argon2i is data-independent throughout and is the conservative choice where side channels dominate. For password storage on a server the answer is Argon2id.

Choosing a work factor is choosing a latency budget There is no universally correct cost parameter, because the parameter is not a security level, it is a division of a fixed latency budget. Decide first what an authentication is allowed to cost the server: a common target is 250 to 500 milliseconds of wall-clock time per verification, which is imperceptible to a user and, at a peak of a few hundred logins per second, still fits on modest hardware. Then set the parameter as high as that budget permits on the hardware you actually run, and re-measure annually, because the budget buys fewer and fewer guesses of protection as commodity hardware improves. NIST SP 800-63B-4 states this as a requirement rather than a suggestion: the cost factor should be as high as practical without harming verifier performance, and should be increased over time. It also requires that the scheme and its cost factor be stored with each credential, precisely so that the migration to a higher factor can be done incrementally as users log in, rather than never.
Python 3, salt, pepper, and three real key-derivation functions 
"""Password storage: salting, peppering, and slow derivation.

Standard library only for scrypt and PBKDF2. The bcrypt and Argon2id
sections need third-party packages:

    pip install bcrypt argon2-cffi

The pepper below is read from the environment for illustration. In a real
deployment the key belongs in an HSM, a TPM-backed store, or a cloud KMS,
on a host separate from the credential database (NIST SP 800-63B-4 3.1.1.2).
"""
import hashlib
import hmac
import os
import secrets

# ----- 1. Salt: 16 random bytes per credential, stored in the clear -----
salt = secrets.token_bytes(16)          # 128 bits; NIST floor is 32 bits

# ----- 2. Pepper: one secret key, never stored beside the hashes --------
pepper = os.environb.get(b"CRED_PEPPER") or secrets.token_bytes(32)

def pre_hash(password: str) -> bytes:
    """Keyed pre-hash with the pepper.

    Two things happen here. The HMAC binds the password to a secret the
    database dump does not contain, and the fixed 32-byte output sidesteps
    bcrypt's 72-byte input limit for long passphrases. Feed the raw bytes,
    not a hex string, so no entropy is lost to encoding.
    """
    return hmac.new(pepper, password.encode("utf-8"), hashlib.sha256).digest()

# ----- 3a. scrypt (standard library) -----------------------------------
# n must be a power of two. Memory used is roughly 128 * n * r bytes:
# 128 * 32768 * 8 = 32 MiB, so maxmem must be raised above the default.
def store_scrypt(password: str) -> bytes:
    return hashlib.scrypt(
        pre_hash(password), salt=salt,
        n=2 ** 15, r=8, p=1, dklen=32, maxmem=64 * 1024 * 1024)

# ----- 3b. PBKDF2-HMAC-SHA256 (standard library) -----------------------
# Compute-only, so use it when FIPS validation forces the choice; the
# iteration count must then be pushed high to compensate.
def store_pbkdf2(password: str) -> bytes:
    return hashlib.pbkdf2_hmac("sha256", pre_hash(password), salt, 600_000, dklen=32)

# ----- 4. Verification: always compare in constant time ----------------
def verify_scrypt(password: str, stored: bytes) -> bool:
    return hmac.compare_digest(store_scrypt(password), stored)

if __name__ == "__main__":
    digest = store_scrypt("correct horse battery staple")
    print("scrypt :", digest.hex())
    print("ok     :", verify_scrypt("correct horse battery staple", digest))
    print("bad    :", verify_scrypt("correct horse battery stapl", digest))
    print("pbkdf2 :", store_pbkdf2("correct horse battery staple").hex())

Two details in that listing are load-bearing and are routinely omitted from tutorial code. The comparison uses hmac.compare_digest rather than ==, because Python's ordinary bytes comparison returns as soon as it finds a differing byte, and an attacker who can time the verification endpoint can recover the stored digest one byte at a time from that timing difference; compare_digest runs in time independent of where the first difference falls. And the pepper is applied through HMAC rather than by concatenation, which both avoids length-extension issues and produces a fixed-length input, the practical way to feed a long passphrase to bcrypt, whose input is silently truncated at 72 bytes.

Python 3, bcrypt and Argon2id via their real APIs 
"""Production-grade password hashing with the two libraries you would
actually deploy.  pip install bcrypt argon2-cffi

Both libraries generate their own random salt and embed it, along with the
algorithm identifier and every cost parameter, in the returned string.
Never supply your own salt to these APIs and never store the parameters
separately -- the self-describing string is what makes incremental
migration to a higher cost factor possible.
"""
import bcrypt
from argon2 import PasswordHasher
from argon2.exceptions import VerifyMismatchError

password = b"correct horse battery staple"

# ----- bcrypt -----------------------------------------------------------
# gensalt(rounds=N) sets the cost exponent: the algorithm runs 2**N key
# expansion rounds. Raise N until one hash costs ~250 ms on your hardware.
bcrypt_hash = bcrypt.hashpw(password, bcrypt.gensalt(rounds=12))
print("bcrypt   :", bcrypt_hash.decode())
print("verify   :", bcrypt.checkpw(password, bcrypt_hash))
print("wrong    :", bcrypt.checkpw(b"not the password", bcrypt_hash))

# ----- Argon2id ---------------------------------------------------------
# RFC 9106 section 4, second recommended option: t=3, p=4, m=2**16 KiB.
# argon2-cffi expresses memory_cost in KiB, so 65536 KiB == 64 MiB.
ph = PasswordHasher(
    time_cost=3, memory_cost=65536, parallelism=4,
    hash_len=32, salt_len=16)
argon_hash = ph.hash(password)
print("argon2id :", argon_hash)

try:
    ph.verify(argon_hash, password)          # returns True or raises
    print("verify   : True")
except VerifyMismatchError:
    print("verify   : False")

# check_needs_rehash reports whether a stored hash was produced with
# parameters weaker than the current policy. Call it on every successful
# login and re-hash in place when it returns True; this is how a fleet of
# credentials is migrated to a higher cost factor without a mass reset.
if ph.check_needs_rehash(argon_hash):
    argon_hash = ph.hash(password)

The check_needs_rehash pattern at the end is the answer to a question every deployment eventually faces: the work factor chosen in 2019 is inadequate in 2026, and the plaintext needed to re-derive the stored value exists for exactly one instant, while the user is logging in. Upgrading at that moment, transparently, is the only migration path that does not require resetting every password in the organisation. It is also why the stored string must carry its own parameters: a system that recorded only the digest, with the cost factor held in a configuration file, cannot tell an old hash from a new one and therefore cannot migrate at all.

III. Case Studies: RockYou and LinkedIn

Case Study 4.2.1: The RockYou Breach and the Birth of Modern Password Wordlists (2009)

In December 2009, the social application developer RockYou suffered a breach exposing approximately 32 million user accounts. The critical failure was not merely the breach itself but RockYou's storage practice: passwords were stored in plaintext, with no hashing whatsoever. When the database was leaked, attackers obtained every user's actual password directly, with no cracking required at all. The leaked password list, now famously known simply as rockyou.txt, revealed staggering patterns in human password choice (the most common password in the set was simply "123456") and was subsequently compiled into what remains, over a decade later, one of the most widely used dictionary-attack wordlists in the security industry, bundled by default with tools like Kali Linux.

The RockYou breach is the canonical teaching example for why plaintext password storage represents a total, irrecoverable failure of authentication security: no hardening control applied after the fact (hashing, salting, MFA) can retroactively protect credentials that were already exposed in readable form.

Password habits change more slowly than the companies that record them More than fifteen years on, rockyou.txt is still a serviceable wordlist. That fact is worth sitting with, because it is evidence about people rather than about software. The distribution of human password choices, heavily concentrated on a few thousand strings, with a long tail of predictable mutations, has proved far more stable than any operating system, cipher, or company in the same period. It is the empirical basis for the shift described in Section IV: if the distribution of what people choose is knowable and stable, then screening a proposed password against that distribution is a stronger control than any rule about character classes, which merely relocates the concentration to a new predictable region such as Password1!. A breach's most durable consequence is often not the accounts it exposed but the model of human behaviour it handed to every attacker afterwards.

Case Study 4.2.2: The 2012 LinkedIn Breach, Unsalted SHA-1 at Scale

In June 2012, LinkedIn disclosed a breach that ultimately exposed roughly 167 million account credentials (the full scope was not confirmed until a 2016 re-sale of the data). LinkedIn had hashed its passwords using SHA-1SHA-1A cryptographic hash function producing a 160-bit digest, published by NIST in 1995. Like MD5, SHA-1 was designed for general-purpose integrity checking, not password storage, and is fast enough that GPU-based cracking rigs can attempt billions of guesses per second against it. SHA-1 is also cryptographically broken with respect to collision resistance as of 2017. NIST formally deprecated SHA-1 for digital signatures in 2011 (SP 800-131A) and it was fully disallowed for most federal uses by 2015., a fast, general-purpose hash never intended for password storage, and critically, without any salt. Because the hashes were unsalted, attackers were able to apply precomputed rainbow tables and massively parallelized GPU cracking to recover the vast majority of the plaintext passwords within days of the leak surfacing publicly, and the exposed dataset was compiled into wordlists used in credential-stuffing campaigns against other services for years afterward, since so many users reused the same LinkedIn password elsewhere.

Hashing without salting and stretching buys almost nothing The breach is often recalled as a partial success, the passwords were hashed, so the damage was limited. The arithmetic says otherwise. Three properties have to hold together, and LinkedIn had one of them. The hash was one-way (yes), unique per credential (no salt, so no), and expensive per guess (SHA-1, so emphatically no). Missing the second property means the attacker's work amortises across the entire database: one pass over a wordlist scores against all 167 million rows at once. Missing the third means that pass runs at billions of candidates per second. Storing an unsalted SHA-1 is closer in outcome to storing plaintext than to storing an Argon2id digest, and the useful formulation of the lesson is not "hash passwords" but "salt them, and stretch them with a function chosen to be slow."

One further consequence outlived the incident. Because so many users had reused the LinkedIn password elsewhere, the recovered plaintexts became fuel for credential-stuffing campaigns against unrelated services for years, an attack the breached organisation could not mitigate and the victim services had not been party to.

IV. Modern Authentication Policy: Hashing, Lockout, MFA, NIST 800-63B

Modern authentication hardening follows layered guidance formalized primarily by NIST SP 800-63B:

1. Mandating Modern Password Hashing Algorithms

Organizations must migrate all credential storage away from fast general-purpose hashes (MD5, SHA-1, unsalted SHA-256) toward purpose-built SHA-256 salting and key stretchingKey StretchingThe general technique of taking a relatively weak input (like a human-chosen password) and applying a computationally expensive process, repeated hashing rounds, in the case of PBKDF2, or a memory-hard function, in the case of Argon2, to make brute-force attacks against it dramatically slower, effectively "stretching" a weak secret into one that is far more resistant to cracking. Key stretching is a design principle applied by all three modern password hashing algorithms: bcrypt (Blowfish rounds), PBKDF2 (HMAC iterations), and Argon2 (memory-hard iterations). workflows such as bcrypt, PBKDF2 (with a NIST-recommended minimum iteration count), or Argon2id, the current OWASP-recommended default, which additionally incorporates a memory-hardness requirement that resists GPU and ASIC-accelerated cracking far better than compute-only algorithms.

2. Enforcing Account Lockout and Rate Limiting

Authentication endpoints must implement failed authentication lockouts after a defined threshold (commonly 5 attempts), combined with progressive delays or IP-based rate limiting, to make both brute-force and credential-stuffing attacks impractical at scale even against weak individual passwords. This detective/preventive hybrid control directly corresponds to the log pattern examined in Section II.

3. Deploying Phishing-Resistant MFA

Following NIST SP 800-63B's Authenticator Assurance Level 3 (AAL3) guidance, organizations should prioritize FIDO2/WebAuthn hardware security keys over SMS or basic TOTP for high-value accounts, since hardware keys cryptographically bind authentication to a specific domain and cannot be intercepted by real-time phishing proxies (as detailed in Topic 1.1).

4. Password Policy Modernization

NIST SP 800-63B's current guidance represents a significant departure from older password policy conventions: rather than mandating frequent forced password rotation and complex special-character requirements (which historically pushed users toward predictable patterns like "Password1!" → "Password2!"), current guidance emphasizes long passphrase length, screening new passwords against known-breached password lists, and eliminating mandatory periodic rotation for passwords that have not been compromised.

What changed in NIST's password guidance, and why The current edition is NIST SP 800-63B-4 (July 2025), and its password clauses in §3.1.1.2 are worth reading in the original because they are unusually direct. A password used as the only factor must be at least 15 characters; one used only as part of a multi-factor scheme may be as short as eight. Verifiers should permit at least 64 characters, should accept every printing ASCII character and the space, and should accept Unicode, counting each code point as one character. Composition rules, the mandated mixtures of upper case, digits, and symbols, shall not be imposed. Periodic forced change shall not be required, though a change shall be forced on evidence that the credential is compromised. Password hints accessible to an unauthenticated party are prohibited, as are knowledge-based questions. Verifiers must request and check the whole password rather than a subset, and must not truncate it.

Each of these reverses a convention that was standard practice for two decades, and each reversal has the same justification: the older rules optimised a model of the attacker (someone guessing at a login prompt, slowly) that stopped describing reality once offline cracking of stolen databases became the dominant threat. Composition rules and forced rotation both shrink the effective search space by pushing users toward predictable transformations, which is the opposite of their intent.

Self-Check Review Questions

Question 1: Explain why fast general-purpose hash functions such as MD5 and unsalted SHA-1 are inappropriate for password storage, and describe how purpose-built password hashing algorithms address this weakness.

General-purpose hash functions like MD5 and SHA-1 were engineered for speed, since their original use cases, file integrity verification, data indexing, benefit from rapid computation. This same speed becomes a critical security liability when applied to password storage, because it allows an attacker who obtains a stolen hash database to test enormous numbers of candidate passwords per second using modern GPU or ASIC hardware, as demonstrated in the 2012 LinkedIn breach where unsalted SHA-1 hashes were cracked en masse within days. Purpose-built password hashing algorithms such as bcrypt, PBKDF2, and Argon2 address this by deliberately incorporating a configurable computational cost (a "work factor" or "cost factor," and in Argon2's case, a memory-hardness requirement as well). This intentional slowness has negligible impact on a legitimate user logging in once, but multiplies the total time required for an attacker attempting billions of guesses by the same large factor, reducing the practical guess rate from billions per second to potentially only a few thousand per second, a difference of five to six orders of magnitude that makes large-scale offline cracking computationally infeasible within a useful timeframe.

Question 2: A stolen password database contains hashes with no unique salt values. Explain specifically how this enables a rainbow table attack, and explain why adding a unique per-password salt defeats this attack even if the underlying hash algorithm is unchanged.

Without a salt, the hash of a given plaintext password is always identical regardless of which user or which system produced it, since the hash function's output depends only on the password input itself. This determinism allows an attacker to precompute a large lookup table mapping common plaintext passwords to their corresponding hash outputs a single time, entirely offline, before ever obtaining the target database. Once the target database is stolen, reversing any hash present in the precomputed table becomes a near-instantaneous lookup operation rather than a fresh computation, and this precomputed table can be reused indefinitely against any other unsalted database using the same hash algorithm. Adding a unique, randomly generated salt per password breaks this precomputation entirely, because the effective input to the hash function is no longer just the password but the password concatenated with a salt value unique to that specific credential. A precomputed rainbow table built for one salt value is worthless against a hash generated using a different salt, and because every password in a properly salted database uses its own unique salt, an attacker is forced to mount an individual, non-reusable cracking attempt against every single hash, eliminating the massive efficiency advantage that makes rainbow tables practical in the first place. Note that the salt does not need to be kept secret, since its purpose is to guarantee uniqueness, not to add secret entropy.

Question 3: An authentication log shows a single source IP attempting logons against many different usernames within seconds, using a set of passwords known to have been leaked from an unrelated breach of a different website. Identify this attack type, distinguish it from a dictionary attack, and describe the multi-factor authentication design that would neutralize it even if a valid stolen credential pair is used.

This scenario describes credential stuffing, distinguished specifically by the source of the attempted passwords: real, previously valid username/password pairs obtained from a data breach of an entirely different, unrelated service. This is fundamentally different from a dictionary attack, which uses a curated wordlist of statistically likely or commonly chosen passwords rather than credentials known to have been valid somewhere else; credential stuffing succeeds specifically because of widespread password reuse across multiple unrelated services by the same individual, not because the passwords themselves are inherently weak or predictable. Multi-factor authentication neutralizes credential stuffing even when the attacker possesses a fully correct, valid username/password pair, because MFA requires proof from at least one additional independent factor category beyond knowledge (the password), such as a possession factor (a hardware security key or authenticator app generating a time-based one-time password) or an inherence factor (a biometric trait). Since the attacker's stolen credential set contains only the knowledge factor and not physical possession of the legitimate user's second-factor device, authentication fails at the second step even though the first (password) step succeeds, rendering the stuffed credentials insufficient on their own to complete the login.

(c) Explain why an account-lockout threshold alone would not have prevented this incident. (d) The clinic's authentication is currently single-factor. Recommend a second factor appropriate to a shared clinical workstation, and justify the choice against at least one alternative you reject.

Answer Key

1. B4.2.A

A password hash is the output of a deliberately one-way function: the verifier can confirm a submitted password by recomputing the digest, but cannot invert the stored value. What the substitution buys is not secrecy but expense, the thief must guess and test, and the encoded parameters m=65536,t=3 set what each test costs. A describes encryption, which is reversible by design and is exactly what a credential store must not be; a scheme an administrator can reverse is a scheme an attacker who takes the key can reverse. C overclaims: if a user chose Summer2025!, the digest of that string will be recovered on the first pass of any modern wordlist no matter how the hash was computed. Hashing raises the attacker's cost per candidate; it does not create entropy the user never supplied. D mistakes an incidental property for the purpose, fixed output length is true of every hash function and is not why one is used here.

2. C4.2.A

The two defences are independent and multiply. The unique salt means each row is effectively a different function, so a single pass over a wordlist scores against one account rather than all of them; against a table the size of LinkedIn's this alone changes the cost by eight orders of magnitude. The work factor then attacks the rate itself: published hashcat benchmarks put SHA-1 in the tens of billions of candidates per second on a single modern GPU and bcrypt at work factor 12 in the low thousands. A is irrelevant, the attacker searches the password space, not the digest space, and digest length bounds nothing here. B is simply false; no cryptographic hash is reversible, and SHA-1's published weakness is in collision resistance, not preimage recovery. D confuses salt with pepper: the bcrypt salt is stored in the clear inside the digest string, and is expected to be.

3. B4.2.B

The diagnostic signature is the shape of the distribution, not the volume: breadth across accounts is enormous, depth per account is two, and two is below five. That is a deliberate parameter choice by the attacker, who has read the same lockout policy the defender wrote. The eleven-hour spread and 46 source addresses are further evasion of per-account and per-source rate limits. A inverts the pattern, brute force is deep and narrow, and would drive one account past the threshold within seconds. C is not supported by the log: credential stuffing is defined by the provenance of the passwords, which authentication logs do not record; you would need corroboration from a breach corpus before making that claim. D is a category error, rainbow tables are an offline technique applied to stolen digests and have no meaning at a live login prompt, where the attacker never sees a hash.

4. B4.2.C

The factor that is actually presented to the relying party is possession of the authenticator that holds the private key; the fingerprint is a local user-verification gesture that releases it. Two independent categories are therefore involved, and the biometric template never crosses the network, which is why compromise of the relying party cannot leak it. A stops at the visible gesture and misses that the signature is evidence of possession. C asserts a rule that does not exist; inherence is one of the three recognised categories, and adding a password would in fact weaken the scheme by reintroducing a phishable shared secret. D misapplies the distinction: what separates multi-factor from mere multi-step is whether the evidence comes from independent categories, not whether it is collected on one piece of hardware, by that reasoning no phone-based authenticator would ever qualify.

5. C4.2.D

Each element in C answers a named failure: the length floor raises the search space, breach screening removes the passwords attackers try first, the automatic reset window and progressive delay cut the online guess rate without handing an attacker a way to disable accounts on demand, and the second factor survives a correct password. A combines a threshold low enough that ordinary typing errors lock users out with a manual reset that turns every lockout into a help-desk call, and scheduled expiry, which drives predictable increments. B identifies a genuine problem and responds by removing the control rather than tuning it; an automatic reset window addresses the abuse without leaving the endpoint unlimited. D imposes composition rules that concentrate choices in a predictable region, and a 24-hour lockout is a denial-of-service primitive available to anyone who knows a username.

6. B4.2.B

A pepper is a secret shared across rows and held outside the database, so its value rests entirely on a threat-model assumption: SQL injection and stolen backups yield table contents, not the contents of an HSM. Where that assumption holds, the attacker cannot compute even one candidate digest. Where it fails, the pepper contributes nothing and only the salted bcrypt beneath it is left, which is why it is an excellent additional layer and an unacceptable sole defence. A confuses the two: the salt is public and per-row and defeats amortisation; the pepper is secret and global and defeats offline computation. Neither substitutes for the other. C reasons from the assumption holding, which is precisely what must not be assumed. D is wrong on mechanics, the per-row salts are still present and still unique, so no amortisation is reintroduced.

FR 14.2.A

Model answer. (a) For a help-desk operator to read a password back, the system must hold it in a recoverable form: plaintext, or encryption under a key the application can access, which for this purpose is operationally equivalent. On the day the table is copied the adversary obtains every student's actual password with no cracking step at all, and, because passwords are reused, working credentials for those students' unrelated accounts elsewhere. RockYou in 2009 is the canonical instance: 32 million plaintext credentials, and a wordlist still in use more than fifteen years later. (b) The three properties are one-wayness, uniqueness per credential, and cost per guess. SHA-256 supplies the first and only the first. Without a salt, one wordlist pass scores against every row simultaneously; without stretching, that pass runs at tens of billions of candidates per second on commodity hardware. LinkedIn in 2012 is the demonstration: unsalted SHA-1 across roughly 167 million rows, the majority recovered within days. (c) Argon2id, with a memory cost around 64 MiB, time cost tuned so that a single verification takes on the order of half a second on the production hardware, parallelism 1, and a unique random salt of at least 16 bytes per credential; bcrypt at work factor 12 or above is an acceptable alternative where Argon2 is unavailable. The salt defends against amortisation and precomputation; the time cost against raw guess rate; the memory cost specifically against GPU and ASIC parallelism, since memory bandwidth, unlike arithmetic throughput, does not scale cheaply with core count. A pepper held in an HSM may be layered on top, with explicit versioning from day one. (d) The existing plaintexts cannot be rehashed and considered safe, because they may already be in an adversary's possession and are certainly in the help desk's. The migration must force a reset of every credential, screen the new choices against a breach corpus, and treat the entire historical set as compromised, including at other services, which is why users should be told plainly rather than merely prompted.
Look for: recognition that reversible storage and plaintext are the same risk; the three properties named and SHA-256 credited with exactly one; concrete parameters with a stated defensive purpose for each rather than a bare algorithm name; and, in (d), the conclusion that rehashing known plaintext preserves the exposure instead of ending it.

FR 24.2.D

Model answer. (a) The pattern is password spraying. The distinguishing evidence is the distribution rather than the total: 3,400 failures spread thinly across all 60 accounts is roughly 57 per account over a weekend, deliberately paced so no account trips a threshold, whereas brute force concentrates hundreds or thousands of attempts on one account within minutes. The out-of-shift success at 03:14 is the compromise indicator and should be triaged as such. (b) Four changes with their targets and costs. Breach-corpus screening on password set: defeats the small high-yield candidate list a spray depends on; the clinic must accept a rejection loop at enrolment and an external or locally hosted corpus to check against. Progressive delay plus per-source and per-endpoint rate limiting: defeats the aggregate volume that per-account thresholds miss; the clinic must accept that shared NAT egress can throttle legitimate staff. A 15-character minimum with no composition rules and no scheduled expiry: raises the search space while removing the predictable increments that expiry produces; the clinic must accept passphrase training and slower typing at the bedside. Second-factor enrolment: defeats a correct password, which is the only control on this list that would have stopped the 03:14 logon; the clinic must accept token provisioning, loss handling, and a documented break-glass path. Alerting on out-of-hours success and on aggregate failure rate is an acceptable fifth. (c) A lockout threshold is a per-account counter, and spraying is engineered to stay beneath per-account counters; 57 attempts spread over 48 hours against an account with a five-failure counter and a 30-minute reset window may never trip it once. The detection this incident needed is an aggregate one, failures per unit time across the whole directory, and breadth of distinct usernames touched per source, which no per-account setting can express. (d) For a shared clinical workstation, FIDO2 hardware security keys issued per staff member are the right choice: authentication is bound cryptographically to the relying party's origin, so a real-time phishing proxy cannot replay it, and the credential travels with the person rather than the shared machine, which preserves individual accountability that shared accounts otherwise destroy. SMS one-time codes are rejected because they are interceptable by SIM-swap and by relay proxies and depend on carrier coverage that clinical interiors often lack; app-based TOTP is a defensible second choice but still relayable in real time and awkward where staff cannot carry personal phones onto the floor.
Look for: spraying identified from the distribution rather than the volume; each proposed setting paired with both a named failure and an accepted cost; an explicit statement in (c) that the control operates at the wrong granularity for this attack; and a second-factor recommendation justified by phishing resistance and by fit to the shared-workstation context, not merely asserted as stronger.
