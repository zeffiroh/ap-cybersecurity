Skill 4.2.a · pairs · 25 min · Offline: yes

Passwords and password policies

Goal

Students learn to classify candidate passwords as compliant or non-compliant against a stated policy, and connect each individual policy rule to the specific attack it defends against. Ties to LO 4.2.A (evaluate a password against a formal policy and explain why each rule reduces risk).

Materials

Steps

Check off all materials above to unlock the steps.

  1. Classify the candidates (10 min). The active policy for this exercise is: min_length: 12, require_upper: true, require_lower: true, require_digit: true, require_symbol: true, banned_list: ["password123", "letmein", "qwerty123456"], history: ["OldPass2023!"]. Each pair reads the five candidate passwords below and writes ACCEPT or REJECT plus a one-sentence justification for each.

  2. Candidate A: abc123

  3. Candidate B: password123
  4. Candidate C: Tr0ub4dor&3xtra!
  5. Candidate D: OldPass2023!

  6. Candidate E: correcthorsebatterystaple9

  7. Compare with the simulation (5 min). Open the simulation and work through its candidate queue to check your classifications. Note any disagreements and discuss why.

  8. Build an attack-mapping table (10 min). As a pair, fill in the table, for each policy rule, name the specific attack class it defends against:

Policy rule Attack it defends against Why
Minimum length
Complexity ban on common patterns
History / reuse check
Account lockout after N failures
Breach/banned-list check

Collaborate

Assign roles: one partner is the "policy auditor" (states ACCEPT/REJECT and cites the exact rule violated), the other is the "attacker" (explains which attack technique the auditor's decision blocks). Swap roles for the attack-mapping table. Compare your completed tables with another pair, identify any attack mapping they listed that you missed.

Exit Ticket

AP

Certificate of Completion

Each student submits: their classification of Candidate E + a one-sentence explanation of why a 26-character password can still be rejected by a policy.

Skill 4.2.b · pairs · 25 min · Offline: yes

Multi-factor authentication

Goal

Students learn to classify authentication methods by factor category, judge whether a described login flow is true MFA, and identify the weakest link in a multi-step login. Ties to LO 4.2.A (explain authentication factors and MFA) and 4.2.B (evaluate the strength of an authentication scheme against phishing/SIM-swap/push-bombing risk).

Materials

Steps

Check off all materials above to unlock the steps.

  1. Classify the scenarios (10 min). Each pair reads the five scenarios below and writes: (a) which factor category each presented credential belongs to (knowledge / possession / inherence), (b) whether the flow is true MFA, and (c) the weakest link, if any.

  2. Scenario A: A user logs in with a password, then a 6-digit code texted to their phone.

  3. Scenario B: A user logs in with a password, then taps "Approve" on a push notification without reading which device or location triggered it.
  4. Scenario C: A user logs in with a password and a memorized answer to "What street did you grow up on?"
  5. Scenario D: A user logs in with a password, then inserts a FIDO2 hardware security key and taps its button when prompted.

  6. Scenario E: A user logs in with a fingerprint scan on their phone, which then also confirms their identity to unlock a saved password that is auto-filled into the site.

  7. Compare with the simulation (5 min). Open the simulation and work through its login-attempt stream to check your classifications. Note any disagreements and discuss why.

  8. Build a comparison table (10 min). As a pair, fill in the table:

MFA method Factor category Resistant to phishing? Resistant to SIM-swap? Recommended use case
Password only
SMS one-time code
Authenticator app (TOTP)
Push notification
Hardware key (FIDO2)
Biometric

Collaborate

Assign roles: one partner is the "login auditor" (classifies each scenario's factor categories and explains the reasoning), the other is the "risk advisor" (recommends whether the scheme is acceptable for a high-value account like a bank or admin login, and what to upgrade). Swap roles for the comparison table. Compare your completed table with another pair and reconcile any disagreement on phishing/SIM-swap resistance.

Exit Ticket

AP

Certificate of Completion

Each student submits: their classification of Scenario B (true MFA or not, and why) plus one sentence naming the attack technique that Scenario B is vulnerable to.

Skill 4.2.c · pairs · 25 min · Offline: yes

Session security

Goal

Students learn to classify session-security vulnerabilities by scenario description and propose the specific technical fix for each. Ties to LO 4.2.B (mitigate session-related risk).

Materials

Steps

Check off all materials above to unlock the steps.

  1. Classify the incidents (10 min). Each pair reads the five scenarios below and writes the vulnerability class (hijacking, fixation, improper timeout, insecure cookie flag) and the specific fix that addresses it.

  2. Incident A: An attacker on the same public WiFi network captures a user's session cookie in plaintext over HTTP and replays it to access the account without a password.

  3. Incident B: A phishing email contains a link with a pre-set session ID embedded in the URL. The victim clicks the link, logs in, and the server keeps using that same session ID. The attacker now uses the identical ID to access the account.
  4. Incident C: A shared office workstation stays logged into the HR portal all weekend because no idle timeout is configured. A janitor discovers the open session Monday morning.
  5. Incident D: A stored XSS vulnerability lets an attacker inject a script that reads document.cookie and exfiltrates the session token, because the cookie has no HttpOnly flag.

  6. Incident E: A user clicks "Log Out." Their browser cookie is deleted, but the server never marks the session record as invalid. A token captured earlier by an attacker still works after the "logout."

  7. Compare with the simulation (5 min). Open the simulation and work through its incident stream to check your classifications. Note any disagreements and discuss why.

  8. Build a defense table (10 min). As a pair, fill in the table:

Vulnerability class Example indicator Specific technical fix
Hijacking
Fixation
Improper timeout
Insecure cookie flag

Collaborate

Assign roles: one partner is the "log auditor" (explains which vulnerability class and why), the other is the "remediation lead" (proposes the exact fix, e.g., "add the HttpOnly flag" or "regenerate the session ID at login"). Swap roles halfway through the incident list. Compare your completed defense table with another pair and reconcile any fix you worded differently.

Exit Ticket

AP

Certificate of Completion

Each student submits: their classification of Incident E + a one-sentence explanation of why deleting a client-side cookie is not equivalent to a secure logout.

Skill 4.2.d · pairs · 25 min · Offline: yes

Least privilege and access control models

Goal

Students learn to identify which access control model is in play in a described scenario and judge whether an access request violates the principle of least privilege. Ties to LO 4.2.B (access control models) and 4.2.C (least privilege / risk of over-privileged accounts).

Materials

Steps

Check off all materials above to unlock the steps.

  1. Classify the requests (10 min). Each pair reads the five scenarios below and writes: (a) which access control model (DAC, MAC, RBAC, or ABAC) is being used or described, and (b) whether the request/situation violates least privilege, and if so, why.

  2. Scenario A: A marketing intern requests write access to the production customer database "just in case it's useful later." No specific task requires it.

  3. Scenario B: An HR employee transferred to a new department two years ago but still has active administrator access to the payroll system from their old role.
  4. Scenario C: An on-call engineer requests elevated production access for a four-hour window to resolve an active incident; the access automatically expires afterward.
  5. Scenario D: A company file server checks a fixed classification label ("Confidential" vs. "Public") on every file and a matching clearance level on every user before allowing access, no user, including file owners, can override this.

  6. Scenario E: A cloud platform grants a contractor access to a project folder only when their department = "Engineering," their device is company-managed, and the request happens between 8 AM and 6 PM on a weekday.

  7. Compare with the simulation (5 min). Open the simulation and work through its access-request stream to check your classifications. Note any disagreements and discuss why.

  8. Build a comparison table (10 min). As a pair, fill in the table:

Model Who sets permissions Flexibility Common use case
DAC
MAC
RBAC
ABAC

Collaborate

Assign roles: one partner is the "requester" (argues why the access should be granted), the other is the "auditor" (applies least-privilege reasoning to approve, deny, or flag the request). Swap roles for the comparison table. Compare your completed tables with another pair, identify any use case or flexibility note they listed that you missed.

Exit Ticket

AP

Certificate of Completion

Each student submits: their classification of Scenario B + a one-sentence explanation of what control would have prevented that access from persisting for two years.
