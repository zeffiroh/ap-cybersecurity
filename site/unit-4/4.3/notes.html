I. Hardening the Endpoint

Where Topics 4.1 and 4.2 examined how endpoints become vulnerable and how credentials are attacked, this topic examines the active controls organizations deploy directly on the endpoint itself to reduce risk before an incident occurs. HardeningHardeningThe process of systematically reducing a system's attack surface by removing or restricting unnecessary functionality, applying security configurations, and layering defensive software, the technical equivalent of removing extra doors and windows from a building rather than just adding a better lock to the front door. NIST SP 800-70, "National Checklist Program for IT Products," provides standardized hardening checklists across vendor platforms. is the umbrella discipline covering every proactive change made to a device's default configuration, installed software, and running services to minimize the number of ways it can be compromised, and to maximize the chance that an attempted compromise is caught quickly if it happens anyway.

Endpoint hardening is best understood as spanning three interconnected control categories, echoing the general control taxonomy (technical, administrative/managerial, and physical) introduced earlier in the course, but applied specifically to the device layer:

  • Technical controls: Software and configuration mechanisms enforced automatically by the system itself, anti-malware engines, host-based firewalls, patch management agents.
  • Managerial (administrative) controls: Organizational policies governing how devices are configured, who can change those configurations, and how compliance is verified, device configuration baselines, acceptable use policies, mobile device management enrollment requirements.
  • Physical controls: Controls limiting direct physical interaction with the device, locked server racks, port-blocking hardware, tamper-evident seals.

The first and most historically familiar technical control is anti-malware softwareAnti-Malware SoftwareSoftware designed to detect, block, and remove malicious programs from a device. Traditional antivirus relies primarily on signature-based detection, matching files against a database of known malware fingerprints, while modern anti-malware suites add heuristic and behavioral analysis to catch malware that has never been seen before. The term "antivirus" is often used interchangeably with "anti-malware" in casual usage, though technically antivirus refers to the older, narrower signature-matching approach., traditionally reliant on signature-based detectionSignature-Based DetectionA malware detection method that compares files or running processes against a database of known malicious "signatures", unique byte patterns, file hashes, or code snippets extracted from previously identified malware samples. Signature detection is fast and produces very few false positives, but it is fundamentally reactive: it can only catch malware that has already been analyzed and added to the signature database, making it blind to brand-new or modified threats. Signature databases are typically updated by vendors multiple times per day; the window between a new malware variant's release and its signature being published is often called the "detection gap.", which matches files against a database of known malicious code fingerprints. Because signature-based detection is fundamentally reactive, it can only catch malware that has already been discovered, analyzed, and cataloged elsewhere, modern endpoint protection has evolved toward Endpoint Detection and Response (EDR)Endpoint Detection and Response (EDR)A category of endpoint security software that continuously monitors and records detailed system activity, process execution, file changes, network connections, registry modifications, and applies behavioral analytics to detect suspicious patterns even when no known malware signature matches, while also providing security teams with tools to investigate and actively respond to detected threats (isolating a host, killing a process, rolling back changes) from a centralized console. Gartner popularized the term "EDR" in a 2013 research report. EDR is distinguished from traditional antivirus by its emphasis on continuous telemetry recording, behavioral detection, and active incident response capability rather than simple prevention alone. platforms, which continuously monitor system behavior, process launches, file modifications, network connections, and apply behavioral analytics to flag suspicious activity patterns even when no known signature exists for the specific malware involved.

Antivirus and EDR answer different questions about the same process Think of traditional signature-based antivirus as a security guard checking IDs against a mugshot book, fast and reliable, but useless against someone whose photo isn't in the book yet. EDR is closer to a guard who also watches behavior: "why is this person trying every door on the hallway one at a time?" EDR doesn't need to recognize the specific attacker; it recognizes the pattern of the attack itself. This is why EDR can catch zero-day malware and fileless attacks that never touch disk in a way signature scanning would recognize.

A second essential technical control is patch managementPatch ManagementThe organizational process of identifying, testing, and deploying software updates ("patches") that fix known security vulnerabilities across an enterprise's fleet of devices, typically on a defined schedule and prioritized by vulnerability severity. Effective patch management closes the window between a vulnerability's public disclosure and its remediation on a given organization's systems, the exact window exploited by worms like WannaCry, examined in Topic 4.1. NIST SP 800-40 Rev. 4, "Guide to Enterprise Patch Management Planning," is the primary federal reference standard for this process., which systematically applies operating system and application updates that close known vulnerabilities before attackers can exploit them. A third is the host-based firewallHost-Based FirewallA firewall that runs directly on an individual endpoint device, such as Windows Defender Firewall or iptables/nftables on Linux, rather than on a dedicated network appliance sitting at the network perimeter. Because it operates on the endpoint itself, a host-based firewall can enforce granular, per-application, per-process rules and continues protecting the device even when it leaves the corporate network (e.g., a laptop on public Wi-Fi), unlike a perimeter firewall. NIST SP 800-41 Rev. 1, "Guidelines on Firewalls and Firewall Policy," discusses host-based firewalls as a complementary layer to network perimeter firewalls, not a replacement for them., which enforces network access rules locally on the device rather than only at the network perimeter, providing protection even when a device roams outside the corporate network entirely, such as an employee laptop connected to public Wi-Fi.

II. Endpoint Protection: Signatures, Heuristics, Behaviour, and EDR

Host-based firewall rules are typically expressed as an ordered list of allow/deny statements evaluated top to bottom, with the first matching rule determining the outcome. The following iptables ruleset illustrates a hardened workstation configuration implementing default-deny inbound policy, a foundational hardening principle requiring that all traffic be blocked by default unless explicitly permitted:

iptables, Host Firewall Hardening Ruleset 
# Flush existing rules and set default-deny policy on INPUT chain
iptables -F
iptables -P INPUT DROP
iptables -P FORWARD DROP
iptables -P OUTPUT ACCEPT

# Allow established/related connections (return traffic for outbound requests)
iptables -A INPUT -m state --state ESTABLISHED,RELATED -j ACCEPT

# Allow loopback interface (local inter-process communication)
iptables -A INPUT -i lo -j ACCEPT

# Allow SSH only from the internal management subnet (never expose to 0.0.0.0/0)
iptables -A INPUT -p tcp -s 10.10.5.0/24 --dport 22 -j ACCEPT

# Explicitly reject legacy remote-admin protocols regardless of source
iptables -A INPUT -p tcp --dport 23 -j DROP   # Telnet
iptables -A INPUT -p tcp --dport 21 -j DROP   # FTP

# Log and drop everything else that reaches the end of the chain
iptables -A INPUT -j LOG --log-prefix "IPTABLES-DROPPED: "
iptables -A INPUT -j DROP

This ruleset enforces default-deny: the INPUT chain policy is set to DROP, meaning any traffic not explicitly matched by an earlier ACCEPT rule is discarded by default. Only established/related return traffic, loopback traffic, and SSH from a defined internal management subnet are permitted; legacy insecure protocols are explicitly and redundantly blocked even though the default-deny policy would already block them, following the hardening principle of defense in depth at the rule-authoring level itself.

Default-deny fails closed; default-allow fails open This is the single most important architectural decision in any firewall configuration, host-based or network. A default-deny policy (block everything, then explicitly permit only what is needed) is dramatically more secure than a default-allow policy (permit everything, then explicitly block known-bad traffic), because default-deny fails safe: any traffic type the administrator forgot to consider is automatically blocked rather than automatically permitted. The asymmetry is worth stating plainly: default-deny requires the administrator to enumerate what is needed, which is a finite and knowable list; default-allow requires enumerating everything hostile, which is neither.

Modern EDR platforms generate structured alerts describing detected suspicious behavior, typically mapped to a recognized behavioral framework such as MITRE ATT&CKMITRE ATT&CKA publicly available, continuously updated knowledge base cataloging real-world adversary tactics (the "why," e.g., Privilege Escalation) and techniques (the "how," e.g., Exploitation for Privilege Escalation) observed in actual attacks, organized into a matrix. Security tools including most modern EDR platforms map their alerts to ATT&CK technique IDs so analysts can quickly understand what stage of an attack a given alert represents. Maintained by the MITRE Corporation, first released in 2013. The Enterprise matrix currently documents 14 tactic categories spanning the full attack lifecycle from Initial Access through Impact.. The following simplified EDR alert illustrates behavioral detection of a process-injection technique, a technique that would evade purely signature-based antivirus, since the underlying process names (svchost.exe) are entirely legitimate Windows binaries being abused rather than malicious files being introduced:

EDR Alert, Behavioral Detection 
{
  "alert_id": "EDR-88213",
  "severity": "HIGH",
  "host": "WKSTN-UMB-0114",
  "timestamp": "2026-07-09T14:02:11Z",
  "detection_type": "behavioral",
  "mitre_technique": "T1055 - Process Injection",
  "parent_process": "winword.exe",
  "child_process": "svchost.exe",
  "description": "winword.exe (Microsoft Word) spawned svchost.exe with
    unusual command-line arguments and immediately performed a
    VirtualAllocEx + WriteProcessMemory sequence against explorer.exe.
    No legitimate Word macro workflow requires this behavior.",
  "recommended_action": "Isolate host from network; terminate PID 4408;
    preserve memory dump for forensic analysis."
}

No malicious file signature is required for this detection, the EDR platform flagged the alert purely from the behavioral pattern (an office document application spawning a system process and injecting code into another process), which is anomalous regardless of whether the specific payload has ever been seen before.

Policy is a control, not a description of controls It is easy to read "hardening" as a list of software. Much of what determines whether a fleet is hardened is written down rather than installed: the configuration baseline a machine is built from and the change process that governs it, the enrolment requirement that decides which devices may hold company data at all, the removable-media rule, the patch service level that commits the organisation to a deployment interval, and the audit that establishes whether any of it is true. These are managerial controls, and they outlast the tools that enforce them, a Group Policy Object blocking USB mass storage is the technical expression of a policy decision, and replacing Group Policy with a different management platform changes the mechanism without changing the control.

A representative managerial control is Windows Group Policy restricting removable storageRemovable Storage Media RestrictionA policy-enforced control blocking or restricting the use of removable storage devices such as USB flash drives on managed endpoints, implemented via Windows Group Policy Objects (GPO) or equivalent mobile device management tooling. This control mitigates both data exfiltration (an insider or attacker copying sensitive files onto a USB drive) and malware introduction (an infected USB drive being plugged into a workstation, historically the infection vector for malware like Stuxnet). Windows implements this via the "Removable Storage Access" policy set under Computer Configuration > Administrative Templates > System > Removable Storage Access in the Group Policy Management Console. device usage, a common vector for both malware introduction (an infected USB drive) and data exfiltration (an insider copying sensitive files). II-A. Three Ways to Decide That a File Is Hostile

"Anti-malware" names a product category, not a technique. Inside any modern agent there are at least three distinct decision procedures running against the same file or process, each with a different failure mode, and the reason the category still exists after four decades is that the three fail in different directions. Reasoning about endpoint protection means reasoning about which of the three is doing the work in a given scenario.

Signatures: identity matching

A signature asks a question about identity: is this object one I have already been told about? In its crudest form the signature is a cryptographic hash of the whole file, which matches one sample and nothing else. In practice vendors use pattern signatures, a sequence of bytes at a given offset, a regular expression over a decrypted section, a fuzzy hash such as ssdeep that tolerates small edits, or an import-table hash that fingerprints which library functions a binary calls. These generalise a little beyond the exact sample, which is why one signature can cover a family rather than a file.

The property that matters is that a signature is a statement about the past. It can only exist after somebody obtained a sample, analysed it, and shipped the result. Two consequences follow directly, and both are structural rather than fixable:

  • A zero-dayZero-DayA vulnerability, or the exploit for it, that is unknown to the party responsible for fixing it, so the number of days the defender has had to prepare is zero. Once the flaw is disclosed and a patch exists, exploitation of unpatched systems is called n-day exploitation, where n is the number of days since disclosure. Most real-world compromise is n-day, not zero-day: the exploit is public and the patch is available, and the victim simply had not applied it. The distinction matters because the two demand different controls, zero-days demand detection and containment, n-days demand patch velocity. sample has, by definition, no signature. There is no configuration, no subscription tier, and no update frequency that changes this; the object has never been analysed by anyone.
  • A trivially modified sample may have no signature either. Recompiling with a different optimisation level, inserting dead code, or re-packing with a different packer changes the byte pattern while preserving behaviour. This is why malware families ship with automated repacking: the marginal cost of generating a new, unrecognised variant is close to zero, while the marginal cost of analysing and signing it is a human analyst's time.

What signatures buy in exchange is precision and speed. A hash match is not a probabilistic judgement; it is a fact, and it produces essentially no false positives. That matters more than it sounds, because a control that blocks legitimate work gets disabled by the people it inconveniences, and a disabled control detects nothing.

Heuristics: static suspicion

A heuristic asks a question about structure: does this object have the shape of something hostile, whether or not I have seen it before? The examination is static, the file is inspected, and in some engines emulated inside a lightweight virtual machine, without being allowed to run on the real system. Features that raise a heuristic score include a very high entropy section (a sign of packing or encryption), a mismatch between declared and actual section sizes, an import table containing the specific combination of memory-writing and process-opening functions used for injection, an executable stub appended to a document, or a digital signature that is absent, expired, or self-signed on a binary claiming to be from a major vendor.

Heuristics generalise where signatures cannot, and they pay for it in false positives. Legitimate software is also packed, also self-signed during development, and also calls unusual APIs. Every heuristic engine therefore sits on a tuning dial between missed detections and blocked payroll software, and the position of that dial is an operational decision rather than a technical one.

Behaviour: watching what it does

Behavioural detection abandons the file as the unit of analysis. It asks: what is this process actually doing, and does that sequence make sense? The agent instruments the operating system, on Windows through kernel callbacks and Event Tracing for Windows, on Linux through eBPF or the audit subsystem, on macOS through the Endpoint Security framework, and records process creation with full command lines and parent lineage, file and registry writes, module loads, network connections, and privilege changes. Detection logic then runs over that stream.

This is the only one of the three that can catch an attack with no malicious file at all. A PowerShell command line that downloads and executes a script entirely in memory writes nothing to disk that a scanner could examine; a credential-theft tool that opens a handle to lsass.exe and reads its memory may be a signed, legitimate administrative binary being abused. What identifies both is the sequence, and the sequence is what behavioural detection records. This class of technique is catalogued in the MITRE ATT&CK matrix, the two just described are T1059.001 and T1003.001, and most vendors label their alerts with those identifiers precisely so that an analyst can locate the alert within an attack sequence rather than treating it as an isolated event.

The cost is inverted from signatures. Behavioural detection is inherently probabilistic: the same sequence that characterises an attack also occurs in backup software, deployment tooling, and vulnerability scanners. It is also, by construction, late, the behaviour has to happen before it can be observed. A behavioural detection is a statement that something already ran.

The three techniques are not a progression, and the newest does not replace the oldest It is tempting to read signatures, heuristics, and behavioural analytics as three generations, with the newest making the others obsolete. That reading is wrong and leads to bad architecture. The three occupy different points on a trade-off between certainty and coverage, and a real agent runs all three concurrently: signatures dispose of the enormous volume of known commodity malware cheaply and with no false positives, heuristics catch repacked variants of the same families before they execute, and behavioural analytics cover what is left, the genuinely novel and the fileless. Removing signatures to "modernise" simply moves millions of trivially identifiable samples onto the expensive, noisy, post-execution path.

EDR, XDR, and what the telemetry is for

Endpoint Detection and ResponseEDR, PreciselyAn agent that (a) continuously records endpoint telemetry to a retained store, (b) evaluates detection logic against that stream in near real time, and (c) exposes response actions, host isolation, process termination, file quarantine, remote shell, to an analyst from a central console. The recording is the part that distinguishes EDR from antivirus: it lets an analyst ask what happened before an alert, which is impossible if nothing was kept. The response capability is also why EDR agents are a high-value target: an attacker who compromises the EDR console inherits remote code execution on every enrolled host. is usually explained as "antivirus plus behaviour," which understates the actual difference. The distinguishing feature is retention. An antivirus makes a verdict and discards the evidence; an EDR keeps a rolling record of what every process did, typically for weeks. That record is what makes the questions an incident actually raises answerable: what ran before the alert, what did the process touch, which other hosts show the same parent command line, and when did this first appear in the estate.

XDR extends the same idea past the endpoint boundary, correlating that telemetry with identity, email, cloud, and network signals so that a single sequence spanning several systems is presented as one incident rather than four unrelated alerts. The value is real but it is a correlation and workflow claim, not a detection-capability claim, and it should be evaluated as such: an organisation that cannot act on the alerts it already receives does not benefit from receiving them pre-correlated.

Application allowlisting: the inverse policy

All three detection techniques share an architecture, everything runs unless something objects. Application allowlistingApplication AllowlistingA control that permits execution only of code explicitly approved by policy, denying everything else by default. Approval is expressed by publisher certificate, file path, or file hash. Publisher rules survive vendor updates but trust everything that vendor signs; path rules are maintainable but only safe if users cannot write to the approved path; hash rules are exact but break on every update. Windows implements this through AppLocker and Windows Defender Application Control; Linux equivalents include fapolicyd and SELinux policy. inverts it: nothing runs unless policy approves it. This is the same default-deny reasoning applied to code rather than to packets, and it is the only control in this chapter that stops a genuinely novel executable without having to recognise anything about it.

Allowlisting is also the control organisations most often abandon after deployment, and the reasons are worth naming because they are predictable. Path-based rules approving a directory that ordinary users can write to are trivially defeated by writing the payload there. Publisher rules extend trust to everything a vendor signs, which includes signed interpreters and signed developer utilities that can execute arbitrary code on the attacker's behalf, the "living off the land" problem catalogued at LOLBAS. And a policy strict enough to be meaningful requires ongoing maintenance every time a business application updates. The control is strong; the failure mode is organisational rather than technical.

II-B. Patching as a Race, and What CVSS Does Not Tell You

Keeping software updated is the least glamorous control in this chapter and the one with the best evidence behind it. The reason it works is narrow and worth stating exactly: a patch does not make a system generally safer, it removes one specific defect that one specific exploit depends on. The value of patching comes from doing this faster than adversaries can operationalise the same defect, which makes it a race with a measurable clock.

The exploit window

Four moments matter, and they do not occur in a fixed order:

  • Discovery. Someone finds the defect. If that someone is an adversary and no one else knows, every deployed system is exposed and nothing can be done, because there is nothing to apply. This is the zero-day period, and its length is unknowable from the defender's side.
  • Disclosure and patch release. The vendor publishes a fix and, usually, an advisory. A CVE identifier is assigned by a CVE Numbering Authority and the record appears in the National Vulnerability Database.
  • Exploit availability. A working exploit becomes public, frequently derived from the patch itself, since the difference between the vulnerable and fixed binaries points at the defect. This is why patch release can increase short-term risk for anyone who has not applied it.
  • Deployment. The organisation actually installs the fix on every affected host, which is the only one of the four the defender controls.

The interval between the third and fourth moments is the n-day window, and it is where most real compromise happens. WannaCry, examined in Topic 4.1, is the canonical demonstration: Microsoft released MS17-010 on 14 March 2017, and the worm that used it spread on 12 May 2017, a gap of roughly two months during which the defect was public, the fix was free, and hundreds of thousands of machines were still vulnerable. The underlying flaw, CVE-2017-0144, is not exotic; it is an input-validation error in SMBv1 that NVD scores 8.8 under CVSS v3.1.

What a CVSS base score is, and what it is not

The Common Vulnerability Scoring SystemCVSSAn open scoring framework maintained by FIRST that expresses the intrinsic severity of a vulnerability as a number from 0.0 to 10.0, derived from a vector of metrics. The Base metrics cover how the flaw is reached (attack vector, complexity, privileges required, user interaction), whether it crosses a security boundary (scope), and what it costs (confidentiality, integrity, availability impact). Threat and Environmental metric groups exist to adjust the base score for real-world exploitation activity and for the specific deployment, but published scores almost always report Base alone. CVSS v4.0 was released in November 2023; most catalogued vulnerabilities still carry v3.1 scores. is the industry's shared vocabulary for severity, and it is routinely misread as a measure of risk. It is not one. The base score is deliberately environment-free: it describes the vulnerability in isolation, on a hypothetical system, with no knowledge of where that system sits.

Read CVE-2017-0144's vector as an example. NVD publishes CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:H/A:H for a base of 8.8. Each metric is a claim about the flaw: reachable over a network, low attack complexity, some privileges required, no user interaction needed, and total loss of confidentiality, integrity, and availability on the affected component. Every one of those is a property of the software.

What the score is silent about is everything that converts severity into risk: whether the affected host is reachable from where an attacker is, what the host is worth, whether a compensating control already blocks the path, whether an exploit exists at all, and whether anyone is currently using it. Two findings with identical 9.8 base scores can carry wildly different risk, and treating the score as a work queue guarantees that effort is spent in the wrong order. Two public data sources exist precisely to supply what CVSS omits: the CISA Known Exploited Vulnerabilities catalog lists flaws with confirmed in-the-wild exploitation, and the Exploit Prediction Scoring System estimates the probability that a given CVE will be exploited in the next thirty days. A defensible triage order uses severity, exploitation evidence, and local exposure together; none of the three is sufficient alone.

Severity is a property of the vulnerability; risk is a property of your deployment This is the single most consequential misreading in vulnerability management, and it survives because the number looks authoritative. A base score of 9.8 on a service that is firewalled off, has no data on it, and cannot reach anything else may warrant a scheduled patch. A base score of 6.5 on an internet-facing host that is in the KEV catalog and holds customer records warrants an emergency change tonight. The score did not lie in either case, it answered a question about the software, and the question that determines the work order is a different one, which only the person who knows the network can answer.

Baselines: patching is necessary and not sufficient

Patching closes defects the vendor has acknowledged. It does nothing about a system that is fully patched and badly configured, a default account left enabled, a legacy protocol still negotiable, telemetry switched off. That gap is what a secure baselineSecure Configuration BaselineA documented, version-controlled specification of how a given operating system or product is to be configured, from which every deployed instance is built and against which every instance is periodically audited. Its purpose is to make the configuration of the estate a known quantity rather than an accumulation of individual decisions, so that drift can be detected and changes can be reviewed. NIST SP 800-53 Rev. 5 control CM-2 requires a baseline; CM-3 requires change control over it; CM-6 requires that configuration settings be established and enforced. is for. The CIS Benchmarks are the most widely used public source: consensus-developed, per-product configuration guides that state each recommended setting, its rationale, the audit procedure that tests it, and the operational impact of applying it. They are published in two profile levels, where Level 1 is intended to be broadly deployable without breaking normal use and Level 2 is a defence-in-depth profile that accepts reduced functionality. The DISA Security Technical Implementation Guides serve the same function for U.S. Department of Defense systems.

The important discipline is not adopting a benchmark but treating the baseline as a controlled artefact. A baseline that is applied once at build time and never audited describes the estate on its first day and nothing after that. Configuration drifts, because people fix things under pressure and do not always change them back, which is why NIST SP 800-53 pairs CM-2 with CM-3 and CM-6: define it, control changes to it, and enforce and monitor the settings continuously.

II-C. Configuring a Host-Based Firewall

A host-based firewall differs from a perimeter firewall in three ways that determine when it is the right control. It travels with the device, so it still applies on hotel Wi-Fi. It sees the local process behind a socket, so rules can be written per application rather than per port. And it filters traffic between two hosts on the same segment, which a perimeter device sitting between segments never sees, the lateral movement that turned a vendor foothold into a point-of-sale compromise at Target passed entirely between internal hosts.

The iptables ruleset above shows the underlying packet-filter semantics. In practice most Linux administrators configure the same filter through ufw, a front end that is easier to audit because each rule reads as a sentence. The following establishes default-deny inbound on a workstation:

ufw, default-deny workstation policy (Ubuntu/Debian) 
# Start from a known state. On a remote host, authorise SSH BEFORE enabling,
# or the first rule you apply will end your own session.
sudo ufw --force reset

# Default posture: nothing inbound, everything outbound.
sudo ufw default deny incoming
sudo ufw default allow outgoing

# Management access, restricted to the admin subnet rather than the world.
sudo ufw allow from 10.10.5.0/24 to any port 22 proto tcp comment 'SSH from mgmt VLAN'

# Rate-limit SSH: ufw denies a source that opens more than 6 connections
# in 30 seconds. This blunts online guessing; it does not replace key auth.
sudo ufw limit 22/tcp comment 'throttle SSH connection attempts'

# Deny a noisy source explicitly. Order matters: ufw evaluates top to bottom
# and stops at the first match, so insert denials ahead of broader allows.
sudo ufw insert 1 deny from 203.0.113.66 comment 'blocked scanner'

# Log what is dropped, or the firewall will be silent about what it stopped.
sudo ufw logging medium

sudo ufw enable
sudo ufw status numbered verbose

Two details in that listing are the ones administrators get wrong. Rules are evaluated in order and the first match wins, so a deny inserted after a matching allow never fires, ufw status numbered exists so that order can be inspected and ufw insert so that it can be corrected. And ufw logging is off by default at installation: a firewall that drops traffic silently gives Topic 4.4 nothing to work with.

Windows Defender Firewall is configured through the NetSecurity PowerShell module. The cmdlets below are the current supported interface; netsh advfirewall still functions but has been superseded.

PowerShell, Windows Defender Firewall (NetSecurity module, elevated) 
# Enable all three profiles and set default-deny inbound on each.
Set-NetFirewallProfile -Profile Domain,Private,Public `
    -Enabled True `
    -DefaultInboundAction Block `
    -DefaultOutboundAction Allow `
    -NotifyOnListen False

# Turn on dropped-packet logging. The default log is capped at 4 MB and wraps,
# so forward it to a collector if you need more than the recent past.
Set-NetFirewallProfile -Profile Domain,Private,Public `
    -LogBlocked True -LogAllowed False `
    -LogFileName "%SystemRoot%\System32\LogFiles\Firewall\pfirewall.log" `
    -LogMaxSizeKilobytes 16384

# Allow RDP inbound, but only from the management subnet and only on the
# domain profile. The same machine on a coffee-shop network gets nothing.
New-NetFirewallRule -DisplayName "RDP from management VLAN" `
    -Direction Inbound -Action Allow `
    -Protocol TCP -LocalPort 3389 `
    -RemoteAddress 10.10.5.0/24 `
    -Profile Domain -Enabled True

# Per-application rule: host-based firewalls can bind a rule to the program
# that owns the socket, which a perimeter device cannot do.
New-NetFirewallRule -DisplayName "Backup agent outbound" `
    -Direction Outbound -Action Allow `
    -Program "C:\Program Files\BackupAgent\agent.exe" `
    -RemoteAddress 10.20.0.0/16 -Profile Any

# Block inbound SMB from everywhere except the file-server subnet. Blocking
# lateral SMB is one of the highest-value host firewall rules in an
# enterprise, and it is exactly the traffic a perimeter firewall never sees.
New-NetFirewallRule -DisplayName "Block inbound SMB" `
    -Direction Inbound -Action Block `
    -Protocol TCP -LocalPort 445 -Profile Any

# Verify. Never trust that a rule applied because the command returned.
Get-NetFirewallRule -Enabled True -Direction Inbound |
    Where-Object { $_.Action -eq 'Allow' } |
    Format-Table DisplayName, Profile, Action -AutoSize

Windows evaluates its rules by a fixed precedence rather than by list order: explicit block rules take effect over explicit allow rules, and both take effect over the profile's default action. That is the opposite convention to ufw, and assuming one while configuring the other is a reliable way to produce a rule that appears in the console and never fires. It is also why the Get-NetFirewallRule verification step belongs in the procedure rather than at the end of it.

The -Profile parameter is the feature with no perimeter analogue. Windows classifies each network the machine joins as Domain, Private, or Public, and applies a different rule set to each, so a laptop can accept management connections on the corporate network and accept nothing at all in an airport, without an administrator touching it. NIST SP 800-41 Rev. 1 treats host-based firewalls as a complement to the perimeter for exactly this reason: the two see different traffic, and neither substitutes for the other.

III. Case Studies: Stuxnet and Target

Case Study 4.3.1: Stuxnet and the Air-Gap USB Vector (2010)

Discovered in 2010, StuxnetStuxnetA highly sophisticated computer worm, widely attributed to a joint U.S.-Israeli operation, designed specifically to sabotage Iran's uranium enrichment infrastructure by targeting the Siemens industrial control systems (SCADA/PLC) that governed centrifuge speed. Stuxnet is historically significant as one of the first publicly documented cyberweapons designed to cause physical, kinetic damage to industrial equipment rather than simply stealing or corrupting data. Stuxnet leveraged four separate zero-day Windows vulnerabilities simultaneously, an extraordinary "exploit budget" that strongly suggested nation-state resources and sophistication. Symantec's 2011 technical dossier remains the authoritative public analysis. was engineered to reach and sabotage industrial control systems at Iran's Natanz nuclear enrichment facility, a network that was deliberately air-gappedAir GapA network security measure in which a computer or network is physically isolated from unsecured networks, including the public internet, with no wired or wireless connection whatsoever, the theoretical "gap of air" that data must physically cross to move between the isolated system and the outside world. Air-gapping is considered one of the strongest network isolation controls available, but it is not absolute: it can still be defeated by physical media (USB drives) or, in extreme cases, novel side-channel techniques. Industrial control systems (ICS/SCADA) in critical infrastructure are frequently air-gapped as a compensating control, since patching such systems is often operationally difficult., meaning it had no direct network connection to the internet. Because a direct network-based infection vector was unavailable, Stuxnet's designers relied specifically on the endpoint-level USB removable-media vector: the worm was engineered to autonomously copy itself onto any USB drive plugged into an infected machine, and to autonomously execute upon that drive being plugged into another machine, regardless of whether that machine was networked at all. This chain of physical media transfer, believed to have involved contractors or employees carrying an infected USB drive into the facility, ultimately allowed Stuxnet to reach and reprogram the specific industrial controllers governing centrifuge rotational speed, causing physical equipment damage while simultaneously feeding falsified sensor readings back to plant operators to conceal the sabotage.

An air gap moves the vector; it does not remove it Stuxnet is the definitive case study proving that network isolation alone (an air gap) does not eliminate endpoint risk, because the endpoint hardening controls covering physical/removable media were the actual point of failure, not the network architecture. This is precisely why managerial controls like removable storage restriction policies (Section II) remain essential even for the most highly isolated, security-critical environments, the threat vector shifts to whatever channel remains open, and USB ports are frequently the last channel standing on an air-gapped system.

Case Study 4.3.2: The Target Corporation Breach, Network Segmentation and Endpoint Blind Spots (2013)

In November–December 2013, retailer Target Corporation suffered a breach that exposed approximately 40 million credit and debit card numbers. The initial foothold was gained not through Target's own systems directly, but through a third-party HVAC (heating, ventilation, air conditioning) vendor with remote network access credentials, which attackers compromised via a phishing email. Critically, once inside, attackers were able to move laterally from the vendor-access segment into Target's point-of-sale (POS) network, a failure of network segmentation combined with insufficient endpoint hardening on the POS terminals themselves, which lacked adequate host-based monitoring to detect the memory-scraping malware ("BlackPOS") subsequently installed on them. Target's centralized malware detection system, FireEye, did generate alerts flagging the malicious activity, but the alerts were reportedly not acted upon by the security team in time to prevent the exfiltration of card data over several weeks.

An alert nobody acts on is indistinguishable from no alert The Target breach is an important counter-lesson to the framing of this chapter: deploying an EDR-class detection tool is necessary but not sufficient. Detection generates an alert; a functioning security operations process must actually triage, investigate, and act on that alert within a meaningful timeframe. This bridges directly into Topic 4.4's coverage of endpoint threat auditing, hardening controls and detection tooling only provide value when paired with an operational process that consumes their output.

IV. Endpoint Frameworks: CIS Controls, NIST 800-53, and Zero Trust

Endpoint hardening at an organizational scale is formalized through several complementary frameworks and control families:

1. CIS Critical Security Controls (Endpoint-Focused)

The Center for Internet Security's Critical Security Controls framework dedicates specific control families directly to endpoint hardening, including CSC 2 (Inventory and Control of Software Assets), CSC 4 (Secure Configuration of Enterprise Assets and Software), and CSC 10 (Malware Defenses), each providing measurable, testable sub-controls that organizations can audit for compliance.

2. NIST SP 800-53 Configuration Management (CM) Family

NIST SP 800-53's CM control family formalizes Windows GPO peripheral block rulesGroup Policy Object (GPO)A Windows feature allowing centralized configuration management across an entire Active Directory domain, administrators define a policy once (e.g., "block USB mass storage") and it is automatically enforced on every joined device in the target organizational unit, without requiring manual configuration of each individual machine. GPOs are a primary mechanism for implementing NIST SP 800-53 control CM-7 (Least Functionality) and SC-7 (Boundary Protection) at scale across a Windows enterprise environment. and other configuration baselines as an auditable, continuously enforced standard rather than a one-time setup task, requiring organizations to establish a documented baseline configuration (CM-2), control and document all changes to that baseline (CM-3), and enforce least functionality by disabling unnecessary ports, protocols, and services (CM-7).

3. Zero Trust Endpoint Verification

Modern endpoint hardening increasingly integrates with Zero Trust ArchitectureZero Trust ArchitectureA security model built on the principle "never trust, always verify", rather than assuming devices and users inside a network perimeter are trustworthy by default, every access request is continuously authenticated, authorized, and validated regardless of its origin, including requests from devices already inside the corporate network. Endpoint health (patch status, EDR agent presence, disk encryption status) is frequently used as one input into these continuous access decisions. NIST SP 800-207, "Zero Trust Architecture" (2020), formalizes this model as a federal reference standard, moving away from the older "castle-and-moat" perimeter-trust model., in which a device's real-time compliance posture (patch level, EDR agent health, disk encryption status) is evaluated as a continuous condition of network access, rather than granting broad trust simply because a device is physically connected to the internal network, directly addressing the lateral-movement failure mode observed in the Target case study.

Every hardening recommendation should span all three control categories A recommendation that names only technical measures has usually missed where the failure will occur. The three categories cover different ground: technical, an EDR agent, a default-deny host firewall, automated patch deployment; managerial, the baseline the build is derived from, the removable-media policy, the patch service level and the audit that tests it; physical, locked enclosures, port blockers on kiosk and point-of-sale terminals, controlled access to equipment rooms. Stuxnet defeated a network architecture through a physical channel, and Target lost card data with detection tooling running and alerting. Neither gap was technical.

Self-Check Review Questions

Question 1: Explain the difference between signature-based malware detection and behavioral (EDR) detection, and describe a scenario in which only the latter would successfully flag an attack.

Signature-based detection compares files or running code against a database of known malicious fingerprints, unique byte patterns or hashes extracted from malware samples that have already been discovered and cataloged by security vendors. This approach is fast and generates few false positives but is fundamentally reactive: it can only identify threats that have already been analyzed elsewhere, leaving it blind to brand-new or modified malware for which no signature yet exists. Endpoint Detection and Response (EDR) platforms instead continuously monitor system behavior, process creation, memory operations, network connections, and apply behavioral analytics to flag anomalous activity patterns regardless of whether any known malicious file signature is present. A scenario in which only behavioral detection would succeed is process injection using entirely legitimate, unmodified system binaries, for example, a malicious Word macro spawning svchost.exe (a completely legitimate Windows process) and using it to inject code into another running process via API calls such as VirtualAllocEx and WriteProcessMemory. Because no new or modified malicious file is ever written to disk, signature-based scanning finds nothing to match against; the attack is entirely "fileless." EDR detects this because the behavioral pattern itself, a document application spawning a system process that performs cross-process memory injection, is anomalous and worth flagging, independent of whether the specific technique has ever been cataloged as a known malware signature.

Question 2: Explain the security principle of default-deny firewall policy and why it is considered stronger than a default-allow policy, using the iptables ruleset structure discussed in Section II as a reference.

A default-deny firewall policy sets the baseline behavior of the firewall to block all traffic by default, requiring administrators to explicitly author rules permitting only the specific traffic types known to be necessary for legitimate operation. A default-allow policy inverts this: all traffic is permitted by default, and administrators must explicitly author rules blocking known-malicious or unwanted traffic patterns. Default-deny is considered architecturally stronger because it fails safe: any traffic type an administrator did not anticipate or forgot to explicitly address is automatically blocked rather than automatically permitted, meaning gaps in the ruleset default toward security rather than exposure. In the iptables example, setting the INPUT chain's default policy to DROP means that even if the administrator forgets to write a rule addressing some unusual or unexpected protocol, that traffic is blocked by default rather than silently allowed through, whereas under a default-allow model, the same oversight would silently expose the host. Default-allow policies are considered a hardening anti-pattern precisely because they require administrators to anticipate every possible malicious traffic pattern in advance, an inherently incomplete task, rather than simply defining the narrow set of traffic that is actually required.

Question 3: Using the Stuxnet case study, explain why network air-gapping alone is an insufficient endpoint security control, and identify the specific managerial hardening control that would have most directly mitigated the infection vector used.

An air gap physically isolates a network from unsecured external networks, including the internet, eliminating remote network-based infection vectors entirely. However, an air gap only addresses the network layer of the attack surface; it does not address endpoint-level vectors that do not require a network connection at all, such as physically transported removable media. Stuxnet was specifically engineered to exploit exactly this gap: rather than attempting to reach the air-gapped Natanz facility over a network connection (which was architecturally impossible), it was designed to autonomously copy itself onto any USB drive connected to an infected host and autonomously execute when that drive was subsequently connected to another machine, allowing it to physically "hop" across the air gap via human-carried media rather than network traffic. The managerial hardening control that would have most directly mitigated this specific vector is a removable storage media restriction policy, enforced, for example, via Group Policy Objects blocking USB mass storage device mounting on sensitive industrial control system workstations, or a strict physical policy prohibiting personally-owned or externally-sourced USB devices from being connected to air-gapped systems at all. This demonstrates that endpoint hardening controls (in this case, a managerial/administrative policy rather than a purely technical one) remain essential even in network architectures that appear maximally secure at the network layer, because the actual point of compromise shifts to whichever channel, physical media, in this case, remains unaddressed.

Practice Questions

Question 1 4.3.B, An organisation's anti-malware agent has current signature definitions, updated four times a day. An adversary compiles a new backdoor that has never been submitted to any vendor and delivers it by email. What happens at the signature layer, and why?
  1. The file is detected, because signature databases include generic entries covering all backdoors.
  2. The file is not detected by signatures, because a signature can only exist after a sample has been obtained and analysed, no update frequency changes this.
  3. The file is detected only if the vendor's cloud lookup times out and the agent fails closed.
  4. The file is not detected because the definitions are four hours stale; hourly updates would have caught it.
Question 2 4.3.B, An analyst reviews an alert: winword.exe spawned powershell.exe with an encoded command line, which allocated memory in explorer.exe and wrote to it. No file was written to disk. Which detection technique produced this alert, and what makes it the only one that could have?
  1. Signature matching, because powershell.exe is a known-abused binary with a published hash.
  2. Static heuristics, because the encoded command line has high entropy.
  3. Behavioural detection, because the finding is a sequence of runtime actions and process lineage rather than a property of any file, and there is no file to examine.
  4. Application allowlisting, because powershell.exe would not be on the approved list.
Question 3 4.3.C, A vendor releases a patch on day 0. A public exploit derived from that patch appears on day 3. An organisation deploys the patch on day 40. Which statement about this sequence is correct?
  1. The organisation faced a 40-day zero-day exposure, since it had no protection for 40 days.
  2. The organisation faced a 37-day n-day window; the flaw was public and fixable throughout, and only the deployment interval was under its control.
  3. Risk fell on day 0 when the patch was released, regardless of deployment.
  4. Publishing the patch had no effect on exploit availability, since exploits are developed independently of patches.
Question 4 4.3.A, Which of the following is best classified as a managerial control for device security, as distinct from a technical one?
  1. A Group Policy Object that blocks USB mass-storage mounting on domain workstations.
  2. A documented, version-controlled configuration baseline derived from a CIS Benchmark, with a defined change-approval process and a scheduled compliance audit.
  3. An EDR agent configured to isolate a host automatically on a high-severity detection.
  4. A host-based firewall rule denying inbound TCP 445 on all profiles.
Question 5 4.3.D, An administrator runs ufw allow 22/tcp, then ufw deny from 203.0.113.66, then checks that the scanner at 203.0.113.66 can still reach SSH, and it can. What is the explanation?
  1. Deny rules are advisory in ufw and require --force to take effect.
  2. ufw evaluates rules in order and stops at the first match; the broad allow was added first, so it matches the scanner's packets before the deny is ever reached. The deny must be inserted ahead of it.
  3. The deny rule needs a port specified, or it applies to no traffic at all.
  4. Source-address denies only work on the OUTPUT chain.
Question 6 4.3.C, A vulnerability-management team ranks its remediation queue strictly by CVSS base score, highest first. What is the principal defect in this method?
  1. CVSS base scores are frequently inaccurate and should be recalculated locally for each finding.
  2. The base score deliberately excludes exposure, asset value, compensating controls, and evidence of real-world exploitation, so ranking by it alone can place a firewalled internal finding above an internet-facing one that is actively being exploited.
  3. CVSS scores expire after 90 days and become invalid for ranking.
  4. The base score already includes exploitation likelihood, so the ranking double-counts severity.
Free Response 1 4.3.B Mitigate Risk, A manufacturer runs 400 office workstations and 30 shop-floor machines that control production equipment. The security lead proposes removing signature-based scanning entirely and relying solely on an EDR platform, on the grounds that "signatures cannot catch zero-days." (a) State what is correct in that reasoning and what does not follow from it. (b) Explain what signature-based detection contributes that behavioural detection does not, and describe the operational consequence of removing it. (c) The 30 shop-floor machines cannot run the EDR agent, because the equipment vendor will not support a machine with third-party software installed. Recommend two controls appropriate to that constraint and explain the mechanism of each. (d) Explain why application allowlisting would be a stronger fit on the shop-floor machines than on the office workstations.
Free Response 2 4.3.D Mitigate Risk, A regional accountancy firm has 90 Windows laptops that staff take to client sites. There is no host-based firewall configuration; every machine runs the shipped defaults. A recent internal test showed that a compromised laptop on the office LAN could reach SMB on every other laptop. (a) Explain why a perimeter firewall did not prevent this and what property of a host-based firewall does. (b) Write, in prose or as cmdlets, the firewall configuration you would deploy, covering default action, profile handling, at least one inbound restriction, and logging, and name the failure each element addresses. (c) Windows resolves conflicting rules by precedence rather than by list order, while ufw uses first-match ordering. Explain the practical consequence of confusing the two. (d) State what must be true for this configuration to keep protecting a laptop that is sitting in a client's office, and name one thing that could silently undo it.

Answer Key

1. B4.3.B

A signature is a statement about a sample somebody has already analysed. If no vendor has ever seen this binary, no signature for it exists anywhere, and the gap is structural rather than a matter of subscription tier or update cadence. A misdescribes what a signature is: pattern and fuzzy-hash signatures generalise across variants of a known family, not across an abstract category like "backdoor." C inverts the design, cloud lookup failure causes agents to fall back on local definitions, not to invent detections. D locates the problem in latency, which is the seductive wrong answer: shortening the update interval to one hour, or one minute, still leaves a sample that has never been submitted undetected forever.

2. C4.3.B

Every element of the alert is runtime state: parent-child lineage, the command line as executed, and a cross-process memory write. None of it is a property of a file, and the scenario states there is no file. Only an agent instrumenting process and memory events can produce this, and the technique corresponds to MITRE ATT&CK T1059.001 followed by process injection under T1055. A fails because powershell.exe is a legitimate signed Microsoft binary whose hash is on no blocklist; blocking it by signature would break Windows administration. B describes something a static engine could notice about the string, but heuristics examine files, and the injection into explorer.exe, the actual finding, is invisible until it happens. D confuses a preventive control with a detection: allowlisting produces a block, not this alert, and most enterprise policies permit PowerShell.

3. B4.3.C

Zero-day means no fix exists. From day 0 a fix existed, so the entire 40 days is n-day exposure, and the 37 days after the public exploit appeared are the dangerous portion. A misuses the term: the defining feature of a zero-day is the vendor's ignorance of the flaw, not the victim's failure to act. C confuses availability with deployment; a patch on a vendor's server protects nothing, and this is the whole reason patch velocity is measured. D contradicts a well-documented dynamic, diffing a patched binary against its predecessor localises the defect, and it is common for public exploits to appear within days of a fix precisely because the fix pointed at the bug.

4. B4.3.A

A managerial control governs how decisions are made, documented, approved, and verified. A version-controlled baseline with change approval and scheduled audit is a process artefact: it exists in policy and produces evidence, and it survives the replacement of any particular tool. A, C, and D are all technical controls, mechanisms the system enforces automatically. The distinction is subtle in A, because a GPO is the enforcement of a policy; the policy requiring removable media to be blocked is managerial, while the GPO that implements it is technical, and the question asks about the control itself.

5. B4.3.D

ufw evaluates its rules top to bottom and the first match decides the packet's fate. The scanner's SYN to port 22 matches the earlier allow, so evaluation stops before the deny is considered. The fix is ufw insert 1 deny from 203.0.113.66, and ufw status numbered is how the ordering is confirmed. A invents a mechanic that does not exist. C is wrong: a rule with no port matches all traffic from that source, which is broader, not narrower. D reverses direction, a source restriction on arriving traffic is an INPUT concern, and OUTPUT governs traffic the host originates.

6. B4.3.C

The base metric group is defined to be environment-independent, so exposure, asset value, existing compensating controls, and current exploitation activity are all outside it by design. Ranking on it alone systematically misorders work. The corrective inputs are local knowledge of reachability plus published exploitation evidence, the CISA Known Exploited Vulnerabilities catalog and EPSS. A misdiagnoses the problem as accuracy; the scores are generally correct answers to the question they were asked. C invents an expiry that does not exist. D is precisely backwards: exploit maturity lives in the Threat metric group, which published base scores do not include, and that omission is the defect in question.

FR 14.3.B

Model answer. (a) The premise is correct: a signature cannot match a sample no one has analysed, so signature scanning contributes nothing against a genuinely novel binary. The conclusion does not follow, because "cannot catch zero-days" is not the same as "catches nothing worth catching." The overwhelming majority of what actually arrives at an endpoint is known commodity malware, and that is what signatures dispose of. (b) Signatures give certainty and negligible cost: a match is a fact rather than a probability, producing essentially no false positives, and the verdict is reached before execution. Behavioural detection is probabilistic and, by construction, post-execution, the behaviour must occur to be observed. Removing signatures therefore moves millions of trivially identifiable samples onto the expensive path, raising analyst alert volume, increasing the number of things that run before being judged, and degrading the signal-to-noise ratio of the queue the team depends on. (c) With no agent possible on the shop-floor machines, defence relocates. Network isolation: place them on a segment with an explicit default-deny between it and the office network, permitting only the specific flows production requires, so an office compromise cannot reach them, the exact failure that produced the Target breach. Removable-media control: block or physically restrict USB mass storage on those machines, since with no network path the remaining channel is physical media, which is how Stuxnet crossed an air gap. Monitoring the segment from a network sensor, and an agentless configuration audit against the vendor's supported baseline, are acceptable additional answers. (d) Allowlisting fits the shop-floor machines because their software set is small, fixed, and changes only when the equipment vendor issues a release, so the maintenance burden that causes allowlisting to be abandoned barely exists, and their inability to run an agent removes the alternative. On 400 office workstations the software set is large and changes constantly, so a policy strict enough to be meaningful generates continuous exceptions, and pressure to loosen it into path rules over user-writable directories, which defeats it.
Look for: the premise granted rather than rebutted; false-positive rate and pre-execution timing named as what signatures contribute; two controls in (c) that do not require software on the device, each with a stated mechanism; and, in (d), an argument from rate of change and maintenance burden rather than a claim that one machine is more important than another.

FR 24.3.D

Model answer. (a) A perimeter firewall filters traffic crossing between segments. Laptop-to-laptop SMB on the office LAN never crosses that boundary, so the perimeter device never sees a packet of it and can express no opinion. A host-based firewall runs on the endpoint itself and therefore sees every arriving packet regardless of origin, including one from a machine three desks away; it also travels with the laptop and keeps applying at a client site where no corporate perimeter exists at all. (b) The configuration: Set-NetFirewallProfile -Profile Domain,Private,Public -Enabled True -DefaultInboundAction Block -DefaultOutboundAction Allow, which makes any inbound flow nobody thought about fail closed rather than open; a New-NetFirewallRule blocking inbound TCP 445 on all profiles, which is the specific lateral SMB path the test exercised; any required management access, RDP or a remote-support agent, permitted only with -RemoteAddress restricted to the management subnet and -Profile Domain, so the same laptop offers nothing on an untrusted network; and -LogBlocked True with an increased -LogMaxSizeKilobytes, because a firewall that drops silently leaves no evidence for the auditing covered in Topic 4.4. A verification step with Get-NetFirewallRule belongs in the procedure, since a cmdlet returning without error is not evidence that a rule is in force. (c) Windows applies explicit block over explicit allow over the profile default, irrespective of the order rules were created. ufw stops at the first matching rule. An administrator carrying the Windows model to Linux writes a deny after a broad allow and it never fires; one carrying the ufw model to Windows carefully orders rules and is then surprised when a block rule further down overrides an allow they intended to win. Both errors produce a rule that is visibly present and functionally absent, which is worse than no rule, because it is believed. (d) It keeps protecting the laptop only while the profile classification is correct, if Windows classifies the client's network as Domain, or a user is able to reclassify it as Private, the permissive rule set intended for the corporate LAN applies in a place it was never meant to. It also depends on the policy being reapplied rather than set once: a local administrator disabling the firewall to make an application work, a VPN or third-party security product installing its own rules, or a machine that has not contacted the domain controller in weeks and so has not received an updated GPO, will all silently undo it. Central enforcement with drift detection is what makes the configuration a standing property rather than a one-time act.
Look for: in (a), the specific point that intra-segment traffic never reaches the perimeter, not merely that host firewalls are "closer"; in (b), each element paired with the failure it addresses and logging present; in (c), the recognition that the confusion produces a silently ineffective rule; and in (d), at least one concrete drift mechanism rather than a general statement that configurations must be maintained.
