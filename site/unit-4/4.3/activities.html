4.3 Activities

Endpoint Hardening Controls · 3

Skill 4.3.a · pairs · 25 min · Offline: yes

Device hardening

Goal

Students apply a device-hardening checklist to a fictional device configuration, identify which controls are missing, and justify each finding using the principle of least privilege and attack surface reduction. Ties to LO 4.3.A (explain and apply hardening controls).

Materials

Steps

Check off all materials above to unlock the steps.
  1. Each pair opens the simulation and works through the device-configuration scenarios. Before submitting each answer they must agree and write one sentence explaining why that control reduces risk.
  2. After the simulation, each pair reviews the configuration card below and identifies which of the five hardening controls the fictional device fails. They record their findings in a table: Control | Pass/Fail | Reason.
  3. Pairs swap their findings table with another pair, who must either agree or rebut each finding with a justification.

Fictional device configuration card (Meridian Technologies, Workstation WS-04)

OS: Windows 10 (installed 18 months ago, no updates applied)
Local accounts: Administrator (password: admin), Guest (enabled, password: none)
Services running: FTP server, Telnet, Remote Desktop, HTTP server, Print spooler
Firewall: disabled
Disk encryption: off
Screen lock timeout: never

Collaborate

Assign roles: one partner is the "security auditor" (identifies failures and writes the finding), the other is the "device owner" (tries to justify why the current setting might seem reasonable). The auditor must respond to each defense with a concrete attack scenario that the control would prevent. Swap roles after finding three issues.

Exit Ticket

AP

Certificate of Completion

Each student submits a ranked list of the three most critical controls the fictional device is missing, with one sentence each explaining the specific risk that control addresses.

Skill 4.3.b · small group · 20 min · Offline: yes

Antivirus and endpoint protection

Goal

Students work in groups to analyze security logs and write behavioral rules that block malicious activities (like ransomware or keyloggers) without blocking benign administrator activities (avoiding false positives). Ties to LO 4.3.A and 4.3.B.

Materials

Steps

Check off all materials above to unlock the steps.
  1. Divide the class into groups of 3–4.
  2. Review the behavior logs below. Each scenario contains both a malicious process and a benign process performing similar actions.
  3. Your team's task is to write a single detection rule for each scenario that triggers on the malicious activity but ignores the benign activity.
  4. Rules should follow a simple structure: IF [process matches criteria] AND [performs action] THEN block.

Behavior Logs for Analysis

Scenario A: File Encryptor vs. Backup Utility

  • Process A (Malicious - Ransomware): supergame.exe (run from Temp folder) opens Documents/ and encrypts 50 files in 3 seconds, writing .locked extensions.
  • Process B (Benign - Backup): backup_agent.exe (run from Program Files) opens Documents/ and reads 50 files in 10 minutes, writing them to an encrypted archive backup.zip.

Scenario B: Remote Access Tool vs. Remote Admin Tool

  • Process C (Malicious - Trojan): explorer_patch.exe launches, runs in the background silently, listens on port 4444 for incoming connections, and spawns cmd.exe when a connection is made.
  • Process D (Benign - Remote Helpdesk): helpdesk.exe launches, prompts the user with a dialog "Allow agent to connect?", listens on port 5900, and starts a screen-sharing session.

Scenario C: Living-off-the-land Script vs. Admin Maintenance Script

  • Process E (Malicious - LOTL attack): powershell.exe is spawned by winword.exe (Word) moments after a user opens an email attachment, immediately downloads a file from an unfamiliar external IP, and disables Windows Defender via a registry edit.

  • Process F (Benign - IT maintenance): powershell.exe is spawned directly by a logged-in IT administrator's session at 2 AM (scheduled maintenance window) and runs a signed internal script that checks disk space on all endpoints.

  • For Scenario C, discuss why a signature-based tool would likely miss Process E entirely (PowerShell itself is legitimate software, not malware) and write a behavioral rule using process parentage (what launched the process) as the key signal.

Collaborate

  • Role 1 (Signature Advocate): Wants to block the threat by hashing the file (e.g., block supergame.exe by name or hash).
  • Role 2 (Behavioral Analyst): Explains why signature block is insufficient (what if the attacker renames the file or compiles a new version?).
  • Role 3 (Business Operations Manager): Warns about false positives. If the rule blocks backup_agent.exe, the company's daily backups will fail! Together, negotiate a rule that satisfies all three constraints.

Exit Ticket

AP

Certificate of Completion

Each group submits their final rule for Scenario A, Scenario B, and Scenario C.

Skill 4.3.c · small group · 25 min · Offline: yes

Patching and regular updates

Goal

Groups act as a patch-management triage board: given a queue of pending vulnerabilities, they decide deployment order and timing using CVSS severity, exploitation status, and exposure. Ties to LO 4.3.B (patch lifecycle) and 4.3.C (prioritization tradeoffs).

Materials

Steps

Check off all materials above to unlock the steps.

  1. Read the queue (5 min). Each group receives the five vulnerability cards below. For each, record the CVSS score, whether it is being actively exploited in the wild, and whether the affected system is internet-facing.

  2. Card A: Internal HR file server, CVSS 9.8, no known exploitation in the wild yet, patch requires a scheduled reboot.

  3. Card B: Public-facing customer web portal, CVSS 9.1, CISA has confirmed active exploitation in the wild starting this week.
  4. Card C: Internal developer workstation, CVSS 4.2, no known exploitation, low business impact if compromised.
  5. Card D: Public-facing VPN gateway, CVSS 7.5, no confirmed in-the-wild exploitation yet, but a working proof-of-concept exploit was published publicly two days ago.

  6. Card E: Legacy internal print server, CVSS 8.8, vendor has marked the product end-of-life, no patch will ever be released.

  7. Rank the queue (10 min). As a group, produce a single ranked list (1 = patch first) for Cards A-E, with a one-sentence justification for each ranking decision.

  8. Check with the simulation (10 min). Open the simulation and work through its patch-triage queue. Compare the urgency labels the simulation assigns with your own ranking. Discuss any disagreements.

Collaborate

Assign roles: one member is the "Security Analyst" (argues from pure exploitability/severity), one is "IT Operations" (raises downtime/compatibility costs of patching), and one is "Business Risk Owner" (weighs impact if each system is breached). Negotiate a final ranked list the whole group agrees on, and note any card where the roles disagreed.

Exit Ticket

AP

Certificate of Completion

Each student submits: their final ranking for Card E (the end-of-life system) plus a one-sentence explanation of what control should be used since no patch will ever exist.
