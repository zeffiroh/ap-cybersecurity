4.4 Activities

Endpoint Threat Auditing · 3

Skill 4.4.a · pairs · 25 min · Offline: yes

Endpoint detection and response (EDR)

Goal

Students analyze a printed or on-screen EDR telemetry log and practice triage: deciding whether each event sequence is benign or suspicious, naming the EDR detection method that would catch it, and selecting the correct response action. Ties to LO 4.4.A (describe how EDR detects and responds to attacks on devices).

Materials

Printed event table (use if devices are unavailable)

# Process Parent Network destination File write
1 powershell.exe winword.exe 203.0.113.44:443 C:\Temp\svc32.exe
2 chrome.exe explorer.exe google.com:443 (none)
3 cmd.exe svchost.exe (none) C:\Windows\malw.bat
4 notepad.exe explorer.exe (none) report.txt
5 wscript.exe outlook.exe 198.51.100.7:80 C:\Users\temp.vbs

Steps

Check off all materials above to unlock the steps.
  1. Individual read (3 min). Each student reads the event table silently and marks each row as "benign" or "suspicious" with a brief reason.
  2. Pair discussion (7 min). Partners compare judgments. For each row marked suspicious they must name: (a) which telemetry stream surfaced it (process/file/network), (b) whether signature or behavioral detection would catch it, and (c) the correct EDR response action (alert only, kill process, isolate endpoint, quarantine file).
  3. Group debrief (10 min). Each pair shares one finding. Instructor uses rows 1, 3, and 5 to illustrate living-off-the-land patterns; rows 2 and 4 to show why not every unusual-looking event is malicious (context matters).
  4. Scenario extension (5 min). Ask: "Row 1 executed before the EDR had a signature for the payload. Why might behavioral detection still flag it?" Students write one sentence answer.

Collaborate

Assign roles: one partner is the SOC analyst (makes the triage call), the other is the threat hunter (must justify or challenge each call with a second hypothesis). After the debrief, swap roles and repeat for a second set of rows provided by the instructor.

Exit Ticket

AP

Certificate of Completion

Each student submits: for event row 1, name the telemetry streams involved, the detection method that would catch it, and the EDR response action you would choose, and explain why isolation is preferred over just killing the process.

Skill 4.4.b · pairs · 25 min · Offline: yes

Log analysis

Goal

Students manually correlate a printed authentication log to find a brute-force pattern, then practice choosing a detection threshold and discussing its false-positive/false-negative tradeoffs. Ties to LO 4.4.B (detect attacks via log correlation).

Materials

Printed authentication log (use if devices are unavailable)

09:10:02  user=mchen    ip=198.51.100.9   result=SUCCESS
09:12:01  user=jsmith   ip=203.0.113.44   result=FAILED
09:12:14  user=jsmith   ip=203.0.113.44   result=FAILED
09:12:22  user=jsmith   ip=203.0.113.44   result=FAILED
09:12:31  user=jsmith   ip=203.0.113.44   result=FAILED
09:12:39  user=jsmith   ip=203.0.113.44   result=FAILED
09:12:47  user=jsmith   ip=203.0.113.44   result=SUCCESS
09:15:10  user=agarcia  ip=198.51.100.22  result=FAILED
09:41:02  user=agarcia  ip=198.51.100.22  result=FAILED

Steps

Check off all materials above to unlock the steps.
  1. Manual correlation (10 min). Each pair reads the printed log and answers: (a) which username shows a brute-force pattern, (b) how many failed attempts occurred and over what time span, (c) what happened at the end of that sequence, and (d) why the two agarcia entries do NOT count as a brute-force pattern.
  2. Check with the simulation (5 min). Open the simulation and work through its authentication log stream to confirm your answer.
  3. Threshold-tuning table (10 min). As a pair, fill in the table below for three candidate detection thresholds, predicting whether each would have caught the jsmith attack and whether it risks false-positiving on ordinary users:
Threshold Would catch jsmith's attack? False-positive risk on typo-prone users
2 failures / 60s
5 failures / 60s
20 failures / 60s

Collaborate

Assign roles: one partner is the "SOC Analyst" (argues for a stricter/lower threshold to catch attacks fast), the other is the "Help Desk Lead" (argues for a looser/higher threshold to avoid paging analysts every time a user mistypes a password). Negotiate a threshold both roles can justify, and write one sentence explaining the compromise.

Exit Ticket

AP

Certificate of Completion

Each student submits: the threshold their pair agreed on, plus one sentence on what could go wrong if the threshold were set too low.

Skill 4.4.c · small group · 25 min · Offline: yes

Identifying compromised devices (indicators of compromise)

Goal

Groups act as an incident-response triage team: given a set of IOCs observed on several devices, they compute a weighted compromise score by hand and decide a verdict and response action for each device. Ties to LO 4.4.B and 4.4.C (combining multiple IOCs into a compromise decision).

Materials

IOC weight table (printed reference)

IOC type Weight
Known-malicious file hash match 6
Antivirus/EDR disabled 5
New unauthorized admin account 4
Unusual outbound traffic 3
Unexpected scheduled task 3
Registry run-key persistence added 2
Cluster of failed logins 1

Verdict thresholds: score < 4 = clean; 4-7 = suspicious; score >= 8 = compromised.

Device cards

  • Device A: antivirus disabled (5) + new unauthorized admin account (4).
  • Device B: cluster of failed logins (1) only.
  • Device C: known-malicious file hash match (6) + unusual outbound traffic (3) + registry run-key persistence added (2).
  • Device D: unexpected scheduled task (3).
  • Device E: new unauthorized admin account (4) + cluster of failed logins (1).

Steps

Check off all materials above to unlock the steps.
  1. Score each device (10 min). Each group sums the weights for Devices A-E using the table above and assigns a verdict (clean / suspicious / compromised).
  2. Check with the simulation (5 min). Open the simulation and work through its device-triage queue to confirm your scores and verdicts.
  3. Response plan (10 min). For every device scored "compromised," write the response action you would take (referencing the EDR response actions from 4.4.a: alert, kill process, quarantine, isolate). For every "suspicious" device, write what ADDITIONAL evidence you would look for before escalating.

Collaborate

Assign roles: one member is the "Triage Analyst" (computes scores), one is the "Incident Commander" (decides the response action for each verdict), and one is the "Skeptic" (challenges whether a single IOC is being over-weighted or whether the group jumped to a conclusion too fast). Reach group consensus on all five devices.

Exit Ticket

AP

Certificate of Completion

Each student submits: Device C's total score, its verdict, and one sentence justifying why three weaker-looking IOCs combined outweigh one strong IOC in isolation (or vice versa, if applicable).
